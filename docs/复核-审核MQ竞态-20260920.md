## 一、机制归因：成立（证据链）

### 1.1 发送点确实在事务内

```java
// NoteServiceImpl.java:79-100
@Override
@Transactional(rollbackFor = Exception.class)          // :80  ← 事务从这里开始
public NoteVO create(NoteCreateRequest req) {
    ...
    noteMapper.insert(note);                          // :90
    saveExtras(note.getId(), req);                    // :92  图片/标签/关联商品同事务写入

    // 事务提交后再发审核消息：避免"消费者先于事务提交读到空笔记"的竞态。
    // @Transactional 方法内直接发消息的坑：MQ 消费者立刻回查，事务还没 commit → 查不到。
    // 这里用最简单的做法：审核提交放在事务边界外（Controller 层事务已提交）。
    auditService.submit(note);                        // :97  ← ★ 仍在事务方法体内

    return detail(note.getId());                      // :99  ← 到这里才返回，事务才提交
}
```

`AuditServiceImpl.submit()` 里是**裸的立即发送**，没有 afterCommit 包装：

```java
// AuditServiceImpl.java:68-76
public void submit(Note note) {
    AuditMessage msg = new AuditMessage(note.getId(), 1);
    RabbitTemplate rabbit = rabbitTemplateProvider.getIfAvailable();
    if (rabbit != null) {
        try {
            rabbit.convertAndSend(AuditMqConfig.EXCHANGE,
                    AuditMqConfig.AUDIT_ROUTING_KEY, msg);      // :73-74  立即发
            log.info("审核消息已入队 noteId={}", note.getId());
            return;
        } catch (AmqpException e) { ... 降级线程池 ... }
    }
    submitLocal(note.getId());
}
```

### 1.2 注释为什么是错的

注释称"审核提交放在事务边界外（Controller 层事务已提交）"。实测：

- `NoteRestController.java:33-36` —— 只有 `@RestController` / `@RequestMapping` / `@RequiredArgsConstructor`
- `NoteRestController.java:56-59` —— `create()` 直接调 service，**无任何事务注解**
- `grep -rn "@Transactional" content/controller/` → **0 命中**

**结论**：Controller 层从来没有事务。事务是 `create()` 自己开的（`:80`），
在第 97 行发消息时**该事务仍在进行中**。注释描述的是一个**从未存在的架构**——
这正是这个 bug 能潜伏至今的原因：读注释的人会以为已经处理过了。

### 1.3 消费端确实是"丢弃"，不是"重试"

```java
// AuditConsumer.java:39-47
try {
    Note note = noteMapper.selectById(msg.noteId());          // :41  另一条连接回查
    if (note == null) {
        log.warn("笔记不存在，丢弃消息 noteId={}", msg.noteId());
        return;   // :44  正常返回 → Spring AMQP 自动 ACK
    }
    auditService.auditOnce(note);
} catch (Exception e) {
    log.error("审核消费失败（已记流水，消息 ACK 不重试）noteId={}: {}", ...);   // :51  吞异常也 ACK
}
```

- 空分支 `return` → **正常返回 = ACK = 消息永久消失**（类注释 `:18-22` 明确说明这是**有意为之**，防毒消息循环）
- 全项目**无 `@EnableRetry` / `RetryTemplate` / 自定义 `containerFactory`**（grep 0 命中）
- `application.yml:64-68` 仅有 `default-requeue-rejected: false` 与 `prefetch: 5`

### 1.4 隔离层面：不是"概率"而是"必然"

- 发布线程 `nio-8080-exec-6`、消费线程 `ntContainer#1-1` —— **不同线程、不同连接**（日志原文可见）
- `application.yml` 未配置 `isolation` → MySQL InnoDB 默认 **REPEATABLE READ**
- 另一连接未提交的 INSERT，**在任何隔离级别下都不可见**（不读脏数据）

所以：**只要消费者的回查早于提交，必然读到 null**。这是确定性事件，不是偶发。

### 1.5 窗口有多宽（为什么有时能躲过去）

第 97 行发完消息后，事务还要继续执行 `detail()`（`:99` → `:123-141`）：

```
noteMapper.selectById          → 1 次
userMapper.selectById          → 1 次
Redis HMGET × 3（计数）        → 3 次跨机往返
likeMapper / collectMapper IN  → 2 次
extraMapper × 3（图/标签/商品）→ 3 次
每个关联商品 productMapper     → N 次
```

**十余次网络往返** = 毫秒级窗口。所以窗口宽度取决于"消费端投递+回查"与"这串组装"谁快——
第一次消费要建连接/声明队列（毫秒~数十毫秒），之后连接热了就变成 0~4ms，于是**全军覆没**。

## 三、严重性修正：「永远不公开」不成立

**这是用户总结里唯一需要纠正的判断。** 项目里有定时补偿任务兜底：

```java
// CompensationTask.java:78-97
/**
 * 审核堆积兜底：扫描"审核中超 10 分钟"的笔记重新送审。
 * auditOnce 自带三层幂等（版本唯一键 + 状态机 CAS），重复审核无副作用。
 */
@Scheduled(fixedDelay = 10 * 60 * 1000, initialDelay = 90 * 1000)   // :82  每 10 分钟
public void retryStuckAudits() {
    LocalDateTime before = LocalDateTime.now().minusMinutes(10);      // :84  超 10 分钟算卡住
    List<Note> stuck = noteMapper.selectAuditingBefore(before, 100);
    ...
    auditService.auditOnce(n);                                        // :92  直接重审（不走 MQ）
}
```

- `@EnableScheduling` 已启用（`ScheduleConfig.java:13`）
- 扫描 SQL 用 **`created_at`**：`NoteMapper.xml:45-53` → `WHERE status='AUDITING' AND created_at < #{before}`
  → 14:00 创建的笔记，14:10 必然被扫到

**日志里也直接看到了自愈**：

```
2026-09-20 14:15:05.435 INFO [scheduling-1] CompensationTask : [补偿] 发现 8 篇审核堆积笔记，重新送审
2026-09-20 14:15:16.196 INFO [scheduling-1] AuditServiceImpl : 审核完成 noteId=4 pass=true status→PUBLISHED
```

**noteId=4 在 14:15:16 被补偿任务救回并发布** —— 从 14:00:37 算起，延迟约 **14.7 分钟**。

**为什么补偿能救活**（幂等没被污染）：消费者在丢弃时**只打日志、没有写审核流水**，
所以 `uk_biz(biz_type, biz_id, biz_version)` 未被占用，补偿时 `saveRecord` 能成功插入 → CAS 生效。

**修正后的严重性表述**：
> 消息被静默丢弃，笔记停留在"审核中" **约 10~20 分钟后由补偿任务重新审核并发布**。
> 影响是**体验退化（用户长时间看到"审核中"）+ 每条消息白跑一次 + 日志噪音**，不是数据永久损坏。

> 【2026-09-20 后续：已修复】上文描述的是**修复前**的行为——而且它成立有一个隐含前提：
> 消费端丢弃时"只打日志、没写流水"，所以幂等键恰好没被占用。这个前提本身很脆
> （§4.1 的 `ERROR` 路径正是踩在同一条键上）。**修复后发送侧改为事务提交后投递
> （`AfterCommitExecutor`），消息不再被丢弃，本节这条竞态已消除**；补偿任务保留为最终兜底。
> 详见文末「后续：已修复（2026-09-20）」。

## 四、复核中额外发现的缺陷

### ★★★ 4.0 最严重：审核幂等键的版本号永不递增 → 被驳回的笔记**永远无法重新发布**

这条是复核中最值得报的发现，**严重程度高于用户报的那个竞态**。

`t_audit_record` 的幂等键是 `(biz_type, biz_id, biz_version)`：

```sql
-- V2__content_and_rag.sql:116
UNIQUE KEY uk_biz (biz_type, biz_id, biz_version),
```

设计意图（`AuditRecord.java:15`、`AuditMessage.java:11` 都写了）：
**"笔记每次编辑 +1，保证同一版本只审一次"**，这样 MQ 重投不会重复处理，而**编辑后的新版本可以重新审**。

**但版本号从来没有人 +1**。全项目 `bizVersion` 的出现位置：

| 位置 | 内容 | 是否递增 |
|---|---|---|
| `AuditServiceImpl.java:69` | `new AuditMessage(note.getId(), 1)` | ❌ 硬编码 1 |
| `AuditServiceImpl.java:160` | `r.setBizVersion(version)` —— 调用方传的也是 `1` | ❌ 硬编码 1 |
| `AuditMessage.java:13` | `record AuditMessage(Long noteId, int bizVersion)` | 字段声明了，但… |
| `AuditConsumer.java:38` | `log.info("收到审核消息 noteId={} version={}", ...)` | **只打印，从不传给 auditOnce** |
| `AuditService.auditOnce(Note note)` | 方法签名里**没有 version 参数** | ❌ 内部写死 1 |

- `AuditMessage` 带出来的 `bizVersion` **被消费端读出来仅用于打日志**，`auditOnce` 拿不到它
- `NoteRestController` **没有编辑笔记的接口**（无 `@PutMapping`）→ 版本号在业务上**永远没有机会递增**
- `resubmit()` 也没有 bump 版本（`NoteServiceImpl.java:217-229`）

**结论：幂等键实际退化成 `(NOTE, noteId)` 这个恒定值 —— 一篇笔记一辈子只能被审核一次。**

**由此产生一个功能性死锁：「重新送审」这个功能永远不可能成功。**

推演一遍：

```
① 发布 → auditOnce → AI 判定驳回
   → saveRecord(id, 1, REJECT) 插入成功（rows=1）
   → updateStatus(AUDITING → REJECTED)   ← 笔记状态 = REJECTED，流水 (NOTE, id, 1) 已占用

② 用户修改内容 → POST /notes/{id}/resubmit
   → 校验 status == REJECTED ✓
   → updateStatus(REJECTED → AUDITING)
   → submit() → 消费者 → auditOnce(note)

③ auditOnce 里：
   → AI 判定通过，verdict.pass() = true
   → saveRecord(id, 1, PASS) → INSERT IGNORE → 撞 uk_biz → rows = 0      ← ★ 被自己上一次的流水挡住
   → if (rows == 0) { log.info("重复审核消息（幂等跳过）"); return; }        ← 提前返回
   → updateStatus 永远不会执行
```

**结果**：笔记永久停在 `AUDITING`，日志里只有一行 `INFO 重复审核消息（幂等跳过）`，
看起来像"正常的幂等跳过"，**完全不像故障**。

而且**没有任何接口能救**：
- `/resubmit` 强制要求 `status == REJECTED`（`NoteServiceImpl.java:224-226`），
  而此时笔记是 `AUDITING` → 拒绝
- 定时补偿任务每 10 分钟重试一次，每次都被同一道幂等闸挡住，**无限循环且永远无效**
- 唯一出路是手工删掉 `t_audit_record` 里那条记录

**影响范围**：任何"审核失败过一次"的笔记（**驳回 REJECT 或 AI 报错 ERROR 都会**）都进入这个状态。
也就是说——**审核驳回 = 这篇笔记永久报废**。这不是边缘场景。

**根因**：幂等键的三段里有两段是常量，幂等设计被架空。
铺设好的基础设施（`AuditMessage.bizVersion` 字段、`AuditRecord.bizVersion` 列、
`t_note` 上的版本语义注释）**全部就位，就是没人接线**。

> 【2026-09-20 后续：已修复】本节结论「一篇笔记一辈子只能被审核一次 / 驳回即永久报废」
> **修复后不再成立**。采用的正是本节推荐的修法 1：`t_note` 新增 `audit_version`
> （发布=1，`resubmit()` 时 +1），并由 `submit` → `AuditMessage` → `AuditConsumer`
> → `auditOnce(Note, int version)` 全链路透传。详见文末「后续：已修复（2026-09-20）」。

**修法方向**（三种，按推荐度）：
1. **在 `resubmit()` 里递增版本** —— 正确复用既有设计：给 `t_note` 加 `audit_version`，
   `resubmit` 时 +1，`submit`/`auditOnce` 透传该值（`AuditMessage` 已经带得动了）
2. **让 ERROR 不占用幂等键** —— 与 4.1 一起修：ERROR 流水改写到独立的表，或版本号加后缀
3. **幂等判定区分"同结果重投"与"新一次审核"** —— `:127` 分支不能一律 return，
   应比对已存在流水的 `status`：若上次是 `ERROR` 则允许覆盖为正常判定

### ★ 4.1 「ERROR 流水占用幂等键」→ 同样导致永久卡死

这条与 4.0 是同一个根因（幂等键设计）的另一种触发方式。

```java
// AuditServiceImpl.java:110-130
try {
    verdict = auditAiClient.review(input);
} catch (Exception e) {
    log.error("AI 审核调用失败 noteId={}: {}", note.getId(), e.getMessage());
    saveRecord(note.getId(), 1, AuditRecord.STATUS_ERROR,            // :116  ★ 写入 version=1 的 ERROR 流水
            Map.of("error", String.valueOf(e.getMessage())));
    return;                                                          // :118  笔记留在 AUDITING
}

// 之后任何一次重审（定时补偿 / 手动重提）：
int rows = saveRecord(note.getId(), 1,                               // :122  同一 version=1
        verdict.pass() ? STATUS_PASS : STATUS_REJECT, ...);
if (rows == 0) {                                                     // :127  ★ INSERT IGNORE 撞 uk → 0
    log.info("重复审核消息（幂等跳过）noteId={}", note.getId());
    return;                                                          // :129  ★ 直接返回，状态永不更新
}
```

**问题**：AI 调用失败时写入的 `ERROR` 流水，**占用了与正常判定相同的幂等键**。
而这个唯一键（`V2__content_and_rag.sql:116`）**不包含 `status`** ——
所以一条 ERROR 记录会把后续所有正常判定全部挡掉。

**注意 schema 层面的细节**：`status` 列允许 `ERROR`，但唯一键里没有它。
数据库注释（`:110`）写的是"同一业务同一版本只审一次，MQ 重投不会重复处理"——
**防重投是对的，但把"基础设施故障"和"业务判定"共用同一个键是设计失误**：
`ERROR` 不是一次"审核结论"，它是"这次没审成"，不应该消费掉幂等额度。

**结论**：这条路径才是真正的"永久停在 AUDITING"，且没有任何接口能救，只能手工删流水。
触发条件是"首次 AI 调用失败"（网络抖动 / Key 失效 / 限流），**概率不低**。

**问题**：AI 调用失败时写入的 `ERROR` 流水，**占用了与正常判定相同的幂等键** `(NOTE, noteId, 1)`。
此后无论补偿任务重试多少次、AI 恢复得多好，`saveRecord` 都返回 0 → 提前 return → **状态永不流转**。

## 五、修复方案评估

| 方案 | 评价 |
|---|---|
| **A. `TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit()`** | ✅ **推荐** |
| **B. `@TransactionalEventListener(AFTER_COMMIT)`** | ⚠️ 有致命坑，见下 |

### 为什么推荐 A：项目里已经有现成的同构实现

`OrderDelayMessageSender.java:42-55` 就是这个模式，而且**已经被两处复用**
（`OrderServiceImpl.java:132`、`DropOrderExecutor.java:128`）：

```java
public void sendAfterCommit(Long orderId) {
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        log.warn("sendAfterCommit 在无事务上下文调用，退化为立即发送 orderId={}", orderId);
        sendNow(orderId);
        return;
    }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() { sendNow(orderId); }
    });
}
```

**复用它的价值**：
1. 同一套已验证模式，语义一致，不引入新概念
2. `isSynchronizationActive()` 分支天然兼容 `resubmit()` 的无事务路径（不会漏发）
3. 零新依赖，符合项目"可降级、零依赖"的既有原则

**落地时要注意的坑**（`afterCommit` 抛异常无法回滚，因为事务已提交）：

```java
@Override
public void submit(Note note) {
    Long noteId = note.getId();
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        doSubmit(noteId);                                   // 无事务：直接走原 MQ/线程池降级链
        return;
    }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() {
            try { doSubmit(noteId); }
            catch (Exception e) {                           // ★ 必须全吞
                log.error("审核消息发送失败（补偿任务兜底）noteId={}", noteId, e);
            }
        }
    });
}
```

除此之外还要把现有的 `submitLocal` 静默分支补上日志（见 4.2）。

### 为什么方案 B 有致命坑

- **`@TransactionalEventListener(AFTER_COMMIT)` 在无事务上下文时默认根本不执行**，
  必须显式加 `fallbackExecution = true`。否则 `resubmit()`（无 `@Transactional`）
  会**静默不送审** → 把"延迟 14 分钟"升级成"永不审核"，**比现状更糟**
- 默认**同步**执行（提交后、`create()` 返回前），会拉长接口 RT
- 若改用 `@Async` 又要引入新问题：切线程丢 MDC、`@Async` 自调用不走代理（项目已多处踩过）、线程池耗尽
- 需新增事件类 + 发布点 + 监听器，与项目"手写 afterCommit"的既有做法不一致

### 一个更彻底的建议

把 `OrderDelayMessageSender.sendAfterCommit` 泛化为通用的 `AfterCommitExecutor`
（无事务即立即执行 + 有事务则提交后执行 + 内部全吞异常），
让**审核、订单延迟取消、抢购建单三个发送点共用唯一出口** —— 从机制上杜绝同类问题再犯。

## 六、confirm / returns 的论断：成立

配置与回调：
- `application.yml:62-63`：`publisher-confirm-type: correlated`、`publisher-returns: true`
- `MqProducerConfig.java:42-47`：ConfirmCallback（记录"Broker 是否收到"，`ack=false` 才报警）
- `MqProducerConfig.java:50-56`：ReturnsCallback（消息到了 Broker 但**路由不到队列**时退回）
- `MqProducerConfig.java:19-23`：类注释自己写明职责范围就是"到没到 Broker / 有没有队列"

**本竞态的时间轴上，这两个回调全程绿灯**：

```
事务未提交
  → convertAndSend 成功
  → Broker 已收到（confirm: ack=true ✅）
  → 路由正常（returns 不触发 ✅）
  → 消费者抢先回查（AuditConsumer.java:41）
  → 读不到（事务未提交）
  → 记 WARN 后 return（消费端主动丢弃）  ← 故障发生在这里，投递层完全无感
```

**所以论断正确**：confirm/returns 是**投递层**可靠性（producer → exchange → queue），
本问题是**并发可见性/时序**问题（消息到达早于事务提交）。两者**正交**，
confirm/returns **不能**用来论证"事务内发消息是安全的"。

## 七、这份材料的面试用法

这个 bug 是**加分项**，不是减分项。它正好命中"**本地事务与消息投递的一致性**"这个经典命题。

**可以这样讲（约 60 秒）**：

> "我在这个项目里踩过一个典型的坑：发布笔记的事务还没提交，审核消息就已经被消费者消费了，
> 消费者回查数据库读不到那行 → 判定笔记不存在，直接把消息丢了。
> 原因是发送动作虽然写着'事务提交后发'，但实际仍在 `@Transactional` 方法体内。
>
> 修法上我对比过两种：`@TransactionalEventListener` 和 `TransactionSynchronization`
> 的 `afterCommit`。我选后者——因为项目里订单延迟取消已经用了这套模式，复用比引入新机制更一致；
> 而且 `@TransactionalEventListener` 在无事务上下文默认**不执行**，我的重新送审接口恰好没有事务，
> 不加 `fallbackExecution` 会从'延迟'变成'永不发送'。
>
> 另外我发现**消息确认机制解决不了这个问题**：`publisher-confirm` 报的是'Broker 收没收到'，
> `returns` 报的是'路由到队列没有'——这条消息这两项全绿，但业务侧读不到数据，照样失败。
> 投递层可靠性和并发时序是**两个不同的失败模式**。"

**这个故事的三个层次**（能答出第三层就赢了）：
1. 现象 → 定位（会用日志 + 理解事务边界）
2. 修复（知道 afterCommit，知道两种方案的取舍）
3. **能区分失败模式的归类**（投递可靠 ≠ 时序正确；并知道补偿任务在兜底，所以严重性可控）

### 9.3 同一版本并发可能出现 PASS + REJECT 两条终态流水（低危，**第二轮已修复**）

> ⚠️ **本节标题原为「残留（未改）」，2026-09-20 第二轮修复已把它修掉；下面第一段是修复前的原始结论，保留不删。**

唯一键纳入 `status` 之后，**同一个 `(biz_type, biz_id, biz_version)` 可以同时存在
一条 PASS 和一条 REJECT**。触发条件很窄：同一版本的消息被并发消费（重投 + 正常投递撞车），
且 AI 两次判定结果不一致。此时两条流水都是"合法"的，而 `updateStatus` 的状态机 CAS
（`WHERE status='AUDITING'`）只会让其中一条的结论真正生效，另一条成为"落库了但没生效"的记录；
`latestRecord` 取最后一条展示时，存在极小概率展示出与实际生效结论不一致的那条。

- **影响**：审核轨迹展示可能与实际状态不符（不改内容是否公开，因为状态流转本身是 CAS 保护的）。
- **当时未改的理由**：修它需要把「流水登记」与「状态流转」**调序**（例如先 CAS 再写流水，
  或让流水登记与状态流转在同一条件更新里绑定），这会推翻既有「幂等三防线」的叙事结构
  （流水表前置挡重投 → 状态机 CAS 兜底），收益（消除一个极窄窗口的展示不一致）小于改动风险。
- **当时设想的修法**：建议方向是"状态流转成功后再补写流水"或"把流水写入改为状态流转的副作用"，
  但那会让"重复投递直接 return、不碰笔记状态"这条防线失效，需要一并重新论证。

**第二轮修复（已落地）**：最终就是按"调序"的方向改的，而且没有推翻三防线的叙事——只是**对调了①与②的先后**：

| | 修复前 | 现在 |
|---|---|---|
| 防线① | 落流水（`INSERT IGNORE` 撞键返回 0 → `return`） | **状态机 CAS 先抢「结论权」**（`WHERE status='AUDITING'` 返回 0 → 不落流水、直接返回） |
| 防线② | 状态机条件更新（CAS） | **只有抢到结论权的那一次才落流水**（`uk(biz_type,biz_id,biz_version,status)` + `INSERT IGNORE` 兜底） |

- **为什么这样就够了**：并发时两道 CAS 只有一个能成功，落流水因此被收窄到"唯一赢家"这一次上，
  **同一版本最多只有一条终态流水**，上面那条"展示与实际结论不一致"的窗口从机制上消失。
- **日志文案随之变化**（`auditOnce`）：撞键分支的 `INFO 重复审核消息（幂等跳过）` 已不存在；
  现在抢不到结论权时记 `INFO 审核结论已被占用（重复投递或并发审核），跳过`，
  抢到了但流水返回 0 行（异常信号）时记 `WARN 状态已流转但流水已存在（版本号未递增？）`。
- **顺带说明一个当时的顾虑不成立**："重复投递直接 `return`、不碰笔记状态"并没有失效——
  现在抢不到结论权的重复投递同样直接 `return`，且比修复前**更早**返回（没写流水就返回了）。
- **代价（诚实说明）**：状态与流水**不在同一事务**。若 CAS 成功而流水写入失败，**笔记状态仍然正确**
  （状态才是唯一真相；驳回原因也随 `updateStatus` 写进了 `t_note.audit_result`），
  只是审核轨迹少一条记录，会记 WARN 便于发现。不把两者放进同一事务的原因：**AI 调用耗时长，
  若与写库同事务会长时间占用数据库连接**。

### 9.4 一处遗留观察（非本报告发现的缺陷，修复时顺带发现）

`NoteMapper.xml` 里的 `updateContent`（"编辑正文 → 回 AUDITING 并 `audit_version + 1`"）
**仍然没有任何调用方**（`NoteRestController` 没有 `@PutMapping`）——即项目**没有对外的编辑笔记接口**。
本轮修复同步把这条 SQL 的语义与 `resubmit` 对齐（都递增版本号），但它依然是死代码。
上文 §4.0 的"版本号永远没有机会递增"仍是对**接口层面**的准确描述。
