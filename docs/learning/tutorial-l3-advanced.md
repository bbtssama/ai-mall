## 第 0 课 带着什么"眼光"读代码：先立一套提问框架

### 本课目标

在进入具体决策前，先给自己装一套"扫描雷达"。没有这套框架你会只见代码不见得失。

### 六个拷问（每看到一个"看似 OK 的写法"都过一遍）

1. **并发下成立吗？** 两/多线程同时执行这段会不会出错？（下单、取消、扣库存全中招）
2. **异常下完整吗？** 中途抛异常，状态/数据会不会停留在"半截"？（事务边界）
3. **越权能防住吗？** 把别人的 id 传进去会不会读到/改到？（归属校验）
4. **类型/精度准吗？** 有没有用错类型导致精度丢失？（BigDecimal vs double）
5. **语义歧义会坑调用方吗？** 方法重载/返回类型会不会让调用方误解？（`R.ok(String)`）
6. **分布式下还能用吗？** 把程序扩成多实例，这套在不在？（Session vs token、DB 乐观锁 vs Redis）

> 拿着这份清单，你随手翻 ai-mall 任何一段"业务核心逻辑"，都会发现它几乎 1:1 踩中
> 其中几个拷问。这正是进阶阅读的价值：**把代码当"决策的证据链"看，而不是当"怎么运行"看**。

## 第 1 课 防超卖：那条 WHERE 背后是一部数据库锁的教科书

### 现状（源码事实）

`ProductSkuMapper.deductStock` 在 `resources/mapper/ProductSku.xml`：

```sql
UPDATE t_product_sku
SET stock = stock - #{qty}, sales = sales + #{qty}
WHERE id = #{id} AND stock >= #{qty}
```

而 `OrderServiceImpl.create` 里在这条 SQL 之前，还有一段"内存预检库存"：
`skuMapper.selectById` 后判断 `stock > qty`，不够则抛 `STOCK_NOT_ENOUGH`。
真正的扣减走上面这条 UPDATE，返回 0 行 → 抛 `STOCK_NOT_ENOUGH`。

### 为什么这么写（推演）

**"先查再改"为什么错？** 两步之间有一个**时间窗**：线程 A 查到 stock=1，线程 B 也查到 stock=1，
两个都通过"内存预检"→ 都执行 UPDATE 扣成 -1，**超卖 1 件**。
（在高并发秒杀下，这个窗会被放大数倍。）

**这条 SQL 为什么对？** 三个机制叠加：
1. **行锁**：`WHERE id=?` 命中带索引的主键，InnoDB 对**这一行**加 X 锁（排他锁），
   并发请求排队，同一时刻只有一个事务能改这行；
2. **原子条件**：`stock >= qty` 的判断和 `stock = stock - qty` 的修改在**同一条 SQL** 内完成——
   判断和修改之间不存在"先查后改"的间隙；
3. **影响行数作信号**：`UPDATE` 满足条件才生效，线程 A 成功（影响 1 行）后，线程 B 的
   `WHERE stock >= qty` 已不满足，影响 0 行——**数据库用返回行数告诉你"这局你输了"**。

**那内存预检是不是多余？** 不。它把"明显不够"的请求挡在**发 SQL 之前**：
- 避免无谓地发起 UPDATE、更快返回友好错误；
- 减少并发场景下冲到数据库的无效请求。
- 但它**不是防线**，真正的防线在 SQL 的 `WHERE`。记忆锚点：**预检是面子，WHERE 是里子**。

### 不这么写的代价

| 错误写法 | 后果 |
|---|---|
| 先 `SELECT stock` 判断再 `UPDATE` | 高并发下超卖（经典事故） |
| `UPDATE SET stock = stock - qty`（无 WHERE 条件） | 库存扣成负数，不报错 |
| 仅在应用层 `synchronized`/`ReentrantLock` | 单机内勉强，**多实例立刻失效**（每个实例各一把锁） |
| 用乐观重试但无条件扣减 | 脏数据叠加，需额外补偿逻辑 |

### 亲手改造路径：升级到 Redis 预减（V3 秒杀方向）

素材包 V3 演进方向是「Redis/MQ/秒杀」。把它拆成一个可上手的练习：

1. **初始化预热库存**：项目启动时把 `t_product_sku.stock` 灌进 Redis（如 key `sku:stock:1`），
   用 `SET` 带 NX 幂等初始化。
2. **请求到来先用 Redis 预减**：
   ```java
   Long remain = redisTemplate.opsForValue().decrement("sku:stock:" + skuId);
   if (remain < 0) { /* 回补一次，提示已抢光 */ return; }
   ```
   `DECR`（本身原子）代替"内存预检"，挡住绝大多数请求，DB 只承担最终结算。
3. **DB 仍是最终防线**：预减只是挡流量，真正落库还是走 `deductStock`（`WHERE stock>=qty`），
   保证万一 Redis 与 DB 不一致时以 DB 为准。
4. **危险点（一定踩的坑）**：Redis 是"挡"，DB 是"闸"。如果只预减不落库，宕机 Redis 丢库存；
   如果预减和 DB 扣减各算各的，会出现"Redis 说卖光了但 DB 还有" / 反向。**两条口径必须在校对后收敛**。

**面试延伸：** 能讲清「Redis 预减 + DB 兜底 / 库存可靠性 / 超卖只发生在二者间隙」的取舍，
比只背"用 Redis 减库存"高一个段位。

### 附加：这一条锁用得对不对，取决于你分得清四种隔离级别

面试官常在这里追问 DB 隔离级别。我们把扣库存这条 UPDATE 放到隔离级别坐标系里看：

| 隔离级别 | 现象 | 扣库存受影响吗 |
|---|---|---|
| READ UNCOMMITTED | 脏读 | 影响行数信号仍在，但读了别人未提交的库存 |
| READ COMMITTED | 无脏读，有不可重复读 | 在 MVCC 下，快照读和当前读要分清 |
| REPEATABLE READ（InnoDB 默认） | 可重复读 | 本行 `UPDATE` 用**当前读 + X 锁**，仍可靠 |
| SERIALIZABLE | 完全串行 | 最安全但吞吐最低 |

**要点**：`deductStock` 走的是**当前读（锁定读）**——`UPDATE` 本身加行锁，
所以就算隔离级别是 REPEATABLE READ，也能保证"同一行只有一个事务在扣"。这解答了
"普通 SELECT 是快照读、不加锁，而 UPDATE 是当前读、是加锁的"——区别就在这里。
理解这点，才能回答"为什么 COUNT/查库存可以用 SELECT，但扣库存必须用 UPDATE"。

### 附加：`version` 乐观锁与"先查后改"为什么不冲突

`t_product_sku` 有 `version`（乐观锁预留）。为什么已经有 `WHERE stock>=qty` 还要 version？
- `WHERE stock>=qty` 解决的是"扣成负数 / 并发扣超"；
- `version`（`UPDATE ... WHERE version=?`，影响 0 行重试）解决的是"**整行基于旧快照的更新**被打断"，
  比如同时要改 price 又要扣库存，两个请求都用旧 version 会互相覆盖。
- 当前 V1 扣库存只用 `stock>=qty` 已够；`version+1` 是给 V3 秒杀强化（把库存行当热行时，
  用版本号做更细粒度的冲突判定）预留的痕迹。你能点破"这两条各自防什么"就进阶了。

## 第 2 课 @Transactional 边界：事务不是越大越好

### 现状（源码事实）

```java
@Transactional(rollbackFor = Exception.class)
public OrderVO create(CreateOrderRequest req) { ... }
```

`cancel` 同样标注。事务内包含：逐项扣库存 → 组 Order → insert → batchInsert 明细 → 清购物车。

### 为什么这么写（推演）

- **一个「下单」是一个业务原子**：扣库存、写订单、写明细、清购物车要么全成要么全不成。
  任何一步失败都要**回滚**（尤其已扣的库存必须退回去——否则用户下单失败货却没了，烂账）。
- **`rollbackFor = Exception.class` 是重点**：Spring 默认只对 `RuntimeException` 回滚，
  `@Transactional` 默认的 `RuntimeException → rollback`，而**受检异常(Exception)默认不回滚**。
  这里显式扩到 `Exception`，表示"哪怕抛出一个受检异常也要一起回滚"，更保守稳妥。
- **为什么要把 Redis 预减、发 MQ 等排除在事务外？** 这是"事务边界"的进阶思考——
  见下方改造。

### 不这么写的代价

| 错误写法 | 后果 |
|---|---|
| 不加 `rollbackFor=Exception.class` | 方法内捕获异常转受检/业务异常时可能只回滚一半 |
| 在事务里做长时间外部 IO（调第三方、发 MQ） | 事务锁持有时间过长，锁竞争/死锁、吞吐暴跌 |
| 把「同步发 MQ / 调外部支付」塞进事务 | 多个事务一起被外部慢响应拖死 |
| 事务方法内自调用（`this.anotherTx()`） | **代理失效**，`@Transactional` 不生效（Spring AOP 经典坑） |

**一个"事务边界"高级拷问**（面试极其爱问）：
> 事务里有一段「扣库存后调外部系统，外部系统要 3 秒」，这样事务是不是要持锁 3 秒？
>> 是的，这是危险设计。正确做法是把「不可逆的核心写操作」放事务内，把「可延后的外部调用」放到事务**提交后**再执行（TCC/事务消息/发 MQ 解耦）。ai-mall 当前无外部依赖，事务内全是本地 DB 操作，边界是合理的。

### 亲手改造路径（事务边界进化）

1. **保持下单事务小而纯**：只做"扣库存 + 写订单 + 写明细 + 清购物车"这些本地写。
2. **把「发支付 / 通知 / 回补」挪出事务**：用 Spring 的事件发布 `@TransactionalEventListener(phase=AFTER_COMMIT)`
   或事务成功后发 MQ——保证"业务已定、通知异步"。
3. **V3 用 MQ 削峰**：把"扣库存"从同步请求里抽成异步下单（请求先到队列，Worker 批量扣），
   事务边界就落在 Worker 那一小块——这是秒杀架构的核心骨架。

### 附加：为什么 `@Transactional` 可能会"悄悄失效"（AOP 代理前提）

`@Transactional` 是 Spring AOP 的实现：**它基于代理（proxy）**——只有"由代理去调用的公有方法"
才会被事务切面拦截。读 ai-mall 时警惕三个高频失效场景：

1. **同类内自调用**：`this.create()` 调同类另一个 `@Transactional` 方法——`this` 是原始对象、
   不是代理，切面不生效（**事务静默失效**，最经典）。
2. **非公有方法**：`private` 方法上的 `@Transactional` 无效。
3. **代理包装受限**：CGLIB 下 `final`/私有细节无法被代理包装，可能失效。
   对策：把事务方法放进"被注入进来的 Bean"里（走代理），或改用编程式事务
   `TransactionTemplate`（给 `execute(callback)`，内部 `setRollbackOnly()` 动态控制边界）。

**亲手验证**：把订单创建抽成 `@Transactional private void doCreate(...)`，再从 `create` 里
`this.doCreate(...)`，观察事务是否失效。**（只练习，改完还原。）**
"自调用自失效"是 Spring 面试名坑，能现场讲清原理 = 证明你踩过并懂实现。

### 附加：`version` 乐观锁与 `WHERE stock>=qty` 各防什么

`t_product_sku` 预留了 `version`（乐观锁）。既然扣库存已经有 `WHERE stock>=qty`，为何还要 version？
- `WHERE stock>=qty` 防的是"**并发扣超** / 扣成负数"（行内库存不足）。
- `version`（`UPDATE ... WHERE version=?`，影响 0 行重试）防的是"**基于过期快照的其它整行更新**
  被打断"——比如同一行同时要改 price 和扣库存，两个请求各持旧 version，后提交的会覆盖前一个的新改动。
- V1 的扣库存只用 `stock>=qty` 已够；`version+1` 是给 V3"把商品行当热行"时更细粒度的冲突判定预留。
  你能讲清"这两条各自防什么、为什么还需要对方"，就比单纯背"有乐观锁"高一个层次。

## 第 3 课 状态机 CAS：为什么必须用 WHERE status 拦

### 现状（源码事实）

`t_order` 状态机：`PENDING_PAY → PAID → SHIPPED → COMPLETED`，`CANCELLED` 为中断分支。
`order/mapper/Order.xml` 的 `updateStatus`（简化示意）：

```sql
UPDATE t_order
SET status = #{toStatus}, <if test="toStatus=='CANCELLED'">cancel_time = #{cancelTime}</if>, version = version + 1
WHERE id = #{id} AND status = #{fromStatus}
```

`cancel` 调用时 `fromStatus=PENDING_PAY, toStatus=CANCELLED`，影响 0 行 → 抛 `ORDER_STATUS_INVALID`。

### 为什么这么写（推演）

想象用户在**同一秒**点了两次"取消"：两个请求同时进入 `cancel`。
- 若只是 `UPDATE SET status='CANCELLED' WHERE id=?`（无状态条件），两次都会成功——
  库存被回补**两次**，超卖库存。
- 用 **CAS（Compare-And-Swap）式条件**：只允许从 `PENDING_PAY` 变到 `CANCELLED`。
  第一个请求成功（状态变 `CANCELLED`）后，第二个请求的 `WHERE status='PENDING_PAY'` 已不匹配，
  影响 0 行 → 拒绝。**库存只会回补一次。**
- 同一个 UPDATE 里 `cancel_time` 只在转 CANCELLED 时回填（`<if>` 动态 SQL）；
  `version = version + 1` 是**乐观锁痕迹**——版本号随每次状态变更递增，为 V3 秒杀强化预留
  （详见第 9 课）。

### 不这么写的代价

| 错误写法 | 后果 |
|---|---|
| 无 `WHERE status=` 直接改状态 | 并发重复取消 → **库存重复回补**，超卖库存 |
| 应用层先 `selectById` 看状态再 Update | 两步之间有窗，状态在窗内已变，越界 |
| 用 `synchronized` 防重复 | 单机有效、多实例失效，且没必要（DB 一行锁即可） |

**边界延伸**：CAS 只解决"同状态并发"；真正的"重复取消"还能被前端幂等键兜底（同一请求带
`idempotency-key`，服务端去重）。面试能把这层"接口幂等 vs 状态 CAS"分层讲清，加分。

### 亲手改造路径

1. 读 `Order.xml` 的 `updateStatus`，确认 `<if>` 动态回填 `cancel_time` 与 `version+1` 的位置。
2. 写一个小并发冒烟：开两个线程同时对同一 `PENDING_PAY` 订单 `cancel`，断言**只有一个返回 200**，
   库存只回补一次。
3. 思考：如果某订单已经从 `PAID → SHIPPED`，你如何在 `cancel` 方法里让错误更快暴露？
   （提示：依赖 `updateStatus` 返回 0 行 → `ORDER_STATUS_INVALID`，而不是在 Service 里多查一次。）

### 附加：状态机只讲 CAS 不够——要能画出整张迁移图

能画清状态、事件、动作三者，才算真懂状态机：

```
[PENDING_PAY] --支付成功--> [PAID] --发货--> [SHIPPED] --确认/自动--> [COMPLETED]
     |
     +----取消(CAS: WHERE status='PENDING_PAY')----> [CANCELLED]
```

**每个迁移关联的"副作用动作"**：
- `PENDING_PAY → PAID`：通常在支付回调里做，需校验金额、幂等防重复回调；
- `PAID → SHIPPED`：发货，写入运单号，可异步通知；
- `COMPLETED`：确认收货，可能由此触发佣金/返现；
- `PENDING_PAY → CANCELLED`：回补库存（本项目 `cancel` 做的事）。

**进阶观察**：ai-mall 只有「创建(PENDING_PAY)」「取消(PENDING_PAY→CANCELLED)」显式做全，
`PAID/SHIPPED/COMPLETED` 是预定状态、未接支付回调。你面试可以主动指出：
"当前 V1 状态机只用了 PENDING_PAY 和 CANCELLED，PAID 之后的迁移需要支付沙箱 + 回调才能闭环，
这正是 V2 演进点"——把"代码没做全的地方"讲成"演进路线"，是有工程眼光的体现。

### 附加：三权分立的错误码设计（为什么按域分段）

`ResultCode` 按域分段（通用/用户1xxx/电商2xxx/AI3xxx），这不是随手排号，是三权分立式设计：
- **语义自解释**：一眼能从码段(1001/2004/3001)判断错误归属哪个业务域；
- **便于扩展**：新增错误码不必担心撞号，按新域开段即可；
- **对外稳定**：前端/网关可按前几位数字做粗粒度错误分类（如"1xx=账号类"重定向登录页）。

能讲出"错误码为什么要分段管理"，就不是背枚举，而是懂**接口给调用方留语义**的工程观。

## 第 4 课 统一返回重载坑：String 引发的 data 丢失事故

### 现状（源码事实）

`common/R.java` 里，作者**明确注释**了这段教训（素材包原文精神）：
> 早期版本 `R.ok(String)` 与泛型 `ok(T)` 并存。当 `R.ok(chatService.chat(req))` 且 `chat()` 返回
> `String` 时，Java 重载决议把 `String` 匹配到 `R.ok(String)`（当成提示语），导致 **data 丢失**。
> 本项目只留 `ok(T)` 和 `ok(String msg, T data)`。

### 为什么这么写（推演）

`ok(String)`（把它当 msg）和 `ok(T)`（当泛型数据）**对 `String` 入参是歧义的**。
Java 重载决议喜欢精确类型匹配——`char[]/String/Object` 这类参数，会优先选中 `ok(String)`，
于是你把应作为 `data` 的 `String` 塞进了 `msg` 槽位。返回体变成：

```json
{"code":200, "msg":"AI 回答的内容", "data":null}
```

前端拿到 `data=null`，以为 AI 没返回。**运行时代码一个字节不少，数据却无声无息丢了。**

### 不这么写的代价

- `data` 为 null，前端兼容逻辑混乱、排查困难（不是报错，是静默错误，最可怕）。
- 这类 bug 靠测试难以覆盖（单测常直接调方法、不走重载决议的返回体断言）。

### 亲手改造路径

1. 在 `R` 上写一个**测试覆盖这个坑**：`assertNotNull(R.ok("hello").getData())`，
   一旦将来有人加回 `ok(String)` 它会立刻红。
2. 给团队约法三章：**不要恢复单参 `ok(String)`**；要传字符串数据时写 `R.ok(msg, data)` 或
   明确包装模型。这条注释留在源码原因就在此——它是"用接口设计消除二义性"的活教材。

**面试延伸：** 聊"重载决议"时能把此坑当真实事故讲出来，比背 `Double.toString` 泛化问题更贴切业务。

## 第 5 课 SSE 时序：如何保证"消息对"一个都不丢

### 现状（源码事实）

`ChatServiceImpl.stream` 返回 `Flux<String>`（SSE），回调链：

```java
chatClient.prompt()...stream().content()
  .doOnSubscribe(... )        // ① 订阅：先持久化用户提问
  .doOnNext(sb::append)       // ② 每收到一块，累加进 StringBuilder
  .doOnComplete(...)          // ③ 流结束了，持久化完整 assistant 回答
  .onErrorResume(...)         // ④ 异常：返回 "[AI 服务暂时不可用，请稍后再试]"
```

### 为什么这么写（推演）

SSE 的难点：**回答是"边生成边来"的**，你不知道它何时结束、会不会中途断。

- **为什么提问在 `doOnSubscribe` 就先存？** 万一流刚发出请求就连不上了（网络断、模型超时），
  ——若不在订阅时就入库，这次提问就**丢了**（孤儿提问）。先落库，保证"用户确实问过"被记录。
- **为什么 assistant 回答放 `doOnComplete` 才存？** 流结束时才有**完整**回答；中途 `doOnNext`
  只是**累加**（`sb::append`，先把每一块攒起来）。
- **为什么 `onErrorResume` 返回兜底文案而不是裸断？** 如果直接被断开，前端收到一个不完整的
  HTTP/SSE 通道即中断——不优雅且有歧义。补一句文案，消息流仍以"完整段"收尾。

整体目标：**一问一答成对入库**，保证"消息对"不丢，也保证后续 `toAiHistory` 重建上下文时完整。

### 不这么写的代价

| 错误写法 | 后果 |
|---|---|
| 不在 `doOnSubscribe` 存提问 | 流中断 → 提问永不入库（孤儿提问） |
| 在收到第一块时就把回答存了 | 存的是**截断的半截回答**，且后续块丢失 |
| 不加 `onErrorResume` | SSE 裸断，前端收到突兀的流中断 |
| 把"每块"都落库 | 频繁写库、且前后块不成整句，重建上下文时语义错乱 |

### 亲手改造路径

1. 手动断网测试：流进行中拔线，验证 `db` 里**提问已存在、assistant 回答不存在或为兜底文案**。
2. 读 `toAiHistory`，确认它把 DB 历史转成 `UserMessage/AssistantMessage` 时**排除了本次提问**
   （避免本轮 AI 自己重复上轮问题）。
3. 思考 V2 RAG 时 `extra_json` 字段用途：素材包预留了 `extra_json`(TEXT，V2 引用来源)。
   未来回答里可附"引用了哪件商品"，就存这里。

## 第 6 课 订单号：从数据库兜底到雪花 ID 的演进推演

### 现状（源码事实）

`orderNo` 生成规则：`yyyyMMddHHmmssSSS`（17 位时间戳）+ 4 位随机 + `userId % 1000`（用户尾号）。
唯一性由 `t_order.uk_order_no` 唯一索引兜底——极端并发下撞号会抛唯一索引异常。

### 为什么这么写（推演）

- **可读性**：字符串里能看出时间、用户尾号，方便人工排查。
- **数据库唯一索引兜底**：即使程序拼出重号，DB 最后一道关卡会拒绝，保证业务不重复。
- **但它不是分布式 ID**：单库单实例 OK，一旦扩成多实例 / 分库，同一毫秒多实例可能拼出相同前缀，
  撞号概率上升，全靠唯一索引"撞了报错"——体验不好（要重试）。

### 不这么写的代价 / 演进方向

| 方案 | 适用 | 问题 |
|---|---|---|
| 数据库自增 id | 单机小系统 | 集群/跨库不唯一，且暴露订单量 |
| 时间戳+随机（现状） | 单库单实例够用 | 多实例撞号依赖唯一索引 |
| **分布式雪花 ID（V2 演进）** | 多实例 | 需分配 workerId，用时间+机器+序列 |

### 亲手改造路径（雪花 ID 落地）

1. 引入/自写一个简单雪花 ID 生成器：`(时间戳 41bit) + (机器/实例 id) + (自增序列)`，保证全局递增唯一。
2. 在 `create` 里把 `orderNo` 改为雪花 ID 字符串；`uk_order_no` 唯一索引保留作最后防线。
3. **验证**：并发起多个实例下单，断言订单号全局不重复、且趋势递增。
4. **注意边界**：雪花 ID 依赖时钟，若有 `workerId` 分配或时钟回拨处理，面试详聊（NTP 回拨是经典考点）。

## 第 7 课 金额与精度：double 是埋了十年的雷

### 现状（源码事实）

- 表 `t_order.total_amount` 是 `DECIMAL(10,2)`；
- `t_product_sku.price` 也是 `DECIMAL(10,2)`；
- 源码明确约定：累加下单 `total` 用 **BigDecimal**，**严禁 double**。

### 为什么这么写（推演）

IEEE 754 浮点二进制无法精确表示 0.1：`0.1 + 0.2 != 0.3`。
在电商金额上，`0.1+0.2=0.30000000000000004` 会直接导致**算错分**、对账失败。
- **`DECIMAL` 存库**：把精确十进制摆进数据库，底层按定点十进制。
- **BigDecimal 计算**：Java 侧用 `BigDecimal`（优先 `BigDecimal.valueOf` / 字符串构造，避免 `new BigDecimal(0.1)`）。
- **严禁 double**：连"临时变量"都不要用 double——一旦中途 double 化，精度已丢。

### 不这么写的代价

| 错误写法 | 后果 |
|---|---|
| 数据库 `FLOAT/DOUBLE` | 累加/比较出现 0.30000000000000004，对账差 1 分 |
| `new BigDecimal(0.1)` | 双进位又丢精度（应 `BigDecimal.valueOf(0.1)`） |
| 中途转 double 再转 BigDecimal | 精度已在转换时丢失，补救无门 |

### 亲手改造路径

1. grep 全项目确认没有 `double total` 出现（当前是 BigDecimal —— 验证规范化）。
2. 写一个单测：`1.0 + 0.1 ...` 持续累加多次，断言与 `BigDecimal` 累加结果一致；
   故意用 `double` 实现一遍，观察偏差在第几次累加出现。
3. 讨论：金额展示层用什么（`scale=2`、子串），避免 `0.1` 变 `0.1` 但 `0.20` 显示成 `0.2` 之类的格式坑。

## 第 8 课 归属校验：越权漏洞的三种典型写法与正确观

### 现状（源码事实）

- 购物车 `updateQuantity(id, userId, quantity)` / `deleteById(id, userId)`：
  **把 userId 写进 WHERE/SQL 条件**。返回 0 行 → `CART_ITEM_NOT_FOUND`（不只说"删除失败"，
  而是把"不是你所有"和"不存在"统一成同一条错——**不泄露别人的 id 是否存在**）。
- 订单 `detail` / `cancel` / `pageMyOrders`：先校验 `userId.equals(order.getUserId())` 或空 → `ORDER_NOT_FOUND`。
- AI 会话 `ensureOwned`：会话不存在或非本人 → `NOT_FOUND`。
- 一言概括：**归属校验下沉到 SQL / 查询后双重校验，拒绝越权**。

### 为什么这么写（推演）

越权 = 用户能操作/读到"别人的资源"。漏洞根因往往是：**只按资源 id 查、没带当前用户 id 判定归属**。

三种典型破坏性写法：
1. **只按 id 改**：`deleteById(id)` —— 谁传别人的 `cartItemId` 都能删，越权。
2. **"存在即得物"**：查到资源就返回，不校验 owner —— 读到别人的订单/会话。
3. **把"不存在"和"非本人"分开报错** —— 帮攻击者枚举哪些 id 存在。

正确观（本项目做法）：
- **改/删带 userId 进 SQL**，影响行数即归属证明；
- **详情/取消用 userId.equals 显式判定**；
- **不存在的 & 非本人的 → 统一返回"不存在/无效"**，对攻击者无信息泄漏。
- id 从哪来？`StpUtil.getLoginIdAsLong()`——**绝不信任前端传来的"我是谁"**，
  身份永远从 token 取。

### 不这么写的代价 / 亲手改造路径

1. 找到 `Cart.xml` 的 `deleteById`，把 `AND user_id = #{userId}` 注释掉，模拟越权——
   观察任意用户能删任意条目。**（只演示，改完立刻还原。）**
2. 把归属判断抽成一个 SPI/拦截治理点，防止后续代码漏写 userId 条件。
3. 面试讲法：能给"三目录模型"(改删入 SQL、详读用 equals、错误统一、身份从 token 取)，
   胜于一句"我们做了权限校验"。

### 阶段 C：V3（并发/性能攻坚，面试重头戏）

| 演进 | 关键动作 | 风险点（面试必答） |
|---|---|---|
| Redis 预减库存 | `DECR` 挡流量 + DB 兜底 | 预减与 DB 不一致、宕机丢库存、需核对收敛 |

| 分布式锁兜底 | 对热点 SKU 加 Redis 分布式锁防重复处理 | 锁的粒度(按 SKU)、过期时间、可重入、红锁之争 |
| 秒杀 | 承接以上，配合状态机 CAS + 版本乐观锁 | 超卖/漏买/重复下单的多层防线协同 |

顺序递进，每一步都能独立验证（冒烟 + 并发脚本），出了事故就知道哪一层出问题。

### 附加：改了并发代码，怎么证明它真的对？（压测与验证方法）

改并发相关代码——尤其是防超卖、CAS——**肉眼 review 不算数**，要用工具制造并发逼它现形：

1. **JMeter / 自写并发脚本**
   - 场景：把某个 SKU 库存设为 3，模拟 100 并发同时下单该 SKU。
   - 断言：下单成功数 == 3（库存量），失败数 == 97；DB `stock` 落为 0，`sales` 恰为 3。
   - 若成功数 > 库存量 → 超卖复现，说明防线失效。
2. **观察 DB 行锁与死锁**
   - 高并发下单时查 `SHOW ENGINE INNODB STATUS` 或监控死锁日志，
     确认没有因为"先查后改"产生大量行级锁等待/死锁。
3. **日志埋点定位"哪一层在挡"**
   - 在"内存预检、Redis 预减后、DB deductStock 后"各打一条日志，
     用并发压测能直观看到：绝大多数请求在 Redis 预减就被挡下，只有少数冲到 DB。
     这是"预减挡流量、DB 兜底"是否生效的可视证据。
4. **对比改造前后的吞吐**
   - 用同一压测脚本分别跑 V1（纯 DB）与 V3（预减+MQ），对比 QPS / P95 延迟，
     让"为什么上 Redis 预减"有数据支撑，面试讲出来不空。

**一套话**：真正做过并发改造的人都会用"压测复现 + 埋点证伪 + 对比吞吐"三件套；
只停留在代码 review 的，往往被"测试环境复现不了并发 bug"打脸。

## 第 10 课 面试高频连环追问：把"亮点"讲成"体系"

### 本课目标

L3 的核心不是"背熟一个点"，而是被面试官**连环追问**时仍有话可说。
这一课把之前八课的关键决策，拧成几组"一问到底"的追问链，帮你演练"层层往下挖"的应对。

### 追问题 1：防超卖的"层层挖"

- **Q1：怎么防止超卖？**
  → `UPDATE ... WHERE stock>=qty`，行锁 + 原子条件 + 影响行数作信号。
- **Q2：为什么不用"先查库存再改"？**
  → 两步之间有间隙，并发下两个请求都通过预检 → 超卖。
- **Q3：那你代码里的"内存预检库存"是不是白写了？**
  → 不是。预检挡掉明显不够的请求、更快友好报错、减少无效 DB 写；但它只是"面子"，
    真正的防线在 SQL 的 `WHERE`。
- **Q4：这个方案扛得住秒杀吗？**
  → 扛不住大规模。单行 X 锁在超高并发下成为热点瓶颈、吞吐低。→ 引出 **Redis 预减挡流量 + DB 兜底 + MQ 削峰 + 分布式锁兜底** 的 V3 演进。
- **Q5：Redis 预减和 DB 结果不一致怎么办？**
  → 预减只是"挡"，DB 的 `deductStock` 才是"闸"，最终以 DB 为准；二者通过校正任务收敛；
    宕机丢库存靠"预减不 commit + DB 兜底"兜住。能承认"存量口和流量口有间隙"并给收敛方案，
    = 成熟的并发观。

### 追问题 2：事务边界的"层层挖"

- **Q1：`@Transactional` 默认回滚规则？**
  → 默认只对 `RuntimeException` 回滚；`Exception`（受检）默认不回滚。
- **Q2：这里为什么 `rollbackFor = Exception.class`？**
  → 显式扩到 `Exception`，表示"哪怕受检异常也要一起回滚"，更保守稳妥，防半截烂账。
- **Q3：事务里能调外部支付系统吗？**
  → 不要。外部 IO 慢会拉长持锁时间，拖垮整个事务。正确做法是"事务提交后异步/事件化"，或 TCC/事务消息。

### 追问题 3：状态机的"层层挖"

- **Q1：取消订单为什么能防并发重复取消？**
  → `UPDATE ... WHERE status='PENDING_PAY'`：第一个请求成功变 CANCELLED，第二个请求
    WHERE 已不匹配 → 影响 0 行 → `ORDER_STATUS_INVALID`，库存只回补一次。
- **Q2：除了 CAS 还需要什么？**
  → 接口幂等（幂等键）防"同一取消请求重复发"；版本乐观锁防并发写覆盖（`version+1`）。
- **Q3：为什么 `cancel_time` 只在转 CANCELLED 时回填？**
  → 用 `<if>` 动态 SQL 精确区分"从 PENDING_PAY → CANCELLED"才写取消时间，其它状态迁移不写，避免脏填充。

### 追问题 4：身份与越权的"层层挖"

- **Q1：userId 从哪来的？**
  → `StpUtil.getLoginIdAsLong()`，从 `Authorization` 头里的 token 反解。
- **Q2：能让前端传 userId 吗？**
  → 绝不。身份永远从 token 取，前端传的"我是谁"不可信。
- **Q3：购物车"不是你的条目"和"条目不存在"为何报同一个错？**
  → 避免帮攻击者枚举哪些 id 存在；兼顾"不是你的"和"不存在"一律归为无效操作。

### 追问题 5：SSE 的"层层挖"

- **Q1：为什么要 `doOnSubscribe` 先存提问？**
  → 防流中断导致提问(孤儿提问)永不入库。
- **Q2：为什么不把回答每收到一块就存？**
  → 会在"半截"时落库；需等 `doOnComplete` 拿完整答案再存，一问一答成对。
- **Q3：`onErrorResume` 兜底文案的意义？**
  → 避免 SSE 裸断，让消息流以一段完整文案收尾，前端不至于收到一个断裂的流。

### 追问题 6：BigDecimal 的"层层挖"

- **Q1：为什么金额必须 BigDecimal？**
  → `double` 的 IEEE754 二进制无法精确表示 0.1，`0.1+0.2!=0.3`，累加出 1 分钱偏差、对账失败。
- **Q2：`new BigDecimal(0.1)` 对吗？**
  → 错。应 `BigDecimal.valueOf(0.1)`（先把 double 经十进制字符串转）。`new BigDecimal(0.1)` 双进位又丢精度。
- **Q3：数据库为什么用 DECIMAL(10,2) 不用 FLOAT？**
  → DECIMAL 是定点十进制，精确；FLOAT/DOUBLE 是近似存储，累加/比较出偏差。

> 练习方式：拿前 8 课的任一"决策"，自己把上表补一个"追问题 X"；能自问自答三层以上，
> 面对真人追问才不会哑火。面试官听的往往不是答案本身，而是你**能不能稳定地把复杂度一层层讲清楚**。

## 结课：一张「决策 → 事故库 → 演进」总表

| 决策（现状） | 防止的事故 | 不这样写的代价 | 演进方向 |
|---|---|---|---|
| `UPDATE ... WHERE stock>=qty` (`deductStock`) | 超卖 | 先查后改并发超卖、扣负数 | V3 Redis 预减 + DB 兜底 |
| `@Transactional(rollbackFor=Exception.class)` | 半截烂账 | 受检异常不回滚、事务内外部 IO 拖死 | 事务边界收敛、异步化 |
| 状态机 CAS `WHERE fromStatus` | 重复取消回补两次 | 并发重复取消 → 库存重复回补 | 幂等键 + 版本乐观锁 |
| `R` 去掉单参 `ok(String)` | data 被当 msg 吞掉 | 静默 data=null 无法排查 | 写单测锁死该坑 |
| SSE `doOnSubscribe`先存提问 + `doOnComplete`存答案 + `onErrorResume`兜底 | 消息对丢失/半截 | 孤儿提问、半截回答、SSE 裸断 | V2 RAG 用 `extra_json` 存引用 |
| 时间戳随机 `orderNo` + `uk_order_no` | 订单号重复 | 多实例撞号靠唯一索引报错 | V2 雪花 ID 全局唯一 |
| 金额 BigDecimal + DECIMAL(10,2) | 1 分钱对账 | `0.1+0.2!=0.3` 精度灾难 | 始终 BigDecimal，展示层控 scale |
| 归属校验下沉 SQL / equals / 统一错误 | 越权读改删 | 传别人 id 就能操作别人的资源 | 抽归属治理点防遗漏 |

> 把这八行连起来，你会发现一条共同的底层思维：**"并发下成立吗？异常下完整吗？越权能防住吗？
> 精度准吗？歧义少吗？扩几台还能用吗？"** 这六个拷问，正是一开始第 0 课给你的提问框架。
> 到这儿你已经把它从"模板"变成了"肌肉记忆"——读任何一段业务代码，这六问会自动启动。

**八节课，八个"看似平凡却保命的决定"。** 你现在对这些代码不再只是"会读"，而是**知道它为何而存在、
坏了会如何、要往哪里走**。这，就是面试官想从你嘴里听到的那种"带着取舍说话"的工程感。

> ✅ 通关：现在回看 `OrderServiceImpl.create` 里那条 `deductStock` 调用——
> 你能顺着它讲出「行锁 → 原子条件 → 影响行数信号 → Redis预减 → MQ 削峰」一整条并发攻防线。
> 把这条线理顺，面试的"防超卖"就稳了。

### 延伸：从"读懂 ai-mall"到"面试讲自己的项目"

把 ai-mall 的能力**转嫁到你自己项目**上，才算真正收为己用。三个速成自检法：

1. **口径对齐**：用一句话说清"我的项目在并发下怎么防超卖/防重复"。如果你说不清，
   多半是还没真正做到 L3 要求的"带着取舍说话"——回炉第 1、3 课。
2. **反例自测**：把 ai-mall 的"错误写法"套到你项目里，自问"如果我这么写会出什么事故"。
   能逐条对应上，说明你掌握了"为什么"而非"是什么"。
3. **演进叙事**：面试讲项目时顺着"V1 现状 → 改进动机 → V2/V3 演进"来讲，
   而不是报菜名式列技术栈。ai-mall 的 V1→V2/V3 路径（第 9 课）就是现成的叙事模板。

> 记住：**面试官要的不是你背下 ai-mall，而是看到你面对任何代码都会"拆、问、再设计"。**
