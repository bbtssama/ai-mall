## 0 面试官视角：他要的不是答案，是"你有没有想过"

一句话先定个调：**面试官问"为什么单体起步"，不是真的不知道，而是想看你有没有**思考的维度**。** 你掉进"答知识点"的坑——`synchronized` 是悲观锁、JWT 是无状态——就输了；你**回答"当时为什么选 A 而不是 B，代价是什么，什么时候该反过来"**——就赢了。

本文把这些回答的组织方式总结成一个可复用的句式，后面每一章都用它：

> **「在这个场景下，我选了 X，因为它……；代价是……；当出现 ①……②…… 时，我会换成 Y。」**

这就是面试官最想听到的三段式：**决策 + 理由 + 边界**。下面每一章，就是把 ai-mall 六个核心决策按这个句式帮你组织好。你可以把它们背下来，但更建议理解后用自己的话讲。

## 1 单体 → 微服务的演进决策

### 1.1 V1 为什么是单体

**面试官：「你们项目是单体的，为什么不做微服务？」**

项目事实（素材包 §1、§9）：ai-mall 是一个 Spring Boot 单体，闭环链路是 注册登录 → 浏览商品 → 加购物车 → 下单（防超卖）→ AI 问答（SSE 流式）。

回答主干：**单体起步是"用最小的复杂度换最大的迭代速度"，微服务是复杂度逼出来的选择，不是越早越好。**

按三段式展开：

- **决策**：V1 用单体（单一 Spring Boot 工程，Java 17 + MyBatis + Sa-Token + Spring AI 全在一个进程）。
- **理由**：
  1. **团队与规模**：小团队、一个域业务，单体一个工程能跑、能测、能部署，运维面最小。微服务光基础设施（服务发现、配置中心、网关、链路追踪、多套 CI/CD）就够一个小团队疲于奔命。
  2. **事务简单**：单体里，扣库存、写订单、写明细在一个数据库、一个事务里搞定（见第 2 章）。拆成微服务后，跨库事务立刻变成分布式一致性问题——复杂度是量级的跳变。
  3. **调用成本低**：单体内部调用是方法调用，几毫秒；微服务间是网络调用，有序列化、网络、超时、重试、限流等一系列兜底。业务没到那个体量，这些成本纯属白付。
  4. **部署简单**：`mvn spring-boot:run` 就起来，一个 jar 包就是全部。这是"能快速试错"的基础。

  关键要补一句：**单体不是"没有结构"**。ai-mall 用"按域分包 + 域内分层"（素材包 §2 的分层约定：common/config/user/goods/order/ai，域内 bean/controller/dto/mapper/service）先做**模块化**——域与域之间不互相操作内部服务、只走公开接口。这套结构单体健康，而且**为将来拆微服务预留了清晰的切割线**。这是单体和"大泥球"的本质区别：**大泥球没有边界，单体有边界。**

- **代价 / 边界**：单体到顶的瓶颈是"一个域的突发流量拉高压垮整条线"、"某域频繁发布影响整条链路"、"单库单表容量到顶"。当出现 ①一个域（比如订单）需要独立扩容、独立发布频率远高于其他域 ②团队大到一个域需要独立小组独立开分支 ③数据库单表撑不住需要分库时——才是拆微服务的时机。

### 1.2 V4 拆分边界依据

**面试官强调「拆分边界」，通常还要追问：拆成几个、按什么拆、拆了事务怎么办。**

项目事实（素材包 §9）：ai-mall 演进路线里 V4 = 微服务。但没有说拆成几个——这一节给你一套**自己论证拆分边界**的方法，这比背答案更有含金量。

**依据一：按"业务域" + "变更频率"拆。** 切分的第一原则是"把会一起变的东西放一个服务"。ai-mall 天然就有清晰的域边界（第 1 章那套分包）：user / goods / order / ai，可以对应成 用户服务 / 商品服务 / 订单服务 / AI 服务。另一个参考是"变更频率"：某个域如果独立发布、独立上线频繁，就值得独立成服务。

**依据二：按"数据边界"拆，服务边界最终落在数据库。** 这是最容易答出亮点的地方——**微服务拆分本质上是数据拆分**。两个服务如果共享一张表、或频繁跨库 join，就说明拆歪了。所以拆分前先看表：ai-mall 8 张表（素材包 §7）正好天然分成 4 组——用户表（t_user）→用户服务；商品/规格/购物车（t_product/t_product_sku/t_cart）→商品服务；订单/订单明细（t_order/t_order_item）→订单服务；会话/消息（t_conversation/t_message）→AI 服务。**数据域不重叠，拆起来才顺。**

**依据三：面对"拆了事务怎么办"，主动引出折中方案。** 拆分后"下单"跨越订单服务 + 商品服务（扣库存）。此时不再有单库事务，只能选：
- **先把"最经得起拆"的交给最终一致性**：比如"查订单"、"商品资料"这类读多写少、允许延迟的数据，用数据同步/缓存/事件解耦。
- **把"强一致必须的"尽量收拢到一个库**：比如"扣库存"这种强一致操作，尽量让它在单个服务 + 单库完成。
- 实在跨库强一致的（比如不同库同时扣库存+写订单），引入复杂方案（见第 2 章分布式事务）——**这往往意味着拆分的边界还没优化好**，好的做法是先调整边界或操作编排，让强一致部分变少。

### 1.3 追问链：这段怎么扛住面试官

> **Q：「微服务」和「分布式」的区别？**
> 单体是多模块在同一进程（本地方法调用）；微服务是把这些模块拆到不同进程/机器（网络 RPC）。分布式是个更宽泛的词——任何跨机器协作都算。微服务是一种分布式架构的落地组织方式。关键直觉：**微服务把"方法的距离"拉成了"网络的距离"，所有本地才有的事（强一致性、延迟、故障隔离）都要重新面对。**

> **Q：你说单体好，那劣势呢？能不能举一个 ai-mall 将来一定会遇到的具体痛点？**
> 具体到本项目：①**AI 域**将来是高频、重计算、要独立扩容的（SSE 长连接很吃连接数），如果和订单挤在一个进程，可能互相拖累；②**订单域**将来要接支付回调、消息推送，是需要独立并发和发布节奏的。这两个是想拆的最直接理由。**先把"这俩迟早要拆"说出来，再补"但现在拆了反而增加复杂度"**——面试官会很满意这个"既看到未来、又守住当下"的判断。

> **Q：拆分微服务后，原来单体里那些 @Transactional 怎么办？**
> 这是第 1 章和第 2 章的交界。答案：**单库事务仍然用（服务内部），跨服务的事务改成"最终一致性"的方案**（本地消息表、Saga 或事件总线），并把"必须强一致"的部分尽量收敛到单个服务内。别一上来就说"用分布式事务"——能不用就不用，是更成熟的判断。

## 2 事务边界设计：扣库存 + 写订单为什么必须同事务

### 2.1 一个事务的边界画在哪

**面试官：「下单这步为什么扣库存、写订单、写明细、清购物车要在一个事务里？」**

项目事实（素材包 §6 order、§8）：`OrderServiceImpl.create` 标注 `@Transactional(rollbackFor = Exception.class)`，内部顺序：取 userId → 逐项查 SKU、校验上架、内存预检 → 调 `deductStock`（`UPDATE ... SET stock=stock-?, sales=sales+? WHERE id=? AND stock>=?`）→ 组 order（orderNo=时间戳17位+4位随机+userId%1000，uk_order_no 兜底；status=PENDING_PAY；收货信息）→ batchInsert 明细（orderId 回填）→ `cartMapper.deleteByUserIdAndSkuIds` 清购物车。

先问一个更基本的问题：**"一个事务"到底包住什么？** 事务的边界（begin … commit/rollback）决定了一组操作是"要么全成、要么全撤"。画边界的判断标准只有一个：

> **凡是"在财务/业务上必须作为一个整体呈现给对方"的操作，就必须在同一个事务里。**

下单就是教科书案例：顾客看到的结果是"货被扣了 + 订单生成了 + 明细有了 + 购物车清了"是**一步**。如果把任何一环拆出去，顾客就会看到"钱（款）变了但订单没有"这种鬼状态。

### 2.2 拆开会发生什么

把「扣库存」和「写订单」拆成两个独立事务，有三种排列，各有各的灾难：

- **先扣库存、后写订单（各自提交）**：扣库存成功提交 → 写订单失败提交（比如商品突然下架/明细格式错）→ **货没了、单没有**，顾客钱白扣。这是最可怕的漏。
- **先写订单、后扣库存**：订单生成了、货没扣 → 两个客人都买到同一个库存 → **超卖**。
- **并行**：更乱，两个独立事务没有先后，结果不可预期。

而**一个事务里**，第 2 个 SKU 扣到一半发现没货抛了 `STOCK_NOT_ENOUGH`，前面第 1 个 SKU 已扣的库存也全部回滚——顾客看到的是"下单失败"，库存仿佛从未动过。**这个"顾客永远看不到中间态"的能力，正是事务的价值，也是 `rollbackFor` 为什么必须写上 `Exception.class` 的原因**（素材包 §8-2 强调默认只回滚 RuntimeException，漏配会导致"扣了库存当成功"）。

### 2.3 跨库 / 跨服务：事务边界跨不过 JVM 怎么办

**面试官：「如果订单和库存不在一个数据库，或拆成两个服务，这个 @Transactional 还保护得了吗？」**

答案很干脆：**保护不了。** `@Transactional` 是 Spring 管理"单个数据库连接"的事务，它的边界在**一个数据库连接之内**。一旦涉及：
- **两个数据库**（订单库 + 库存库）——一个应用连两套库，两个连接、两个事务，`@Transactional` 管不住。
- **两个服务**（订单服务 + 商品服务）——连连接都不是同一个，更别提事务。

这时"强一致"从"数据库保证"变成了"应用层要自己组织"的问题，也就是分布式事务。

### 2.4 分布式事务简述：2PC / TCC / Saga / 本地消息表

这块面试频率极高，但你只要讲清**四种主流方案的本质差异 + 各自代价**，就够了。不要背实现细节，要讲思路。

**① 两阶段提交（2PC / XA）。**
- 思路：一个"协调者"先让所有参与者"预备"（prepare，锁定资源、写undolog、保证能提交），全部预备成功才"提交"（commit）；任一失败就全部"回滚"。
- 特点：**强一致**、对业务透明（数据库层帮实现 XA）。
- 代价：**协调者单点 + 同步阻塞**——prepare 后所有资源被锁住等协调者拍板，一个节点慢全链路卡；协调者挂了大伙儿都悬着（需要超时/补偿）。**吞吐被锁死，不适用于高并发。**

**② TCC（Try-Confirm-Cancel）。**
- 思路：把每个服务操作拆成三拍——Try（预占资源，如冻结库存）、Confirm（确认提交）、Cancel（回滚释放）。Try 全成功才 Confirm，任一步失败对已 Try 的做 Cancel。
- 特点：**业务级约束显式化**，比 2PC 灵活、性能更好（不需要数据库层面锁住整个事务）。
- 代价：**侵入性极强**——每个服务都要自己实现 Try/Confirm/Cancel 三套逻辑 + 幂等 + 补偿，代码复杂度和心智成本显著上升。

**③ Saga（编排式 / 编排 + 补偿）。**
- 思路：把一个长事务切成多个本地事务串起来，每个都有对应的"补偿事务"（undo）。走正路成功一个连一个；走到某步失败，就**反向调用前面每一步的补偿**把状态"补回去"（比如扣库存了就加回来）。
- 特点：**没有全局锁、异步、能扛高并发**，是微服务下单的常见选择。
- 代价：**最终一致**——中间有一段时间顾客可能看到"下单成功但库存还没扣完/已回补"；补偿逻辑要你自己写对且幂等。不是强一致。

**④ 本地消息表 / 可靠消息最终一致。**
- 思路：主服务"写业务 + 写一条待发消息"在**同一个本地事务**里，靠一张消息表记状态；后台任务轮询把消息可靠地发到 MQ，下游消费并幂等处理。
- 特点：**实现相对简单**（很多团队第一版用这个）、能保证"主操作真正完成才发消息"。
- 代价：业务侵入（要建消息表）、最终一致、需要处理消息堆积/重复消费。

**背结论的口诀：**
- 要**强一致** → 2PC（代价是吞吐与阻塞）或尽力把强一致收敛到单库。
- 要**高并发 + 弱一致可接受** → Saga（编排补偿）或本地消息表 + MQ。
- 要**最灵活/最严格业务约束** → TCC，但先问问自己值不值得那堆样板。

对 ai-mall 这种起步项目，**正确做法其实是"先用单体把强一致留在单事务里"**（见第 1 章），等真要拆再评估——先别急着上分布式事务。

### 2.5 追问链：分布式事务怎么答才不露怯

> **Q：你说用 Saga，它怎么保证"补偿一定执行"？**
> 答一层：Saga 的补偿路由由"状态 / 事务日志"驱动，哪个本地事务成功、哪个失败、补偿执行到哪一步，都要可靠持久化；任何环节进程崩溃后，由后台恢复 / 定时扫描接着走。别硬吹"零丢失"，说清楚"靠持久化 + 恢复机制逼近可靠"，是更可信的表述。

> **Q：幂等是什么意思？为什么要幂等？**
> 答：同一个操作执行多次，效果等于执行一次。网络重试、消息重复消费、前端重复提交都会造成"同一笔钱扣两次/同一库存回补两次"。解法是"用唯一业务键（如订单号/幂等键）去重"。落到 ai-mall——`uk_order_no` 唯一索引、`updateStatus` 的 `WHERE status=?` 条件判重，其实都是"幂等"的不同形态（见第 3 章、第 5 章）。**把项目里已有的幂等点串进回答，很加分。**

> **Q：ai-mall 现在用了分布式事务吗？**
> 答：没有，也不需要。它是单体 + 单库，所有强一致都在一个 `@Transactional` 里完成（素材包 §8 的防超卖+整体回滚）。这反而是个正确示范——**不该用的分布式事务别硬上**。真要往 V4 微服务走，才需要考虑本节的方案，而且要"按需、收敛强一致范围"地引入。

## 3 乐观锁 vs 悲观锁 vs 原子 UPDATE 的适用边界

### 3.1 三种方案的底层差别

面试官常把三者放在一起逼你区分。先讲清楚咱们项目用的是哪种——素材包 §8-1 明确：

> 防超卖**不是先查再减**，而是 `UPDATE t_product_sku SET stock=stock-?, sales=sales+? WHERE id=? AND stock>=?`。**内存预检库存只是提前给友好报错，真正防线在这条条件 UPDATE。**

这是第三种，常被称为「**原子 UPDATE / 条件 UPDATE**」。它和"乐观锁（version CAS）"有什么不同，是面试的分水岭。

用一张表讲清楚三者：

| 方案 | 思路 | 并发控制谁做 | 典型写法 | 冲突代价 | 适用 |
|---|---|---|---|---|---|
| **悲观锁** | 先锁住资源，再读-改，别人排队 | 数据库行锁（`SELECT ... FOR UPDATE`） | 先 lock 再读写 | 锁持有期间全体阻塞，吞吐低 | 写冲突极频繁、必须串行 |
| **乐观锁** | 读取带版本号，更新时校验版本没被改 | 应用层重试（`WHERE version=?`，失败重读） | `UPDATE ... WHERE id=? AND version=?` | 冲突重试，放大请求 | 读多写少、冲突率低 |
| **原子 UPDATE（本项目）** | 把"校验条件"和"更新"合并成一条 SQL | 数据库行锁 + 条件原子完成 | `UPDATE ... WHERE id=? AND stock>=?` | 冲突的是"条件不成立→影响0行"，直接失败无重试 | 库存/余额这种"基于当前值做条件运算" |

**最核心的差别在第三行**：乐观锁校验的是"**version 没被别人改过**"（只关心"我这个版本还新鲜吗"），而原子 UPDATE 校验的是"**库存还剩多少**"（直接校验业务量本身）。对库存这个业务，`stock >= ?` 是**业务上更贴切的条件**——不用引入一个额外的 version 计数器，条件本身就表达了"够不够"。

### 3.2 选型树：什么场景用什么

给一个可复用的判断流程，面试时"当场选型"很加分：

1. **这个修改是"基于当前值做条件运算"吗？**（库存减、余额扣、账户金额加）
   - 是 → **用原子 UPDATE**（`WHERE 剩余 >= 需要`），数据库最擅长，无应用层重试。**这是库存/金额的默认选项。**
2. **修改是"改进来时只认版本"？**（如编辑文档，只管"你有没有基于最新版改"）→ **用乐观锁**（version + 重试）。冲突少时最省。
3. **写冲突极频繁、更新前必须看到一致快照做复杂决策？**（如取票机锁座位：读+判+占必须完整串行）→ **用悲观锁**（`FOR UPDATE`），或用数据库提供的条件 UPDATE 走 "check-then-act" 合并。
4. **跨 JVM / 跨机并发？** → 单机悲观/乐观都失效，得用 Redis 分布式锁 / 中间件（V3 秒杀的 Redis 场景）。

### 3.3 追问链：为什么扣库存不上版乐观锁

> **Q：很多地方写"乐观锁防超卖"，你们为什么不用 version？**
> 答（关键得分点）：①素材包 §7 表里**确实预留了 `version` 字段**（乐观锁痕迹，V3 秒杀强化用），说明作者想到过；②但 V1 的库存扣减**特意没用 version**——因为库存这个字段，`stock >= ?` 本身就是"版本检查"（条件即版本），再套一层 version 是重复；③乐观锁的优势在"**冲突少、失败可优雅重试**（改文档）"，而抢购场景**冲突率极高、重试会空前放大并发压力**，乐观锁不仅不省，反而更容易被击穿。所以原子条件 UPDATE 才是库存的正确选型。**先承认表里有 version 的伏笔，再解释为什么不现在用——这比含糊其辞高级得多。**

> **Q：条件 UPDATE 有没有缺点？**
> 答：有。①它是"失败即失败"，不重试，抢购体验是"瞬秒没"，需要前端友好提示 + 可能的排队（V3 秒杀用 MQ 削峰）；②它只在"单行"上安全，跨多行/跨表的强一致仍要靠事务（第 2 章）；③它不解决"读到的旧数据做复杂逻辑"——如果下单要先做"多 SKU 组合库存预检"这种跨行判断，光靠单行 UPDATE 不够。

> **Q：Redis 怎么做库存？（V3 相关）**
> 答：秒杀一般用 Redis 里的整数做库存，扣减走 **Lua 脚本**保证原子（`if GET < need then fail; DECRBY;`），DB 只是最终落账。Redis 的原子性靠单线程命令/Lua，和 DB 的"条件 UPDATE"思路同源，都是"check and act 原子化"。答到这里，面试官会看到你"DB 方案 vs 缓存方案"是**同一种思维的两种载体**。

## 4 SSE 流式与落库一致性

### 4.1 流式接口最难的不是"流"，是"两侧"

**面试官：「AI 返回用 SSE，为什么麻烦？难点在哪？」**

先讲清 SSE 是什么：`POST /api/v1/chat/stream`（`produces = TEXT_EVENT_STREAM_VALUE`，返回 `Flux<String>`，素材包 §6 ai 域）。响应是**服务端单向、实时推流**的字幕式输出。普通接口要么一次性返回，要么是请求/响应成对；而流式接口的响应是"一段一段不停给"，**时长不确定、可能失败、可能中途断**。

于是难点根本不在"能不能推流"（框架早解决了），而在**流的生命周期两端**：
1. **流的开始**：用户问题什么时候落库？
2. **流的结束**：回答完整落库还是逐段落库？中途失败怎么办？

### 4.2 时序安全：doOnSubscribe / doOnComplete / onErrorResume

项目事实（素材包 §6 ai）：`ChatServiceImpl.stream` 用 Spring AI 返回 `Flux<String>`，加四个操作符：

- `doOnSubscribe` 先持久化**用户问题**——防流失败留「孤儿提问」；
- `doOnNext(sb::append)` **累加**回答到内存；
- `doOnComplete` 持久化**完整 assistant 回答**；
- `onErrorResume` 返回 `"\n\n[AI 服务暂时不可用，请稍后再试]"`——防 SSE 裸断。

把这四个算子按时间线排：

```
[请求进来]  --doOnSubscribe-->  存"用户问题"        ← 开始就存，杜绝孤儿提问
   │
[AI 逐字吐]  --doOnNext-------->  内存 sb.append     ← 只累加，不落库（避免存一堆碎块）
   ...
[AI 吐完]   --doOnComplete----->  存"完整回答"        ← 只有完整才落库
   │
[AI 中断]   --onErrorResume---->  返回兜底文案       ← 把异常翻译成"可收尾的人话"，不让流裸断
```

这里有一个值得在面试里被强调的设计直觉：**落库时机选择与流式响应天然冲突**。如果流式"每来一段就存"，数据会碎且重复；如果流式"等全部完了再存用户问题"，用户问题就太晚存档（万一中途断了就丢）。解法是**开场存问题（快）、结尾存回答（一整块）**——把"两个端点"保护住，中途的碎块只做内存累加。

### 4.3 为什么"问题-回答"必须成对落库

延续上一节，面试官会追问"为什么不干脆只在最后存一下用户问题？"

- 用户问题如果等流结束才存：流一旦中途失败（AI 挂了、网络抖了、浏览器关了），**用户这一问就丢了**——他发了消息，系统没记录。这是「孤儿提问」。
- 回答如果逐段存：一旦中途失败，库里会存进半截回答，将来翻历史看到一半，还以为是完整答案。这是「残缺回答」。
- 所以设计成**问题带头存、回答收尾存、出错给兜底文案**：保证**每一问都有完整的一问一答落库**，聊天记录对账完整（素材包 §8-8「保证消息对不丢」）。这也是为什么 `doOnSubscribe` 在"订阅一开始"就执行——它比"等结果"提前了整条流的生命周期，是时间线上的关键防护。

### 4.4 追问链：SSE 断了你说给谁听

> **Q：SSE 是单向的，如果用户想中途打断（没意思了），技术上怎么办？**
> 答：SSE 单向，前端要"打断"得另发一个取消请求（用一个中断信号/取消 token 去取消那条 Flux）。而 WebSocket 是双向的，前端可直接在连接上"打断"。这是 SSE 的一个边界——本项目是纯问答场景、用户一般不打断，所以 SSE 够用；真要做"边问边改"的强交互，才换 WebSocket。

> **Q：SSE、WebSocket、以及"一次性返回完整回答"，你会怎么选？**
> 答：一次性返回实现最简单，但等待体验差、对账也简单；SSE 单向推送，适合"服务端单向实时输出"，实现比 WS 简单、浏览器原生支持（EventSource），是慢生成内容（AI 回答、日志流）的甜点位；WebSocket 双向全双工，适合强交互（聊天室、协同编辑、实时控制）。**按"是否需要双向 + 是否需要推送"选，而不是谁都上 WebSocket。**

> **Q：如果这次连接断了，重连后用户看到什么？**
> 答：因为"问题-回答"已经成对落库，重连后从数据库把历史记录原样读出即可（`MessageMapper.selectByConversationId`，[旧→新]，素材包 §6 ai）。前端展示的是**数据库里的最终版本，不是那次半断的流**。这就是"落库一致性"带给用户的价值：**流会断，但在库里的对账是完整的。**

## 5 无状态认证与多端登录

### 5.1 无状态到底意味着什么

**面试官：「无状态认证，'无状态'的'状态'指什么？」**

先纠一个常见误解：很多人以为"无状态 = 不存任何东西"，这是错的。准确说是——**认证状态（谁登录了、登录建立了没）不放在服务器端**，而是由客户端（浏览器/App）保存并每次带着。

把它和 Session 对比（素材包 §6、§5 sa-token 配置）：

| | Session（服务端有状态） | Sa-Token 无状态 Token |
|---|---|---|
| 登录后谁保存"会话" | 服务器内存（HttpSession） | 客户端（每次请求带头） |
| 服务器要不要存会话 | 要 | **不要**（Token 自证身份） |
| 多实例部署 | 要 Session 共享（sticky/共享/Redis） | **天然可用**（不依赖单机内存） |
| 主动让某 Token 失效 | 好办（删 Session） | 难（要在客户端或额外存储拦） |
| 会话存放位置 | JSESSIONID Cookie | `Authorization` 头 |

关键洞察：`token-style: uuid` + `is-log: false`（素材包 §5）说明 Token 是**随机串不编码用户信息**。Sa-Token 拿到 Token 后其实还是要"查"——但查的是"这个 Token 对应的登录记录在哪"，而默认实现可以放内存/放缓存，**关键是服务器不依赖"特定一台机器的内存"**，服务拆多实例可横向扩展。这一点是"无状态"能力的核心收益。

### 5.2 is-concurrent / is-share：多端登录的产品决策落到配置

**面试官：「多端登录怎么做？两个手机都登同一个号会怎样？」**

项目事实（素材包 §5）：`is-concurrent: true`、`is-share: false`。

- `is-concurrent: true`：**允许并发登录**——即同一个账号**可以同时在多个设备登录**（如果 false，后登录会把前一个踢掉）。
- `is-share: false`：登录的 Token **不共享**——每端一"签"一次，得到各自独立的 Token（如果 true，同一次登录的多端共用同一个 Token）。

所以本项目是：**同意一账号多端同时在线，但每一端是独立的 Token**。这背后是一个**产品决策**（"允许多设备，但互不干扰"），落到两个布尔配置。答这个题要说：**产品要什么，配置就答应什么**，而不是背"这两个配置叫啥"。

再补一句：`is-concurrent: true + is-share: false` 意味着"允许并发 + 独立 Token"，那要"多端互踢"（A 端登录把 B 端挤下线）就得 `is-share: false + is-concurrent: false`（新登录顶掉旧）。这是两种常见产品形态，口述切换即可展示你理解到位。

### 5.3 无状态的代价：吊销难，怎么治

**面试官：「Token 怎么注销？用户改密码，旧 Token 还能用吗？」**

讲透无状态的最大软肋：**服务端不记录"谁持有哪个 Token"，所以"让某个 Token 立刻失效"没有直接手段。**

对应策略（按可接受度依次）：
1. **靠过期时间**：fixed 7 天（`timeout=604800`），过期自然失效。这是本项目 V1 的做法，最简单。
2. **靠登出作废**：`/api/v1/auth/logout` 调 StpUtil.logout()，把"这条登录"置为失效，后续用这个 Token 访问会被拦截（重新认证）。
3. **升级为"有状态可吊销"**：把 token→用户 的映射存进 Redis（Sa-Token 支持插拔存储）。这样改需求时能"指定踢出/禁用"，代价是引入一个共享存储——本质是"在无状态方案上叠一个可吊销层"，常见于"管理员封禁用户""检测到安全事件一键下线"。

答"改密码后旧 Token 复用"：V1 靠 7 天过期兜底（有一个窗口期）；严谨起见应在改密码时主动将旧 token 加入黑名单 / 换掉（Sa-Token 可配置处理），项目当前未做这个收紧是已知取舍（素材包 §9 无单测、收敛点）。**主动承认边界 + 给出收紧方案，比硬说自己完美更有说服力。**

### 5.4 追问链：Token vs Session 答出层次

> **Q：Token 和 JWT 有什么区别？你更倾向哪个？**
> 答：Token 是泛称；JWT 是"自包含"的 Token（把用户/角色/过期时间签进 Token 本身，验签即信，零查证）。Sa-Token 用的 uuid 式 Token **不编码用户信息，解码不了，只能"查"**——本质是"服务端可查的随机串"，比 JWT 少一层签名密钥管理，对单体更简单；但 JWT 能跨服务直接验签共享身份，微服务化后更爽。**所以这是"查证成本" vs "签发/吊销管理"的取舍。**

> **Q：Token 存 localStorage 被 XSS 偷了怎么办？**
> 答：存 localStorage 有 XSS 风险（脚本可读）；存 Cookie 要防 CSRF。业界没有绝对安全，要结合威胁模型（本项目是学习/求职项目，V1 做了最基本的约定——走 `Authorization` 头、CORS 只放 localhost——不引入额外 OAuth/刷新令牌那套是合理取舍；生产级会加 HttpOnly Cookie + 双 Token：短活 access + 长活 refresh 续期）。**把"知道风险 + 知道升级路径"讲出来，比假装没风险强太多。**

## 6 V1 全量知识注入 → RAG → Agent 的能力演进

### 6.1 从"把商品清单塞进 prompt"说起

**面试官：「AI 怎么知道你们卖什么？」（这是本期最可能被追问的加试题）**

项目事实（素材包 §6 ai 域、§8-?）：`buildSystemPrompt` V1 的实现是——

1. `productMapper.selectAllOnSale()` 每次问答都从库取**全量在售商品**；
2. 裁剪字段 `id/name/subTitle/minPrice/detail`，`ObjectMapper` 序列化成 JSON；
3. 把 JSON 塞进 **system prompt**，并三条铁律：基于商品库如实回答、库外的东西坦诚说不知道、**不编造**。

这个方案的本质叫「**全量上下文注入**」（Context Injection / In-Context Learning）：把领域数据当 prompt 上下文喂给模型，模型不改变权重、只借助这段上下文作答。它的优点：实现极简、数据天然最新（每次现取）、诚实性靠指令约束；缺点：商品一多 prompt 撑爆、token 成本线性涨、检索精度为零（所有商品不分主次全塞进一锅炖）。这就引出 V2。

### 6.2 V2：检索增强生成（RAG）

**面试官：「商品涨到 10 万件，你那个全量塞法还撑得住吗？」**

撑不住。升级方向是 **RAG（Retrieval-Augmented Generation，检索增强生成）**。思路从"全喂"变成"先检再喂"：

1. 离线把商品资料切块 + embedding（向量化），存向量库；同时保留关键词/倒排索引（**混合检索**提升召回）；
2. 用户提问 → 问题也 embedding → **召回 Top-K 最相关片段** → 相关性重排（rerank）；
3. 只把"召回的一小段"塞进 prompt → 模型只基于这些生成。

演进收益（对比 V1）：**prompt 长度与商品总量解耦，只与 K 相关**（万件不慌）；回答聚焦到最相关几件；还能返回"我依据了这份商品资料"提供**引用来源**（素材包 `t_message.extra_json` 即 V2 存放引用的预留字段）。代价：要管向量库、embedding、同步更新、召回调优（分块/重排/混合）——一套完整链路。

> 判断框架：**知识是"变动的数据"还是"稳定的能力"？** 电商商品 = 频繁变动的数据 → 用检索（RAG），知识在库、模型不动；稳定的问答风格/固定话术 → 才考虑微调模型。

### 6.3 V3/V4/V5：从问答到能动手的 Agent

**面试官会继续顺着吹「你说的都是傻问傻答，能不能让 AI 帮我下单？Agent 是怎么回事？」**

把本项目素材包 §9 的演进路线串成一条"能力阶梯"：

- **V1（现状）：预置知识问答**。AI 只能"基于喂进来的商品清单回答"，不能越界。
- **V2：RAG 导购 + 支付 + 内容笔记**。知识从全量注入升级为检索式，回答有来源；开始有支付、笔记，AI 语料更丰富。
- **V3：Redis / MQ / 秒杀**。缓存 + 削峰 + 秒杀，冲击更高的并发；这是"工程能力"的强化，与 AI 关系不大但系统扛得住更多用户。
- **V4：微服务**。系统被拆成多个服务（第 1 章），此时 AI 域可独立扩容（SSE 长连接是吞连接的大户）。
- **V5：Agent / 推荐 / NL2SQL**。**这是 AI 能力质的跃迁**：
  - **推荐**：从"被动回答"到"主动猜你要买什么"，需要行为数据 + 推荐引擎；
  - **Agent**：AI 不只是"回答问题"，而是**能把"帮我下单这个耳机"拆解成多步任务**——检索商品 → 校验库存 → 调用下单工具 → 确认结果。它从"聊天"变成"能动手的工具人"。关键转折是：AI 从"被塞知识"变成"能调用工具"，即从纯文本生成变为 **工具调用（function calling）+ 规划（planning）+ 记忆（memory）** 的 Agent 环；
  - **NL2SQL**：让非技术用户"用人话查数据"——AI 把你的中文请求翻译成 SQL 去查询。这要求更强的语义理解与安全护栏（防 SQL 注入）。

要讲出"Agent 为什么是演进终点而非一蹴而就"：每上一级，都要依赖前一级打下的基础——V2 的检索让 AI"答得对"，V3/V4 的工程能力让它"扛得住"访问 + 能独立部署，V5 才谈得上"能动手"。这正是一步步演进的原因，而不是一步到位。

### 6.4 追问链：AI 加载候补题怎么答

> **Q：RAG 和微调你选哪个？**
> 答（前面已铺垫）：取决于"知识是变动的数据还是稳定的能力"。商品库变动频繁 → RAG（数据在库、模型不动、成本随召回 K 走）；固定风格/强领域话术且数据稳定 → 微调（知识固化进权重，但训练/托管成本高、数据一变要重训）。电商导购明显是前者。

> **Q：SSE 流式和 RAG 冲突吗？**
> 答：不冲突。RAG 改变的是"**喂给模型什么**"（prompt 的知识部分），SSE 改变的是"**输出怎么推**"（响应的传输方式）。两者正交：RAG 决定内容对不对，SSE 决定反馈快不快。做一个"RAG+SSE"的导购就是"先检索召回精确内容，再流式地把结果打字机式输出"。

> **Q：怎么看"让 AI 自己能下单"的安全风险？**
> 答：Agent 能动手 = 能执行操作，风险随之而来——必须做**权限边界（只能操作你自己的账号）、额度/频率限制、操作前确认、全量审计日志**。所以 Agent 不是"能调工具就上线"，而是"先让它在沙箱里只读、再加克制的写操作、再逐步放开并伴随审计"。答到这里，表明你不只是懂 demo，还懂生产级约束。

## 7 收尾：把 ai-mall 讲成一段自洽的"产品进化史"

如果你被问到"讲讲你这个项目"，别按功能列表念，而是**按"为什么这么设计、将来怎么长"讲成一个自洽的演化叙事**：

1. **起步（V1）**：单体 + 域分包，强一致留在单事务，防超卖用条件原子 UPDATE，用无状态 Token 方便将来多实例。能跑、能学、边界清晰。
2. **成长（V2~V3）**：AI 从"全量塞知识"升级到"检索式 RAG"（规模可控）；引入 Redis/MQ/秒杀（扛住并发），支付与笔记补齐商业化。
3. **分裂（V4）**：数据边界清晰后才拆微服务（用户/商品/订单/AI 天然分域），跨服务强一致收敛，必要时上 Saga/本地消息表等最终一致。
4. **智能（V5）**：走 RAG → Agent → 推荐 → NL2SQL，AI 从"会答"到"能动手"，伴随权限与审计加固。

**这一段叙事本身就是面试的加分项**——它证明你不只是会调框架，而是把整个系统的取舍、代价、演进方向都想透了。而把 ai-mall 当案例分析，正是这个思考过程的具象化。

最后，把本文的三段式再强调一次，面试时遇到任何"为什么"都能用上：

> **「在这个场景下我选 X，因为（理由）；代价是（代价）；当出现（触发条件）时，我会换成 Y。」**

这可能就是你在面试里最值钱的一句话。
