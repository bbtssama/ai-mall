## 开课前：准备与约定

本教程带你操作的是 **ai-mall（AI 种草商城）** —— 一个用 Spring Boot 写成的真后端程序。
整条链路是：**注册登录 → 浏览商品 → 加购物车 → 下单（防超卖）→ AI 问答（流式回答）**。

**你需要准备：**

| 东西 | 说明 |
|---|---|
| 一台能上网的电脑 | Windows 即可，教程命令以 Windows 为例 |
| Java 17 与 Maven | 运行后端程序用。命令行输入 `java -version` 能看到 17 就 OK |
| MySQL 客户端 | 初始化数据库用。本机装 MySQL 客户端，或直接用任意 MySQL 工具 |
| 项目源码 | 已解压在本地，教程假设项目根目录叫 `ai-mall` |
| 一个命令行窗口 | Windows 上叫「命令提示符(cmd)」或「PowerShell」，教程里统一用 cmd |

**三个"动手约定"：**

1. **命令环境小贴士（重要，先读）：**
   Windows 的 PowerShell 里，`curl` 这个词被系统默认占用（它是另一个命令的别名）。
   为了让本教程的命令在你机器上一定有效，**我们统一使用 `curl.exe`**（Windows 10 及以上自带的真家伙）。
   在 cmd（命令提示符）里用 `curl` 或 `curl.exe` 都一样，教程统一写 `curl.exe`。

2. **看不懂的命令怎么办：** 先照抄跑一遍，再回来看「刚才代码里发生了什么」。
   本教程的每一课都保证：**照着做 → 一定看到期望结果**；看不懂没关系，那是第 2 课之后的事。

3. **期望返回里的 `...` 是什么意思：** 服务器返回的 JSON 里，用 `...` 表示「这里还有别的字段，
   不同环境略有差异」，你只需要关注教程点名的关键字段（比如 `code`、`token`）。

**时间预估：** 全程约 40~60 分钟，咖啡一杯。

## 第 0 课 在浏览器输入网址，到底发生了什么？

### 本课目标

在你亲手操作商城之前，先把底层的那件"小事"讲清楚：**你敲下一个网址，回车，然后屏幕上出现了页面——这中间发生了什么？**

### 一个生活类比：去商场

把「打开一个网站」想成「去一家商场买东西」：

| 生活中的商场 | 电脑里的网站 |
|---|---|
| 你（顾客） | 浏览器 |
| 商场大门 | 网址（一个地址，带你找到商场） |
| 前台接待员 | 服务器程序（后端） |
| 商场的仓库/账本 | 数据库 |

一次购物大致是这样：**你走到商场 → 找到前台 → 开口说话 → 前台去仓库查/拿 → 把结果递给你**。
电脑世界完全一样，只是每一步都有**固定的格式**——就像打电话要先拨号、接通后要先说"喂"。

### 一次完整的"访问"分四步

1. **你输入网址**：比如 `http://localhost:5173`。这相当于告诉出租车司机商场地址。
2. **浏览器发出"请求"**：浏览器按规矩用一句话向服务器要东西。这句话里包含：
   - **去哪**：地址（网址）
   - **怎么去**：用什么方式（本课先不纠结，第 1 课后你会反复见到）
   - **带什么**：有时还会附上一张小纸条（数据）
3. **服务器处理并"响应"**：服务器听懂你的话，去数据库查，然后把结果打包成一句话回给你。
4. **浏览器展示**：浏览器把收到的"话"翻译成你能看的页面（按钮、图片、文字）。

> 💡 记住两个词，后面全程出现：
> **请求（Request）** = 你向服务器说的话；**响应（Response）** = 服务器回你的话。

### 认识网址的四个部分

把网址 `http://localhost:5173` 拆开看，它像一张**快递单**：

```
http://  localhost  :5173   /api/v1/products
 ①        ②         ③            ④
```

| 部分 | 名字 | 类比 | 本例 |
|---|---|---|---|
| ① `http://` | 协议 | 用什么交通工具送（汽车/飞机） | HTTP 协议 |
| ② `localhost` | 主机名 | 寄到哪个城市 | 本机（你自己这台电脑） |
| ③ `:5173` | 端口 | 城市里的哪栋楼（门牌细分） | 5173 号门牌 |
| ④ `/api/v1/products` | 路径 | 楼里的哪个房间 | 商品的房间 |

> 💡 `localhost` 就是"我自己这台电脑"。所以 `http://localhost:5173` 的意思是
> "访问我自己电脑上 5173 端口那栋楼里的某个房间"。

### 动手：第一次访问

在浏览器地址栏输入并回车：

```
http://localhost:5173
```

**期望看到：** 一个商城页面（这是 ai-mall 的前端页面）。

**你可能想问：** 那后端在哪？别急——前端页面只是"门面"，真正的"商场"（后端程序）
在 **8080 号门牌**（端口 8080）。我们第 1 课就去把商场大门打开。

**刚才代码里发生了什么（通俗版）：**
浏览器把这句"话"按 HTTP 请求的格式发出去 → 前端程序（Vue3 写的，跑在 5173 端口）收到后，
把一个做了美化的网页回应给你 → 浏览器把网页画出来。
这里牵扯到一个事实：ai-mall 的**前端**和**后端**是**两个分开的程序**。
前端负责"好看"，后端负责"干活（查数据库、算价格）"。

## 第 1 课 把商城「唤醒」：启动数据库与后端

### 本课目标

让整条链路的"心脏"跳动起来：**数据库先就位，后端程序再启动**。启动成功后，
你会第一次看到"服务器程序"长什么样（一堆日志刷屏，别怕）。

### 生活类比：商场开门前的准备工作

商场正式营业前要做三件事：

1. **仓库理货**：把货摆好、账本建好（= 初始化数据库）；
2. **店员点到**：让所有员工各就各位（= 启动后端程序）；
3. **开门迎客**：大门打开，接待员就位（= 后端开始监听 8080 端口，随时接客）。

### 动手：三步走

**第一步：初始化数据库（给仓库建账本）**

打开命令行，进入项目根目录（以下命令在你解压项目的那个目录执行），运行：

```bat
mysql -h192.168.6.102 -uroot -proot123 < sql/init.sql
```

**期望看到：** 没有任何报错，命令静静结束（MySQL 命令执行成功时通常不打印任何东西）。

这一句说的是：连接数据库服务器 `192.168.6.102`，用账号 `root`、密码 `root123`，
把 `sql/init.sql` 这个"建表格 + 塞种子数据"的剧本整个演一遍。
演完以后，数据库里就有 **8 张表** 了（用户、商品、购物车、订单、AI 会话等），
并且货架上已经摆好了 **4 件商品**（我们第 4 课会见到它们）。

> 💡 种子数据（预置货物）长这样，记住它们，后面全是熟脸：
> AirSound Pro 耳机 ¥399 ／ 闪充宝 65W GaN ¥89~129 ／ 云朵唇釉 ¥69 ／ 轻氧手环 ¥199~249。

**第二步：启动后端（商场开门）**

```bat
cd backend
mvn spring-boot:run
```

**期望看到：** 一大段日志滚动，最后出现类似这行就说明开门成功：

```
Tomcat started on port 8080
```

**第三步（可选但推荐）：启动前端（门面装修）**

另开一个命令行窗口：

```bat
cd frontend
npm install
npm run dev
```

**期望看到：** 类似 `Local: http://localhost:5173/` 的输出。
装过一次依赖后，以后每次只需 `npm run dev`。

### 现在代码里发生了什么（通俗版）

后端程序启动时，Spring Boot（一个"程序总管"框架）按清单做了这些事：

- 找到启动类 `AimallApplication`（上面标着 `@SpringBootApplication`，意思是"我就是入口"）；
- **清点员工**：扫描项目里所有"员工"（Java 里叫 Bean/组件），
  它们按部门放好：`user`（会员部）、`goods`（商品部）、`order`（订单部）、`ai`（AI 部）、
  `config`（后勤部）、`common`（行政部——统一格式、统一处理出错）；
- **接通仓库**：把数据库连接配置读进来（`application.yml` 里的连接信息）；
- **安排接待**：在 8080 端口"摆好接待台"（Tomcat 服务器启动，开始听客人说话）；
- **立规矩**：设置"安检门"（Sa-Token 拦截器）——绝大部分请求要通过安检，
  只有两个口子免检（我们马上会用到）：注册口和登录口。

> 🧠 记忆锚点：**8080 = 后端大门（接待台在这）**；**5173 = 前端大门（装潢门面在这）**。

## 第 2 课 注册账号：办一张会员卡

### 本课目标

用命令行向后端喊一句"我要注册"，后端给你建一个会员档案。
成功标志：返回 `code: 200`。

### 生活类比：办会员卡

你到商场前台（8080 号接待台）说："我要办会员卡，用户名 `xiaocao_01`，密码 `123456`。"
前台小哥：查一下别重名 → 给密码"打码存档" → 写入会员名册 → 回一句"办好了"。

### 动手：发一个注册请求

在命令行（项目根目录即可）运行：

```bat
curl.exe -X POST http://localhost:8080/api/v1/auth/register ^
  -H "Content-Type: application/json" ^
  -d "{\"username\":\"xiaocao_01\",\"password\":\"123456\",\"nickname\":\"小操\"}"
```

> 小贴士：`^` 是 cmd 里的"换行继续写"符号，你可以把这几行合并成一行再回车，效果一样。
> 也可以先随意注册一个名字，比如 `tiger1999`。

**期望返回（核心字段）：**

```json
{"code": 200, "msg": "...", "data": ...}
```

看到 `code: 200` 就是成功。最后面的 `data` 是新会员的档案信息，不重要，先不管。

**再试一次（见证"查重"）：** 把上面命令原样再跑一遍，这次你会看到：

```json
{"code": 1001, "msg": "...", "data": null}
```

`code: 1001` 翻译过来是「用户名已存在」——同一个用户名不能注册两次。

**注册规则（记住了，登录也用得上）：**

- 用户名：3~20 位，只能由字母、数字、下划线组成（比如 `xiaocao_01` 合法，`小操` 不合法）；
- 密码：6~32 位；
- 昵称：可填可不填（不填系统会送你一个默认昵称「种草用户 + 4 位随机数字」）。

### 现在代码里发生了什么（通俗版）

你这句话按顺序经过了这些部门：

1. **安检门（Sa-Token 拦截器）**：看一眼——哦，是 `/api/v1/auth/register`，注册口免检，放行。
2. **接待台（AuthRestController）**：把你说的话收下，先检查格式（用户名合不合规、密码够不够长），
   不合格直接怼回来 `400`。
3. **店长（UserServiceImpl）**：
   - 先查会员名册有没有重名（数据库还有一道"唯一索引"兜底，相当于双保险）；
   - 把密码交给 **BCrypt 加密器**处理——注意！**不是**把 `123456` 直接存进数据库，
     而是存成一串打乱的乱码（这叫密码哈希，我们第 9 课延伸讲）；
   - 填上默认昵称、角色 `role=0`、状态 `status=1`（正常），写入 `t_user` 表。
4. **行政部（GlobalExceptionHandler）**：如果中间任何一步出错，它会统一包装成
   `{"code": ..., "msg": ...}` 的格式回给你，前端永远看到同一个模板。

> 🔐 思考题：为什么数据库里不直接存你的明文密码？
> 提示：万一数据库被偷走，小偷拿到的是"打乱的乱码"，还是解不开你的真实密码。
> （真正的答案里还有"每次加密结果还不一样"的细节，那是 L2 的事。）

## 第 3 课 登录：领取你的「入场手环」

### 本课目标

用刚注册的账号登录，**拿到一枚令牌（token）**。这是全教程最重要的一步——
后面所有"带身份的操作"（加购物车、下单、问 AI）都要出示它。

### 生活类比：入场手环

商场有规矩：**办完会员卡后，每次进场都要去前台领一枚"手环"，凭手环全场通行**。
手环上印着一串独一无二的编号，7 天有效。
你逛超市、买东西都不用再掏会员卡，递手腕就行——收银员一看编号就知道你是谁。

电脑世界也一样：**token（令牌）就是那枚手环**。它是一个很长的随机字符串，有效期 **7 天**。

### 动手：登录并保存 token

```bat
curl.exe -X POST http://localhost:8080/api/v1/auth/login ^
  -H "Content-Type: application/json" ^
  -d "{\"username\":\"xiaocao_01\",\"password\":\"123456\"}"
```

**期望返回：**

```json
{
  "code": 200,
  "msg": "...",
  "data": {
    "token": "一个很长的随机字符串",
    "user": {"id": 1, "username": "xiaocao_01", "nickname": "小操", "avatar": "...", "role": 0}
  }
}
```

**把 `token` 那串价值"收藏"起来**（复制到记事本），等下节课要用。
为了演示方便，本教程把它记为 `<TOKEN>`，你操作时替换成自己复制的那串。

**再验证一次"错误密码"：** 把密码故意改错（比如 `wrong123`）再登录：

```json
{"code": 1003, "msg": "...", "data": null}
```

`1003` = 密码错误。注意：**无论用户名错还是密码错，提示都是 1003**，
这是故意的——不让坏人通过报错信息猜出"哪个用户名存在"。

### 现在代码里发生了什么（通俗版）

1. **接待台收下话**，把用户名、密码交给店长；
2. **店长校验密码**：把数据库里存的"乱码"和你的密码用 BCrypt 算法比对（`matches`），
   对不上就统一报 1003；
3. 检查账号状态：要是账号被停用（`status=0`），报 `1004`（用户被禁用）；
4. 一切正常 → **`StpUtil.login(用户id)`**：这是 Sa-Token 框架的"发手环机"，
   它签发一个 token，并且内部记住"这个 token 属于哪个用户id"；
5. 返回 `LoginVO(token, userVO)`。`userVO` 里是会员信息，
   注意**没有密码字段**——会员卡上不会印密码。

> 🧠 记忆锚点：**token = 手环**。后面每节课的操作，都要在请求里带上这枚手环
> （加一个请求头 `Authorization: <TOKEN>`），后端才知道"你是谁"。

## 第 4 课 逛货架：商品列表与详情

### 本课目标

带着手环逛商场：先看**货架上有哪些商品**（列表），再**凑近看某一件的细节与规格**（详情）。
顺便亲身体验一次"不带手环会被拦在门外"。

### 生活类比：看货架

你戴着入场手环，走到 1 楼货架区。货架上每件商品贴着一张**价签**——
注意价签写的是**起售价**（这商品最低配的那档多少钱）。
想看得更细（比如颜色、容量、库存），得让店员把商品取出来给你看。

### 动手

**① 商品列表（货架全景）**

```bat
curl.exe http://localhost:8080/api/v1/products/ ^
  -H "Authorization: <TOKEN>"
```

**期望返回（核心字段）：**

```json
{
  "code": 200,
  "msg": "...",
  "data": {
    "records": [
      {"id": 1, "name": "AirSound Pro 耳机", "subTitle": "...", "minPrice": 399.00, ...},
      {"id": 2, "name": "闪充宝 65W GaN", "subTitle": "...", "minPrice": 89.00, ...},
      {"id": 3, "name": "云朵唇釉", "subTitle": "...", "minPrice": 69.00, ...},
      {"id": 4, "name": "轻氧手环", "subTitle": "...", "minPrice": 199.00, ...}
    ],
    "total": 4,
    "page": 1,
    "pageSize": 10
  }
}
```

看到了吗？就是数据库里那 4 件种子商品（上架状态的才会出现）。
`minPrice` 是**起售价**：比如闪充宝有两个规格（¥89 和 ¥129），起售价就是 89。

**② 不带手环逛商场（体验安检门）**

```bat
curl.exe http://localhost:8080/api/v1/products/
```

**期望返回：**

```json
{"code": 401, "msg": "未登录或登录已过期", "data": null}
```

`401` = 没戴手环，安检门拦住你。这也印证了第 1 课的规矩：
只有注册口、登录口免检，其余全部门口都要手环。

**③ 商品详情（凑近看规格）**

```bat
curl.exe http://localhost:8080/api/v1/products/1 ^
  -H "Authorization: <TOKEN>"
```

**期望返回：** `data` 里是这个商品的完整信息（介绍文案），外加一个 `skus` 列表——
也就是它的**规格档**（SKU，比如颜色/容量/价格/库存），结构类似：

```json
{
  "data": {
    "id": 1,
    "name": "AirSound Pro 耳机",
    "detail": "...种草图文...",
    "skus": [{"id": 1, "skuName": "...", "price": 399.00, "stock": ..., ...}]
  }
}
```

> 💡 记住 `skuId`：第 5、6 课加购物车和下单都要用到它（示例统一用 `skuId: 1`）。

### 现在代码里发生了什么（通俗版）

- **列表**：Shopkeeper（ProductServiceImpl）调 Mapper 问数据库："把上架的商品给我，按页来"。
  数据库用一条 **SQL** 把商品表和规格表接起来查（叫 `LEFT JOIN`），
  顺便算出每件商品的最低价（`MIN(price)`）当作起售价，再按页码截取（`LIMIT` 分页）。
  分页结果包成 `PageResult{records,total,page,pageSize}`——规矩是每页最多 100 条。
- **详情**：先查商品，确认它**存在且是上架状态**（`status=1`），再把规格档一起返回。
  注意列表**不含**大段介绍（detail）——货架上看一眼就走，没必要把所有商品的大段文案全搬出来；
  想看才单独看详情。
- **安检**：每次请求先过 Sa-Token 拦截器——请求头里没有 `Authorization` 或手环过期，
  直接报 401，由全局异常处理器统一转成 `R` 格式。

## 第 5 课 加购物车：往购物篮里放东西

### 本课目标

把看中的商品**放进购物篮**（不用立刻付钱），还能查看、改数量、移除。

### 生活类比：购物篮

你提着购物篮在货架间穿梭，看中一件就拿一件。
同一件商品你要是拿两次，店员会帮你**合并成一个条目、数量相加**（最多 99 件）。
购物篮是**专属于你的**——别人动不了你的篮子。

### 动手

**① 加购：**

```bat
curl.exe -X POST http://localhost:8080/api/v1/cart ^
  -H "Content-Type: application/json" ^
  -H "Authorization: <TOKEN>" ^
  -d "{\"skuId\":1,\"quantity\":1}"
```

**期望返回：** `{"code": 200, ...}`。

**② 查看购物篮：**

```bat
curl.exe http://localhost:8080/api/v1/cart ^
  -H "Authorization: <TOKEN>"
```

**期望返回（核心字段）：** 一个数组，里面每一项是一行"购物篮条目"：

```json
{
  "code": 200,
  "data": [
    {
      "id": 1,
      "skuId": 1,
      "skuName": "...",
      "price": 399.00,
      "quantity": 1,
      "productName": "AirSound Pro 耳机",
      "mainImg": "...",
      "subtotal": 399.00
    }
  ]
}
```

注意 `subtotal`（小计）= 单价 × 数量，是自动算好给你的。

**③ 把同一商品再加一次**（把上面 ① 原样再跑一次），再跑 ② 查看：
会发现**不是新增一行，而是原来的条目数量变成 2**。

**④ 改数量：** 先记下 ② 返回里的条目 `id`（示例是 1），然后：

```bat
curl.exe -X PUT http://localhost:8080/api/v1/cart/1 ^
  -H "Content-Type: application/json" ^
  -H "Authorization: <TOKEN>" ^
  -d "{\"quantity\":3}"
```

**期望返回：** `code: 200`。再查一次购物篮，数量已是 3。

**⑤ 移除条目（演示完记得清空，为下单做准备）：**

```bat
curl.exe -X DELETE http://localhost:8080/api/v1/cart/1 ^
  -H "Authorization: <TOKEN>"
```

**期望返回：** `code: 200`。购物篮空了。

> 📌 若想全清空，用 `DELETE http://localhost:8080/api/v1/cart`（清空整个购物篮）。

### 现在代码里发生了什么（通俗版）

- **加购前先"过三关"**（CartServiceImpl）：SKU 存在吗？商品上架吗？库存够吗？
  注意这是**内存里先看一眼**（预检），只是提前给你友好提示；
  真正的库存扣减在第 6 课下单时才发生（防止"你只是放进篮子就把货扣了"）。
- **同 SKU 合并**：数据库给"用户 + 商品规格"建了唯一索引（`uk_user_sku`），
  保证同一个篮子不能出现两行同规格——第二次加购走"数量相加"分支（封顶 99）。
- **购物篮是你的**：查、改、删都带你的用户 id 作为条件（`userId` 藏在 token 里，
  由 `StpUtil` 取出）。改/删时如果影响的记录数是 0，说明这个条目根本不是你的 ——
  报 `2005`（购物车条目不存在）。这叫**归属校验下沉到 SQL**：数据库层直接判"这是不是你的东西"。
- **展示字段一次查齐**：查询时把 SKU 名、商品名、图片一起 JOIN 出来，
  免得前端每看一行还要再问三次。

> 🧠 记忆锚点：**购物车只是"篮子"，不扣库存**。真正的"扣货"发生在下单那一刻。

## 第 6 课 下单：收银台结账与仓库防超卖

### 本课目标

把购物篮里的东西正式**下单**：生成一个订单（相当于一张快递单），并触发仓库真正扣库存。
这是全项目**最核心**的一课——它的"防超卖"设计是整个 ai-mall 的灵魂。

### 生活类比：收银台结账 + 仓库小哥

你拎着篮子到收银台。收银流程是这样的：

1. **核实**：篮子里的每样东西，店员先对讲机问仓库："XX 还有货吗？还有 5 件？好。"
   注意不只是"问"，而是**让仓库当场从货堆里先拿走**——"从 5 件里减 1 件，减完剩 4"。
2. **开单**：收银台打出一张**快递单（订单号）**，单子上写明：买什么、快照单价、收货人、总价。
   所谓"快照"，就是**价格以这一刻为准**——哪怕明天涨价，这张单子还是今天的价。
3. **一气呵成**：扣库存、写订单、写明细是一套连续动作——任何一步失败，全部撤销重来
   （货退回仓库、单子作废），绝不出现"库存扣了但订单没生成"的烂账。
4. **清篮**：买单成功，购物篮里这些东西划掉。

**为什么"防超卖"是重点？** 想象最后一件商品，你和另一个人同时递上付款——
如果店员"先查再减"（查还有 1 件 → 都通过 → 都扣），就会卖出去 2 件只有 1 件的货（超卖）。
ai-mall 的解法是：**"查"和"减"必须是同一步、一口气完成**，谁先成功，谁拿到货。

### 动手

**① 先把购物篮准备好**：如果你刚才清空了，重新加购一件（`skuId:1, quantity:1`，见第 5 课 ①）。

**② 下单：**

```bat
curl.exe -X POST http://localhost:8080/api/v1/orders ^
  -H "Content-Type: application/json" ^
  -H "Authorization: <TOKEN>" ^
  -d "{\"items\":[{\"skuId\":1,\"quantity\":1}],\"receiverName\":\"张三\",\"receiverPhone\":\"13800001234\",\"receiverAddress\":\"北京市朝阳区某某大厦 101\"}"
```

**期望返回（核心字段）：**

```json
{
  "code": 200,
  "data": {
    "orderNo": "形如 20250606123456 的长订单号",
    "status": "PENDING_PAY",
    "totalAmount": 399.00,
    ...
  }
}
```

`PENDING_PAY` 意思是"等待付款"——订单刚刚诞生，还没付钱。
`totalAmount` 是总价（全部明细用 BigDecimal 精确累加，绝不用浮点数算钱）。

**③ 看看我的订单列表：**

```bat
curl.exe "http://localhost:8080/api/v1/orders?page=1&pageSize=10" ^
  -H "Authorization: <TOKEN>"
```

**期望返回：** 分页结构，`records` 里躺着刚下的那单（按时间倒序，最新的在最前）。

**④ 取消订单（见证"状态机"）：** 记下订单的 `id`，执行：

```bat
curl.exe -X POST http://localhost:8080/api/v1/orders/1/cancel ^
  -H "Authorization: <TOKEN>"
```

**期望返回：** `code: 200`。取消后这单状态变 `CANCELLED`，**库存回补**（货物退回仓库）。
如果对同一天再取消一次，会看到 `2008`（订单状态无效）——
因为"待付款"的订单才能取消，已经取消的不能再取消。

### 现在代码里发生了什么（通俗版）

下单这步的代码逻辑（OrderServiceImpl.create，全程在一个**事务**里）逐条执行：

1. **购物篮非空校验**：下单明细为空 → `2006`（购物车为空）。
2. **逐件过秤**：每件商品——查 SKU → 商品必须上架 → 内存预检库存。
3. **真·扣库存（防超卖核心）**：执行这条 SQL：

   ```sql
   UPDATE t_product_sku SET stock = stock - 1, sales = sales + 1
   WHERE id = ? AND stock >= 1
   ```

   关键在 `WHERE stock >= 1`——**数据库自己先确认"够减"再减，这一查一减是原子的一口气**。
   返回 0 行 = 这一瞬间货被别人抢光 → 报 `2004`（库存不足）。
   两个并发请求同时来，数据库会让它们排队，只有一个人成功。
4. **定格快照**：把这一刻的商品名、规格名、单价**复制进订单明细**
   （以后商品改名涨价都不影响这张单）——这就是 `t_order_item` 里的"快照"字段。
5. **开快递单**：生成订单号（时间戳 + 4 位随机数 + 用户尾号；万一撞号，数据库唯一索引兜底），
   状态 `PENDING_PAY`，写上收货信息，插入 `t_order`。
6. **写明细**：把明细批量写入 `t_order_item`。
7. **清购物篮**：把这次下单涉及的商品从购物篮划掉。

**事务 = 要么全成，要么全不成**：如果第 4 步之后突然断电/报错，
前面扣掉的库存会**自动回滚**（货退回去、单子作废），不会留下半截烂账。
取消订单也同理（`@Transactional`）：先校验归属（不是你的单 → `2007`）→
用"状态机 CAS"更新状态（必须从 `PENDING_PAY` 变 `CANCELLED`，防并发重复取消）→
成功才逐条把库存加回来。

> 🧠 记忆锚点：**防超卖 = 仓库小哥"拿货时才数"**，不是"先数好再拿"。

## 第 7 课 AI 问答：和懂行的 AI 店员聊天

### 本课目标

让 AI 店员回答你关于商品的问题。它**只依据店里的真实商品信息回答**，不会瞎编。
顺便体验"流式回答"（像打字机一样一句句蹦出来）和"历史会话"（聊天记录不丢）。

### 生活类比：一位拿着商品手册的 AI 店员

商场里有一位 AI 店员，它手里有一本**商品手册**（内容 = 当前在售商品的信息）。
你问它："想买个降噪耳机，帮我推荐？"它就翻手册、组织语言回答你。
规矩是：**手册里有的，如实答；手册里没有的，坦诚说不知道——绝不编造**。
（手册是"预置知识"形态；以后版本会换成更聪明的"查资料再回答"，那是 V2 的事。）

### 动手

**① 普通问答（一次性得到整段回答）**

```bat
curl.exe -X POST http://localhost:8080/api/v1/chat/ ^
  -H "Content-Type: application/json" ^
  -H "Authorization: <TOKEN>" ^
  -d "{\"message\":\"想买个降噪耳机，帮我推荐一款\"}"
```

**期望返回：** `code: 200`，`data` 是一段中文回答（推荐 AirSound Pro 之类的合理建议）。
注意路径末尾的 `/` 不能省（`/chat/`）。

**② 流式问答（见证"打字机"）**

```bat
curl.exe -N -X POST http://localhost:8080/api/v1/chat/stream ^
  -H "Content-Type: application/json" ^
  -H "Authorization: <TOKEN>" ^
  -d "{\"message\":\"轻氧手环能测睡眠吗\"}"
```

**期望看到：** 回答**一段一段地**蹦出来（SSE 流式），而不是一次性吐完。
`-N` 参数告诉 curl"不要缓冲，来一点显示一点"。

**③ 历史会话（聊天记录都存着）**

查看你所有的会话列表：

```bat
curl.exe http://localhost:8080/api/v1/chat/conversations ^
  -H "Authorization: <TOKEN>"
```

**期望返回：** 一个会话数组（第一次提问时如果没指定会话，系统会自动建一个，
并以你的问题前 20 个字当标题）。

再查某个会话的完整聊天记录（把 `<ID>` 换成上面的会话 id）：

```bat
curl.exe http://localhost:8080/api/v1/chat/conversations/<ID>/messages ^
  -H "Authorization: <TOKEN>"
```

**期望返回：** 一串消息，用户问的和 AI 答的交替排列（角色 `USER` / `ASSISTANT`）。

> 想要自己指定会话？先 `POST /api/v1/chat/conversations` 建一个，然后问答时把
> `conversationId` 放进请求体即可（不填则自动新建）。会话归属校验很严格：
> 看别人的会话会得到 `404`（会话不存在）——和购物篮一样，你的就是你的。

### 现在代码里发生了什么（通俗版）

- **普通问答**：后端把"商品手册"（在售商品列表：id/名称/副标题/起售价/详情）序列化成 JSON，
  写进给 AI 的"系统提示词"（system prompt），强调"基于商品库如实回答、没有就说不、
  不编造"；再把历史对话一起交给 AI 模型（`deepseek-v4-pro`，经 OpenAI 兼容接口中转）；
  拿到完整回答后，**把"你问的"和"AI 答的"双双存进数据库**（消息表，一问一答配对存）。
  调用失败时统一转 `3001`（AI 服务错误），不会把底层异常甩给你。
- **流式回答（SSE）**：AI 的回答像打字机一样按内容块（Flux 流）送达。时序上特别讲究：
  **订阅一开始就先保存你的提问**（防止流中途断掉导致"提问丢了"）；
  **回答全部流完才保存完整 AI 回答**（一问一答成对入库，不丢任何一边）；
  万一 AI 服务中途挂掉，会补一句「[AI 服务暂时不可用，请稍后再试]」的兜底文案，
  而不是让你盯着半截空白发愣。

> 🧠 记忆锚点：**AI 只答"手册里有的"**；**流式 = 打字机**；**问答成对入库 = 聊天记录不丢**。

## 第 9 课 卡住了？常见问题排查表

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| 后端启动失败，说端口被占用 | 8080 被别的程序占了 | 关掉占用程序，或改 `application.yml` 端口。也可以先看是不是有个旧的后端没关 |
| MySQL 连接失败（报错含 `Communications link failure` 等） | 数据库没启动 / 地址或密码不对 | 确认 `192.168.6.102` 可达、`root/root123` 正确；先跑第 1 课第一步初始化 |
| 所有请求都返回 401 | 没带 `Authorization` 头，或手环已过期（7 天） | 重新登录取新 token，请求头里带上 |
| 登录返回 1003 | 用户名或密码不对 | 重新注册一个用户名，或换个密码再试 |
| 注册返回 1001 | 用户名已被注册 | 换个用户名 |
| 下单返回 2004 | 库存不足（或并发抢光） | 换个商品/规格试，或等取消订单回补库存 |
| 下单报参数错误（400） | 请求体字段名或格式不对 | 检查收货人三个字段名与 items 结构；对照第 6 课命令逐字符核对 |
| AI 问答返回 3001 | AI 服务（中转接口）不可用 | 等一会儿再试；确认环境变量 `DEEPSEEK_API_KEY` 已配置 |
| 流式回答只拿到开头就停 | 网络/服务抖动 | 重试；正常情况会补兜底文案不会裸断 |
| 冒烟测试若干项失败 | 后端未启动或数据库未初始化 | 回到第 1 课按顺序重来 |

> 兜底大招：把后端命令行窗口里的**日志**翻到最后 20 行——报错都会写成日志，
> 逐行读一遍往往就能定位（或者把日志截图发给懂行的人看）。

### 一条闭环链路（今天你从头走到尾）

```
注册(办卡) → 登录(领手环token) → 商品列表/详情(逛货架)
   → 加购物车(放篮子) → 下单(收银台+仓库防超卖) → AI 问答(懂行店员)
```

### 你今天收获的"黑话"（能说人话解释的就算学会）

- **HTTP 请求/响应**：你说话，服务器回话，格式固定。
- **URL = 快递单**：协议 + 主机 + 端口 + 路径。
- **后端 / 前端 / 数据库**：干活的商场 / 好看的门面 / 仓库与账本。
- **token = 入场手环**：无状态，7 天有效，请求头 `Authorization` 携带。
- **统一返回 R{code,msg,data}**：所有回答一个模板；`401` 没登录、`1001` 用户名存在、
  `1003` 密码错、`2004` 库存不足。
- **防超卖**：`UPDATE ... WHERE stock >= ?` 一查一减原子完成，配合事务全成或全不成。
- **快照**：下单瞬间把品名、价格定格进订单，以后变价不影响。
- **SSE 流式**：AI 打字机式回答，提问先存、回答完再存，成对不丢。
