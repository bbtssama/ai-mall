## 0. 开场白：这篇文章是写给谁的

假设你从来没写过代码，甚至不知道"后端"和"前端"到底谁是谁。你只知道：手机里有个 App 或者网页，能注册、能逛商品、能把东西放进购物车、能下单、还能跟一个 AI 聊天问"这个耳机适合跑步吗"。

这篇文章要做的，就是掀开后台的帘子，让你看看**这些操作背后，电脑到底在忙活什么**。

我们不讲代码。我们只讲**三个比喻**、**一条链路**、**五个 Why**：

- 三个比喻：餐厅（接口=菜单、服务=厨房、数据库=仓库）
- 一条链路：登录 → 逛商品 → 加购物车 → 下单 → 问 AI
- 五个 Why：为什么要登录？为什么要防超卖？AI 怎么会"认识"商品？为什么要统一返回？为什么要错误码？

把这三个比喻记住，整篇文章你就吃透了。等下你会看到，"AI 种草商城"（我们叫它 ai-mall）这个项目，本质上就是一间**开了 AI 外挂的餐厅**。

## 1. 全景故事：一次购物，系统里发生了什么

先给你一个总览，让你知道我们接下来要讲哪几件事。假如你是一位顾客，在 ai-mall 上完成了一次完整购物：

1. **注册账号** —— 相当于在餐厅办了一张会员卡。
2. **登录** —— 前台验明身份，发给你一张**钥匙牌（Token）**；从此你走到哪儿，门卫看你挂着牌就放行。
3. **浏览商品** —— 你翻看菜单（商品列表）。菜单上每道菜都有介绍和起步价。
4. **加购物车** —— 你拿起一个购物篮，把选中的"菜"放进去。篮子是挂在**你的账号**名下的，别人拿不走。
5. **下单** —— 你到收银台结账：厨房（服务层）确认每样菜都有货，从**仓库（数据库）**里扣掉库存、给你打出订单小票，同时你的购物篮被清空。
6. **防超卖** —— 如果"手速最快的十万人同时抢 5 台耳机"，仓库的扣货规则保证：**第 5 台卖完就卖完，第 6 个来的人只能收到"库存不足"，绝不会多卖**。
7. **AI 问答** —— 你问客服机器人（AI 助手）"这个耳机适合跑步吗"。机器人不是瞎猜，它**手里真的有一份最新的商品清单**，照着清单回答，不知道就说不知道。

整个系统的设计，就是围绕这条链路展开的：**注册登录 → 浏览商品 → 加购物车 → 下单（防超卖）→ AI 问答**。

接下来的每一章，就是把这条链路里的每个环节拆开，讲给你听。

## 2. 后台、接口、数据库：一间餐厅的故事

**【核心比喻 1】：整个系统是一间餐厅。**

- 你看到的前端页面（网页/手机界面）= **餐厅大堂 + 点餐平板**
- 后端程序 = **厨房**
- 数据库 = **仓库**
- 接口（API）= **菜单**（你只能点什么菜，由菜单决定）
- 服务层（Service）= **厨师大厨**（接到点单，去仓库取货、加工、出菜）

下面我们一层一层看。

### 2.1 前台与后台：餐厅大堂和厨房仓库

一间餐厅分两个区域：

- **前厅（前端）**：顾客看得见、摸得着的地方——桌椅、菜单、点餐平板。顾客在这里点菜。
- **后厨（后台/后端）**：顾客看不见的地方——灶台、冰箱、仓库。菜是在这里做出来的。

你手机上那个界面（前端）长得再好看，它自己**不会算账、不会记库存、不会记得你是谁**。它只是一个"点餐平板"：把你想吃什么，翻译成一句话，递进后厨；再把后厨端出来的菜，摆盘端到你面前。

真正的活儿——查库存、扣库存、记订单、认人——全在后厨（后端）完成。

这个项目是"单体"结构：一间餐厅就一个厨房，没有分店。菜谱、灶台、仓库都在一起，方便管理，适合项目刚起步时用。

### 2.2 菜单 = 接口（API）

餐厅不会让你直接冲进厨房喊"给我炒个菜"。你只能**看着菜单点菜**：菜单上写了"宫保鸡丁 38 元"，你就照着菜单点。

在系统里，这份"菜单"就是**接口（API）**。接口规定了：

- **能点什么菜**：比如"注册"、"登录"、"看商品列表"、"加购物车"、"下单"、"问 AI"……每个操作就是一道菜。
- **下单格式**：比如点"加购物车"这道菜，你必须说明加哪个商品（哪些参数）。
- **上菜格式**：后端一定会按统一的方式把结果端出来。

在我们这个项目里，菜单上的菜长这样（你看一眼格式就行，不用记）：

- 注册一份：`POST /api/v1/auth/register`
- 登录一份：`POST /api/v1/auth/login`
- 商品列表：`GET /api/v1/products`
- 加购物车：`POST /api/v1/cart`
- 创建订单：`POST /api/v1/orders`
- 问 AI：`POST /api/v1/chat/stream`

菜单有一个总前缀 `/api/v1`，意思是"这一版菜单的菜都在这条街"。将来菜单改版了，就换前缀再出一版，老顾客不受影响——这是设计上的一个小心思。

为什么一定要通过"菜单"点菜，而不是直接进厨房？因为：

1. **安全**：顾客不能碰灶台，不能自己改库存。
2. **分工**：前厅和后厨各自干各自的活，谁也不用知道对方内部长什么样。
3. **稳定**：只要菜单不变，厨房内部随便装修，顾客都没感觉。

### 2.3 厨房 = 服务层（Service）

菜单上的菜，是谁做的？是厨房里的**厨师（服务层，Service）**。

点餐平板把"我要点宫保鸡丁"递给厨房，厨师开始干活：检查食材有没有 → 从仓库取鸡丁 → 起锅烧油 → 装盘。顾客不需要知道厨师是怎么颠勺的。

在我们系统里，每一个业务都有对应的"厨师组"：

- **user（用户组）**：管注册、登录、登出、查"我是谁"。
- **goods（商品组）**：管商品列表、商品详情、购物车。
- **order（订单组）**：管下单、查订单、取消订单。
- **ai（AI 组）**：管会话和 AI 问答。

每个组内部又按工种分：有人负责接单（Controller）、有人负责跑腿（Service）、有人负责进出仓库（Mapper）。一层管一层，谁也别越级——这就是为什么出了问题好排查：客人投诉菜咸了，直接找对应厨房组的对应厨师，不用把整间餐厅翻一遍。

### 2.4 仓库 = 数据库（Database）

厨师做菜，食材从哪来？从**仓库（数据库）**。

仓库里有一排排货架，每个货架存一类东西，我们项目里一共 **8 个货架（8 张表）**：

| 货架 | 存什么 |
|---|---|
| 用户货架 | 每个顾客的账号、昵称、头像、加密后的密码 |
| 商品货架 | 商品叫什么、详情介绍、在不在售 |
| 商品规格货架 | 同一商品的不同规格：价格、**库存**、销量 |
| 购物车货架 | 谁的篮子里放了哪个商品、放了几件 |
| 订单货架 | 每张订单：总额、状态、收货人 |
| 订单明细货架 | 订单里每件商品的"留底照片"（名称、价格快照） |
| 会话货架 | 你开了几个 AI 聊天窗口 |
| 消息货架 | 每个聊天窗口里你说了啥、AI 回了啥 |

仓库的关键特点是**记性特别好**：今天关店，明天开门，数据还在。顾客昨天加进购物车的耳机，今天打开还在——就是仓库的功劳。

还有个细节：订单明细货架里存的不是"商品编号"而是"名称+价格**快照**"。什么意思？厨师出菜时把这道菜当时的样子拍了张照存下来。将来菜涨价了、改名字了，**你已经下单的这张小票上还是旧价格**——这就是"快照"，保护顾客，也保护账目清楚。

### 2.5 一次完整点餐：三者怎么配合

把上面串起来，一次"看商品详情"的操作全过程是这样的：

1. 你在点餐平板上点了"查看 AirSound Pro 耳机详情"。
2. 前端依照**菜单（接口）**的格式，向后端发出请求：`GET /api/v1/products/{id}`。
3. 后端的**接单员（Controller）**收到请求，交给**商品组厨师（Service）**。
4. 厨师去**仓库（数据库）**查这个商品的资料，还要顺带问一句库存规格（SKU）的情况。
5. 厨师把查到的东西整理好，按菜单上的"上菜格式"端出来。
6. 前端拿到结果，摆盘成漂亮的页面给你看。

**核心思想：前端只负责"好看"，后端负责"干活"，数据库负责"记住"。** 三者各司其职，通过"菜单"（接口）这个固定规矩沟通。

## 3. 登录是怎么回事：钥匙牌 + 门卫

**【核心比喻 2】：登录 = 进门领钥匙牌；之后每一次操作，都靠"钥匙牌 + 门卫"来认人。**

### 3.1 为什么非要登录

想象一间餐厅，不设会员、不查身份，谁进来都能拿菜——那购物车里的东西根本分不清是谁的，订单也没法记到人头上。

ai-mall 要做的三件大事都离不开"认人"：

- **购物车**要挂在某个人名下；
- **订单**要知道是谁下的、谁有资格取消；
- **AI 聊天记录**要知道是跟谁聊的。

所以第一步，你得先**注册**：起个用户名（3~20 位，字母数字下划线）、设个密码、可写可不写昵称。注册好了，系统默认送你一个昵称，叫"种草用户加四位随机数"——就像餐厅会员卡默认印"尊贵的顾客 4821"。

### 3.2 钥匙牌 = Token

注册之后要**登录**：输入用户名和密码。后端验明正身后，会发给你一张"钥匙牌"，专业叫法叫 **Token**。

这张钥匙牌有讲究：

- **有有效期**：咱们这张牌有效期 **7 天**（604800 秒）。7 天后过期，你需要重新登录。就像有些健身房会员卡，久了不续就失效。
- **不带任何你的隐私**：它只是一串随机字符（UUID 风格），店里一看这串字符，就知道"哦，这是钥匙牌"。
- **无状态**：餐厅不另外开一本"谁手里有牌"的账本——牌本身就能证明身份。后端程序重启、换台机器，这牌照样有效。

登录成功后，后端返回的不只是钥匙牌，还附上一张"顾客信息卡"（你的 id、用户名、昵称、头像这些），方便前端立刻显示"欢迎回来，种草用户 4821"。注意：**密码是绝对不会出现在这张卡上的**。

从这一刻起，你每次请求都要**把钥匙牌挂在请求头上**（专业叫法：请求头 `Authorization`）。就像一个会员，进店先亮牌。

### 3.3 门卫 = 拦截器（Interceptor）

钥匙牌发下去了，谁来验？**门卫（拦截器）**。

ai-mall 的门口（后端入口）站着一位门卫，规矩很明确：

- **把后厨的每个门都看住**：所有通往后端干活的路（即所有 `/api/` 接口），都要先过门卫这一关。
- **亮牌就放行，不亮牌就请回**：请求带着有效的钥匙牌（Token），放行进厨房；没带或牌过期了，直接被拦下，并礼貌地回一句"未登录或登录已过期"（专业编号 401）。
- **少数门不拦**：**登录**和**注册**这两个门是不拦的——不然你一个新顾客还没领牌，门卫就把你轰走了，那谁还能进门？这两个叫"白名单"。

所以"门卫"是整个系统的安全第一关：**不认脸，认牌**。牌是真的，你是你；牌是假的，直接拒之门外。

在购物车那章里你会看到，服务员还会用你的牌去查"这是谁的篮子"——牌不仅用来通行，还用来**对号**。

### 3.4 密码为什么要"加密"（BCrypt）

有人会问：密码在数据库里存的不就是密码本身吗？

不是。餐厅仓库里存的**不是你的密码，而是密码加工后的"暗号"**。这个加工过程叫 **BCrypt 加密**（一种"单向"算法：只能把密码变成暗号，几乎没法从暗号倒推出密码）。

为什么这么设计？想想看：万一仓库失窃，黑客偷到了整个用户货架——如果上面全是明文密码，那所有顾客的密码全泄露了，而且很多人**一个密码走天下**，连银行都可能被连坐。但如果上面全是"暗号"，黑客拿到也解不开，损失就小得多。

登录时怎么验证？不是把存着的暗号"解密"回密码（解不开），而是把你这次输入的密码**现场再做一次同样的加工**，看结果跟仓库里存的暗号**对不对得上**。对得上，放行。

这里还有一个很多人没注意的细节：如果用户名不存在，后端回复的是"用户名或密码错误"？不对——它**统一回"密码错误"（错误码 1003）**。哪怕你输入的用户名根本不存在，它也照样说"密码错误"。

为什么故意"装傻"？因为如果它老实说"用户名不存在"，就相当于告诉黑客："这个账号存在，你可以专心猜密码/搞攻击了。"**不暴露用户名是否存在**，是保护顾客的一层小心思。

### 3.5 登出和"我是谁"（/me）

- **登出（logout）**：把钥匙牌收回来作废。以后这张牌就不好使了。
- **"我是谁"（/me）**：前端一打开页面，需要立刻知道"当前登录的顾客是谁"——它就拿着你的钥匙牌来问后端。后端凭牌查出你的 id，再去仓库取你的资料。整个过程**不用你再输一遍密码**，因为钥匙牌已经证明了一切。

> 小结：登录这一篇，你只需要记住四个词——**注册领卡、登录发牌、门卫验牌、密码存暗号**。

## 4. 购物车与下单：购物篮、收银台、仓库

**【核心比喻 3】：购物车 = 购物篮；下单 = 收银台结账；防超卖 = 仓库的"按单锁货"规矩。**

### 4.1 购物车 = 挂在账号上的购物篮

购物车就是超市里的**购物篮**，而且这只篮子是**实名制**的：

- 篮子是**挂在你的账号（用户 id）名下**的——别人取不走你的篮子，你也不能动别人的。
- 篮子里的货是"**规格**"级别：不是"耳机"这一整个商品，而是"AirSound Pro 耳机 · 黑色"这种具体规格。因为同一个商品可能有不同颜色、不同价格，结账时要分清楚。
- 同一个规格如果放两次，系统会**自动给你合并**：比如先加了 2 件，再加 1 件，篮子显示 3 件。
- 不过篮子有个容量上限：**单件商品最多放 99 件**。超过就加不进去了——倒也不是真放不下，主要是防止有人把购物车当仓库使。
- 购物车页面会给你算好**小计**："单价 × 数量"，方便你结账前看个大概。

### 4.2 加进购物车时，后台在检查什么

把货放进篮子，不是随手一丢，服务员（后端）会做三重检查：

1. **这个规格存在吗？** 别是个不存在的幽灵货。
2. **这个商品还在售吗？** 下架的商品不能进篮子。
3. **库存还够吗？** 先看一眼仓库大概还有货没有——这里只是"先问一句"，给你一个友好的即时提醒。

注意最后一步的用词："**先问一句**"。它还不是最终拍板，真正的扣库存发生在下单那一刻（下面细讲）。这里只是**提前给个好脸色**，免得你辛辛苦苦选了半天，结账时才告诉你没货。

还有一个细节值得讲：改数量、删条目这些操作，服务员都会**拿着你的钥匙牌核对"这是不是你的篮子"**，而且这个核对是掺进仓库查询里一起做的——不是先查出来再对比，而是**查的时候就带上"只有你的能查到"**。这样即使有人捣乱，拿着别人的篮子编号来操作，也查不到、改不动，直接被告知"条目不存在"。这叫**把归属校验沉到数据库层**，小偷想越权都没门。

### 4.3 下单 = 收银台结账，一套动作做完

点"去结算"，就是走到收银台。这一步后端要一口气干完一串活，你可以想象成收银员的一套标准动作：

1. **确认篮子有东西**：空篮子不能结账，直接提示"购物车是空的"。
2. **逐样核对并锁货**：每一样货，确认还在售、库存够。
3. **扣库存**：从仓库里把货"拿走"。**这一步是真正的关键**（下一节细讲）。
4. **给每样货拍照留底**：把当时的商品名、规格名、价格做成"快照"存进订单明细——菜价以后变了也赖不掉账。
5. **累加总价**：把所有货的钱加起来。注意：总价是用**精确的小数运算**算的（BigDecimal），一分钱都不会差（4.7 节细讲）。
6. **生成订单**：给这张订单编一个**唯一订单号**——时间是精确到毫秒的"年月日时分秒"，再加 4 位随机数、再加你的用户尾号。好比收银小票上的流水号，全世界（这个系统里）不重样。
7. **订单状态置为"待付款"**（PENDING_PAY）。
8. **记下收货信息**：收货人、电话、地址。
9. **清空购物篮里本次下单的货**：你都结账了，篮子对应的货自然就清掉了。

这一套动作里，最精彩的是第 3 步"扣库存"——它演着一出**防超卖的大戏**，我们单开一节讲。

### 4.4 防超卖：仓库怎么防"货不够还卖"

先看一个事故场景（也是当初开发这个系统的**核心痛点**）：

> 直播间上架了 5 台限量耳机，一秒内涌进来 1 万人同时点"下单"。

如果系统是"先查库存、再扣库存"两步走，会出大乱子：1 万个人几乎同时查到"库存还有 5"——每个人都觉得自己买到了，于是 1 万人一起扣库存。结果呢？库存变成负数：**卖了 1 万份，货只有 5 份**。这就是**超卖**，电商最怕的事故之一。

怎么治？仓库改变规矩：**查和扣，必须捆绑成一步，而且带上"够不够"的条件**。

路径很形象——仓库管理员执行的其实是这么一条命令：

> "把库存减掉 1"——**但是**有一个前提："只有在当前库存 ≥ 1 的情况下，才允许减"。

翻译成人话："这单货，仓库里还有 ≥ 我买的数量，才放行；没有，这笔操作**一行货都没扣成**，直接告诉你'库存不足'（错误码 2004）。"

这个规矩带来两个魔法效果：

1. **原子**：查和扣是一锤子买卖，中间没有人能插队。1 万人同时来，仓库管理员一个一个处理：前 5 个成功，第 6 个开始，库存已经是 0，"库存 ≥ 数量"这个前提不成立，直接被拒——**正好 5 份，绝不多卖**。
2. **行锁保护**：这条命令执行时，仓库会临时给"这一行货"上把锁，其他人排队等着，谁也别想同时改库存改成负数。

那 4.2 节里说的"加购时先看一眼库存"岂不是多余？不多余——那个"先看一眼"是为了**体验**（提前告诉你快没了、提前委婉拒绝），真正的**防线**是下单时这条"带条件扣减"的命令。就算前面所有检查都漏了，这一条也能兜住底。

顺带一提：下单那天卖出去的货，销量（sales）也会跟着 +1。库存一路减、销量一路加，超市盘货时对得上账。

### 4.5 事务：下单是一锤子买卖，要么全成要么全撤

刚才那套"收银台动作"（扣库存、写订单、写明细、清购物车）有一个致命问题：**如果做到一半停电了怎么办？**

比如：库存已经扣了，但订单还没写进仓库，突然程序崩了——顾客钱被扣了、货没了、订单也没了，这账就烂了。

解决这个问题的机制叫**事务（Transaction）**，俗名"一锤子买卖"：

> **要么全成，要么全撤。** 这一串动作要么全部成功落账；只要其中任何一步失败，前面做过的所有步骤**全部撤销**（已经扣掉的库存也会自动加回来），就像什么都没发生过。

靠这个机制，下单永远不会出现"库存扣了订单没写"这种半截账。系统里下单、取消订单这几个关键操作都套着这个保护罩。

### 4.6 取消订单：反悔也要按规矩来

下单之后想反悔？可以，但要按规矩。

第一，**只有订单的主人才能取消**。拿别人的订单号来取消？查都查不到，直接回"订单不存在"。

第二，**只有"待付款"状态的订单才能取消**。都已经付款、发货、收货了，你还怎么撤？规矩是：只有当订单**还站在"待付款"这一步**时，才允许把它改成"已取消"。而且这个"改状态"命令同样带着条件：

> "把订单状态改成'已取消'"——**但是**前提是："它当前状态必须是'待付款'"。

为什么这么防？想象两个人同时点取消：第一个人成功了，第二个人在快要成功的一瞬间，发现前提不成立了（已经不是待付款了）——于是第二个人**取消失败**，不会出现"同一张单被取消两次、库存被加回两次"的乌龙。

第三，取消成功后，**要把这批订单里占用的库存全部加回仓库**——货还在店里，下次还能卖。

这套"改状态必须带着当前状态当条件"的设计，术语叫**状态机**：订单的一生被严格规定为 待付款 → 已付款 → 已发货 → 已完成 / 已取消，每一步都只能走合法的路，不许乱跳、不许重走。

### 4.7 小钱钱要算得精确：为什么不用 double

程序员界有个著名的笑话：`0.1 + 0.2` 算出来不等于 `0.3`，而是一长串莫名其妙的小数。

原因很抽象（二进制的锅），但结论很务实：**用普通小数运算（double）算钱，会累积出丢分、丢厘的误差**。标价 129.00 的商品，三件算下来可能变成 386.9999……，结账时怎么跟顾客交代？

所以 ai-mall 规定：**所有金额一律用精确十进制定点运算（BigDecimal），数据库里存 DECIMAL 类型**。一分是一分，一厘是一厘，绝不用会丢精度的浮点数算钱。

> 小结：购物这一篇，你只需要记住四句话——**实名篮子、查货三步、结账一套、扣货一锤**。其中"扣货一锤"（带条件的库存扣减）就是防超卖的秘密。

## 5. AI 助手为什么"认识"咱们的商品

现在来到这个项目最特别的地方：**AI 种草助手**。你可以在聊天框里问它："AirSound Pro 适合跑步吗？""云朵唇釉有什么色号？"

问题来了：AI 又不是我们店里的员工，它怎么知道我们卖什么？**答案很简单：店里把商品清单"塞"给它当背景知识。**

### 5.1 把商品清单塞给 AI 当"背景知识"

想象你请了个很聪明的顾问，但他从没进过你店。你想让他帮你接待顾客，怎么办？**先把货架上的货挨个跟他介绍一遍。**

ai-mall 就是这么干的：每当顾客发起一次 AI 问答，后端先去仓库把**所有正在售卖的商品**取出来——每个商品带上它的名字、副标题（一句话卖点）、**起步价**和详情介绍——然后整理成一份结构清晰的清单（专业叫法：序列化成 JSON），作为**背景知识（system prompt）**塞给 AI，再附上一条"上岗守则"：

- 回答要**基于这份商品清单，如实回答**；
- 清单里没有的，**坦诚说不知道**；
- **不许编造**。

于是 AI 的回答就有了"底"：你问耳机，它翻着清单说"有，AirSound Pro，399 起，卖点是……"；你问清单上没有的东西，它会老实承认不了解——而不是一本正经地胡编。

为什么每次对话都要重新塞一遍？因为商品会变：下架了、上新了、改价了。**每次提问都拿最新清单**，AI 永远"认识"的是最新货架。这是最简单也最可靠的做法（这个项目叫 V1 方案）；以后商品多了、清单太长塞不下了，会升级成更高级的"检索式问答（RAG）"策略——先把最相关的商品挑出来再塞给 AI，这是后话（第 8 节再提）。

### 5.2 打字机效果：什么是"流式回答"（SSE）

AI 回答一大段文字要花好几秒。如果要求它"想完一整段，一次性发给你"，你会对着空白聊天框干等好几秒——体验像断网一样。

于是这个项目用了**流式回答（SSE）**：AI 说几个字，后端就转发几个字给你，像**打字机**一样，字是一个一个蹦出来的。你几乎感觉不到等待，还能看着它"思考"。

背后的动作是这样的：后端收到你的问题时，**第一时间先把你的问题存进仓库**（防止网络断了导致你的话白说、聊天记录缺一半）；然后一边接收 AI 一个字一个字吐出来的回答，一边转发给你；等 AI 说完了，再把**完整回答**存进仓库。万一 AI 半路掉线，后端也不会让连接就这么干断掉，而是补一句贴心的话："AI 服务暂时不可用，请稍后再试"——**聊天记录永远成双成对：有你一句，就有 AI 一句。**

### 5.3 对话记录存在哪：会话与消息

你问"这个耳机适合跑步吗"，系统会给你开一个**会话（聊天窗口）**，窗口标题默认取你问题的前 20 个字；你继续追问，问答都记在这个窗口里。

- 你问的每一句话、AI 回的每一句话，都存在仓库的**消息货架**里，并且标明是谁说的（用户还是 AI）。
- 你下次打开网站，历史对话还能翻出来看——因为 AI 回答时会**参考这个窗口里之前的对话**（专业叫法：历史消息转成对话上下文），它记得你刚才说过什么，回答才连贯。
- 会话和消息也是**实名制**的：只能看自己的窗口，别人窗口的编号递过来，后端一律回"会话不存在"。

> 小结：AI 这一篇，你只需要记住三句话——**现场塞清单、打字机式回答、对话全留档**。

## 6. 统一返回 + 错误码：全店统一的对讲机

假设你是这家餐厅的老板，你会遇到一个头疼的问题：服务员、厨师、仓库管理员回答顾客的方式五花八门——有人说"行"，有人说"OK"，出错了有人说"退后！"，有人说"Error 42"……顾客懵，新来的员工也懵。

**统一返回**和**错误码**，就是来解决这个"各说各话"的问题的。

### 6.1 为什么要有"统一返回"

ai-mall 给所有接口立了一条规矩：**不管哪道菜、不管成功失败，端上桌的盘子长得一模一样。** 盘子固定三格：

- **code**：这单成没成（用编号回答，见下一节）
- **msg**：给顾客看的白话（"成功"或"库存不足"之类）
- **data**：真正的"菜"（商品列表、订单资料、AI 回答……）

比如查商品列表：成功时 code=200、msg="ok"、data=商品列表；库存不足时 code=2004、msg="库存不足"、data=空。

好处是巨大的：**前端（点餐平板）只需要学会认一种盘子**，不用为每道菜写一套接收逻辑；后端新加任何接口，也闭着眼套同一个模板。整个团队沟通成本骤降，出问题也好查——这就是"约定优于配置"，规矩定在前，麻烦少在后。

素材包里还有一个很细的教训：早期的项目曾遇到过"成功消息"和"成功数据"两种盘子长得太像、被程序搞混，导致数据丢失的事故。所以这个项目**故意删掉了一个容易混淆的写法**，只保留一种明确区分的成功返回——一个看似无聊的细节，背后是一条踩过的坑。

### 6.2 错误码 = 对讲机频道编号

光有"统一盘子"还不够，还得让电脑之间能**快速、精确地**说清楚"问题出在哪"。于是有了**错误码**：一组组编号，按业务分区，像对讲机频道一样泾渭分明：

- **通用区（200 / 400 / 401 / 403 / 404 / 500）**：成功、请求格式不对、没登录、没权限、找不到、服务器坏了——全行业通用的"普通话"。
- **用户区（1xxx）**：用户名已存在（1001）、用户不存在（1002）、密码错误（1003）、账号被禁用（1004）——跟"人"有关的事。
- **电商区（2xxx）**：商品不存在（2001）、规格不存在（2002）、商品已下架（2003）、**库存不足（2004）**、购物车条目不存在（2005）、购物车是空的（2006）、订单不存在（2007）、订单状态不对（2008）——跟"买卖"有关的事。
- **AI 区（3xxx）**：AI 服务出错（3001）——跟"聊天"有关的事。

看一眼编号段位，就知道是哪块地盘出的事：**1 开头是账号问题，2 开头是买卖问题，3 开头是 AI 问题。** 前端拿到编号，可以立刻决定界面怎么表现：是弹"请登录"、跳回购物车、还是显示"稍后再试"；程序员排障时，看到 2004 不用猜就知道是库存的事。

这套编号系统还有一个作用：**把"发生了什么"和"怎么告诉顾客"分开**。后端内部知道最精确的原因（比如"库存不足"），但对外永远只在盘子 msg 里放一句顾客能看懂的话，**技术细节绝不往外抖**（详见下一节）。

### 6.3 全局兜底：出了意外先别崩，回一句"服务器开小差了"

程序再小心，总会有没预料到的意外。老板的担心是：出意外时，顾客千万别看到一堆吓人的报错乱码（而且这些乱码可能还藏着系统的内部秘密）。

于是餐厅设了一个"**兜底广播**"（全局异常处理）：所有没被专门处理的意外，最后统统被它接住，统一换成一句友好的人话——"**服务器开小差了…**"（编号 500）。至于真正的错误细节（哪行代码炸了），只记在**内部日志**里给程序员看，**绝不泄露给顾客**。这就像：后厨失火了，对顾客只说"抱歉，今天暂停营业"，而不是把消防通道图拍顾客脸上。

下面这张表是"兜底广播"的完整规则，你瞄一眼感受下"分类处理"的哲学就行：

| 出了什么事 | 顾客听到什么 | 编号 |
|---|---|---|
| 业务上明确的错误（如库存不足） | 对应的白话（"库存不足"） | 各自编号 |
| 没登录 / 登录过期 | "未登录或登录已过期" | 401 |
| 提交的格式不对（缺字段） | 具体哪个字段错了 | 400 |
| 请求的东西不存在 | "不存在"类提示 | 404 |
| 其他所有没料到的意外 | "服务器开小差了…" | 500 |

这套设计里藏着三层用心：**业务错误说人话、格式错误说细节、未知错误守口如瓶。**

> 小结：这一篇记住三句话——**盘子统一装、编号分地盘、意外兜底不露底**。

## 7. 复盘：把整条链路串成一日游

现在，我们把前面所有章节连起来，模拟你的完整一天。你早上 8 点打开 ai-mall：

1. **进门**：你输入账号密码登录。后端验明身份，发你一张**钥匙牌**，有效期 7 天。你顺手点"我的"页面，前端拿钥匙牌问"我是谁"，后端回你昵称和头像。（门卫已就位，之后每个请求都先过它这关。）
2. **逛店**：你翻商品列表。后端去仓库把在售商品翻出来，算出"起售价"（同一商品最便宜的那个规格的价格）摆上菜单。
3. **加篮**：你看中 AirSound Pro 耳机，点"加入购物车"。后端查：规格存在 ✓、在售 ✓、有货 ✓。篮子归你名下，同一规格再加自动合并。
4. **结算**：你点了终于下单。后端收银台一套动作：逐样核货 → **带条件扣减库存**（防超卖的关键一锤）→ 给每件货拍"价格快照"留底 → 精确算总价 → 生成唯一订单号 → 订单置为"待付款" → 清空你的购物篮。整个过程罩着"事务"保护罩：任何一步失败，全部撤销。
5. **问 AI**：下单后你好奇"这耳机通勤戴合适吗"。后端立刻把**最新商品清单**塞给 AI 当背景知识，AI 照着实货回答；回答以**打字机模式**一个字一个字蹦给你；你和 AI 的对话**成双成对**存进仓库，下次还能翻。
6. **反悔**：你想取消订单。门卫验牌 → 查订单归属是你 ✓ → 必须是"待付款"状态才能取消（状态机）→ 库存原封不动加回仓库。

一天下来，你既当了顾客，又看到了后厨的全貌。**这 6 步,就是这个项目完整的"闭环链路"。**

## 8. 延伸思考：以后网站变大了怎么办

你现在能听懂"系统为什么这么设计"了，不妨再想一层：**这间餐厅以后会开成全国连锁，怎么办？** 项目的开发者已经想好了大方向：

- **V2（扩张期）**：AI 回答从"每次塞全部商品"升级成"检索式问答（RAG，只挑相关的商品给 AI）"；加上支付宝/微信沙箱支付（真收钱）；还准备上线"内容笔记"功能，让顾客发种草笔记。
- **V3（流量期）**：改造超卖防线——把库存放进更快的"缓存仓库"（Redis），用消息队列（MQ）削峰（万人抢购时排队处理），做秒杀专场。订单表里那个预留的 version 字段，就是给将来"更狠的并发控制"埋的伏笔。
- **V4（分店期）**：一间大厨房拆成多个微服务，各管各的（用户一个服务、订单一个服务、AI 一个服务），独立上线、独立扩容。
- **V5（智能期）**：AI 全面升级，做个性化推荐、智能导购，甚至"你说人话，它帮你查数据"。

能看到这层演进，说明你不仅听懂了现状，还看懂了趋势——这正是"原理讲解"想给你的东西。

## 9. 结语：你现在已经"听懂后台"了

最后把全篇浓缩成一张"每个核心概念一句话"的卡片，你可以收藏它：

| 你听到的词 | 其实是 | 大白话 |
|---|---|---|
| 后端 / 接口 / 数据库 | 厨房 / 菜单 / 仓库 | 干活、点菜规、记性 |
| Token | 钥匙牌 | 登录后发的身份凭证，7 天有效 |
| 拦截器 | 门卫 | 每个请求先验牌 |
| BCrypt | 密码暗号 | 存加工结果，单向不可逆，丢了也不怕 |
| 购物车 | 实名购物篮 | 挂在账号名下，最多单件 99 |
| 下单 + 事务 | 收银台结账 | 一锤子买卖：全成或全撤 |
| 防超卖 | 带条件扣库存 | "库存够才扣"，万人抢也不超卖 |
| 状态机 | 订单规矩 | 只能按"待付款→已付款→…→已取消"走 |
| 快照 | 价格留底 | 下单时的商品名和价格，永久存档 |
| BigDecimal | 精确算钱 | 一分不差，不用会丢精度的浮点 |
| SSE 流式 | 打字机回答 | 字一个一个蹦，不让你干等 |
| 背景知识（system prompt） | 塞给 AI 的商品清单 | AI 照着实货回答，不说谎 |
| 统一返回 R | 统一盘子 | code/msg/data 三格，前端只认一种 |
| 错误码 | 编号频道 | 1=账号、2=买卖、3=AI，一看就懂 |
| 全局异常兜底 | 意外救场 | 说人话、记日志、不露底 |

一间开了 AI 外挂的餐厅：**门卫认牌、厨师照单做菜、仓库记性超好、货不够绝不多卖，还请了个手里拿着最新商品清单的 AI 顾问。**

这就是 ai-mall 的全部秘密。现在如果有人再问你"这个系统的后台在干什么"，你可以从容地告诉他：**它是一间把"认人、记账、防超卖、AI 导购"都安排得明明白白的餐厅。**
