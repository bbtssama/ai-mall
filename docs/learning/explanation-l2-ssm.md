## 0 总览：八个设计决策的地图

ai-mall 是一个单体的 Spring Boot 电商项目（Java 17 + MyBatis XML + Sa-Token + Spring AI + MySQL 8），闭环链路是：注册登录 → 浏览商品 → 加购物车 → 下单（防超卖）→ AI 问答（SSE 流式）。

对初级开发者来说，这个项目的价值不在于技术多新，而在于**每一个设计决策都能讲出理由**。本文把八个最重要的决策排成一张表，随后逐章展开：

| # | 决策 | 一句话动机 |
|---|---|---|
| 1 | 按域分包 + 域内分层 | 让"用户/商品/订单/AI"各自独立成岛，为将来拆微服务铺路 |
| 2 | 手写 XML SQL，逐接口 @Mapper | 把 SQL 的"解释权"握在自己手里，代价是放弃 MP 的便利 |
| 3 | 统一返回 R + 全局异常 | 全接口一张盘子、一套错误语义，前端与排查成本双降 |
| 4 | 乐观扣库存（带条件 UPDATE） | 用数据库原子性直接消灭超卖，不依赖应用层锁 |
| 5 | 状态机 CAS 取消订单 | 用"条件更新返回行数"防并发重复取消，保证库存回补只发生一次 |
| 6 | Sa-Token 无状态 Token | 免疫 Session 的集群问题，代价是"吊销难" |
| 7 | V1 预置商品知识，V2 换 RAG | 用最廉价的方式治 LLM 幻觉，等数据量上来再上检索 |
| 8 | BigDecimal 金额 | 钱是精确量，浮点数的误差在金额上不可接受 |

阅读建议：第 1、2 章讲"骨架怎么搭"，第 3〜6 章讲"请求怎么被接住、数据怎么不被搞坏"，第 7、8 章讲"两个跨域的质量问题"。你可以在任意一章独立阅读——每章都是完整的 背景→设计→优劣→换一种做法 闭环。

## 1 按域分包与分层，为微服务埋伏笔

### 背景

SSM 初学者最常见的组织方式是按**技术层**分包：`controller/`、`service/`、`mapper/`、`entity/`，每个包里把所有业务的类堆在一起。这样做在项目只有几百行时很直观，但项目一长就会暴露问题：改一个下单逻辑，你要在 controller 包里翻 20 个文件找"哪个是订单的"；负责订单的人动一动公共 service，可能误伤用户模块。

ai-mall 的目录结构是另一个流派——**先按业务域切，再在域内按技术层分**：

```
common/    # R、ResultCode、BusinessException、GlobalExceptionHandler、PageQuery、PageResult
config/    # AiConfig / PasswordConfig / SaTokenConfig / WebConfig
user/      # 注册/登录/登出/me
goods/     # 商品列表/详情/SKU / 购物车
order/     # 下单/列表/详情/取消
ai/        # 会话管理 / 问答（SSE）
```

每个业务域内部又保持统一骨架：`bean / controller / dto / mapper / service / service.impl`。实体类叫 `bean` 而不是 `entity`，Controller 统一叫 `XxxRestController`，接口统一前缀 `/api/v1`。

### 设计

这套设计有两层含义：

**第一层：域即边界。** `user` 域不允许直接操作 `order` 域的表；跨域协作走对方的公开接口（Controller）而不是互相 import 内部服务。域的边界就是将来服务的边界——现在它们是同一个 JVM 里的"内聚模块"，将来是网络上独立的进程。

**第二层：域内分层即演员表。** 每个域内部，Controller 只做"接单与转译"（参数校验、调用服务、包装返回），Service 只做"业务编排"（规则、事务、防超卖、组装结果），Mapper 只做"数据访问"（一条 SQL 一个方法）。职责单向流动：Controller → Service → Mapper，不允许反向。配套的约定还包括：Service 实现用构造器注入（`@RequiredArgsConstructor` + `private final`），不用字段注入——依赖关系在编译期就固定，测试时也好替换。

### 优劣

**优势：**

- **可读性**：找"下单逻辑"= 进 `order/service/impl`，目录即地图。
- **可测试性**：域间依赖少，可以独立测一个域的 Controller/Service。
- **演进性**：域切好之后，拆微服务 = 把某个域连包带 Mapper 搬出去 + 把内部调用改成 HTTP/RPC，改动范围被域边界天然限定。这就是"为微服务埋伏笔"。
- **规范统一**：新成员照葫芦画瓢，每个新业务域都是同一套骨架，代码风格不需要讨论。

**代价：**

- **开发初期更慢**：加一个简单功能要动 controller/dto/mapper/service/impl 五个文件，相比"一个 controller 里一把梭"有样板成本（不过这套骨架本身就是无脑复制的，边际成本递减）。
- **过度设计风险**：如果业务足够小且确定不会长大，这种分包是杀鸡用牛刀。ai-mall 的判断是：它的演进路线明确（V4 就要拆微服务），这笔投资值得。

### 换一种做法会怎样

- **按技术层全局分包**：最省事，但域边界消失，微服务拆分时等于"把层切碎再重新拼成域"，几乎要重做。
- **Maven 多模块**（`user-module`/`order-module` 各自一个子工程）：域边界更硬（编译期隔离），是单体向微服务过渡的经典中间态。代价是模块间通讯要先定义好 API 契约，构建复杂度上升。ai-mall 用单模块 + 包边界，是"先软隔离"，等真正要拆时再硬化为多模块，成本可控。
- **直接上微服务**：小团队小项目直接微服务是灾难——网络故障、分布式事务、服务发现、部署链路全部提前到场。域分包 + 单体是"用最小的代价保留最大的拆分自由度"。

## 2 手写 XML SQL 与逐接口 Mapper 的取舍

### 背景

2020 年代写 MyBatis，主流选择几乎都是 MyBatis-Plus：`BaseMapper` 自带 `selectById/insert/updateById`，`LambdaQueryWrapper` 免写 SQL，再加 PageHelper 一行分页。ai-mall 反其道而行：**MyBatis 3.0.4 原生 XML 手写 SQL，不引入 MyBatis-Plus/PageHelper，分页手写 `LIMIT offset,size`**。

### 设计

具体约定有四条：

1. **SQL 全部进 XML**：8 个 XML 映射文件（User/Cart/Product/ProductSku/Order/OrderItem/Conversation/Message），`mapper-locations: classpath:mapper/**/*.xml`。复杂查询（如商品列表 LEFT JOIN SKU 求 `MIN(price)` 起售价再 GROUP BY 全列）在 XML 里写，而不是注解拼字符串。
2. **逐接口 `@Mapper` 注册**：每个 Mapper 接口一个 `@Mapper`，启动类上没有 `@MapperScan`。谁用谁声明，装配关系显式可见。
3. **手写分页**：`PageQuery{page, pageSize}` + `getOffset() = (page-1) × pageSize`，Mapper 方法收 `offset,size`，SQL 里 `LIMIT #{offset}, #{size}`，返回 `PageResult{records, total, page, pageSize}`。
4. **驼峰映射**：`map-underscore-to-camel-case: true`，数据库 `stock_count` 自动映射 `stockCount`，省掉大部分 `resultMap` 样板。

### 优劣

**优势：**

- **SQL 全透明**：每条 SQL 都是可读、可审查、可优化的明文。`.xml` 是纯声明式资源，不用点进框架源码猜"条件拼接出来的 SQL 长什么样"。
- **学习价值**：这是初级求职项目——面试官问"分页怎么实现的"，答"PageHelper 的插件拦截 SQL"和答"我手写 `LIMIT offset,size`，total 单独 count 一次"是两种完全不同的印象。手写意味着你真的理解 SQL。
- **精细控制**：`UPDATE ... WHERE stock>=?` 这种带条件的原子扣减、`<if>` 动态更新（状态机里只有取消才回填 `cancel_time`、`version+1`），在 MP 的 wrapper 里写要么别扭要么只能落到自定义 SQL——那不如直接全用 XML。
- **依赖更少**：少两个框架引用（MP、PageHelper），排查"摇一摇就一堆启动报错"的范围更小。

**代价：**

- **样板代码多**：单表简单 CRUD 也要写 XML 和接口方法，没有 `BaseMapper` 的"零 SQL"便利。
- **动态 SQL 容易写糙**：`<if>` 嵌套多了，XML 的可读性下降，而且漏写条件会导致全表更新（经验教训：`<update>` 忘记加 `<where>` 的灾难）。
- **无类型安全**：SQL 是字符串，字段名拼错要到运行时才知道（MP 的 Lambda 表达式部分解决了这个问题）。

### 换一种做法会怎样

- **MyBatis-Plus 全家桶**：迭代速度最快，单表 CRUD 几乎零成本，但"每一条复杂 SQL 都是逃生舱"——项目里一旦出现 `selectOnSalePage` 这种 LEFT JOIN + 聚合 + 条件分页，MP 的 winner 基本帮不上忙，最后还是回到自定义 SQL/XML。选 MP 等于"简单场景快、复杂场景还是写 XML"，选全 XML 等于"所有场景都写 SQL，但心智模型只有一个"。ai-mall 选择了后者，换来的是**全项目只有一种数据访问心智**。
- **注解式 SQL（`@Select`）**：适合单行短 SQL；一旦 SQL 超过三四行，注解里拼字符串比 XML 更丑，且无法复用 `<sql>` 片段。
- **Spring Data JPA**：对象图导航舒服，但复杂的原生查询要写 `@Query(nativeQuery=true)`，且需接受框架对表结构的隐式假设（如 `snake_case` 命名约定），对"SQL 说话算数"这个原则是反向的。
- **代码生成器**（MP 生成器 / mybatis-generator）：可以"既要手写又要快"——生成基础 CRUD，复杂查询仍手写。ai-mall 没有引入生成器，因为 8 张表规模下生成器省下的时间不值一行配置的成本。

一句话总结：**这个取舍的本质是"把 SQL 的解释权留在自己手里"。** 对初级开发者，这是一笔"现在慢一点、将来不慌"的投资。

#### 补一段：手写 SQL 该怎么"读"——以商品列表为例

既然 SQL 全在 XML 里，你读懂项目的第一步就是"读出 SQL"。拿商品分页列表（`selectOnSalePage`）当样本，它其实是三条 SQL 的协作：

1. `countOnSale`：先 `COUNT(*)` 数出"总共多少页"，配合 limit 算总页数——这是手写分页的固定两步之一（先 count 后取数）。
2. `selectOnSalePage(offset,size)`：真正取这一页的记录。它 **LEFT JOIN** 商品规格表，`MIN(price)` 求出"同商品最便宜规格的价格"作为**起售价**（那款 ¥399 的耳机、¥89-129 的闪充宝，列表上显示"起 ¥89"就是这条 MIN 的功劳）；因为用了聚合函数，还要 `GROUP BY` 全列；再叠加 `status=1`（只在售）和 `LIMIT` 分页。
3. 商品**详情**（`selectById`）则是另一条独立的 SQL，带出完整 detail 和规格列表——列表页"轻"只给够列表展示的字段时间和价格，详情页才"重"地取全文，这叫**按需取列**：列表和详情各取各的，避免详情页的大字段拖慢列表接口。

这段 SQL 之所以放在 XML 而不是 MP 里，正是因为它有"LEFT JOIN + 聚合 + 分页 + 条件"四个要素叠加——任何 ORM 的"对象式查询"在这里都只会碍手碍脚。**读懂了它，你就明白了"手写 XML"到底在保护什么：SQL 的每一个 JOIN、每一个 GROUP BY、每一个条件，都由你说了算。**

### 一个延伸：为什么分页要"先 count 再取数"？

这是新手常问的。分页接口要返回 `total`（总共多少条），前端才画得出"共 3 页"。total 从哪来？只能单独 `COUNT(*)` 一次。所以一次分页请求背后其实是两条 SQL：`COUNT(*)` 拿 total + `LIMIT` 拿 records。那些省略 count、只返回"下一页还有没有"的做法（游标分页/keyset）适合无限滚动的信息流，不适合电商这种"需要明确页码和总数"的列表。ai-mall 用 `PageResult{records, total, page, pageSize}` 的四件套，就是标准的"页码式 + 总数"模型——业界最保守、最通用，代价是每次多一次 count 查询（对单体小项目可忽略）。

## 3 统一返回体 R 与全局异常处理

### 背景

没有约定的接口层是什么样？有的接口成功返回 `{data: [...]}`，有的返回裸数组，出错了这个返回 `"error"` 那个返回 `-1`。前端要为一个错误格式写一套特判，后端每写一个接口都要重新发明返回格式。更糟的是：异常直接以默认格式抛给前端——500 页面上出现一大段 Java 堆栈，既难看又泄露内部信息。

ai-mall 的做法是两件配套的事：**统一返回体 R** + **全局异常处理**。

### 设计

**返回体 `R<T>{ code:int, msg:String, data:T }`**，静态工厂：

- `ok()` / `ok(T data)` / `ok(String msg, T data)` —— 成功三件套；
- `fail(String msg)`（默认码 500）/ `fail(ResultCode)` / `fail(int code, String msg)` —— 失败多件套。

**错误码分段（ResultCode 枚举）**，按业务域分区，一眼可读：

| 段 | 含义 | 例子 |
|---|---|---|
| 通用 | HTTP 语义对齐 | SUCCESS(200) BAD_REQUEST(400) UNAUTHORIZED(401) FORBIDDEN(403) NOT_FOUND(404) SERVER_ERROR(500) |
| 用户 1xxx | 账号问题 | USERNAME_EXISTS(1001) USER_NOT_FOUND(1002) PASSWORD_ERROR(1003) USER_DISABLED(1004) |
| 电商 2xxx | 买卖问题 | PRODUCT_NOT_FOUND(2001) SKU_NOT_FOUND(2002) SKU_OFF_SHELF(2003) STOCK_NOT_ENOUGH(2004) CART_ITEM_NOT_FOUND(2005) CART_EMPTY(2006) ORDER_NOT_FOUND(2007) ORDER_STATUS_INVALID(2008) |
| AI 3xxx | 聊天问题 | AI_SERVICE_ERROR(3001) |

**业务异常 `BusinessException`**：带 code 的 `RuntimeException`，在 Service 里"发现问题就抛"（如库存不足就 `throw new BusinessException(STOCK_NOT_ENOUGH)`），不用在层层调用里手动传错误标记。

**`GlobalExceptionHandler`（@RestControllerAdvice）** 兜住所有没被处理的异常，按类型翻译成统一的 R：

- `BusinessException` → `R.fail(code,msg)`（记 warn 日志）
- Sa-Token `NotLoginException` → 401「未登录或登录已过期」
- 参数校验失败（`MethodArgumentNotValidException`）→ 400 + **第一条**字段错误 `field + message`（而不是列出全部）
- 缺参数 / 请求体不可读 → 400
- URL 不存在（`NoResourceFoundException`）→ 404
- 其他一切意外 → 500「服务器开小差了…」，`log.error` 记录完整堆栈，但**不把堆栈泄漏给前端**

### 优劣

**优势：**

- **契约稳定**：前端只需解析一种盘子；后端闭眼套模板，新接口零格式讨论。
- **错误可编程**：错误码是结构化数据，前端可以 `switch(code)` 决定 UI（2004 跳购物车提示、401 跳登录页），不需要解析人话字符串。
- **内部信息隔离**：堆栈只进日志，前端永远只看到一句话——安全性和可排查性同时满足。
- **HTTP 语义与业务语义解耦**：HTTP 状态码只表达"传输层面"的问题（400/401/404/500），真正的业务原因（库存不足 vs 商品下架）放进 code。这样不会出现"需要传 2004 但 HTTP 只能给 200"的尴尬。

**代价：**

- **where 子句的复杂度**：全局异常处理是"约定的魔法"，新人如果不知道 `@RestControllerAdvice` 的存在，会以为每种错误都要手写 try-catch，从而写出冗余代码。
- **统一 ≠ 简单**：code 段位本身需要维护，新增业务域要记得挑段位，不然编号撞车。
- **日志与响应分离**：谁负责记日志、谁负责响应，职责要讲清楚，否则会出现"异常被吞了但没人知道"。

### 专门讲一个坑：去掉 `ok(String)` 单参重载

这是本项目最有"源码级教育意义"的决策之一。早期项目里 `R` 同时存在 `ok(String)`（含义是"成功消息"）和泛型 `ok(T data)` 两个单参重载。看起来人畜无害，直到有人写下：

```java
R.ok(chatService.chat(req))   // chat(...) 返回 String
```

Java 重载解析在编译期按**最具体的静态类型**匹配：参数是 `String`，"单参 ok(String)" 比 "泛型 ok(T)" 更具体，于是编译器选了 `ok(String)`，`data` 字段**变成 null**——AI 的回答丢了，接口还是"成功"的，前端拿到一个成功但空 data 的响应。这种 bug 不会报错，只在线上静默出错，极难排查。

修复方式不是"提醒大家注意"，而是**结构上消灭歧义**：只保留 `ok()`、`ok(T data)` 和双参 `ok(String msg, T data)`——单参场景下"字符串到底是要当消息还是当数据"这个问题**根本不允许存在**。这个决策展示了设计的一个朴素原则：**能用结构消灭的坑，就不要靠自觉规避。**

### 换一种做法会怎样

- **直接用 HTTP 状态码承载业务错误**（404=商品不存在、409=库存不足）：省掉一层封装，但 HTTP 状态码集合不够表达业态（"购物车为空"该用哪个？200? 400?），且网关/浏览器对 4xx/5xx 有默认行为，扩展性差。业界主流仍然是"HTTP 语义 + 业务码"双层。
- **返回 `ResponseEntity<T>`**：Spring MVC 原生支持，灵活但**每接口都要自己决定状态码**，统一性靠自觉，恰好是本文要反对的。
- **错误全在 data 里返回（N 种返回格式）**：回到起点，不讨论。
- **API First / OpenAPI 契约**：用 schema 统一返回体是更工程化的路径，但需要引入契约生成/校验链路，单体小项目成本偏高。R + ResultCode 枚举是它的轻量近似。

#### 补一段：不是所有异常都要"统一"

细心的读者会问：既然有全局异常处理，为什么还要在 Service 里到处抛 `BusinessException`？这不是重复吗？其实两者分工完全不同——**全局异常处理管"翻译"**，`BusinessException` 管"表达"。

- **表达层（Service）**：业务发现"库存不足""商品下架"，它**说不清"该用什么 HTTP 码"，它只知道自己违反了什么业务规则**。所以它抛一个带 `ResultCode` 的 `BusinessException`，把"到底错在哪"这个事实说清楚。注意：`BusinessException` 是 `RuntimeException` 子类——**故意让它在方法签名上不强制捕获**，省去一堆 try-catch 样板，一路向上冒泡到全局异常处理器。
- **翻译层（GlobalExceptionHandler）**：接住这个异常，从 `code` 字段读出 2004，组装成 `R.fail(2004,"库存不足")` 返回。它是"最后一道闸"，把"内部的事实"翻译成"客户能看懂的架子"。

这个分层的巧妙在于：**业务代码根本不需要关心 HTTP 层**。新增一种错误 = 在 ResultCode 枚举里加一个常量 + 在出错处抛一句 BusinessException，全局处理器零改动。反过来想：如果没有 `BusinessException`，Service 要么 return 失败结果在调用链上层层传（样板爆炸），要么直接 `throw new RuntimeException("库存不足")`（丢失错误码结构化信息，全靠字符串匹配）。带 code 的异常，就是"想表达业务事实 + 又想省样板"之间最优雅的平衡点。

## 4 乐观扣库存防超卖，为什么胜过先查再减

### 背景

超卖是电商第一事故：库存 5 台，卖出 5000 单。它的根因不是"库存数据错了"，而是**读和写之间有空窗**。

经典的错误实现是两步走：

1. `SELECT stock FROM t_product_sku WHERE id=?` → 内存里判断 `stock >= qty`
2. `UPDATE t_product_sku SET stock = stock - qty WHERE id=?`

两个请求并发时，可能都读到 stock=5，都判断"够"，都执行扣减——最终 stock 变 3（5-1-1），但两次都该成功？不对，更糟的场景：都读到 1，都扣 1，库存变 -1，超卖。**问题不在 SQL 写错了，在于"判断"和"扣减"不是原子的一步。**

### 设计

ai-mall 的扣库存 SQL（`ProductSkuMapper.deductStock`）是单条条件 UPDATE：

```sql
UPDATE t_product_sku
SET stock = stock - #{qty}, sales = sales + #{qty}
WHERE id = #{skuId} AND stock >= #{qty}
```

关键在 `WHERE ... AND stock >= #{qty}`：**扣减与判断合并成一条语句**。数据库的 UPDATE 自带行锁：并发请求会串行执行这一行，第二个请求执行时 stock 已经减过了，`stock >= qty` 不成立 → 影响行数为 0。Mapper 返回 0 → Service 抛 `STOCK_NOT_ENOUGH`。

设计细节还有两层：

- **内存预检是"体验层"**：下单前在内存里 `stock` 先看一眼（加购时也预检），只是为了**提前**给用户友好提示（"库存不足，别白忙一场"），不是防线；真正的防线永远是这条 SQL。预检被并发击穿也没关系——SQL 兜底。
- **整体事务**：下单方法标注 `@Transactional(rollbackFor = Exception.class)`，扣库存、写订单、写明细、清购物车同事务。任一步失败整体回滚，**已经扣掉的库存同步回滚**。注意 `rollbackFor = Exception.class` 是显式写的——Spring 默认只对 `RuntimeException`/`Error` 回滚，如果业务异常是受检异常或漏配，就会出现"扣了库存不回滚"。

### 优劣

**优势：**

- **一条 SQL，零额外组件**：不需要锁表、不需要分布式锁、不需要队列——数据库在"单行条件更新"上本来就安全。
- **无死锁风险（相对）**：只在目标行上加锁，锁的粒度是"这一行库存"，比 `SELECT ... FOR UPDATE` 整行锁定更克制（其实也是行锁，但拿到锁到释放的时间极短）。
- **性能好**：行锁只在写瞬间存在；没有应用层锁的线程等待开销。
- **语义清晰**："0 行受影响 = 没扣成"是数据库原生语义，不需要额外状态同步。

**代价：**

- **失败即放弃**：返回 0 行就直接抛异常，**不做重试**。用户抢购失败就失败了，体验上"瞬秒没"。
- **扣减幂等靠事务**：如果没有 `@Transactional` 包裹，SQL 扣成功了但后续写订单失败，库存就少了——防线是"SQL + 事务"的组合，缺一不可。
- **不解决"超卖到多 SKU 组合"**：跨多件商品的整单库存一致性仍靠单行扣减逐条完成 + 事务回滚，没有库存预留（reserve）模型，巨大订单会占着库存直到提交。

### 换一种做法会怎样

- **悲观锁 `SELECT ... FOR UPDATE`**：先锁行再读再改。同样可靠，但锁持有时间 = "读+判断+扣减"全程，并发吞吐低于条件 UPDATE；且容易忘加锁、容易在 SQL 里埋死锁。条件 UPDATE 是"锁得晚、放得快"的优化版。
- **应用层锁（`synchronized`/`ReentrantLock`）**：只在单机单进程有效；项目一旦多实例部署就全部失效。且把"数据的一致性"交给了"进程内状态"，架构上站不住。
- **Redis 分布式锁 / Lua 扣减**：跨实例可靠，是 V3 秒杀场景的正解（ai-mall 的 V3 路线就是 Redis/MQ/秒杀）。代价：引入 Redis 依赖、锁过期/续期/可重入问题全要来一遍；对单体起步项目是过度工程。
- **乐观锁 version CAS + 重试**：`UPDATE ... SET stock=stock-1, version=version+1 WHERE id=? AND version=#{old}`，失败重读重试。适合"冲突少、允许重试"的场景；抢购场景冲突率高，重试会放大请求量。**注意**：本项目表里预留了 `version` 字段（乐观锁痕迹，V3 秒杀强化用），但当前 V1 的库存扣减并没有走 version——它用的是"条件即版本"：`stock >= qty` 本身就是版本检查，比 version 更贴合"库存"这个业务量（version 检查只管"没被别人改过"，条件检查直接管"还剩多少"）。

一句话：**"先查再减"把并发控制交给应用层，"条件 UPDATE"把并发控制还给数据库。** 数据库在这个场景里比你更专业。

#### 补一段：事务边界为什么必须"包住扣库存"

第 4 章的设计里，`deductStock` 和"写订单"分开看是各自独立的 SQL，它们之所以成为一个不可分割的整体，靠的是外层方法上的 `@Transactional(rollbackFor = Exception.class)`。你可以做一个思想实验，看这个边界为什么必须：

- **只扣库存、不写订单**（事务边界画在扣完那一刻）：库存扣了，但订单/明细还没落库就抛异常——库存凭空消失。
- **只写订单、不扣库存**（先写订单再扣）：订单记下了但库存没减——货会超卖。
- **两条都在一个事务里**（本项目）：要么"库存-1 且订单-1 且明细成对 且 清购物车"全部落库，要么全部回滚回到下单前。**哪怕第 3 个 SKU 扣到一半发现没货了，前面两个 SKU 已扣的库存也会跟着一起回滚**——顾客完全感知不到这段"拆东墙补西墙"的中间态。

所以真正的防线从来不是"那一条 UPDATE"，而是"**条件 UPDATE + 事务边界 + 抛错回滚**"三件套。这也是为什么素材包强调下单方法和取消方法都挂了 `@Transactional`：没有事务，扣库存这条 SQL 再原子，也兜不住"半截下单"这种账目残缺。

顺带一提事务的回滚行为：`rollbackFor = Exception.class` 是**显式**写的，它扩大到了"所有异常都回滚"，而不是 Spring 默认的"只回滚 RuntimeException"。为什么这么写？因为下单里很可能抛自定义检查异常或 Error 层级的东西，一旦漏配 rollbackFor，就会出现"扣了库存却认为成功"的静默错误——把 rollback 范围显式放宽，是"宁可多回滚，绝不少回滚"的防御姿态。

## 5 状态机 CAS 取消订单

### 背景

订单不是一张"死表"，它有生命周期：待付款 → 已付款 → 已发货 → 已完成 / 已取消。每个状态变化的背后都有业务副作用——最重要的是：**取消订单要回补库存**（把占用的库存加回去）。

由此引出两个并发问题：

1. **重复取消**：用户手抖点了两次取消，或两个设备同时取消。如果两次都"成功"，库存会被回补两次，而订单只取消了一次——库存虚增。
2. **取消与状态冲突**：订单已经付款了还想取消？业务上允许吗？不允许——取消只能发生在"待付款"。

### 设计

ai-mall 的订单状态更新走的是**带前状态条件的 CAS 更新**（`updateStatus`）：

```sql
UPDATE t_order
SET status = #{toStatus}
    <if test="toStatus == 'CANCELLED'">, cancel_time = #{cancelTime}</if>
    , version = version + 1
WHERE id = #{id} AND status = #{fromStatus}
```

调用方（取消订单）：`updateStatus(id, PENDING_PAY, CANCELLED, now)`。设计要点：

- **`WHERE status = 'PENDING_PAY'` 是状态机守门员**：只有当前状态恰好是待付款，这次"改到已取消"的命令才生效；否则影响行数为 0。
- **0 行 = 状态已变**：Service 收到 0 行，抛 `ORDER_STATUS_INVALID`——这次取消**没有生效**，库存也**不会**回补。两个并发取消请求，只有一个能拿到 1 行，另一个拿到 0 行，**回补库存天然只执行一次**。
- **归属校验先行**：取消前 `selectById` 后用 userId 校验订单归属，不是本人 → `ORDER_NOT_FOUND`（不泄露他人订单存在性）。
- **回补库存**：取消成功后，`selectByOrderId` 遍历明细逐条 `addStock`，把占用的库存加回。
- **version 随更新 +1**：乐观锁痕迹，V3 秒杀强化时启用（当前状态机 CAS 已足够，version 是冗余保险的伏笔）。

### 优劣

**优势：**

- **并发安全靠数据库**：CAS 条件更新是原子的，不需要应用层 `synchronized`、"double-check"这类脆弱手段。
- **语义即规则**：状态机不是写在 `if` 里的业务逻辑，而是**写在 WHERE 里的约束**——漏了判断也不可能绕过，因为数据库不认识"你忘了判断"。
- **幂等副作用**：回补库存与"取消成功"严格一一对应，账不会虚。
- **审计友好**：`cancel_time` 只在取消时回填，状态变更可追溯。

**代价：**

- **状态转移写死在调用方**：每个调用方要自己记得"from→to"合法性（取消：待付款→已取消）。状态多了之后，合法转移表散落在各 Service 里，容易漏（比如"已发货想取消"在别处可能写漏判断）。
- **条件更新看起来平凡，容易被新人"优化"掉**：有开发者在 review 时把它"简化"成 `UPDATE ... SET status=... WHERE id=?`——灾难。
- **版本字段当前是半闲置的**：它记录了乐观锁的意图，但 V1 没有真正启用，属于"预留"。

### 换一种做法会怎样

- **应用层读-判-写**（先查 status 再 `if` 再更新）：最直觉也最危险——判断与写入之间有空窗，并发下两次"判断通过"，重复取消发生。这正是第 4 章教训的翻版。
- **状态机表驱动**：把"合法转移"定义成一张表（`from → {to1,to2...}`），Service 查表决定是否放行，再执行条件更新。状态多了以后这种结构化更稳，但 V1 只有 5 个状态，表驱动的抽象成本不划算。
- **引入状态机框架（Spring StateMachine 等）**：功能全（事件、guard、action、持久化），但对 5 个状态的订单是杀鸡用牛刀，学习曲线和样板远大于收益。
- **消息队列驱动状态流转**：取消请求 → 发消息 → 消费端幂等执行取消。能解并发和重试，但需要 MQ，且把"立即生效的取消"变成"异步最终一致"，用户感知变差——单体阶段没必要把简单问题复杂化。
- **用幂等键（idempotency key）**："取消"请求带一个唯一键，服务端去重。适合外部客户端重试的场景；本项目取消来自登录用户自己的操作，状态机 CAS 已经足够。

核心思想：**状态机的本质不是"枚举状态"，而是"每一次状态跃迁都必须是一个受约束的原子操作"。** 约束写成 SQL 条件，比写在 if 里可靠得多。

## 6 Sa-Token 无状态认证与 Session 的对比

### 背景

SSM 经典认证方案是 Session：登录成功，服务器把会话（`HttpSession`）存在**自己的内存**里，给浏览器种一个 `JSESSIONID` Cookie；之后请求凭 Cookie 找到服务器内存里的会话。

这方案在单体单机时代没毛病，但一放大就露怯：

- 部署两台服务器，用户在 A 登录，请求落到 B——B 的内存里没有这个会话，**登录掉了**。这就是 Session 亲和性/共享问题。
- 前后端分离（Vue 在 5173，后端在 8080）后，跨域带 Cookie 要处理 CORS `allowCredentials` 与 `SameSite`，别扭。
- 所有会话挤在服务器内存，重启即全员掉线。

### 设计

ai-mall 用 **Sa-Token 无状态 Token**：登录成功，服务端生成**一串随机 Token（uuid 风格）**返回给前端；前端之后每个请求在 `Authorization` 头里带上它；服务端**不依赖任何服务端存储**来认人。

关键配置与行为：

- `token-name: Authorization`：前端放哪一栏，约定清楚。
- `timeout: 604800`（7 天）：Token 有效期。`active-timeout: -1`：不做"活跃续期"（即不因活跃而无限续命，固定 7 天过期）。
- `is-concurrent: true, is-share: false`：允许同一账号多端同时登录，但每端一个独立 Token（互不挤掉）。这是"多设备登录"的产品决策。
- `token-style: uuid`：Token 是一串无意义随机数，**不含任何用户信息**。
- **拦截器统一鉴权**：`SaInterceptor` 拦截 `/api/**`，白名单只有三个：登录、注册、`/error`。未带/无效 Token → `NotLoginException` → 全局异常处理器翻译成 401「未登录或登录已过期」→ 前端跳登录页。
- 业务里需要"当前用户是谁"处，直接 `StpUtil.getLoginIdAsLong()` 拿用户 id，比如购物车/订单归属校验，**不用再把用户 id 传来传去**。

### 优劣

**优势：**

- **无服务器会话状态**：任何一台服务器都能验证这个 Token（验证逻辑就是"这串随机数是我签发的、没过期"）——**天然适合多实例部署**，不需要 Session 共享、sticky session、或额外引入 Redis 存会话。
- **前后端分离友好**：Token 走 HTTP 头，不碰 Cookie，跨域 CORS 配置简单（本项目 CORS 放开 `localhost`/`127.0.0.1:*`，`allowCredentials(true)`）。
- **轻量纯粹**：uuid 风格 Token 不编码用户信息，没有 JWT 的签名/密钥管理负担；`is-share: false` 让"多端互踢"这种产品需求一行配置搞定。
- **无需存储实现**：Sa-Token 的默认实现足够 V1；将来要真正登出即失效/服务端吊销，换持久化存储（Redis）是插件化的，API 不变。

**代价：**

- **吊销困难**：无状态 = 服务端不记得谁持有哪个 Token。用户改密码后，"旧 Token 还活着 7 天"（除非额外引入黑名单/存储）。这是无状态方案的固有代价。
- **过期策略粗粒度**：固定 7 天，「7 天内必须重新登录」对低频用户不算友好；主动续期/滑动过期需要额外设计（`active-timeout` 这里设了 -1，即不做活跃续期）。
- **Token 存哪是前端的责任**：存 localStorage 有 XSS 风险，存 Cookie 要 CSRF 防护。本项目身份认证契约简单，V1 不做加固是取舍。

### 换一种做法会怎样

- **经典 Session + Cookie**：单机/内网最优，实现零成本、可服务端主动失效（logout 立刻生效）。代价就是集群共享、跨域、重启掉线三大痛点的套餐。**单体单实例部署时它完全可用**——ai-mall 选择 Token 不是因为 Session 不能用，而是项目的演进路线（V4 微服务、随时多实例）从一开始就值得用无状态方案。
- **JWT（自包含 Token）**：Token 里直接编码用户 id/角色/过期时间，验签即可，连"查证"都不需要。优势是真正零状态、可跨服务共享身份；代价是要管密钥、要处理过期与吊销、Token 变大。Sa-Token uuid 风格本质是"服务端可查的随机串"，比 JWT 少一层签名复杂度，多一层（最终来自存储的）查证——对单体项目更简单。
- **Redis 集中 Session**：解决集群共享，但引入 Redis 依赖和会话管理心智，且仍是"服务端有状态"。
- **OAuth2 / SSO / JWT+刷新令牌双 Token**：企业级多应用认证体系，对单个电商单体项目是严重过度设计，V5 阶段做 Agent/推荐时再说。

一句话：**Session 的问题是"状态放错了地方"——放在服务器内存里；Token 把状态交还给客户端，服务器因此变得可任意横向扩展。** 代价是"吊销"这个能力被削弱，V1 用 7 天过期来兜底。

#### 补一段：认证的另一半——密码怎么存、登录怎么验错

Token 解决了"登录之后怎么认人"，但"登录那一刻怎么验证密码"同样有讲究，它是认证体系不可拆开的一半。ai-mall 用到两个决策：

**第一，密码用 BCrypt 单向散列存储。** 用户注册时，`password_hash` 字段存**不是**用户的明文密码，而是 BCrypt 加工后的"暗号"。这是单向的：从暗号几乎不可能倒推出明文。为什么坚持单向？因为数据库一次拖库，泄露的若是明文，用户在全国到处用的同一套密码全完了；若是 BCrypt 暗号，黑客拿到也基本解不开（BCrypt 内建随机盐 + 慢哈希，暴力破解成本极高）。注意本项目用的是 `spring-security-crypto` 里的 **BCrypt 模块**，而不是完整引入 Spring Security——为了一个 `PasswordEncoder` 不值得拉进整个安全框架全家桶，这是"按需引入最小依赖"的又一例。

**第二，登录失败统一回"密码错误"，不暴露用户名是否存在。** 登录流程是：先 `selectByUsername` 查用户 → `passwordEncoder.matches(明文, 存hash)` 比对 → 用户不存在或密码不匹配，**统一**抛 `PASSWORD_ERROR`（1003）。为什么故意不给用户一个"你用户名输错了"的明确反馈？因为如果系统老实说"用户名不存在"，就等于免费告诉攻击者"这个账号存在，你尽管去撞密码"。统一回"密码错误"，让攻击者对"账号是否存在"无从下手——这是信息最小化在认证场景的经典应用。同理，`status == 0`（账号被禁用）会单独抛 `USER_DISABLED`，这是"账号被管理员封禁"的明确业务信号，与"用户名/密码错"是两种语义。

配套还有一个细节：注册时用户名有格式校验（`^[a-zA-Z0-9_]{3,20}$`），且表上 `uk_username` 唯一索引兜底——**先查重是对用户的友好预检，唯一索引是最后的硬防线**。即使两个并发注册请求同时通过查重，也只有一个能真正 insert 成功，另一个被唯一索引拦下，这与防超卖"SQL 条件 + 事务"的思路一脉相承：**能用数据库约束兜底的，就不要只靠应用层判断。**

> 认证的两半小结：**登录之后再认人是 Token 的活，登录那一刻验密码和防探测是"BCrypt 单向 + 统一错误"的活。** 两个拼在一起，才是完整的"门卫"。Sa-Token 拦截器防的是没有 Token 的人，BCrypt + 统一错误防的是"想冒充你的人"——一前一后，各有分工。

## 7 V1 预置商品知识与 V2 RAG 的演进逻辑

### 背景

AI 问答（聊天机器人）的第一大风险是**幻觉**：LLM 会一本正经地编造不存在的商品、价格、功能。让它当导购，它可能告诉你"我们有 999 元的 8K 耳机"——而店里根本没这货。

怎么让 AI "知道"店里卖什么？直觉方案是把商品数据喂给它。但问题有两个：

1. **要"新鲜"**：商品上下架、改价是常态，AI 的知识不能停在训练时点。
2. **要"诚实"**：光把数据塞进去不够，还得约束它"不知道就说不，不许编"。

### 设计（V1：预置商品知识）

ai-mall V1 的答案非常朴素，三步走（`buildSystemPrompt`）：

1. 每次发起问答时，`productMapper.selectAllOnSale()` 把**所有在售商品**从库里取出来（每次都取 = 永远最新）；
2. 裁剪字段：只留 `id / name / subTitle / minPrice / detail`，`ObjectMapper` 序列化成 JSON——精简成 AI 够用的最小知识集；
3. 把这份 JSON 作为 **system prompt（系统指令）** 塞给 AI，并在指令里写死三条铁律：基于商品库如实回答；知识库里没有的，坦诚说不知道；**不编造**。

配套的可靠性设计（SSE 流式时序）：

- 订阅即刻先把**用户问题**持久化（`doOnSubscribe`）——防止流式传输中途失败导致"用户问了但没留档"的孤儿提问；
- 逐字累加回答（`doOnNext`）；
- 流正常结束才持久化**完整回答**（`doOnComplete`）；
- 出错时 `onErrorResume` 补一句「AI 服务暂时不可用，请稍后再试」，而不是让连接裸断——**保证"问题-回答"成对存在**。

### 优劣

**V1 的优势：**

- **实现极简**：一个 `selectAllOnSale` + JSON 序列化 + 一段 prompt，没有向量库、没有 embedding、没有检索服务。
- **数据天然最新**：每次问答都从数据库现取，改价立即生效（RAG 的索引反而有更新延迟问题）。
- **零幻觉兜底靠指令**：诚实性三原则直接写进 system prompt，大部分情况下能压住编造倾向。
- **对 SSE 场景透明**：知识是 prompt 的一部分，与流式输出机制不冲突。

**V1 的代价（也是 V2 的动机）：**

- **上下文规模失控**：商品数量增长后，"全部商品 JSON" 会撑爆 prompt 窗口，token 成本线性上涨，且模型对超长 prompt 的注意力会稀释——**知识越多，回答越"泛"**。
- **检索精度为零**：问"适合跑步的耳机"，所有商品不分主次全塞进去，AI 要自己从大杂烩里挑；相关知识越少，答对的概率越低。
- **每个问题都全量传输**：一样的商品清单，每个问题都重复传一遍，浪费带宽与延迟。

### 换一种做法会怎样（V2：RAG）

**RAG（检索增强生成）** 的思路是反过来的：**先检索，再生成**。

1. 把商品库离线切块 + 向量化（embedding），存进向量库；同时保留关键词倒排索引（混合检索）；
2. 用户提问时，先把问题向量化，**召回 Top-K 最相关的商品片段**（并做相关性重排）；
3. 只把"召回的 K 段"塞进 prompt 生成回答——知识量从"全部"降到"精选"。

相比 V1 的演进逻辑：

- **成本可控**：prompt 长度与商品总量解耦，只与 K 有关，商品万件也心不慌——**解决了 V1 的规模瓶颈**。
- **精度提升**：检索把"最相关的几个商品"直接喂到嘴边，回答聚焦。
- **引用来源可展示**：可以返回"我依据了这几条商品资料"，给回答配引用。

RAG 的代价是：要管 embedding、向量库、同步/更新、召回质量调优（分块、重排、混合检索）——一套完整链路。ai-mall 的 V2 路线正是如此（RAG 导购），并且**消息表里已经预留了 `extra_json` 字段**（V2 存放引用来源）——这是"设计为演进留接口"的典型例子：表的扩展字段先躺着，等检索上线再启用。

还有一种替代路线值得对比：**微调模型**——用"商品问答对"去微调一个专用模型，让商品知识进权重。优点是回答风格稳定、无检索延迟；缺点是要攒数据、要训练/托管专用模型，且商品数据一变又要重新微调。**对"商品频繁变动"的电商场景，RAG 的"知识在库、模型不动"明显更合理**；微调更适合"知识稳定、回答风格要求高"的场景。

> 这个演进逻辑可以顺带给你一个判断框架：**知识是"变动的数据"还是"稳定的能力"？前者用检索（RAG/查库），后者用模型本身（微调/prompt）。**

#### 补一段：SSE 流式为什么用"响应式流"，以及它暴露的三个可靠性坑

AI 回答慢，不能一次性生成完再返回，否则用户对着空白聊天框干等。ai-mall 用了 **SSE（Server-Sent Events，服务端单向推送）**：后端把 AI 吐出的内容**一边生成一边推**，前端表现为"打字机"效果。接口 `POST /api/v1/chat/stream` 的 `produces = TEXT_EVENT_STREAM_VALUE`，返回类型是 `Flux<String>`——这是 **Reactive/响应式流**的写法：`Flux` 是一个"异步、背压感知、可能发出多条"的序列，而不是一次 `String` 的普通返回值。

为什么是 `Flux<String>` 而不是"一个会等待的常规方法"？因为常规的 `Controller` 方法要**等返回值凑齐才返回**；而 `Flux<String>` 是"持续产生消息的流"，Spring MVC 会把它当流式响应逐帧推给前端，浏览器就能在**第一个字生成时就立刻看到**。这是"流式交互"与"一次性响应"在接口层面的分水岭。

写流式代码最容易踩三个可靠性坑，本项目的算子设计正好是三个解法：

1. **孤儿提问**：如果用户在"问题刚发出、回答还没生成完"时网络断了，用户这句话就丢了。解法：`doOnSubscribe`（订阅开端）**先把用户问题落库**——问题一发出就存档，不留孤儿。这一步比"等流结束再存"提前了整条流的生命周期，是时间线上的关键。
2. **半截回答入库**：如果直接在 `doOnNext` 每来一段就往库里写，会造成"回答存了一堆碎块"。解法：`doOnNext` 只做 `sb.append`（内存里累加成完整字符串），真正写库放在 `doOnComplete`（流干净结束时）——只有完整结束才落库，中途再颠簸也只当没发生。
3. **流裸断**：如果 AI 服务中途报错，不处理的话连接就直接断掉，用户看到的是"对话死在半路"。解法：`onErrorResume` 返回一句「AI 服务暂时不可用，请稍后再试」，把"硬错误"翻译成"兜底文案"，保证每条流都有一个结尾。

把这三点串起来看：**`doOnSubscribe` 存问题、`doOnComplete` 存回答、`onErrorResume` 兜底尾部**——它们保证了"问题-回答"这对记录是完整、可对账的。这也是为什么素材包强调"SSE 时序是核心可靠性设计"：流式接口的坑不在"能不能推流"（框架早已解决），而在"**流的生命周期两侧怎么落库、断了怎么办**"——这正是初级开发者最容易忽视、而本项目已经替你踩平的地方。

> 换一种做法：如果不用 SSE 流式返回，可以用"一次性 JSON 返回完整回答"（接口返回 `R<String>`，本项目的 `POST /api/v1/chat` 就是普通问答），实现最简单，但等待体验差；也可以用 WebSocket（双向，前端还能中途打断），但要处理连接管理、心跳、断线重连，复杂度高得多。对"服务端单向推送、几乎不需要前端插话"的 AI 问答场景，SSE 是**复杂度与体验之间的甜点位**——所以项目同时保留了普通问答（简单场景）和 SSE（体验场景）两套接口。

## 8 BigDecimal 金额

### 背景

浮点数的账是每个程序员迟早要算的一笔：`0.1 + 0.2` 在 IEEE 754 二进制浮点下不等于 `0.3`，而是一串 `0.30000000000000004`。日常打印没人注意，但**金额不行**：一分钱的误差在财务上就是事故，累计起来就是纠纷。

电商场景的金额还有更多雷区：价签 129.00、数量 3 件、优惠叠加、分页对账……任何一步用错类型（`double`、`float`），都可能出现"对不上账"。

### 设计

ai-mall 的金额纪律有三条：

1. **Java 侧全程 `BigDecimal`**：价格、小计、总额、快照，一律 BigDecimal；**累加总额严禁 double**——文档里直接写了"Decimal 累加，严禁 double"。
2. **库侧 `DECIMAL(10,2)`**：数据库字段类型用定点十进制，天然精确到分，且能被索引/比较。
3. **乘法用小数计量**：小计 = `price × quantity`，BigDecimal 的乘法保证精确；不要先转 double 再乘再转回。

（素材包还明确：下单价钱、订单明细快照里的 productName/skuName/price，全部来自 SQL 查询时的原始值，不经过任何浮点换算；订单总金额由 Decimal 逐项累加得到。）

### 优劣

**优势：**

- **精确**：定点十进制在"金额"这个量纲上是数学正确的（对分、对厘）。
- **一致**：Java 侧与数据库侧同构（BigDecimal ↔ DECIMAL），没有类型转换的隐性损耗。
- **规范即保险**：团队约定"金额只用 BigDecimal"，review 时一眼可查，从结构上避开浮点误差类 bug。

**代价：**

- **样板与心智**：BigDecimal API 不如原生类型顺手，要处理 `scale`（精度位数）与舍入模式（`RoundingMode`），新人容易写出 `new BigDecimal(0.1)`（用 double 构造，又引回误差！应使用 `new BigDecimal("0.1")` 字符串构造）。
- **序列化/展示**：前端拿到的 JSON 数字可能出现科学计数法形态，需要配置序列化格式（本项目 Jackson 全局 `date-format` 是时间，金额的展示精度要靠类型策略/BigDecimal 的 toString 行为配合）。
- **性能**：BigDecimal 比 double 慢若干个数量级，但电商金额计算量相对业务 IO 可忽略——**为性能牺牲货币精确性的优化是负优化**。

### 换一种做法会怎样

- **`double`/`float`**：快，但注定有误差；对账失败就是事故。**电商/金融之外可以凑合，金额上不行。** 这也是素材包把"金额用 BigDecimal"当作铁律的原因。
- **`long` 以"分"为单位存储**：经典方案——金额一律按分存成整数（`long`），运算全部整数运算，展示时除以 100。优点是快、精确、无舍入歧义；缺点是"每处展示都要记得 /100"，且 `DECIMAL` 与 `long` 的语义映射要靠团队纪律。**对中小型项目，BigDecimal + DECIMAL 语义更直白**；对超大规模订单量，`long(分)` 是常见优化。
- **数据库侧约束兜底**：字段类型本身用 `DECIMAL(10,2)`（本项目即如此），即使某个开发者不小心塞了浮点，DB 也会因精度/类型约束报警或截断，属于"最后一公里防线"。
- **第三方金额库（如 Joda-Money）**：把金额做成一等公民类型（货币 + 金额），适合金融级多币种场景；单币种单项目里，BigDecimal + 纪律约定已经足够，多一个依赖反而增加学习成本。

> 判断题速记：**凡涉及钱：Java 用 BigDecimal（字符串构造）、库用 DECIMAL、展示格式化到分。** 三条守住了，金额这块就稳了。

## 9 回放：一次下单背后的八个决策

把八个决策放回同一条业务链路里，看它们如何协同。顾客"小种草"完成一次下单：

1. **登录（决策 6）**：`POST /api/v1/auth/login` 验密（BCrypt）成功 → 签发随机 Token → 前端此后每次请求带 `Authorization` 头 → **门卫（SaInterceptor）** 对 `/api/**` 逐一验牌。购物车/下单时 `StpUtil.getLoginIdAsLong()` 拿用户 id。
2. **加购（决策 1）**：请求进 `goods` 域的 CartController → CartService（构造器注入）→ CartMapper XML SQL。同 SKU 合并数量、封顶 99，更新/删除 SQL 带 `user_id` 条件（归属校验下沉数据库，查 0 行即非本人条目）。
3. **下单（决策 4、5、8）**：进 `order` 域，`@Transactional` 开启。为每件 SKU：内存预检 → **条件 UPDATE 扣库存**（`WHERE stock>=?`，0 行 → `BusinessException(STOCK_NOT_ENOUGH)`）→ 组订单明细快照（含 price，BigDecimal）→ `BigDecimal` 累加总价 → 生成唯一订单号（时间戳+随机+用户尾号，唯一索引兜底）→ 写订单（状态 PENDING_PAY）→ 清购物车。任一异常 → 整体回滚。
4. **取消（决策 5）**：归属校验 → `updateStatus(id, PENDING_PAY, CANCELLED, now)`，CAS 条件更新返回 0 行 → `ORDER_STATUS_INVALID`；成功 → 逐条 `addStock` 回补库存。
5. **任何一步出错（决策 3）**：异常被 `GlobalExceptionHandler` 按类型翻译成统一 `R{code,msg,data}`——业务错给业务码（2001~2008），没登录给 401，参数不对给 400，没料到的给 500「服务器开小差了…」，堆栈只进日志。
6. **问 AI（决策 7）**：`selectAllOnSale` 取最新在售商品 → 裁剪成 JSON → 塞 system prompt → SSE 流式回答，提问先行落库、回答完整落库、出错兜底文案——聊天记录对账完整（决策 3 的 AI 版）。

看到没？**没有哪个决策是孤立的**：分层（1）决定了事务代码放哪，手写 SQL（2）让条件 UPDATE（4、5）写得出来，统一返回（3）让所有失败都有同一张脸，无状态认证（6）让归属校验三行搞定，BigDecimal（8）让账目永远对得上，AI 知识注入（7）让导购不胡说。**设计决策之间是互相支撑的。**

## 10 结语

八个决策可以浓缩成四条"如果重写一遍我依然会这么做"的理由：

1. **能交给数据库的并发控制，绝不自己写锁**（条件 UPDATE、CAS 状态机）；
2. **能用结构消灭的坑，绝不留着靠自觉**（去掉 `ok(String)`、金额只用 BigDecimal）；
3. **能少依赖就少依赖，但要为演进留接口**（手写 XML 不用 MP、`version`/`extra_json` 字段预留、Token 无状态、域分包等着拆微服务）；
4. **每一层都只说一种话**（R 统一返回、域内单向分层、错误码分段）。

项目当前没有单元测试（靠 `scripts/smoke-test.ps1` 黑盒冒烟 9/9）——这是已知的短板，也是你可以立刻下手补强的地方：八个决策里的并发正确性（防超卖、重复取消、金额精确）恰恰是最值得写测试去锁死的部分。

如果你读懂了这篇文章，你就拥有了一个面试可复用、动手可验证的分析框架：**任何设计选择题，都从 背景（问题是什么）→ 设计（怎么解的）→ 优劣（代价是什么）→ 换一种做法（为什么不选别的）四个角度想一遍。** ai-mall 整本代码，不过是这套框架的作文。
