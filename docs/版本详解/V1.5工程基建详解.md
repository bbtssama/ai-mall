## 【易错关键点】（先背这个，全文读完回来再背一遍）

1. **Boot 默认线程池队列无界**（`Integer.MAX_VALUE`）——永远触发不到拒绝策略，请求堆积最终 OOM；生产必须显式**有界队列+明确拒绝策略**（[线程池](V1.5工程基建详解【知识词典】.md#线程池)）。
2. **Tomcat 线程池复用，MDC 不清理会串号**——上一个请求的 traceId 残留到下一个请求；Filter 必须 `finally { clear() }`（[MDC](V1.5工程基建详解【知识词典】.md#mdc)）。
3. **异步线程读不到 MDC**——ThreadLocal 线程隔离，换线程就丢；用 [TaskDecorator](V1.5工程基建详解【知识词典】.md#taskdecorator) 在提交时复制、执行时设置、执行完清理（[TransmittableThreadLocal](V1.5工程基建详解【知识词典】.md#ttl) 进阶知道即可）。
4. **Flyway 对存量库要 `baseline-on-migrate`**——已有 V1 表的库首次跑 Flyway 会因"非空库无 baseline"拒绝执行（[baseline](V1.5工程基建详解【知识词典】.md#baseline-on-migrate)）。
5. **迁移只增不改**——已执行的 SQL 永不修改（checksum 校验会拒绝启动）；改表结构=新增一条 V<N>__ 迁移（[checksum](V1.5工程基建详解【知识词典】.md#checksum)）。
6. **上传安全三件套缺一不可**——MIME 白名单（不是黑名单）+ UUID 重命名（防[路径穿越](V1.5工程基建详解【知识词典】.md#路径穿越)/覆盖）+ 大小限制（[上传安全](V1.5工程基建详解【知识词典】.md#上传安全三件套)）。
7. **本地文件返回要用 `Content-Disposition: attachment` 或受限目录**——上传 `.html` 含 JS 直接 inline 打开=存储型 XSS（[存储型 XSS](V1.5工程基建详解【知识词典】.md#存储型-xss)）。
8. **mock 静态方法用 `Mockito.mockStatic`**——StpUtil.getLoginIdAsLong() 是静态调用，普通 mock 注入不进去（[mockStatic](V1.5工程基建详解【知识词典】.md#mockstatic)）。
9. **CallerRuns 是"反压"不是失败**——队列满时提交线程自己执行，天然减速上游；Abort 才是快速失败（[拒绝策略](V1.5工程基建详解【知识词典】.md#拒绝策略)）。
10. **IO 密集型线程数 > CPU 核数**——线程大部分时间在等 IO（查库/调 AI），切换成本换吞吐值得（[IO 密集](V1.5工程基建详解【知识词典】.md#io-密集-vs-cpu-密集)）。
11. **可降级是本项目一以贯之的设计哲学**——storage 默认 local、voice 降级 Edge-TTS、V2 的 MQ 降级线程池、V3 的 Redis 降级 DB——**任何中间件都不是启动的先决条件**（[可降级](V1.5工程基建详解【知识词典】.md#可降级设计)）。

# 第 0 章 为什么要 V1.5：玩具与能上线的分界线

## 0.1 先看三个"真实事故场景"

**场景一：凌晨两点，用户说"下单失败"，你翻日志——**

```
ERROR ... NullPointerException
ERROR ... AI 服务暂时不可用
INFO  ... 订单创建成功     ← 这三条是谁的请求？什么顺序？互相有关吗？
```

成千上万行日志交织，没有任何字段能把"同一个请求"的日志串起来。你修不了 bug，因为你**看不见事故现场**。（→ 第 2 章 [traceId](V1.5工程基建详解【知识词典】.md#traceid)）

**场景二：你在新机器克隆项目，跑起来报"Table 't_user' doesn't exist"——**

同事手工改过自己库的表结构（加了个字段），没告诉任何人。SQL 脚本是最新的吗？谁的库是"对的"？数据库的**真相**不存在了。（→ 第 1 章 [Flyway](V1.5工程基建详解【知识词典】.md#flyway)）

**场景三：图片都存在应用目录 `./uploads/`，周三磁盘满了，整个后端挂了——**

静态资源（图片）和运行时数据（日志/编译产物）混在一起；想迁移到对象存储？代码里 20 处 `new File("./uploads/...")`，改不动。（→ 第 3 章 [对象存储抽象](V1.5工程基建详解【知识词典】.md#对象存储抽象)）

## 0.2 V1.5 的答案：六块拼图

| 拼图 | 解决哪个事故 | 一句话 |
|---|---|---|
| [Flyway](V1.5工程基建详解【知识词典】.md#flyway) | 场景二 | 数据库结构有版本历史，真相唯一 |
| [traceId](V1.5工程基建详解【知识词典】.md#traceid) 三件套 | 场景一 | 每个请求一根线，串起全链路日志 |
| [对象存储抽象](V1.5工程基建详解【知识词典】.md#对象存储抽象) | 场景三 | 图片存储可插拔：本地↔MinIO 零改业务 |
| [线程池](V1.5工程基建详解【知识词典】.md#线程池) | V2 审核异步的前置 | 有界+反压，拒绝 OOM |
| 单元测试 | "改一处崩三处" | 守住钱（订单/扣库存）和门（鉴权） |
| Compose+CI | "我机器上能跑" | 一键起环境，每次推送自动验证 |

## 0.3 设计总原则：可降级、可插拔

V1.5 确立的原则贯穿后续所有版本：**任何中间件都不是应用启动的先决条件**——

```
storage: 默认 local（零依赖），配了 minio 才用 MinIO
voice:   本机 VITS 不可用 → Edge-TTS        （V1）
MQ:      RabbitMQ 不可用 → 线程池降级        （V2）
Redis:   不可用 → 降级走 DB                  （V3）
```

> 💡 **心智模型**：基建不是"加东西"，是**给 V1 这台裸机装仪表盘（traceId）、装刹车（线程池/测试）、装标准接口（storage 抽象）**。仪表盘让你看见问题，刹车让问题不失控，标准接口让未来的升级（V2 的 MQ、V3 的 Redis）不必大动干戈。**V1.5 的每一块都能回答"V2/V3 哪里直接用到了它"**——这是"业务驱动演进"反过来的运用：基建也讲投资回报。

# 第 1 章 Flyway：数据库版本管理

> 核心机制：[Flyway](V1.5工程基建详解【知识词典】.md#flyway) · [迁移](V1.5工程基建详解【知识词典】.md#迁移migration) · [baseline-on-migrate](V1.5工程基建详解【知识词典】.md#baseline-on-migrate) · [checksum](V1.5工程基建详解【知识词典】.md#checksum)

## 1.1 问题驱动：没有它会怎样

V1 的做法：`sql/init.sql` 一个手工执行的建表脚本。三宗罪：
- **漂移**：每个人手工执行，有人改了自己的库没同步脚本——脚本与真实库的差异随时间扩大；
- **不可回溯**：字段为什么从 VARCHAR(50) 改成 (100)？什么时候改的？没有历史；
- **新环境搭不起来**：init.sql 是"最终态快照"，但如果线上库是三个版本前建的，中间的 ALTER 没有记录。

**本质问题：数据库结构没有"版本"概念，也没有"真相唯一"的仲裁者。**

## 1.2 Flyway 怎么工作（5 分钟原理）

比喻：**游戏的存档系统**——每次过关自动存档（执行迁移并记录版本号），读档时逐个比对"哪几关还没打"（对比 flyway_schema_history 表与迁移目录），只补打缺的。

```
backend/src/main/resources/db/migration/
├── V1__init.sql           ← V1 的 10 张表
├── V2__content_and_rag.sql
└── V3__pay_and_drop.sql
```

> **注（当前仓库状态，V5 后期补记）**：上面这个目录是 V1.5 当时的快照，只为演示 Flyway 的比对逻辑。
> 现在的迁移目录已有 **5 个文件**：`V1__init` / `V2__content_and_rag` / `V3__pay_and_drop` /
> `V4__payment_order_unique`（只加唯一索引）/ `V5__note_audit_version`（加 `t_note.audit_version`
> + 把 `t_audit_record` 的唯一键改成 4 列）。**表数仍是 24**——V4 / V5 都不建表，
> 正好是"迁移只增不改"这条纪律的两次实践。

启动时 Flyway：
1. 查 `flyway_schema_history` 表（没有就建）——已执行过 V1、V2；
2. 扫描 migration 目录，发现 V3 没执行过；
3. **按版本号顺序执行** V3，成功后插入一行记录（版本号、描述、执行时间、[checksum](V1.5工程基建详解【知识词典】.md#checksum)）；
4. 全部执行完才放行应用启动（启动即校验，**结构永远与代码同步**）。

## 1.3 本项目的接入：一个关键决策（面试高频）

V1 已经存在、库里有 10 张表——直接跑 Flyway 会怎样？**报错拒绝执行**：非空库且没有 baseline 记录，Flyway 不知道"这个库处于什么版本"，不敢乱动。

解法（`application.yml`）：

```yaml
spring:
  flyway:
    enabled: true
    baseline-on-migrate: true      # ★ 首次对存量库执行时，先打 baseline（默认版本 0）
    baseline-version: 0            # baseline=0，V1 迁移被视为"未执行"会被跑——
                                   # 但 V1__init.sql 全部 CREATE TABLE IF NOT EXISTS（幂等），安全
    locations: classpath:db/migration
```

**为什么 V1 迁移敢重跑**：所有建表都写了 `IF NOT EXISTS`——存量库已建过表，重放无害；全新库则正常建表。**"迁移幂等"与"baseline 接存量"配合，新旧库都能接管**。这个决策的完整链条（为什么不从 V2 开始编号？——因为全新环境也需要 V1 的表，V1 迁移必须存在且可重放）面试值得完整讲一遍。

## 1.4 迁移纪律（团队约定）

- **只增不改**：已执行的 SQL 永不修改——Flyway 启动时校验 checksum，改了就拒绝启动（保护"历史不可篡改"）；
- **改表 = 新迁移**：`V4__add_xxx.sql` 写 ALTER；
- **命名**：`V<版本>__<双下划线><描述>.sql`（版本号全局递增，别用日期分叉）；
- **失败处理**：迁移执行到一半失败会留下 `success=0` 的记录，下次启动报 "Detected failed migration"——修复 SQL 后 **DELETE 那行失败记录**再启动（DDL 多数不支持回滚，人工裁决）。

# 第 2 章 traceId 全链路：日志从"一团乱麻"到"一根线"

> 核心机制：[traceId](V1.5工程基建详解【知识词典】.md#traceid) · [MDC](V1.5工程基建详解【知识词典】.md#mdc) · [ThreadLocal](V1.5工程基建详解【知识词典】.md#threadlocal) · [TaskDecorator](V1.5工程基建详解【知识词典】.md#taskdecorator) · [logback pattern](V1.5工程基建详解【知识词典】.md#logback-pattern)

## 2.1 问题驱动：日志为什么"串不起来"

100 个并发请求的日志交织在同一个文件里。要把"一个请求"的日志挑出来，你需要每行日志带同一个**请求标识**。0 基础的做法是给每个方法加 `log.info("traceId={} ...", traceId)` 参数——侵入所有方法签名，灾难。

**[MDC](V1.5工程基建详解【知识词典】.md#mdc)（Mapped Diagnostic Context）** 解决它：日志框架（SLF4J/Logback）自带的"线程储物柜"——你在任意代码里往 MDC 塞个值，**同一个线程后续所有 log 语句的 pattern 里都能自动打出它**，方法签名零改动。

## 2.2 三件套总览（先背结构）

```
① TraceIdFilter（入口）：请求进来 → 生成/沿用 traceId → 存 MDC → 响应头回传 → finally 清理
② MdcTaskDecorator（跨线程）：任务提交时快照 MDC → 执行线程设置 → 执行完清理
③ logback pattern（输出）：[%X{traceId}] 占位符——%X 就是"从 MDC 取"
```

## 2.3 入口：TraceIdFilter 逐行精读

```java
protected void doFilterInternal(HttpServletRequest request,
                                HttpServletResponse response,
                                FilterChain filterChain) throws ServletException, IOException {
    String incoming = request.getHeader("X-Trace-Id");
    // 上游（网关/其他服务）传了就沿用，否则自己生成 —— 为 V4 微服务链路追踪预留
    String traceId = StringUtils.hasText(incoming) ? incoming : TraceIdContext.generate();

    TraceIdContext.set(traceId);                    // 存进 MDC
    response.setHeader("X-Trace-Id", traceId);      // 响应头回传（前端报障时直接贴 traceId）
    try {
        filterChain.doFilter(request, response);    // 放行：后续所有日志自动带 traceId
    } finally {
        TraceIdContext.clear();                     // ★ 必须清理！
    }
}
```

**为什么是 Filter 不是 Interceptor**（面试高频）：Filter 是 Servlet 规范层，**最先执行、最后退出**，能覆盖包括静态资源在内的所有请求；Interceptor 在 Spring MVC 层，DispatcherServlet 之后才介入——越早设置 MDC，覆盖的日志越全。

**为什么 finally 必须清理**：Tomcat 线程池**复用线程**——这个请求结束，线程归还池子，下个请求拿到的还是这个线程；不 clear 的话**下个请求的日志带着上个请求的 traceId**（串号）——排查事故时被误导比没有 traceId 更糟。

**为什么响应头也回传**：用户报障时"我刚才下单失败了"→ 客服要 traceId → 用户从浏览器开发者工具的响应头里复制 `X-Trace-Id` 贴给你 → 精准定位。**可观测性是双向的：日志里能查到，用户手里拿得到**。

## 2.4 坑一：异步线程里 traceId 丢了（本章最重）

**事故现场**：V2 的审核降级走线程池，日志里审核线程的日志**没有 traceId**——

```
[traceId=abc123] 发布笔记 service 层日志          ← Web 线程：有
aimall-async-1    审核完成 noteId=9527           ← 池线程：没有！
```

**根因**：MDC 底层是 [ThreadLocal](V1.5工程基建详解【知识词典】.md#threadlocal)——**线程隔离**的储物柜。Web 线程存的 traceId，池线程天然看不见（这是 ThreadLocal 的特性不是 bug——隔离正是它存在的意义）。

**解法：[MdcTaskDecorator](V1.5工程基建详解【知识词典】.md#taskdecorator)**——线程池的"任务包装器"，在任务的三个生命周期点做手脚：

```java
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        // ① 提交时刻（Web 线程）：快照当前 MDC —— 此时还能拿到 traceId
        Map<String, String> context = MDC.getCopyOfContextMap();
        return () -> {
            // ② 执行时刻（池线程）：把快照设置进本线程
            Map<String, String> previous = MDC.getCopyOfContextMap();
            if (context != null) MDC.setContextMap(context);
            try {
                runnable.run();
            } finally {
                // ③ 执行完毕（池线程）：恢复原状（池线程也复用，同样防串号！）
                if (previous != null) MDC.setContextMap(previous);
                else MDC.clear();
            }
        };
    }
}
```

三个时刻缺一不可：①不快照=传不过去；②不设置=池线程没值；③不恢复=池线程串号（与 Filter 的 finally 同一个道理——**凡是池化的线程，离开时都要还一个干净的储物柜**）。

进阶认知（知道即可）：跨**线程池传递**（A 池提交给 B 池）时 TaskDecorator 会失效（快照发生在 A 的 decorate，但 A 里提交任务时 MDC 已经没值了）——阿里的 [TransmittableThreadLocal](V1.5工程基建详解【知识词典】.md#ttl)（TTL）通过"注册中心+Agent 字节码"解决；本项目单层池，Decorator 够用。

## 2.5 logback pattern：让 traceId 真的打出来

MDC 存了值还要 pattern 里"取"：

```xml
<pattern>%d{HH:mm:ss.SSS} [%thread] [%X{traceId:-NONE}] %-5level %logger{36} - %msg%n</pattern>
```

`%X{traceId}` = 从 MDC 取 key 为 traceId 的值；`:-NONE` 是缺省（没值时打 NONE 而不是空——空会让日志列错位）。滚动策略：50MB/文件、30 天、总 2GB 上限——**日志不治理，磁盘会被日志写满**（又一个真实事故源）。

## 2.6 Actuator：给运维一双眼睛

`/actuator/health`（存活/就绪探针，V3 里 redis 健康自动并入）、`/actuator/info`。K8s/docker 的重启判据就靠 health——**没有健康检查的容器编排是盲飞**。

## 本章动手作业

1. 任意接口请求，从响应头拿 X-Trace-Id，`grep '该值' logs/aimall.log`——同一请求的所有日志一根线。
2. 发布一篇笔记（走线程池审核），确认 `aimall-async-` 线程的日志**也带同一个 traceId**（Decorator 生效）。
3. 把 Filter 的 finally clear 注释掉，连发两个请求——第二个请求日志带的是第一个的 traceId（亲手复现串号，再改回来）。
4. 思考：为什么 MdcTaskDecorator 的 finally 里要"恢复 previous"而不是简单 clear？（答：池线程可能有池自己设的上下文——粗暴 clear 可能抹掉别人的东西；恢复原状是最安全的还原。）

# 第 3 章 对象存储抽象：本地/MinIO 双实现 + 上传安全

> 核心机制：[对象存储抽象](V1.5工程基建详解【知识词典】.md#对象存储抽象) · [上传安全三件套](V1.5工程基建详解【知识词典】.md#上传安全三件套) · [路径穿越](V1.5工程基建详解【知识词典】.md#路径穿越) · [存储型 XSS](V1.5工程基建详解【知识词典】.md#存储型-xss) · [预签名 URL](V1.5工程基建详解【知识词典】.md#预签名-url) · [懒初始化](V1.5工程基建详解【知识词典】.md#懒初始化)

## 3.1 问题驱动：本地存图片的三宗罪

V1 的 `t_message.extra_json` 存 base64、图片散落本地目录——①磁盘与备份治理混乱（静态资源混进运行时数据）；②无法迁移（20 处 `new File` 硬编码）；③没有 URL 语义（前端只能靠后端接口转一手）。

## 3.2 抽象层设计

```java
public interface StorageService {
    StoredObject store(MultipartFile file, String dir);   // 存
    String url(String objectKey);                          // 取 URL
    String newObjectKey(String dir, String originalFilename); // 生成对象键
}
```

两个实现：`LocalStorageService`（默认，文件落本地、URL 走 `/files/**` 静态映射）与 `MinioStorageService`（S3 兼容对象存储，[预签名 URL](V1.5工程基建详解【知识词典】.md#预签名-url) 直传直取）。`StorageConfig` 按配置二选一装配——与 V2 的 EmbeddingClient、V3 的 PayChannel 同族（**可插拔家族第一棒**，面试可串成设计哲学）。

**MinIO 的[懒初始化](V1.5工程基建详解【知识词典】.md#懒初始化)**：不在构造时连 MinIO（连不上就启动失败），第一次使用时才建 client——"配了 minio 但没启动容器"不影响应用启动，用到才报错。可降级原则的又一处落地。

## 3.3 上传安全三件套（红线）

上传接口是**公网写入点**，攻击面最大。三件套（FileRestController）：

**① MIME 白名单**——只允许 image/png、jpeg、gif、webp。为什么白名单不是黑名单：黑名单永远列不全（.svg 含脚本、.html 含 JS、双扩展名、大小写变体……）；白名单"不在名单里=拒绝"天然完备。同时校验扩展名与 Content-Type（两者都要过）。

**② UUID 重命名**——`newObjectKey` 生成 `dir/uuid.ext`：
- 防[路径穿越](V1.5工程基建详解【知识词典】.md#路径穿越)：用户上传文件名写 `../../etc/cron.d/evil`，拼路径时逃出上传目录；UUID 键完全忽略原始文件名，穿越无从谈起；
- 防覆盖：猜到别人的对象键就覆盖别人的图。

**③ 大小限制**——`spring.servlet.multipart.max-file-size=10MB`；不限制=一个 10GB 文件写满磁盘的 DoS。

**附加一刀（XSS）**：即使白名单了图片，本地存储的 `/files/**` 静态映射要防"上传 html 直接入内联打开"——白名单已挡掉 html，纵深防御再加 [Content-Disposition](V1.5工程基建详解【知识词典】.md#content-disposition) 或独立域名（浏览器同源策略隔离）。**上传的每个文件都是不可信输入**——这句话是三件套的总纲。

## 本章动手作业

1. 上传一张图 → `uploads/` 下出现 uuid 命名的文件；URL 能访问。
2. curl 伪造 `Content-Type: image/png` 但文件体是文本 → 拒绝（魔法字节/内容校验）。
3. 上传文件名带 `../` 的文件 → 落盘仍是 uuid 键（穿越无效实证）。
4. 配置切 minio 但不起容器 → 应用照常启动（懒初始化）；起 minio 后上传走 MinIO（预签名 URL 语义）。

# 第 4 章 线程池：从 Boot 默认的 OOM 陷阱到有界+反压

> 核心机制：[线程池](V1.5工程基建详解【知识词典】.md#线程池) · [拒绝策略](V1.5工程基建详解【知识词典】.md#拒绝策略) · [CallerRuns](V1.5工程基建详解【知识词典】.md#callerruns) · [IO 密集 vs CPU 密集](V1.5工程基建详解【知识词典】.md#io-密集-vs-cpu-密集)

## 4.1 先撞南墙：Boot 默认线程池是颗地雷

`@Async` 不配线程池时用 Boot 的 `applicationTaskExecutor`——**队列容量 Integer.MAX_VALUE**（无界）。后果链条：

```
提交速度 > 执行速度 → 队列无限增长 → 堆内存耗尽 → OOM → 全站挂
```

更阴险的是它**永不触发拒绝策略**——没有报错、没有日志，直到 OOM 前一刻系统看起来"一切正常"。生产代码**必须显式配置有界池**。

## 4.2 AsyncConfig 逐参数精读

```java
@Bean(name = {"taskExecutor", "appExecutor"})
public ThreadPoolTaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);        // 常驻 4 线程
    executor.setMaxPoolSize(16);        // 上限 16
    executor.setQueueCapacity(200);     // ★ 有界队列 200
    executor.setThreadNamePrefix("aimall-async-");   // 日志里一眼认出池线程
    executor.setTaskDecorator(new MdcTaskDecorator()); // traceId 跨线程（第 2 章）
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    // 优雅停机：等任务跑完再关
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(30);
    return executor;
}
```

**参数怎么定（面试必问）**：
- **4/16 的依据**：本应用 IO 密集（查库/调 AI/写文件），线程大部分时间在等 IO——[IO 密集型线程数可以大于 CPU 核数](V1.5工程基建详解【知识词典】.md#io-密集-vs-cpu-密集)（切换成本换吞吐）。经验公式起点：CPU 核数 × 2 ~ × 4，压测再调。
- **队列 200**：给突发留缓冲但不无限——超出即触发拒绝策略，**宁可快速降速也不要无限堆积**。
- **[CallerRunsPolicy](V1.5工程基建详解【知识词典】.md#callerruns)**：队列满时**让提交任务的线程自己执行**——Web 线程被迫跑任务→它处理后续请求的速度自然变慢→提交速率自动下降。这叫**反压（backpressure）**：不是拒绝而是把压力传导回上游、让上游自然减速。对比 AbortPolicy（抛异常快速失败）——按业务选：能减速的选 CallerRuns，不能拖的选 Abort。

**两处通用范式回收**：有界+等待上限（V3 Redis 连接池同款）；优雅停机（与 voice 的 VITS 进程 destroy 同款）——**资源治理的思路是通用的**。

## 本章动手作业

1. 写个测试循环提交 1000 个 sleep(100ms) 的任务，观察：前 4 个立即执行（core）、后续 200 个进队列、再往后触发 CallerRuns（提交线程也慢下来）。
2. 把队列改 Integer.MAX_VALUE 重跑——内存监控看队列堆积（复现"无声 OOM 前夜"，改回）。
3. 思考：AI 审核任务用 CallerRuns 还是 Abort 合适？（答：CallerRuns——审核可延迟不可丢；若是用户实时等待的任务（如导出报表同步下载）则 Abort+提示重试。）

# 第 5 章 单元测试：守住钱和库存

> 核心机制：[mockStatic](V1.5工程基建详解【知识词典】.md#mockstatic) · [@TempDir](V1.5工程基建详解【知识词典】.md#tempdir) · [测试金字塔](V1.5工程基建详解【知识词典】.md#测试金字塔)

## 5.1 为什么第一批测试是它们

测试的优先级 = **出事故的代价**。钱（订单扣库存）、门（鉴权越权）、文件（上传安全）、跨线程（MDC）——这四类错了是资损/安全/排查灾难；页面样式错了顶多是体验问题。**测试策略是风险管理，不是覆盖率数字**（[测试金字塔](V1.5工程基建详解【知识词典】.md#测试金字塔)：大量快的单测+少量关键链路集成测试）。

V1.5 的 15 个用例（OrderServiceImplTest 扣库存 CAS/状态机/越权 404、LocalStorageServiceTest 上传安全、MdcTaskDecoratorTest 跨线程传递、PageQueryTest）+ V3 的 PaymentServiceTest 5 例——**每个测试对应一类事故**，写在测试类的 javadoc 里。

## 5.2 关键技巧：mockStatic 钉住 StpUtil

业务代码里到处是 `StpUtil.getLoginIdAsLong()`（Sa-Token 静态调用）——单测没有登录态，怎么办？普通 `@Mock` 注入不进静态调用。**`Mockito.mockStatic`**：

```java
try (MockedStatic<StpUtil> mocked = Mockito.mockStatic(StpUtil.class)) {
    mocked.when(StpUtil::getLoginIdAsLong).thenReturn(42L);   // 钉死"当前用户=42"
    // ... 执行被测方法：内部所有 StpUtil 调用都返回 42
    mocked.verify(StpUtil::getLoginIdAsLong);                  // 还能验证调用
}
```

为什么叫"钉"：mockStatic 只在 try-with-resources 作用域内生效，出域自动卸载（不影响其它测试）——**静态 mock 是全局副作用，必须严格限定作用域**。有了它，Service 层测试不需要启动容器、不需要登录流程，毫秒级跑完。

**纯内存原则**：CI 跑 `mvn test` 不需要 MySQL/Redis/RabbitMQ——Mapper 被 mock、StpUtil 被钉、文件用 [@TempDir](V1.5工程基建详解【知识词典】.md#tempdir)（JUnit 自动建临时目录、测试完自动删）。**测试依赖外部环境=测试不可靠**（环境挂了测试也红，你分不清是代码错还是环境错）。

## 本章动手作业

1. `mvn test` 全绿，观察总耗时（应 <10 秒，纯内存）。
2. 故意把 OrderServiceImplTest 的库存断言改错跑一次——看失败信息能否定位"哪类事故没守住"（体会测试的"事故描述"价值），改回。
3. 思考：为什么不给 ProductService.pageOnSale 写测试？（答：可以写但优先级低——列表查错了是体验问题不是资损；测试精力按事故代价分配。）

| 问题 | 一句话答案 |
|---|---|
| 为什么要 Flyway | 数据库结构纳入版本管理，真相唯一；启动即校验，代码与结构永不脱节 |

| 症状 | 原因 | 处置 |
