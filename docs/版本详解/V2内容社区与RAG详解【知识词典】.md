## 一、内容社区与 Feed 流

### UGC
**一句话：用户生成的内容（User Generated Content）——笔记/评论/弹幕，与 PGC（平台/专业生成）相对。**

比喻：餐厅的"顾客留言墙"（UGC）vs 菜单（PGC）——留言墙零成本扩张但需要管理（审核），菜单精致但产能有限。

原理展开：UGC 是双刃剑：带来内容生态（网络效应：用户越多内容越多、内容越多用户越多），也带来审核成本与法律风险（违规内容由平台担责）——这正是 V2 引入 AI 审核+MQ 的业务出发点。判断一个"内容功能"值不值得做，先问 UGC 的量与风险是否匹配治理能力。
→ 返回[主文档 0.1](V2内容社区与RAG详解.md#01-你已经是内容社区的资深用户)

### UGC 语料
**一句话：把用户笔记当作 RAG 的知识库素材——回答"说明书答不了的问题"的唯一来源。**

比喻：官方说明书是"商品的自述"，用户笔记是"旁人的证词"——自述只说好话，证词才有"戴久了耳朵疼"这种真话。

原理展开：官方说明书答参数（"IPX5 防水"），UGC 答体验（"戴着跑步出汗没坏""通勤地铁开降噪世界安静"）——**体验类问题只有 UGC 语料能答**，这是本项目 RAG 不可替代的价值锚点，也是"种草社区+RAG"互相成就的业务逻辑（社区为 RAG 供语料，RAG 让笔记的价值兑现）。纯电商项目抄不走这套设计——它没有语料来源。
→ 返回[主文档 5.2](V2内容社区与RAG详解.md#52-立边界结构化-vs-非结构化说反就是原理性错误)

### 种草
**一句话：通过真实体验分享激发他人购买欲的内容行为（小红书核心模式）。**

比喻：朋友说"这个真好用你买吧"（种草）vs 电视广告"它能让你更强"（硬广）——前者可信因为利益无关，后者被免疫因为利益相关。

原理展开：技术映射：`t_note_product`（笔记关联商品）是"种草"的数据化——内容与交易的接缝，读者点一下跳商品页。没有它，内容社区和商城是两张皮（很多练手项目的通病）；有了它，才有"[内容飞轮](#内容飞轮)"的变现一环。
→ 返回[主文档 1.1](V2内容社区与RAG详解.md#11-全景10-张表一张图)

### Feed 流
**一句话：信息流——按时间或热度排序、支持无限下滑的内容列表。**

比喻：食堂打饭窗口的菜品陈列——按"刚出锅"（最新）或"卖得最火"（热度）排，你端着盘子一路走一路挑，挑到哪算哪（无限刷），没人让你"直接跳到第 50 个菜"。

原理展开：Feed 的两个技术内核都在本项目落地：[游标分页](#游标分页)（无限刷的底层）与 [N+1 攻防](#n1-问题)（每屏 20 条的组装效率）。排序策略（最新/热度）对应产品形态：最新=社区感（人人有曝光）、热度=消费感（爆款聚集）——本项目两种都做，前端可切换。
→ 返回[主文档第 2 章](V2内容社区与RAG详解.md#第-2-章-feed-流上游标分页干掉-offset-深分页)

### 瀑布流
**一句话：卡片不等高、按列排布、随滚动加载的信息流布局（小红书/Pinterest 标配）。**

原理展开：实现比想象简单：CSS `column-count: 4`（多列布局）+ `break-inside: avoid`（卡片不被跨列拆断），配"加载更多"按钮触发游标翻页——**布局是 CSS 的事，数据是游标分页的事**，两者解耦。图片高度不一是瀑布流的视觉特征，也是它的实现前提（等高就成了网格）。
→ 返回[主文档 0.1](V2内容社区与RAG详解.md#01-你已经是内容社区的资深用户)

### 游标分页
**一句话：用"上一页最后一条的排序值"做过滤条件（WHERE x < cursor）翻页，代替 OFFSET 扫描丢弃。**

比喻：读书用书签（记住读到哪了）——下次从书签处继续；而不是每次都从第 1 页数起数到第 300 页（OFFSET 的做法）。

原理展开：OFFSET 的死刑判决：`LIMIT 100000, 20` 要**扫描并丢弃**前 10 万行，翻得越深越慢——产品上等于惩罚深度用户。游标分页：`WHERE id < #{cursorId} ORDER BY id DESC LIMIT 20` 走主键索引直接定位，**深度无关、开销恒定**。代价：不能跳页（游标只有"下一个"语义）——Feed 天然连续翻无所谓，后台管理要跳页用 offset，**按场景选型，不是谁替代谁**。这个"承认边界"的表述比"游标更优"的绝对化说法面试更加分。

代码对应：`NoteMapper.selectPage` + `NoteQuery.cursorId`。
→ 返回[主文档 2.1-2.2](V2内容社区与RAG详解.md#21-先撞南墙limit-100000-20-有多慢)

### 二元组游标
**一句话：当排序键可能重复（并列）时，游标必须是（排序键, 唯一键）复合条件，否则漏数据。**

比喻：按"比赛积分"排名次——积分并列的人怎么分先后？规则必须补一条"积分相同看编号"。只按积分做"下一位"的锚点，并列的一批人就全丢了。

原理展开：按 `hot_score DESC, id DESC` 排序时若游标只用 hot_score：`WHERE hot_score < 999` 漏掉所有 999 分的其它笔记；只用 id（热度序下 id 无序）：漏"热度更高但 id 更小"的。正确写法：`(hot_score < #{h} OR (hot_score = #{h} AND id < #{cursorId}))`——先比热度、平了比 id（id 唯一保证全序，"下一个"永远有定义）。**通用规律：排序键 N 列，游标就是 N 元组，最后一列必须是唯一键**。这是游标分页最容易讲错/写错的细节。

代码对应：`NoteMapper.xml` pageWhere 的 otherwise 分支。
→ 返回[主文档 2.3](V2内容社区与RAG详解.md#23-二元组游标本项目最容易讲错写错的细节)

### N+1 问题
**一句话：列表接口对每条记录再发一次关联查询（1 次列表 + N 次关联）导致 SQL 数爆炸。**

比喻：班主任要全班 50 人的家长电话——错误做法：每次只问一个学生（50 趟）；正确做法：发一张表让所有人一次填完（1 趟，批量）。

原理展开：20 篇笔记 ×（作者+封面+标签+商品+互动态）= 101 条 SQL；每条 ~1ms 网络往返，RT 直接爆炸。对策：**批量 IN 查询 + 内存分组组装**（groupingBy / contains）——无论页大小固定 5 条 SQL。进阶认知：N+1 的本质是"把集合操作退化成了逐条操作"，ORM 的懒加载（JPA 的 fetch lazy、MyBatis 嵌套 select）是最常见的诱发点——本项目 MyBatis 全显式 SQL，N+1 只会来自自己写的循环。

代码对应：`NoteServiceImpl.assembleList`（5 条批量 SQL 的完整实现）。
→ 返回[主文档 3.1](V2内容社区与RAG详解.md#31-n1-攻防列表接口优化的第一答)

### 幂律分布
**一句话：少数爆款获得极高互动、大多数内容是长尾——社交内容的天然形态。**

比喻：城市人口——几个超级城市（爆款）吸纳巨量人口，绝大多数城镇（长尾）人口稀少；不存在"所有城市人口一样多"的国家。

原理展开：为什么模拟数据必须服从它：均匀假数据（每篇 200 赞）没有梯度——热门榜排不出名次、爆款与长尾无差异、推荐没有"热门"可选。生成策略：10% 爆款（800~5000 赞）+ 90% 长尾（3~300）。相关联的还有"口碑分布"（55% 含缺点段）——全好评语料没有信息量，RAG 检索不出真实感。**数据的"分布形态"本身就是设计对象**，这是模拟数据章的核心思想。
→ 返回[主文档第 11 章](V2内容社区与RAG详解.md#第-11-章-模拟数据让-500-篇笔记长得像真的)

### 热度公式
**一句话：把多维度互动加权合成一个可排序的分数——like×3 + collect×5 + view×1。**

比喻：考试的综合分——平时作业（浏览，量大权重低）+ 小测（点赞）+ 期末（收藏，最强意图权重最高）。

原理展开：权重设计的业务依据：收藏=强购买意图（"我要买/要再看"）、点赞=弱认可、浏览=免费。互动发生时重算即时回写（V2，DB）；V3 升级 Redis zset（ZADD 热度榜实时排序）。面试追问"为什么不用时间衰减"——真实热度公式通常加时间衰减（72 小时前的 1000 赞不如今天的 500 赞）；本项目数据量小、笔记周期短，未加——知道这是简化即可。
→ 返回[主文档 4.2](V2内容社区与RAG详解.md#42-对策唯一索引兜底不靠代码)

### 软删除
**一句话：用状态标记（OFFLINE）代替物理 DELETE，数据可追溯可恢复。**

比喻：档案室的"作废"章——文件还在柜子里（可查可恢复），只是标记不再流通；碎纸机（物理删除）才是真的没了。

原理展开：笔记下架用 `UPDATE status='OFFLINE'`：内容合规可追溯（违规内容删了证据也没了）、用户误操作可恢复、外键引用（点赞/收藏/审核流水）不断裂。配套动作：下架必须联动移除 RAG 索引（`ragIndexService.remove`）——否则检索会召回已下架内容（[脏语料](#脏语料)）。
→ 返回[主文档 1.2](V2内容社区与RAG详解.md#12-三个值得单独讲的设计决策)

## 二、互动与幂等

### 唯一索引幂等
**一句话：用 UNIQUE KEY 让数据库物理上拒绝重复数据，把并发正确性交给存储层。**

比喻：电影院座位号唯一——两个人（并发请求）抢同一个座，出票系统（数据库）只认第一个，第二个人拿到的必然是"座位已占"的拒绝，不存在两张同号票。

原理展开：`uk(note_id, user_id)`：同一用户对同一笔记最多一条点赞记录。直接 INSERT，重复时抛 [DuplicateKeyException](#duplicatekeyexception) → 捕获当"已点过"处理。对比"先查后插"：两次并发都查到"没点过"→ 各插一条（[TOCTOU](#toctou)竞态）——**两步逻辑的中间永远有被插队的窗口，唯一索引把"判断+拒绝"焊进了一条原子操作**。这是"幂等三兄弟"（唯一索引/状态机条件更新/version 乐观锁）中最便宜的一个：零额外代码，建表时一个约束搞定。

代码对应：`t_note_like` 的 `uk_note_user` + `NoteServiceImpl.like` 的 catch。
→ 返回[主文档 4.2](V2内容社区与RAG详解.md#42-对策唯一索引兜底不靠代码)

### DuplicateKeyException
**一句话：Spring 对 SQL 唯一键冲突（MySQL error 1062）的统一异常封装（DataAccessException 家族）。**

比喻：Insert 卡在"门禁"上——不是程序错误，是数据库在说"这条已经存在了"。

原理展开：用途：捕获它区分"真的失败"与"重复请求"——幂等实现的信号弹。注意它属于 `DataAccessException` 体系（Spring 把各家数据库错误码翻译成统一异常），所以 catch 它而不是笼统的 Exception——笼统 catch 会把"库挂了"也当成"重复"静默吞掉。业务语义分叉：点赞/收藏捕获后**静默**（重复=已达成）；限量发售捕获后**报"限购"**（重复=业务失败）——同一个异常两种语义，按场景选。
→ 返回[主文档 4.2](V2内容社区与RAG详解.md#42-对策唯一索引兜底不靠代码)

### TOCTOU
**一句话：Time-Of-Check-To-Time-Of-Use——检查与使用之间被并发插队，经典竞态模式。**

比喻：看红绿灯过马路（check：现在是绿灯）——走到路中间（use）时灯变了；看的时候没错，用的时候世界变了。

原理展开：凡是"先查再改"的两步逻辑都有 TOCTOU 窗口：先查后插（点赞插两条）、先查后判再更新（V3 支付回调双过）。解法都是同一族：**把检查与使用合并成一步原子操作**——唯一索引（判断与拒绝在 DB 内一条完成）或条件更新/CAS（判断与写入在一条 UPDATE 内）。识别 TOCTOU 的嗅觉比背解法更值钱：看到两步逻辑就问"这两步之间被插队会怎样"。
→ 返回[主文档 4.1](V2内容社区与RAG详解.md#41-先撞南墙狂点红心会发生什么)

### 丢失更新
**一句话：两个并发写都基于旧值计算，后写者覆盖前写者——一方的更新凭空消失。**

比喻：两人同时编辑同一份在线文档的同一行（没有协同锁）——后保存的人覆盖了先保存的人的修改。

原理展开：反例：`count = SELECT`（都读到 100）→ Java 各自 +1 → 两个 `UPDATE SET count=101`——两次加法只生效一次。对策：`SET count = count + 1`（数据库内计算，行锁串行化）或 CAS（`WHERE count=旧值`）。凡是"读出来算一算再写回去"的代码都要过一遍丢失更新检查。
→ 返回[主文档 4.3](V2内容社区与RAG详解.md#43-计数不丢失原子自增-vs-先读后写)

### 冗余计数
**一句话：把 count(*) 聚合结果冗余成列，列表展示免聚合查询——代价是写路径要维护一致性。**

比喻：教室后墙的"班级人数牌"——不用每次来人都重数全班（count(*)），但要保证进出门时有人更新牌子（写路径维护）。

原理展开：读路径收益：Feed 每屏 20 条展示 like_count，若走 `COUNT(*) FROM t_note_like WHERE note_id=?` × 20 次=聚合灾难；冗余列直接读。写路径成本：增减计数必须与关系表操作**同事务**（否则出现"关系删了计数没减"的永久漂移）。演进：V2 用 DB 原子自增（简单正确）；V3 升 Redis 计数+定时落库（热点写的正解）——**先简单正确，再按压力演进**。
→ 返回[主文档 1.2](V2内容社区与RAG详解.md#12-三个值得单独讲的设计决策)

## 三、RAG 核心

### RAG
**一句话：Retrieval-Augmented Generation（检索增强生成）——先查资料、再回答。**

比喻：开卷考试——不让学霸（模型）背题库，而是发给它一本可以翻的资料（你的语料）；模型负责"读资料组织答案"，检索负责"找到对的那一页"。

原理展开：三步：①检索（从语料库找最相关的 3~5 段）；②增强（把片段塞进 prompt 当参考资料）；③生成（模型基于资料回答，而非凭训练记忆编）。解决了大模型的两大死穴：知识截止（训练后的新知识它不知道）与幻觉（没依据时它编）。本项目落地：语料=说明书+UGC 笔记，检索=Hybrid（双通道），生成=带来源标注回答。

常见追问：*"RAG 和微调的区别？"*——微调改模型的"脑子"（贵、慢、知识固化），RAG 给模型"发资料"（便宜、即时、可撤）；绝大多数企业知识场景 RAG 优先。
→ 返回[主文档 5.1](V2内容社区与RAG详解.md#51-rag-一句话0-基础)

### RAG 的边界
**一句话：RAG 只管非结构化文档（说明书/笔记），不管结构化实时数据（价格/库存走 SQL）——说反就是原理性错误。**

比喻：图书馆（RAG）管"查阅资料"，教务系统（SQL）管"查实时成绩"——你不能去图书馆问"我这次考了几分"，也不能靠教务系统理解"什么是傅里叶变换"。

原理展开：判别式：数据要**精确且实时**（价格、库存、订单状态）→ SQL；问题是**说明性/体验性**（防水吗、戴着疼吗）→ RAG。错配的后果：用 RAG 查价格——语料是快照（改价后 AI 报旧价）且检索是模糊的（可能报隔壁商品价）；用 SQL 答体验——SQL 只能精确匹配关键词，"戴久了舒服吗"没法 WHERE。**这是 V2 全篇第一红线，面试说反基本出局**。
→ 返回[主文档 5.2](V2内容社区与RAG详解.md#52-立边界结构化-vs-非结构化说反就是原理性错误)

### 长上下文 vs RAG
**一句话：模型上下文再大也不能替代 RAG——四个结构性理由：语料动态/首字延迟/权限隔离/成本。**

比喻：家庭药箱 vs 药店——再大的药箱（上下文）也装不下所有药（持续增长的语料）、翻找太慢（延迟）、客人不能看你的私人药（权限）、每次补货全买一遍（成本）。

原理展开：四条逐一：①**语料动态增长**——笔记每天在发，"每次全量塞"今天的 128K 明天就不够；②**C 端首字延迟**——长上下文 [Prefill](#首字延迟) 耗时随长度线性涨，打字机第一字等数秒；③**权限隔离**——检索层可按来源过滤（只检公开笔记），全塞 prompt 没有权限边界；④**成本**——全量 token×对话次数的费用失控。这四条是 2026 年业界共识决策树，面试必背。

常见追问：*"什么场景长上下文反而合适？"*——一次性分析长文档（合同审阅、论文总结）：文档固定、单次交互、无权限分层——此时直接塞比搭 RAG 便宜。
→ 返回[主文档 5.3](V2内容社区与RAG详解.md#53-必考题几百份文档为什么不塞长上下文)

### 语料
**一句话：RAG 检索的知识库素材——本项目的双语料 = 商品说明书（MANUAL）+ 种草笔记（NOTE）。**

比喻：词典的两大来源——官方释义（说明书）与用例摘录（用户笔记）：前者权威但干瘪，后者鲜活但有噪音。

原理展开：双语料设计的意义：说明书答"是什么"（参数、规格），UGC 答"怎么样"（体验、缺点）——两类问题覆盖商品认知的完整光谱。语料治理三原则：①来源唯一（uk(source_type,ref_id)，同来源一份）；②替换语义（更新=删旧写新，防[脏语料](#脏语料)）；③下架联动（内容下线索引同步移除）。
→ 返回[主文档 5.2](V2内容社区与RAG详解.md#52-立边界结构化-vs-非结构化说反就是原理性错误)

### Chunking
**一句话：把长文档切成几百字的小片段——检索按片段做、上下文按片段拼。**

比喻：教科书分章节——你不会为了查一个知识点通读全书，翻到那一节（片段）就够。

原理展开：为什么必须切：①检索粒度——整篇的相似度是"平均的相似度"，细节问题匹配不上；②上下文效率——只把命中的 3~5 片段（几百字）进 prompt，不是整篇几千字；③命中精度——片段级匹配让"找到的那一页"真的是答案所在页。本项目策略：固定 300 字 + 50 字[重叠](#重叠-overlap)——性价比最高的起步方案；进阶（语义切分/父子切片）按需演进。

代码对应：`KnowledgeChunk.CHUNK_SIZE/CHUNK_OVERLAP` 常量 + `RagIndexServiceImpl.split`。
→ 返回[主文档 6.3](V2内容社区与RAG详解.md#63-切片固定长度重叠逐行读-split)

### 重叠 overlap
**一句话：相邻切片保留一段重复内容，防止关键句被从中间切断导致两边语义残缺。**

比喻：两块相邻监控摄像头视野要有一部分交叠——交叠区保证"任何位置至少被一个摄像头完整拍到"，没有盲区也没有"半张脸"。

原理展开：切断的代价演示：`"...跑步出汗也没 | 坏，续航很顶"`——"出汗也没坏"这个关键语义两边都不完整，检索（相似度低）与生成（上下文残缺）双输。步长 = 切片长 - 重叠（300-50=250）：每次前进 250 字、每片取 300 字——数学上保证**任何连续 250 字必完整落在某一片中**。过大的重叠浪费存储与检索预算，过小失去保护——50/300 是工程常用配比。
→ 返回[主文档 6.3](V2内容社区与RAG详解.md#63-切片固定长度重叠逐行读-split)

### Embedding
**一句话：把文本映射成高维向量（如 256/1536 维的浮点数组），语义相近的文本在向量空间里距离近。**

比喻：把每句话变成地图上的一个点——意思相近的话挤在一起（"续航久"和"电池耐用"相邻），无关的话相距很远；算两句话像不像 = 算两个点的距离。

原理展开：三个工程铁律：①**同一系统内所有向量必须来自同一模型**——不同模型的向量空间不可比（A 模型里"猫"在第 3 维有值，B 模型在 第 7 维——跨模型算距离无意义）；②查询与语料用同一模型（同一个"地图"）；③维度恒定（256 维的向量没法和 1536 维的算余弦）。本项目因 [EmbeddingClient](#embeddingclient) 抽象，切换模型=换实现类，但**切换后必须全量重建索引**（旧向量作废）——字典里多说一句这种边界，面试就不慌。
→ 返回[主文档 6.4](V2内容社区与RAG详解.md#64-embeddingclient一个现实约束催生的可插拔设计)

### EmbeddingClient
**一句话：向量化的可插拔抽象——local 哈希（默认，零依赖）与 spring-ai（真实模型）两个平行实现。**

比喻：翻译接口的"机翻"与"人工"两个实现——调用方（业务代码）只说"翻译这句话"，不在乎背后是谁翻的。

原理展开：存在理由是现实约束：DeepSeek 不提供 embedding 接口，硬依赖某 embedding 服务则没配它的机器 RAG 跑不起来。抽象三方法（embed/dimension/name），配置切换（`aimall.rag.embedding=local|spring-ai`），业务零改动——与 StorageService/PayChannel 同族的**可插拔设计哲学第四次出现**。诚实边界：local 实现只捕获字面（见[哈希技巧](#哈希技巧)），语义质量靠 spring-ai 实现——**接口契约先行，质量按预算升级**。
→ 返回[主文档 6.4](V2内容社区与RAG详解.md#64-embeddingclient一个现实约束催生的可插拔设计)

### 余弦相似度
**一句话：两向量夹角的余弦（∈[-1,1]），衡量方向相似性而非长度——文本相似度的标准度量。**

比喻：两支箭的夹角——方向一致（语义相同）夹角为 0 余弦为 1；垂直（无关）为 0；相反（矛盾）为 -1。箭的长短（文本长度）不影响"方向是否一致"。

原理展开：为什么用余弦不用欧氏距离：文本向量化的"模长"常受文本长度影响（长文本向量数值大），而语义看方向——余弦天然免疫长度干扰。工程捷径：向量先 [L2 归一化](#l2-归一化)（都变单位长度）后，**点积=余弦**——省一次模长计算，本项目 embed 出口统一归一化就是这个原因。

代码对应：`HybridRetriever.cosine`（归一化向量的点积）。
→ 返回[主文档 7.2](V2内容社区与RAG详解.md#72-检索主流程hybridretrieverretrieve-逐段精读)

### L2 归一化
**一句话：把向量除以自身模长变成单位向量——之后点积就等于余弦相似度。**

比喻：把所有箭都削成一样长（单位长度）——剩下的差异只剩方向，直接比夹角就行。

原理展开：数学：`v / ||v||` 后 `||v||=1`，则 `dot(a,b) = cos(θ)·||a||·||b|| = cos(θ)`。工程意义：检索时每对向量省两次模长计算（语料数千条×查询一条），在 embed 出口一次性归一化最划算。注意：**必须全库统一**——归一化的与未归一化的混算余弦结果无意义。
→ 返回[主文档 6.4](V2内容社区与RAG详解.md#64-embeddingclient一个现实约束催生的可插拔设计)

### 哈希技巧
**一句话：把文本切成 2-gram、哈希到固定维度桶内累加——零依赖的"穷人版 embedding"（Hashing Trick）。**

比喻：给每个词组发一个编号（哈希），统计"这句话里出现过哪些编号"——两句话共用的编号越多越像。它只认"字面"，不懂"意思"。

原理展开：LocalHashEmbeddingClient 的流程：文本归一化（小写去空白）→ 滑窗切 2-gram → 每个 gram `floorMod(hash, 256)` 落桶 +1 → L2 归一化。**能**：捕获字面重叠（"降噪耳机"与"耳机降噪"共享 4 个 2-gram → 相似）；**不能**：捕获语义（"续航久"与"电池耐用"零 gram 重叠 → 不相似，真实 embedding 模型知道它们是一回事）。两个细节值得讲：①2-gram 与 MySQL ngram **口径一致**——两个通道的"词"粒度对齐，RRF 融合才有意义；②单字文本退化处理（无 2-gram 可切时哈希单字，否则全 0 向量必失配）。

常见追问：*"哈希碰撞怎么办？"*——两个不同 gram 落同桶会互相污染，但 256 维对数千级语料的字面统计，碰撞噪声可接受；维度调大可降低碰撞率。
→ 返回[主文档 6.4](V2内容社区与RAG详解.md#64-embeddingclient一个现实约束催生的可插拔设计)

### 语义鸿沟
**一句话：字面不同但意思相同（"续航久"vs"电池耐用"）——关键词匹配跨不过去，这正是向量检索存在的原因。**

比喻：两国人说"水"和"water"——字面零相似，意思完全一样；只认字面的翻译官（BM25）傻眼，懂含义的翻译官（embedding）没问题。

原理展开：反方向的鸿沟同样存在：字面相似但意思不同（"苹果手机"vs"苹果好吃"）——向量也可能翻车（共享"苹果"的语义）。**两个方向的失配分别对应两类高频问题**（体验类问法多样=语义鸿沟；型号类专有名词=字面失配）——这就是 [Hybrid](#hybrid-检索) 必须双路的理论根源。
→ 返回[主文档 5.4](V2内容社区与RAG详解.md#54-语义鸿沟为什么单靠关键词检索不够)

### BM25
**一句话：基于词频（TF）与逆文档频率（IDF）的经典相关性打分算法——MySQL FULLTEXT / ES 的默认排序依据。**

比喻：判断一道菜和"辣"有多相关——辣椒出现次数（TF：越多越辣）× 辣椒的稀缺度（IDF：在川菜馆里"辣"不稀奇，在甜品店里"辣"字很说明问题）。

原理展开：直觉：一个词在这篇文档出现越多（TF↑）且在其它文档越罕见（IDF↑），这篇文档与该词越相关。它**天然是字面匹配**——词没出现就 0 分，换同义词就失配（[语义鸿沟](#语义鸿沟)）。本项目关键词通道走 MySQL FULLTEXT（内部 BM25 变体打分），向量通道补语义——两路互补。

常见追问：*"TF-IDF 和 BM25 什么关系？"*——BM25 是 TF-IDF 的改良版（TF 加饱和：出现 10 次不比 5 次相关两倍；文档长度归一化），是当下事实标准。
→ 返回[主文档 7.1](V2内容社区与RAG详解.md#71-先想清楚为什么要两路)

### Hybrid 检索
**一句话：关键词（BM25/FULLTEXT）与向量两路并行召回、再融合排序——2026 年 RAG 生产基线。**

比喻：找餐厅——大众点评搜索框（关键词：你写什么搜什么）+ "猜你喜欢"（语义：理解你的偏好）——两个都给你，综合排序；只靠一个总漏掉另一半需求。

原理展开：为什么必须双路：两类死穴场景（精确型号词 BM25 强/向量弱；体验类模糊问法向量强/BM25 弱）在电商**都高频**——单路必有一类问题答不上。业界共识：Hybrid 比单路召回率普遍高 10~20%——"两小时工作量换双保险"。本项目：关键词通道=MySQL ngram FULLTEXT，向量通道=全量内存余弦，融合=[RRF](#rrf)。单通道故障时 `safe()` 降级为另一路托底——可降级传统延伸到检索层。
→ 返回[主文档 7.1](V2内容社区与RAG详解.md#71-先想清楚为什么要两路)

### RRF
**一句话：Reciprocal Rank Fusion——按各路排名倒数（1/(k+rank)）累加融合，只看名次不看分数。**

比喻：两个评委各给选手排名（不给分）——最终名次 = 两个榜单的综合：两边都排前的选手自然最高，只在一边靠前的次之。评委打分标准不同没关系，反正只看名次。

原理展开：三个为什么：①**为什么用排名不用分数**——BM25 可上百、余弦 ∈[0,1]，量纲不同直接加权=拿厘米加斤；RRF 免疫量纲。②**为什么双路命中自动加分**——两路都进前 20 的片段得 1/61+1/61 叠加，天然排最前——**双确认**（字面+语义都说相关）无需显式编码，公式涌现。③**为什么 k=60**——压平第 1 名与第 2 名差距（1/61 vs 1/62），避免单路第一名碾压；k 小则头部权重集中，k 大则越平滑。对比"分数加权融合"：需调权重超参且量纲问题依旧——RRF 用更少假设拿到更稳效果。
→ 返回[主文档 7.3](V2内容社区与RAG详解.md#73-rrf一行公式与三个为什么)

### Top-K 与 Candidate-K
**一句话：每路粗筛召回 Candidate-K 条（如 20），融合后再截断 Top-K（如 5）进 prompt——两层过滤。**

比喻：选秀——海选各赛区 20 强（Candidate-K：要足够多以体现多路），决赛只留 5 人（Top-K：预算有限）。

原理展开：为什么不能直接取 Top-K：融合需要足够候选池——若每路只取 5 条，"另一路的第 6 名"（可能是双确认的高价值片段）永远进不了融合。为什么最终只留 5：进 prompt 的片段受上下文预算与注意力稀释约束——片段越多模型越容易"看串"。本项目 candidateK=20 / topK=5，都是 RagProperties 可调项。
→ 返回[主文档 7.2](V2内容社区与RAG详解.md#72-检索主流程hybridretrieverretrieve-逐段精读)

### 向量存 MySQL
**一句话：向量以 JSON 存 MEDIUMTEXT、检索时全量加载内存算余弦——数千切片量级的最优解，上万换向量库。**

比喻：几百本书直接堆在书桌上随手翻（内存检索）——够快够好；几万本就得建索引卡片系统（pgvector/ANN 索引）。

原理展开：**真实理由是"MySQL 没有向量索引能力"，而当前切片规模的代价可接受——不是"数据少所以随便存"。** 判断依据是数学不是感觉：500 笔记×300 字/50 字步长 ≈ 数千切片，全量加载（每片 256 维 JSON ≈ 2KB，总 ~10MB）+ 内存余弦 = 毫秒级。**触发条件：切片数到上万**——加载耗时与内存膨胀使全量扫不可接受 → 换 pgvector（SQL 生态内）或 Milvus（专用 ANN）。**架构上已铺好退路**：检索走 VectorRetriever 抽象，届时换实现类业务零改动。面试口径："我知道向量库是标配，我是在**没有向量索引能力的前提下用内存检索顶住**，并在切片上万时换实现——**为数千条数据上 Milvus 才是过度设计**。"
→ 返回[主文档 1.2](V2内容社区与RAG详解.md#12-三个值得单独讲的设计决策)

### 脏语料
**一句话：已失效/下架/旧版本的内容仍留在检索库里——RAG 会一本正经引用不存在的东西。**

比喻：过期报纸还插在报架上——读者按"最新消息"引用了一年前的事件。

原理展开：来源三途：内容下架未联动、内容编辑后旧版未清、索引部分失败。治理：①index 是**替换语义**（删旧写新，同事务）；②下架调 remove 整体移除；③全量重建兜底任务。**脏语料比没语料更糟**：没语料 AI 说"不知道"（诚实），脏语料 AI 引用错误信息（自信地错）——对可信度的伤害是后者大。
→ 返回[主文档 6.2](V2内容社区与RAG详解.md#62-为什么是删旧写新而不是追加)

## 四、Agent 分流

### 双工具路由
**一句话：给模型同时注册 searchProduct（SQL）与 searchDocs（RAG），由模型按问题性质自选——代码不写意图 if-else。**

比喻：给新助理两个电话本——"供应商名录"（实时价格找这）和"用户评价册"（口碑体验找那），告诉它各自什么时候用；之后来电你不用转接，助理自己判断打哪个本。

原理展开：为什么不用规则路由：自然语言意图无法枚举（"这玩意儿贵吗""预算内有没有替代款""值不值"都是价格意图）——规则的覆盖永远是有限集，而模型的语义理解就是为开放集而生。这就是 2026 年 Agentic RAG 的"Agentic"所在：**模型是路由器，工具是执行器**。配套机制：system prompt 定总纲 + 工具 description 定分工（[工具描述工程](#工具描述工程)），两级引导双保险。

代码对应：`AiConfig` 的双 defaultTools + `KnowledgeSearchTool`。
→ 返回[主文档 8.2](V2内容社区与RAG详解.md#82-为什么不写-if-else核心思想)

### 工具描述工程
**一句话：@Tool 的 description 要写清"返回什么 + 何时该调 + 何时不该调"——它是模型选工具的唯一依据。**

比喻：工具箱上贴标签——"十字螺丝刀：拧十字螺丝，别拿来撬 paint 罐"——正反两面都写，新学徒才不会拿错。

原理展开：模型看不到 Java 代码，全靠这段文字决定调不调、怎么传参。本项目的对称经验：V1 踩过"该调不调"（description 只写两个字，模型开始编商品）→ 学会**正向说清**（返回什么/何时调）；V2 防"抢着调错"（两个工具都沾边时模型可能拿 RAG 查价格）→ 加**负向引导**（"价格、库存等实时信息不要用本工具（用 searchProduct）"）。正负结合是工具描述的完成态。

代码对应：`KnowledgeSearchTool` 的 @Tool description。
→ 返回[主文档 8.2](V2内容社区与RAG详解.md#82-为什么不写-if-else核心思想)

### 来源标注
**一句话：RAG 回答附带知识片段的来源（官方说明书/用户笔记）——可信度可感知、可验证。**

比喻：论文的引用标注——"据 XX 研究"和"我觉得"的说服力天差地别；读者可以顺着引用去核实。

原理展开：工程落地：searchDocs 返回的每条片段带 source 字段（MANUAL→"官方说明书"、NOTE→"用户种草笔记"）+ system prompt 要求"回答注明来源"。产品意义：用户能区分"官方参数"与"个人体验"（可信度权重不同）；出问题时能溯源。这是 RAG 从黑盒变白盒的关键一步——**可信 AI 产品的最低配置**。
→ 返回[主文档 8.3](V2内容社区与RAG详解.md#83-来源标注rag-从黑盒变白盒)

### 内容飞轮
**一句话：UGC 笔记 → RAG 语料 → 更好的导购/文案 → 帮新用户写出更好的笔记 → 更多 UGC——每一步喂养下一步。**

比喻：滚雪球——雪（语料）越厚滚出的雪球（AI 质量）越大，大雪球又粘起更多雪。

原理展开：飞轮五环：①用户发笔记（生产）；②审核通过入索引（治理）；③AI 导购能答体验问题/AI 文案引用真实体验（消费）；④新用户被帮助写出更真实的笔记（再生产）；⑤语料更厚（回到①）。**这是"种草社区+RAG"独有的正循环**——纯电商没有语料来源（飞轮缺环）、纯社区没有消费场景（飞轮没出口）。面试画在白板上，这张图就是 V2 的全部价值主张。
→ 返回[主文档 0.2](V2内容社区与RAG详解.md#02-v2-在补什么v1-留下的三个名不副实)

## 五、消息队列（审核链路）

### 异步解耦
**一句话：把"秒级耗时的 AI 审核"从发布请求链路剥离——发布秒回、审核后台完成，两者耗时互不影响。**

比喻：餐厅点单与服务员传菜分离——顾客下单 10 秒拿号（发布秒回），后厨慢慢做（异步审核）；没人让顾客站着等菜炒完。

原理展开：判断标准（项目铁律）：MQ 的引入必须能回答"砍掉它会怎样"——本场景答案是"用户点发布要干等 3~10 秒"。这不是"为了用 MQ 而用 MQ"——对比反面：为每个接口都套 MQ 是过度设计。异步的代价也要能说：状态不再即时（发布后有个"审核中"中间态）、失败处理复杂化（要流水/补偿）——**收益与代价都摆出来才是完整的设计判断**。
→ 返回[主文档 9.1](V2内容社区与RAG详解.md#91-为什么这个设计企业味足先算一笔体验账)

### DirectExchange
**一句话：精确匹配 routingKey 的交换机——一把钥匙开一把锁，最简单直白。**

比喻：分机号总机——拨"8021"只接通 8021 工位，不碰别的。

原理展开：AMQP 三种常用交换机的选型：**Direct**（精确匹配，当前一种消息时最简）；**Topic**（通配符匹配 "note.*"/"order.#"，多类消息统一入口时用）；**Fanout**（广播，所有队列都收一份）。本项目只有审核一种消息 → Direct；将来订单事件多了可演进 Topic——**按需演进，不预支复杂度**（这句话本身就是面试加分句）。
→ 返回[主文档 9.2](V2内容社区与RAG详解.md#92-mq-拓扑与三个决策)

### 死信队列 DLX
**一句话：被拒绝/过期/超长的消息不丢弃，而是按死信参数重新路由到"收容所"队列——失败可被发现。**

比喻：快递三次投递失败的包裹进"滞留仓"——不是扔掉，等主人或客服来处理。

原理展开：两种死法两条用途：①**失败收容**（V2 审核）：消费端重试耗尽的消息进 DLQ，人工/补偿任务处理——没有 DLQ，失败消息直接蒸发，问题无从排查；②**延迟投递**（V3 订单）：TTL 过期+死信路由=延迟队列（详见 [V3 词典](V3支付与Redis详解【知识词典】.md#死信队列再认识)）。配置在队列上（x-dead-letter-exchange / x-dead-letter-routing-key）。
→ 返回[主文档 9.2](V2内容社区与RAG详解.md#92-mq-拓扑与三个决策)

### 毒消息
**一句话：必然失败的消息（如下游已挂）在"重入队→消费→失败"里无限循环——打爆日志与 CPU。**

比喻：对讲机没电了还在循环呼叫——对方永远回不了，你的电池先耗尽。

原理展开：默认行为的问题：Spring AMQP 抛异常默认 requeue（重回队首）→ 死循环。本项目对策：`default-requeue-rejected: false` + 消费端 catch 吞掉 → 消息 ACK（出队）+ ERROR 流水 + DLQ 收容——**"失败可被发现"优于"失败被无限重试"**。什么消息值得重试：瞬时故障（网络抖动、死锁）——可通过延迟重试（DLX 兜一圈）实现；什么不值得：确定性失败（服务挂了、消息格式错）——重试一万次也一样。分清这两类是 MQ 消费端设计的成熟度标志。
→ 返回[主文档 9.3](V2内容社区与RAG详解.md#93-消费端幂等三防线本章核心)

### 消费端幂等
**一句话：MQ 语义是 at-least-once（至少一次），重复投递是常态，消费逻辑必须自带幂等。**

比喻：快递可能重复派送同一个包裹——签收方要认得"这个我签过了"，不能重复入库两次。

原理展开：为什么必然重复：生产者超时重发（broker 收到了但 ack 没到）、消费者处理完还没 ACK 就崩溃（重启后消息重投）——**重复不是 bug 是协议特性**。幂等三方案：唯一键（INSERT IGNORE 撞键跳过）、状态机条件更新（WHERE 期望状态）、version 乐观锁——本项目审核链路用了前两个。判别式：**凡消费代码，先问"这条消息来两次会怎样"**。
**关键前提（易被忽略）**：唯一键保护的是"**同一次请求的重投**"，不是"这条内容只能处理一次"。所以键里要有能区分"同一次"与"新一次"的维度，且那个维度**必须真的会变**——本项目是 `biz_version`（来自 `t_note.audit_version`，发布=1、重新送审 +1），并且唯一键含 `status`，使 `ERROR`（"这次没审成"，非结论）不与 PASS/REJECT 争抢同一个幂等位（`V5__note_audit_version.sql`）。反例：版本号写死 = 幂等键退化成常量，一次驳回或一次报错就永久堵死后续处理。
→ 返回[主文档 9.3](V2内容社区与RAG详解.md#93-消费端幂等三防线本章核心)

### 消息只带 id
**一句话：消息体只放标识符（noteId），消费时回查最新数据——消息是"通知"不是"数据载体"。**

比喻：快递单上只写"订单号 12345"不写货品明细——仓库按单号取最新实物；写明细反而可能"单上写着红色、仓库已换成蓝色"。

原理展开：三个好处：①消息体小（不占 Broker 内存）；②**消费时数据总是最新**（消息躺队列 5 分钟、笔记被编辑过，审核的仍是最新版——若消息带内容就是旧版）；③敏感内容不进 Broker（内网也不能假设安全）。代价：消费端多一次 DB 回查——可接受。与"事件溯源/CDC"路线的对比知道即可：那种场景消息要带全量数据（消费方无库可查），选型看消费端有没有数据源。
→ 返回[主文档 9.2](V2内容社区与RAG详解.md#92-mq-拓扑与三个决策)

### 事务外发消息
**一句话：MQ 不参与数据库事务——事务内发消息永远有"回滚但消息已飞"的窗口。**

比喻：给朋友发微信说"钱已转账"的同时在银行 APP 点撤销——微信发出去收不回，转账却没了。

原理展开：竞态现场：`@Transactional` 方法里 convertAndSend 成功 → 方法后续步骤异常 → **DB 回滚但消息已发出** → 消费者查到不存在的数据（幽灵消息）。解法阶梯：①afterCommit 回调（本项目**现行做法**：`common/tx/AfterCommitExecutor` 是唯一出口，订单延迟消息与审核消息都走它，Spring 事务同步器）；②本地消息表（强一致标准解——消息与业务同事务落库，定时投递）。三级递进按一致性要求选，面试聊分布式事务的入门题就是它。
**一个易踩的变体**：消息本身没回滚，但**消费者比事务提交先跑**——同一条竞态的镜像（读不到未提交的数据 → 判定"记录不存在"→ 丢弃消息）。本项目的审核链路先踩了这一个：早期的"submit 放在事务边界外"只有注释、Controller 层实际没有事务，10 次发布有 9 次被丢弃；改成 afterCommit 才真正解决（见 `docs/复核-审核MQ竞态-20260920.md`）。
→ 返回[主文档 9.4](V2内容社区与RAG详解.md#94-事务外发消息v2-踩过的坑)

### 发布者确认
**一句话：publisher-confirm——Broker 收到消息后回执 ACK 给生产者，"消息不丢"的发送端一半。**

比喻：挂号信回执——邮局签收了给你一张回执；没回执你才知道要补寄。

原理展开：默认发消息是"发射后不管"（fire-and-forget）——网络抖动丢了生产者不知道。开启 `publisher-confirm-type: correlated` 后每条消息有异步回执，可监听成功/失败做补发。消息可靠性的完整链：发送端 confirm + Broker 持久化（队列 durable+消息 persistent）+ 消费端处理成功才算闭环——**三段缺一段都可能丢**，面试要按链答不能只背一个词。
→ 返回[主文档 12.2](V2内容社区与RAG详解.md#122-面试速查表30-秒一答)

### prefetch
**一句话：消费者一次最多预取几条未 ACK 消息——消费端的背压控制。**

比喻：食堂打饭窗口一次最多摆 5 份餐——吃完一份（ACK）再补一份；窗口不会把 100 份全堆给你（堆着也凉了=客户端内存爆了）。

原理展开：不设上限的问题：Broker 把消息疯狂推给客户端，客户端内存缓冲爆炸 + 消息"在途"状态难以管理。本项目 prefetch=5 的依据：审核是秒级慢任务，预取多了消息全堆在客户端内存（Broker 失去调度权）。经验值：快任务（毫秒级）可到几百，慢任务个位数——**按任务耗时定预取**。
→ 返回[主文档 9.2](V2内容社区与RAG详解.md#92-mq-拓扑与三个决策)

### at-least-once
**一句话：MQ 的投递语义——消息至少到达一次（可能重复），配合消费端幂等保证效果上的恰好一次。**

比喻：重要信件寄两封防丢——可能两封都到（重复），但你拆一封就够了（幂等）。

原理展开：三种语义对比：at-most-once（可能丢，性能最好）、at-least-once（可能重复，工程默认）、exactly-once（理论美好，代价极高——真正的 exactly-once 需要事务性消息+幂等消费，多数"exactly-once"实现本质是 at-least-once+消费幂等）。工程选择：**接受 at-least-once，把重复交给消费端幂等**——这是性价比最高的组合，也是本项目的设计前提。
→ 返回[主文档 9.3](V2内容社区与RAG详解.md#93-消费端幂等三防线本章核心)

## 六、内容安全

### 先发后审 vs 先审后发
**一句话：先发后审（发布即入队审核，通过才公开）安全但慢；先发后审（先公开再巡查）快但风险外溢——本项目取"发布秒回+秒级 AI 审"的折中。**

比喻：地铁安检口（先审后发：人人过闸再上车，慢但安全）vs 公共广场（先发后审：先进场，保安巡查，快但风险在场上）——本项目是"高铁站快速安检"：1 秒过闸（秒回）但闸机很灵（AI 秒审）。

原理展开：本项目的实现：内容落库为 AUDITING（**对外不可见**——不是"公开了再撤"）→ AI 数秒内出结果 → PUBLISHED/REJECTED。对用户像"先发"（点了发布立即有反馈），对系统是"先审"（未过审内容从未公开）——两头的优点都拿到，靠的是**异步**。
→ 返回[主文档 9.1](V2内容社区与RAG详解.md#91-为什么这个设计企业味足先算一笔体验账)

### 审核流水
**一句话：每次 AI 判定的原始结果入库留痕（ai_result_json）——可追溯、可翻案、可统计误判率。**

比喻：法官的庭审记录——判决书（笔记状态）之外要有笔录（AI 原始判定），上诉时才能复盘。

原理展开：只在主表打状态的问题：出争议（用户申诉"我笔记没违规"）时无据可查——AI 当时判了什么、置信度如何全是黑箱。流水表三用：①翻案依据；②复核入口（reviewer/reviewed_at 字段预留人工）；③质量统计（某类目误杀率——AI 审核系统的运营指标）。**概率性系统必须留判定证据**，这是 AI 工程与确定性工程的重要差异。
→ 返回[主文档 1.2](V2内容社区与RAG详解.md#12-三个值得单独讲的设计决策)

### 宁漏勿杀
**一句话：审核拿不准时倾向放行——误杀正常用户的伤害大于漏过一条软广。**

比喻：机场安检的"人工复检"逻辑——可疑但不确定的行李开箱细查（人工复核），而不是直接没收（误杀）；宁可多花复检成本，不能让旅客平白受损失。

原理展开：伤害的不对称性：误杀（正常用户被拒发、体验受挫、流失）是**对个体的确定性伤害**；漏放（一条软广存活几小时后被巡查下架）是**对平台的或有小损失**。落地三处：提示词"拿不准时倾向 pass"、AI 失败只记 ERROR 不动笔记（停审核中待人工）、流水表留人工复核入口。**审核系统宁可不作为，不可乱作为**——这条价值观是内容安全章的灵魂。
→ 返回[主文档 9.5](V2内容社区与RAG详解.md#95-审核提示词三个温度的第三副面孔)

### 人工复核兜底
**一句话：AI 审核定位是"过滤 99% 明确内容"，灰区交给人工（reviewer 字段已预留）——AI 不是终审。**

比喻：机场的自动值机（AI：处理 95% 常规旅客）+ 人工柜台（处理改签/无成人儿童等边缘）——自动化消化大头，人处理长尾。

原理展开：生产系统的审核分层：机审明确违规（色情/违禁品）→ 直接拒；机审明确安全 → 直接过；**机审不确定/用户申诉 → 人工**。本项目的预留：流水表 reviewer/reviewed_at 字段、ERROR 状态的笔记停留 AUDITING 等人工——**把"AI 会出错"设计进系统**，而不是假设它不会错。
→ 返回[主文档 9.3](V2内容社区与RAG详解.md#93-消费端幂等三防线本章核心)

### AI 不直写业务数据
**一句话：AI 的产出（文案/审核结论）永远不直接落成公开业务数据——必须经过人的确认与流程的把关。**

比喻：AI 是实习生——它可以起草报告（草稿）、可以初审单据（流水），但盖章发布的必须是人（或人定的流程）。

原理展开：本项目两处红线：①AI 文案只出草稿（editable=true，用户编辑后走发布+审核流程）；②AI 审核的判定要过幂等状态机才改笔记状态（不是 AI 说什么就是什么）。反例推演：AI 文案直接发布——幻觉生成的虚假体验=虚假宣传（法律责任）；AI 审核直改状态——模型抽风时批量误杀。**"AI 辅助、流程把关"是内容平台的安全底线**。
→ 返回[主文档 10.2](V2内容社区与RAG详解.md#102-红线ai-只出草稿)

## 七、MySQL 全文检索

### FULLTEXT 索引
**一句话：MySQL 内建的倒排索引——支持 MATCH...AGAINST 全文检索与相关性排序。**

比喻：书后的"索引页"（倒排索引：词→页码列表）——查"光合作用"直接翻到标注的页，而不是从第 1 页逐页读（LIKE '%xx%'）。

原理展开：为什么 LIKE '%x%' 不行：前缀通配使 B+ 树索引失效 → 全表扫描。FULLTEXT 建的是**倒排索引**（词 → 出现文档列表），按词直查。中文必须配 [ngram](#ngram-解析器)（默认解析器按空格分词，中文整句一个词）。使用：`WHERE MATCH(title, content) AGAINST ('降噪' IN NATURAL LANGUAGE MODE)`，结果自带相关性排序。
→ 返回[主文档 3.2](V2内容社区与RAG详解.md#32-中文全文检索ngram-一站式讲透)

### ngram 解析器
**一句话：MySQL 8 的中文分词方案——把文本按 n 元字符组（默认 2 字一组）切词建倒排，中文检索才能命中。**

比喻：中文没有空格分词，就像一整串没有分隔符的字母——ngram 是"每两个字母切一刀"的暴力但有效解法：`"主动降噪" → 主动|动降|降噪`。

原理展开：默认解析器的死刑：按空格/标点切词（英文设计）→ 中文整句 = 一个词 → 搜任何子串都不命中 → **检索全失效**（不是慢，是根本搜不到）。`WITH PARSER ngram` 启用二元切词后"降噪"能精确命中。两条固有局限：①纯字面无语义（"续航"搜不到"电池耐用"——语义缺口交给 RAG 向量通道，这正是 Hybrid 的理由）；②单字查询无结果（token 是 2 字）。**建中文全文索引不带 ngram 是新手 100% 会撞的坑**——搜索一切词都 0 结果。

代码对应：`V2__content_and_rag.sql` 的 `FULLTEXT KEY ft_title_content (title, content) WITH PARSER ngram`。
→ 返回[主文档 3.2](V2内容社区与RAG详解.md#32-中文全文检索ngram-一站式讲透)

### ngram_token_size
**一句话：ngram 的分词粒度参数（默认 2，即二元组），MySQL 启动时全局配置。**

比喻：切香肠的刀距——默认每 2 厘米切一段；改刀距全桌的香肠都要重切（重建索引）。

原理展开：2 对中文够用（常用词基本都是双字起步）；3 更精确（能命中三字词如"蓝牙歌"）但索引更大、2 字词反而可能失配。改它需要改 my.cnf + 重启 MySQL + **重建全部 ngram 索引**（token 变了倒排结构全变）——所以默认值即最优，除非有明确的检索质量数据支撑才动。本项目用默认 2，并与 local 哈希向量的 2-gram **口径对齐**（两通道词粒度一致，融合才有意义）。
→ 返回[主文档 3.2](V2内容社区与RAG详解.md#32-中文全文检索ngram-一站式讲透)

### 自然语言模式
**一句话：MATCH...AGAINST 的默认模式——按相关性打分排序返回，无需运算符。**

比喻：普通搜索框（输入关键词，结果按"相关度"排）vs 高级搜索语法（+必须含 -必须不含 *通配）。

原理展开：三种模式：**NATURAL LANGUAGE MODE**（默认，相关性排序，本项目用）；BOOLEAN MODE（支持 +/-/* 运算符做精确控制——"必含某词且排除某词"的搜索页高级筛选）；QUERY EXPANSION（二次检索，少见）。本项目搜索是"用户随手输关键词"场景，自然语言模式最贴合；BOOLEAN 留给将来做高级筛选。
→ 返回[主文档 3.2](V2内容社区与RAG详解.md#32-中文全文检索ngram-一站式讲透)

### 为什么不上 ES
**一句话：不是"数据少所以不用"——是"触发条件没到 + 退路已铺好"。**

> ⚠️ **口径纪律（重要）**：**别说**"数据量决定选型——500 篇笔记上 ES 是装航空母舰"。这话两条硬伤：①它是**规模借口**不是工程理由，被问"那 50 万条呢"就崩；②**等于主动承认项目没见过规模**。

**正确句式**："ES 的成本我清楚（独立系统的部署/监控、MySQL→ES 双写一致性、运维复杂度），它的收益兑现点在百万级文档、复杂聚合、高亮、多表联合搜索、拼音同义词 analyzer。**我的触发条件是：MySQL 全文检索 P99 超过体验阈值（200ms），或笔记量到十万级。**检索层是抽象接口（HybridRetriever），到点换实现业务不动——**现在是没触发，不是判断它不够用**。"

**★ 关键区分（最容易讲错的地方）**：这套话术**只适用于笔记检索**——那里确实用 ngram FULLTEXT 做出了完整方案，可以理直气壮说"方案完备，只是暂不上 ES"。**商品搜索不能套用**：商品至今是 `LIKE '%kw%'`，那是**没做**，不是"选型上认为 MySQL 够"。把两者混成一谈，等于用笔记的完成度去掩盖商品的缺口。

原理展开：ES 的真实成本：一个独立系统（部署/监控/升级）、数据双写的一致性问题（MySQL→ES 同步链路）、运维复杂度。它的收益兑现点：百万级文档、复杂聚合、高亮、多表联合搜索、拼音/同义词等 analyzer 生态。本项目同时留了退路：检索层是抽象接口，量级上来换实现业务不动。面试的答法是**先说触发条件和退路，再说"我知道 ES 强在哪"**——两头都占，且把"为什么不做"讲成工程判断而不是规模借口。
