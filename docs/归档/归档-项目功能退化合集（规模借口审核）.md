
# 项目功能退化合集（规模借口审核）

> **审核目标**：找出全项目所有「**因为数据少（500 条 / 100 商品 / 演示项目），所以用 XX 简单方案就够了**」式的表述。
>
> **为什么要审**：这种论证有两个致命伤 ——
> 1. **它是规模借口，不是工程理由**。面试官一句"那你有 50 万条怎么办"就把你问死，因为你手里只有"现在少"，没有答案。
> 2. **它等于主动承认项目是玩具**。"才 500 条"听着聪明，实则暴露自己没见过真实规模。
>
> **正确姿势**：不说"数据少所以够用"，要说「**还没做成熟方案 + 何时会塌 + 换什么 + 什么条件触发**」。

| 判定 | 含义 | 处理 |
|---|---|---|
| 🔴 **纯规模借口** | 理由就是"数据少"，无其他工程依据 | 必须改 |
| 🟡 **混合** | 既提数据量，也提了真实工程理由（零依赖铁律/阶段优先级/引入新组件的运维成本） | 改措辞：把重心从"数据少"移到真实理由 |

**★ 关键区分：**
- **「没做」**（功能缺口 / 技术债）—— 绝不能用"数据少"当理由

> **数据规模是"触发条件的标尺"，不是"选型的理由"。**
>
> 100 商品 / 500 笔记不代表"所以简单方案够用"，只代表"**这些方案还不需要提前上，但每一处都必须说清：它在什么量级会塌、塌了换什么**"。
>
> 同一个"500 条"，判断结果可以完全相反，取决于**数据形态**而不是**数据条数**：
> - 500 篇**UGC 长文本** → 需要全文 + 语义检索（笔记、RAG）→ **做了 FULLTEXT(ngram) + 向量混合**

### 2.2 🔴 向量检索：全表加载 + 内存算余弦

**位置**：`backend/src/main/java/com/aimall/content/mapper/KnowledgeMapper.java:20-25`

```
 * MySQL 没有向量索引（那是 pgvector / Redis Stack 的活）。
 * 当前数据量（数百篇笔记 + 说明书 ≈ 数千切片）下，全量加载后在内存里算余弦
 * 是几毫秒级的事；数据量上万后应把 selectAllWithEmbedding 换成
 * 向量库的 ANN 查询——由于检索层已抽象为 VectorRetriever 接口，
 * 届时只替换实现类，业务代码不动。
```

**🔴 判定：混合理性依据 + 规模借口 → 必须改措辞**

**技术事实**：`HybridRetriever.retrieveByVector()` **每次查询都把全部切片连向量捞进 JVM 内存**再逐个算余弦。这是 O(N) 全表扫——和商品 `LIKE '%kw%'` 是**同一类问题**（全表扫），只是发生在 Java 侧而不是数据库侧。

**它坏在哪**：
- 每次问答都全量加载（**无缓存**，`selectAllWithEmbedding()` 每次都打库）；
- 切片数是**永久累积**的——笔记增长 → 切片线性增长 → **每次 RAG 查询的内存与耗时线性增长**；
- 单机 JVM 堆会被拖垮（数千切片约 10MB 尚可，十万切片就是 GB 级，直接 OOM）。

**但这条也有真实工程理由**（所以不是纯借口）：MySQL 确实**没有原生向量索引**，在 SQL 里算余弦**根本没有可选项**——这不是"因为数据少所以偷懒"，是"**数据库层面没有这个能力**"。这条要保留，但要把"当前数据量…是几毫秒级的事"这个**规模论证**换成**能力论证**。

**改成什么**：
> MySQL 无向量索引能力，SQL 侧无法做 ANN 检索——所以向量通道只能在 Java 侧算。当前实现是**全量加载 + 内存余弦（O(N) 全表扫）**，性能随切片数线性退化、且每次查询都打库无缓存。
> 这是**能力缺口不是规模借口**：正解是引入向量索引（pgvector 的 HNSW，或 Milvus），触发条件**不是"有多少条"而是"内存占用/查询 P99 逼近阈值"**。检索层已抽象为 `VectorRetriever`，换实现类业务零改动。
> ⚠️ 被追问时必须能说出"**O(N) 全表扫，且无缓存，每次问答重算**"——这才是知道自己的方案烂在哪。

**它坏在哪**（说清才算懂）：
- prompt token **线性增长** → **成本线性增长**（AI 按 token 计费）；

> ⚠️ 有个**已经做了的**相关优化要区分开：历史**图片**刻意不回喂模型（只取文字），因为图片按尺寸计 token 成本更高。

### 2.5 🔴 热门榜重建的硬上限 1000

**位置**：`backend/src/main/java/com/aimall/content/service/impl/NoteServiceImpl.java:64-65`

```java
/** 榜单全量重建的候选规模：全站笔记量级远小于此，够覆盖 */
private static final int HOT_RANK_REBUILD_SIZE = 1000;
```

**🔴 判定：纯规模借口（"全站笔记量级远小于此，够覆盖"）**

**它坏在哪**（★ 比"性能差"更严重——这是**数据正确性**问题，已读代码核实）：

`rebuildHotRank()` 的实际动作是**先 `delete` 整个 zset，再灌入 `LIMIT 1000` 的结果**：

```java
List<Note> top = noteMapper.selectPublishedForRank(HOT_RANK_REBUILD_SIZE); // LIMIT 1000
redisOps.delete(HOT_RANK_KEY);          // ← 先清空
for (Note n : top) { redisOps.zAdd(...); }  // ← 只灌前 1000
```

于是产生一个**真实的、可推演的缺陷**：
1. **增量维护的成果会被周期性擦除**。日常互动走 `refreshHotScore` → `zAdd`，**不受 1000 限制**，所以一篇笔记**可以靠点赞爬进榜单**；
2. 但定时重建一到，**先清空再只灌 DB 前 1000** —— 那篇靠增量爬进来的笔记**如果排名在 1000 之外，会被无声抹掉**；
3. 结果：**榜单内容在"重建周期"上呈现锯齿形抖动**——爬上去、被擦掉、再爬、再被擦。用户看到的是"榜单一会儿有一会儿没有"，**而且不报错**。

> ★ 这才是这条的真正危害：**不是慢，是静默的、周期性的数据丢失。** 性能问题用户能感知（卡），榜单错乱用户只会觉得"这 App 有问题"但说不出哪错——**这类 bug 最难排查也最伤信任**。

**改成什么**：
> 热门榜周期重建以 DB 为真值做"覆盖式重建"，但**候选窗口硬编码 1000 条**——超出窗口的笔记无法重建，且重建会**先清空再灌入**，导致**增量爬到榜上但排名靠后的笔记被周期性擦除**（榜单随重建周期抖动）。**这是正确性问题，不是性能问题。**
>
> 两个修正方向（择一，都要说清语义）：
> 1. **重建改游标分批全量**（照抄同项目 `RagIndexBuildService.buildAll()` 的 `while(true)+cursor` 写法），让 zset 与 DB 完全对齐；
> 2. 或者**把语义讲明**：榜单 = 「**候选池内** Top N」，候选池用**热度阈值**而不是拍脑袋的条数来维护，并说明"增量 zAdd 可绕过窗口"这个已知行为。
>
> ⚠️ **面试被问到时的价值**：这是一条**能主动讲出来的真实缺陷**，而且能讲出"增量与全量重建的口径不一致"这种**深水区**问题——比背十个八股都显功底。
> 💡 **对比参照**：同一份代码里的 `RagIndexBuildService.buildAll()` 就做对了——它用 `while(true) + cursor` **分批拉取**，注释写"避免一次加载 500 篇全文撑爆内存"。**同一个项目里，有正确答案可以抄。**

**位置**：`backend/src/main/java/com/aimall/goods/bean/Cart.java:12`、`CartService.java:10`

```
* 规划：V3 拟将购物车迁移至 Redis Hash 以提升读写性能。
```

> 购物车当前落 MySQL。**选它的真实理由是事务一致性**——加购/改数量/删除与订单创建（清购物车）在**同一事务**内，走 Redis Hash 就跨了存储、要额外处理一致性。
> 迁 Redis Hash 的收益是高频读写的性能，**触发条件是购物车读写成为瓶颈**；届时要么接受最终一致，要么把"清购物车"改成幂等的异步补偿。

### 3.2 V4 只拆 AI 服务（表述已在正确轨道）

**位置**：`V4服务化详解【知识词典】.md:57`

```
拆开 = 要么 Seata、要么本地消息表最终一致——日订单量两位数的演示项目付不起。
```

**🟡 判定：** "日订单量两位数"是**规模借口**，但**真正的理由就写在句子里**——"**同一事务**锁库存+建订单+清购物车，拆开必须为分布式事务买单"。**真实理由是"事务边界不可拆"，不是"量小"。**

**改成什么**：

## 五、正确口径模板（背下来直接用）

### 5.1 "为什么用简单方案"的通用答法

> ❌ **不要说**："我们数据量只有 X，所以用 Y 就够了。"
>
> ✅ **要说**三件事：
> 1. **现在是什么**：Y 是我当前的实现（说清它的技术本质）；
> 2. **它什么时候会塌**：Y 的边界是……（**具体的失效机制**，如"O(N) 全表扫"/"token 线性增长必超窗"/"候选窗口截断导致漏数据"）；
> 3. **换它的触发条件 + 目标方案**：当……出现时（**可观测的信号**：P99 / 内存 / 数据量级 / 功能需求），换成 Z；且我的抽象层已铺好，换实现不动业务。

**核心心法**：**"没做"和"不需要"是两回事。** 说不出"何时塌"= 不知道方案烂在哪；能说清"何时塌"还说"够用" = 自贬。

### 5.2 触发条件该怎么写（要有可观测信号）

| ❌ 坏的触发条件 | ✅ 好的触发条件 |
|---|---|
| "数据量大了就换" | "商品量到十万级，或 LIKE 查询 P99 > 200ms" |
| "性能不够就优化" | "每次 RAG 检索的内存占用接近堆上限，或检索 P99 逼近体验阈值" |
| "用户多了就上" | "需要靠注册中心做故障摘除/流量转移时（误判代价才真实出现）" |

### 5.3 一句话总纲

> **数据量是"触发条件的标尺"，不是"选型的理由"。**
> 真正决定选型的是**数据形态**（长文本？结构化多维度？）和**失效机制**（会怎么塌），而不是**有多少条**。

#### 🔴 新-1：面试速查表里藏着错误口径（**最该改**）
**位置**：`V2内容社区与RAG详解.md:873`
> `| 中文搜索怎么做 | FULLTEXT + WITH PARSER ngram（2-gram 切词）；500 篇量级不上 ES |`

**🔴 为什么**：**这是给用户背下来的 30 秒答案**。同文档 `:287/:289` 已经写了正确口径，**速查表却没同步**——等于**把错误口径做成了背诵卡**。面试时脱口而出的就是这句"500 篇量级不上 ES"。
**改成**：`| 中文搜索怎么做 | FULLTEXT + WITH PARSER ngram（2-gram 切词，默认解析器整句一个词故必须加）；语义缺口交向量通道。ES 的触发条件 = 检索 P99 > 200ms 或量到十万级 |`

#### 🔴 新-2："砍掉 ES"的三段式里，只有这条是规模借口
**位置**：`项目设计文档.md:80`
> `- ★ **砍掉 ES**：100 商品 + 500 笔记，MySQL 全文索引完全够——**所以不做 ES**。`

**🔴 为什么**：这是"砍掉它系统会出什么问题"框架的第三条。**同框架的其余几条全是真实业务理由**（`:78` 砍掉 AI 审核→人工审核成本极高；`:79` 砍掉防超卖→一开库存就超卖），**只有这条理由是纯数据量**——在正确的框架里塞了一句错话，更显突兀。
**改成**：`- 砍掉 ES：笔记的字面检索由 MySQL ngram 全文索引覆盖，语义由向量通道补——两个明确能力都已落地；ES 的增量价值（多维聚合筛选、拼音/同义词 analyzer）对应的是商品搜索的缺口，触发条件见 §5.2。`

#### 🔴 新-3：把 ES 列进"伪需求清单"，与自己的判断矛盾
**位置**：`项目设计文档.md:596`
> `5. **伪需求清单（明确不做）**：直播、复杂优惠券/拼团、多级分销、推荐算法论文级调参、**ES 全文检索（当前数据量不需要）**、区块链类噱头、**秒杀**。`

**🔴 为什么**：ES **不是伪需求，是缺口**——同一个文件 `:564` 自己写着"商品 LIKE 是**未完成的缺口**，不是选型结论"。**把"没做的缺口"和"明确不做的伪需求"混在一张清单里，等于自我否定。**
**改成**：把 ES 从"伪需求清单"移出，放到"**已知缺口与演进路线**"里（与商品搜索的技术债条目并列）。

#### 🔴 新-4：热度衰减未做的理由是"数据量小"
**位置**：`V2内容社区与RAG详解【知识词典】.md:102`
> `面试追问"为什么不用时间衰减"——真实热度公式通常加时间衰减（72 小时前的 1000 赞不如今天的 500 赞）；本项目数据量小、笔记周期短，未加——知道这是简化即可。`

**🔴 为什么**：热度衰减是**功能没做**，理由却写成"数据量小、笔记周期短"（都是**模拟数据集的属性**）。
**真理由应该是**：**衰减系数需要真实行为数据来校准**（衰减多快才合理，取决于真实用户的点赞时间分布）——**当前没有真实数据可校，拍一个系数比不衰减更不可信**。
**改成**：`热度公式未加时间衰减。真理由是：衰减系数的标定依赖真实用户的行为时间分布（多久算"旧"），当前只有模拟数据，拍一个系数反而引入不可验证的失真。触发条件是接入真实用户行为数据后，用离线评测标定。`

#### 🔴 新-5：布隆过滤器"100 商品绰绰有余"
**位置**：`V3支付与Redis详解.md:428`
> `海量 key（百万级商品）才需要；本项目 100 商品，空值缓存绰绰有余。`

**🔴 为什么**：理由又落回"100 商品"。
**真依据**（技术层面，与商品总数无关）：**无效 key 的占比**。空值缓存的问题是**每个无效 id 都占一份内存**，所以它的适用边界是"**恶意 id 的种类有限 / 攻击面可控**"；一旦攻击者用**无穷随机的 id** 打，空值缓存的内存就被打爆——**这时与你有多少真商品毫无关系**。
**改成**：`空值缓存与布隆的取舍点不在商品总数，在**无效 key 的基数与来源**：空值缓存每条无效 key 占一份内存（适合无效 key 种类有限、可枚举）；布隆用**固定内存**挡任意无效 key（适合攻击者能构造无穷随机 id）。当前用空值缓存 + TTL，风险是随机 id 攻击下的内存增长——触发条件是出现这类攻击特征或缓存内存占比异常。`

> ★ 同 `V3…【知识词典】.md:291` 有同样的"100 商品绰绰有余"表述，一并改。

#### 🔴 新-6：会话历史不截断"演示级会话不长"
**位置**：`简历语句技术深挖笔记.md:1286`
> `治理：只带最近 N 轮（滑动窗口）；更早的摘要压缩。本项目演示级会话不长未做截断，**知道这个演进方向**。`

**🔴 为什么**：与前面 A5（`ChatServiceImpl` 全量历史）是**同一个缺口**，这里用"演示级会话不长"当理由——**这是"用别人的使用习惯给自己免责"**：你不能假设用户不会聊很久，而且**超窗是硬失败**。
**改成**：与 A5 统一口径——`历史截断未做：当前每轮带全量历史，token 与成本随轮数线性增长，且会顶到上下文窗口硬失败。正解是滑窗 + 旧对话摘要，触发条件是成本或窗口压力出现（不是"用户没聊长"）。`

#### 🔴 新-7：心跳探活（已在 A14 记）— 补充更准的理由
`V4…【知识词典】.md:177` 的"演示项目用心跳够了"，**真约束**是：接入 active health check 需要给服务加 actuator 健康端点**并与注册中心做联动配置**（不是"演示所以不用"）。

## 七-补2、一处判定分歧（需你定夺）

`后端求职/03-现職退化方案与技术债清单.md:49/51`「限流固定窗口…**防刷够用**」：

- 我判 **🔴**：因为"防刷够用"是**断言**，且 `:51` 说"要严格我知道该上滑动窗口"——**等于承认自己是侥幸过关**；
- 审计 agent 判 **🟢**：因为依据其实不是"数据少"，而是"防刷/成本控制场景**容忍**该突刺 + 突刺上限**算得清**（2 倍）"。

**折中结论（建议采纳）**：**判定本身可以宽松，但措辞必须改**——把"够用"这个形容词，换成**量化后的容忍度**：

> ❌ "防刷场景固定窗口够用，要严格我知道该上滑动窗口/令牌桶"
> ✅ "固定窗口的突刺上限是 **2 倍**（窗口交界处）。AI 接口**按次计费**，限流目的是**控成本**——成本封顶为预算的 2 倍，在可接受范围内。要**精确计量**或**保护脆弱下游**时，换滑动窗口/令牌桶。"

**理由**：面试官听到"够用"会追问"凭什么够用"；听到"**突刺上限 2 倍、成本封顶 2 倍预算**"就无从追问——**这是把形容词换成数字的威力**。

## 九、面试防御口诀

被问到任何一个"退化/简化"点时，**三步走**：

1. **承认它是最简实现**（不要辩解"够用"）；
2. **说出它的失效机制**（技术本质，不是"数据少"）；
3. **给触发条件 + 目标方案 + 抽象层现状**。

> **最忌讳的一句话**："我们的数据量只有几百条，所以这样够了。"
> —— 这句话把"我没做过大规模系统"主动交出去了。

### 触发条件要用"可观测信号"（对比表）

| ❌ 坏的写法 | ✅ 好的写法 |
|---|---|
| "数据量大了就换" | "商品量到十万级，或 LIKE 查询 **P99 > 200ms**" |
| "性能不够就优化" | "RAG 检索内存占用接近堆上限，或检索 P99 逼近体验阈值" |
| "用户多了就上" | "需要靠注册中心做故障摘除/流量转移时" |
| "量级到了再上多级缓存" | "本地缓存省的网络往返 > 多实例一致性成本时" |

### 一句话总纲

> **数据量是"触发条件的标尺"，不是"选型的理由"。**
> 决定选型的是**数据形态**（长文本？结构化多维度？）和**失效机制**（会怎么塌），不是**有多少条**。
>
> 同一句"500 条"，判断结果可以完全相反：
> - 500 篇 UGC 长文本 → **需要**全文 + 语义检索 → 做了 ngram FULLTEXT + 向量混合
> - 100 个结构化商品（要多维筛选）→ **需要**倒排索引 → **没做，是债**
>
> 判据是"这个数据形态需要什么能力"，不是"有多少条"。
