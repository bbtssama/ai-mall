## 1. SKU / SPU 概念（购物车/订单里的 skuId 到底指什么）

- **SPU**（Standard Product Unit）= 一个"商品"概念（如 AirSound Pro 耳机）
- **SKU**（Stock Keeping Unit）= 库存量单位 = "规格"（曜石黑 / 奶白色），每个 SKU 独立价格、库存、销量

```
t_product（SPU，4 个商品）
 └── t_product_sku（SKU，8 条规格）
     ├── id=1 曜石黑  ¥399  库存1000
     └── id=2 奶白色  ¥399  库存800
```
- **为什么两级**：不同规格价格/库存/销量分开；详情页"¥399起"= `MIN(price)`
- **表关联画像**：
  - `cart`（谁买了哪个SKU几件）N:1 → `sku` → N:1 → `product`
  - `order_item`（订单明细）存 `skuId` + **商品名/单价快照**
  - `cart` 只存 skuId，展示时 JOIN；`order_item` 额外存快照（因为历史订单要定格，防商品改名改价影响历史记录）

## 2. DTO 是什么

- **DTO** = Data Transfer Object（数据传输对象）：为一次跨层传输而裁剪的对象
- **Bean（实体）** = 一张表 = 一个对象（字段=列）；**DTO** = 按"这次请求/响应需要什么"造
- 三类 DTO：
  - 入参：`XxxRequest`（接收前端提交 + 放校验注解）
  - 出参：`XxxVO`（决定返回给前端什么，**脱敏**——如 UserVO 不带 passwordHash）
  - 聚合：`OrderVO` 可带 `items`（Order Bean 里没有这列）
- 记忆：**Bean 是照表搬字，DTO 是按需裁剪的快递包裹**。改接口字段改 DTO 不改 Bean。

## 3. @Valid 与参数校验（本次实测验证过的结论）

- `@Valid` 的作用：**激活字段校验注解**（@NotNull/@Min/@Max）。写到字段上的规则必须靠 @Valid 才会执行。
- **关键**：query 绑定对象（如 PageQuery）**默认不校验**，RequestBody 对象**默认也不校验** → **规范：凡要校验就显式加 @Valid**。
- 失败抛的异常不同，全局处理器分支：
  - `@RequestBody @Valid` → `MethodArgumentNotValidException`
  - `@Valid PageQuery`（query/表单）→ `BindException`
- **本次修复的真实 bug**：商品/订单列表方法缺 `@Valid`，且全局处理器漏了 BindException → 非法分页参数会返回 500 而非 400。现已修复（两处 page 方法加 @Valid + GlobalExceptionHandler 加 BindException 分支）。
- 自查：`GET /products?pageSize=9999` → 400 "pageSize 每页最多 100 条"

## 4. 商品列表 SQL 解读（selectOnSalePage）

一句话：**只返回在售商品，每个商品带"起售价"，分页输出。**

```sql
SELECT p.id, p.spu_name, ..., MIN(s.price) AS min_price
FROM t_product p
LEFT JOIN t_product_sku s ON s.product_id = p.id   -- 一个商品关联出多行(多个SKU)
WHERE p.status = 1                                   -- 先过滤：只要在售
GROUP BY p.id, ...                                    -- 按商品合并成一行
ORDER BY p.id DESC                                    -- 新的在前
LIMIT #{offset}, #{size}                              -- 分页 offset=(page-1)*pageSize
```

要点：
- **LEFT JOIN**：保左表所有行 → 没 SKU 的商品也保留（相对 INNER JOIN 不漏商品）
- **WHERE 先于 GROUP BY**：先过滤再聚合
- **GROUP BY** 把一商品的多个 SKU 合并成一行，`MIN(s.price)` 求起售价
- **GROUP BY 后 SELECT 的非聚合列必须都出现在 GROUP BY**（MySQL8 ONLY_FULL_GROUP_BY）
- **`#{}`** 预编译占位符、防 SQL 注入；`${}` 直接拼接、有注入风险
- resultType + `map-underscore-to-camel-case:true` → `spu_name`→`spuName`、`min_price`→`minPrice`

演练动画：见 `docs/sql-animation.html`（分步演示连接/过滤/聚合/排序/分页）

## 5. 运维备忘：spring-boot:run 子进程残留

- `mvn spring-boot:run` 会 fork 独立 java 子进程，Maven 退出后子进程可能残留继续占端口导致"Port in use"
- 排查：`Get-NetTCPConnection -LocalPort 8080 -State Listen` 拿 OwningProcess → `Stop-Process -Id <pid> -Force`
- 更干净的启动方式：`mvn package` 出 jar 后 `java -jar`（进程树单一好管理）

## 6. Sa-Token 工具类大白话（StpUtil / StpLogic）

### 核心思想（30 秒）
> Sa-Token 管"登录状态"：登录成功发一张"门禁卡"（token）；请求带卡 → 认出你是谁 → 放行/拒绝。帮你干了三件事：**发卡 / 认卡 / 收卡**。

### StpUtil —— "前台接待"（全静态方法，项目里直接用）
| 方法 | 大白话 | 本项目哪里用 |
|---|---|---|
| `login(id)` | 登录，给 id 用户发卡 | `UserServiceImpl.login` |
| `getTokenValue()` | 拿这张卡（token 字符串） | `login` 后返回给前端 |
| `getLoginId()` / `getLoginIdAsLong()` | 读卡：这是哪个用户 | `me` / 各 Service 取当前用户 |
| `logout()` | 收卡：让卡失效 | `UserServiceImpl.logout` |
| `checkLogin()` | 没带卡直接抛异常 | Sa-Token 拦截器默认行为 |

### StpLogic —— "幕后真身"
- `StpUtil` 每个方法内部都是调 `StpLogic("login")` 同名方法（默认体系）
- **多套登录体系**（如商城前台顾客 + 后台管理员）→ `new StpLogic("admin")` 各管一套，token 互相独立
- 一句话：**StpLogic = 一套完整登录体系；StpUtil = 默认那套的快捷方式**

### token 生命周期（本项目完整链路）
```
① login → StpUtil.login(userId) → 服务端存表 {token(uuid) → userId} → getTokenValue() 返回前端
② 前端存 localStorage，请求带 Authorization: <token>
③ 拦截器(SaInterceptor) 验 token → 有效放行；无效抛 NotLoginException → 全局异常返回 401
④ logout → StpUtil.logout() → 服务端删记录 → 旧 token 再拿来就 401
```

### 面试快问快答
1. **StpUtil 和 StpLogic 关系？** StpUtil 是静态门面，委托给默认 StpLogic；多套登录 new 不同 StpLogic。
2. **token 重启会怎样？** V1 存内存 → 重启全失效，需重新登录；V3 存 Redis → 不丢、多实例共享。
3. **防 token 被盗？** 基础版：有效期 7 天（`timeout: 604800`）；生产：HTTPS + 短有效期 + Redis 并发会话控制。

## 7. JWT 与 Sa-Token 的三种"卡"（重要对比）

| 方案 | 卡长什么样 | 服务端存表 | 能踢人/封号 | 重启/多实例 |
|---|---|---|---|---|
| **Sa-Token 默认**（V1 本项目） | 随机串 uuid | ✅ 存（内存 Map） | ✅ logout 真删 | 内存：重启全失效；Redis：共享 |
| **手写 JWT**（早期 order-system-v2） | `xxxx.yyyy.zzzz` 签名串 | ❌ 不存 | ❌ 只能等过期 | 天然无状态 |
| **sa-token-jwt** | JWT，由 Sa-Token 生成 | 默认存 / 可配无状态 | 默认 ✅ / 无状态 ❌ | 同上 |

### 关键认知：JWT 与"存不存表"是两个正交维度
| 凭证形态 | 随机串 | JWT（可验签、payload 可读） |
|---|---|---|
| 会话存储 | 服务端存表（可撤销） | 服务端不存（纯无状态） |

组合出：① 随机串+存表 = Sa-Token 默认；② JWT+不存 = 无状态 JWT；③ JWT+存表 = 有状态 JWT（sa-token-jwt 默认）。

### sa-token-jwt 是什么
> 把 `StpUtil` 内部"生成卡"那步，从"随机串+存表"换成"JWT 签名 + 可选存表"。**业务代码一行不改**，仍用 `StpUtil.login/getLoginIdAsLong`，变的只是 token 物理形态。

- **有状态模式（默认）**：payload 只有 loginId，会话仍存服务端 → token 防伪造（改 payload 会被验签发现），仍可踢人
- **无状态模式（`stateless: true`）**：所有会话数据塞进 payload，服务端零存储 → 无法强制踢人（logout 只丢前端卡，token 过期前仍有效）

### 面试话术（背）
> "V1 用 Sa-Token 内存模式，logout 能真删记录、可强制下线；V3 上 Redis 解决重启丢失和多实例共享；JWT 无状态方案我了解取舍：好处是服务端零存储、跨服务好验证，坏处是无法主动踢人只能等过期，所以电商这种需要封号/强制下线的场景，我更倾向有状态的 Redis 会话方案。"

### 本项目演进对照
```
V1  随机串 + 内存表      （最简单，重启全失效）
V3  随机串 + Redis 表    （重启不丢、多实例共享）← 官方推荐形态
V4? JWT + Redis 表       （拆微服务后想跨服务验签）
    或  JWT 无状态        （放弃踢人/封号能力时）
```

## 8. 有状态 JWT 的意义

### 相比"随机串+存表"，多三个收益
1. **凭证可本地验签**：多服务用共享密钥本地解签名即知真伪（不查表确认"是我们发的"）；随机串必须查共享会话表。→ V4 微服务后网关验签放行
2. **payload 携带身份摘要**：userId/role 直接读 payload（签名防篡改），很多场景不用查表
3. **渐进迁移路径**：想切无状态时关掉存表（stateless）即可，token 形态、业务代码都不用动

### 相比"无状态 JWT"，保留可撤销能力（最值钱）
| 能力 | 有状态 JWT | 无状态 JWT |
|---|---|---|
| logout 真删记录 | ✅ | ❌ |
| 封号/强制下线 | ✅ | ❌（只能等过期） |
| 限制并发登录数 | ✅ | ❌ |
| 服务端零存储 | ❌ | ✅ |

### 一句话总结
> 有状态 JWT = 既要 JWT 的"防伪 + 可读 + 可验签 + 可迁移"，又要存表的"可撤销、可踢人"。是工程折中；没有"多服务验签/将来想无状态"诉求时，随机串+Redis（Sa-Token 官方默认）更简单够用。

## 9. `StpUtil.getLoginIdAsLong()` 为什么不用传参（ThreadLocal 机制）

### 核心
> "当前登录用户"是**请求级上下文**：一次请求从头到尾在**同一个线程**执行，当前请求（连带 token）就在该线程的 **ThreadLocal** 里。所以 Controller → Service → Mapper 任何一层都能"无参"拿到当前用户。

### 完整链条（比"拦截器放 ThreadLocal"更准确）
```
① 请求进来（浏览器带 Authorization: <token>）
② Spring MVC DispatcherServlet 把当前 request 放进 RequestContextHolder（Spring 的 ThreadLocal）
③ Sa-Token 拦截器（SaInterceptor）：从 ThreadLocal 里的 request 读 token → 验 token → 查会话表 → 确认 userId → 放行
④ 业务代码 StpUtil.getLoginIdAsLong()：再走一遍"ThreadLocal 拿 request → 拿 token → 查会话 → 返回 userId"
```
关键：Sa-Token 不是"拦截器把 userId 塞 ThreadLocal"，而是**每次从 ThreadLocal 里的 request 现场取 token 再查会话**。

### 对比三种"取当前用户"方案
| 方案 | 做法 | 缺点 |
|---|---|---|
| 方法传参 | `cartService.list(userId)` 层层传 | 每个方法签名带 userId，啰嗦易漏 |
| request attribute（早期 order-system-v2 的做法） | `request.getAttribute("userId")` | 到处拿 request 对象 |
| ThreadLocal（Sa-Token 做法） | `StpUtil.getLoginIdAsLong()` 随时取 | 隐蔽：没显式传参，其实依赖请求上下文 |

> 早期项目 LoginInterceptor 就是"解析 JWT → request.setAttribute(userId)"，和 Sa-Token 本质同一件事，只是封装更优雅。

### ⚠️ ThreadLocal 两个坑（面试必问）
1. **异步线程拿不到**：ThreadLocal 不跨线程。`@Async`/线程池/MQ 消费者/定时任务没有请求线程 → 无上下文。**解决**：请求线程里先取出 userId，作为参数传进异步任务（V3 引入 MQ 后下单通知的消费者必须靠消息体携带 userId，不能靠上下文）。
2. **线程池复用会"串号"**：不清理 ThreadLocal，下一个请求可能读到上一个用户的 id → 越权。Spring 的 RequestContextHolder 在请求结束自动清理，这是框架管清理的原因。

### 面试话术
> "`StpUtil.getLoginIdAsLong()` 不传参的原理：Spring MVC 把当前 request 放进 RequestContextHolder（ThreadLocal），请求处理全程同一线程，Sa-Token 从 ThreadLocal 里的 request 读 token、查会话得到 userId。它和早期手写 JWT 的 request.getAttribute 是同一思路，只是封装在框架里。注意 ThreadLocal 的坑：异步线程会丢失上下文（要显式传参），线程池复用要靠框架正确清理避免串号。"
