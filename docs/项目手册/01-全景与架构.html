1.1项目定位与核心闭环

一句话定位 掌握

对应文档：README.md · 项目设计文档.md 第 1 章

一句话：一个"内容社区为流量入口、电商交易为变现主干、AI 为智能引擎"的种草商城，三块互相供血，缺一块商业闭环就断。

内容社区 掌握

发种草笔记（图文 + 关联商品）→ 刷 Feed 流 → 点赞收藏。
为什么需要它：没有 UGC，商城就只是个普通 CRUD。内容带来两样别人简历上没有的东西——非结构化长文本（RAG 的语料）和热点写（点赞、浏览、热榜的真实高并发场景）。

→ 04 页

电商交易 掌握

浏览商品 → 加购物车 → 下单 → 支付 → 收货。
为什么需要它：这是资损场景的集中地。超卖一次、重复支付一次，都是真金白银。面试官所有"并发/事务/幂等"的追问，最终都会落到这条链上。

→ 02 / 03 页

AI 导购 了解

AI 客服问答：能调工具查商品（Function Calling），也能基于说明书与笔记回答"用起来怎么样"。
为什么需要它：给前两块提供业务合理性，也让技术叙事有落点。但它是了解层，不是主角——开口先讲交易与并发，AI 只说"业务场景之一"。

→ 06 页

三块为什么能互相支撑？——它们是一条链上的上下游，不是三个并排的功能：

发笔记UGC 产出
被种草Feed / 搜索
看商品笔记关联商品
下单防超卖 / 幂等
支付验签 / 回调
回社区晒单再产 UGC
打个比方 这不是"三个独立的店拼在一个商场里"，而更像一家餐厅的"招牌菜 → 排队 → 点单 → 复购"：内容社区是门口飘出来的香味（获客），电商是后厨（变现），AI 是服务员（提升转化）。 香味不能直接变成钱，但没有香味，后厨就没客人——这就是"AI 只了解层、但内容社区是地基"的由来。
机制与代码

这个闭环不是 PPT 上的箭头，它在数据库与代码里有对应的落点：

  • 内容 → 商品：t_note_product（笔记关联商品，即"种草清单"）
  • 商品 → 订单：t_cart → t_order + t_order_item
  • 订单 → 支付：t_payment（uk_order_id 兜住"一订单一活单"）
  • 回到社区：口碑沉淀成新的 t_note，同时成为 RAG 语料（t_knowledge_chunk）

统一入口的返回体是 R{code,msg,data}，前端只认这一种结构，所以任何一层的失败都能被同一种方式处理：

common/api/R.java:11-17, 32-33
public class R<T> {
    public static final int CODE_SUCCESS = 200;
    private int code;
    private String msg;
    private T data;
    ...
    public static <T> R<T> ok(T data) {
        return new R<>(CODE_SUCCESS, "操作成功", data);
    }
面试怎么讲
30 秒版本 "我做的是一个种草商城，定位是内容社区做流量入口、电商交易做变现主干、AI 做智能引擎。它不是三个功能拼在一起—— 内容社区产出笔记，笔记关联商品形成种草，用户被种草后下单支付，订单完成后又回来晒单产新内容，是一条闭环。"
别说错 别把 AI 说成项目主打。正确顺序是：先说内容 + 电商这条闭环，AI 一句带过。 面试官听到"AI 商城"第一反应是"蹭热点"，你要用"内容社区是 V3 许多技术的地基"把他按回传统后端语境——笔记必须有内容域，点赞热榜才有东西可点。

1.2设计方法论：三问筛伪需求

三问宪法 掌握

对应文档：项目设计文档.md 第 2 章（原文称"本项目的设计宪法"）

一句话：每引入一个技术栈之前，先过三关，任一关答不上来就不做。这是让"技术堆砌"变成"业务驱动演进"的唯一手段——也是面试里最能体现思维层次的点。

  1. 砍掉它，系统会出什么真实业务问题？ 答不上来 = 硬塞。比如"砍掉 RabbitMQ"→ 笔记发布要等 AI 审核几秒，用户体验崩坏。业务问题是技术选型的唯一入场券。
  2. 真实企业里它怎么用？我这是不是"玩具用法"？ 用法失真 = 一问就露馅。比如"购物车用 Redis Hash"在某些场景没错，但本项目的京东式购物车要"多端同步 + 持久化 + 失效分组"，那是 MySQL 的强项。
  3. 2026 年了，这方案还是主流吗？ 过时 = 主动暴露短板。比如 RAG 现在的主流是 Hybrid（向量 + BM25）+ Rerank，而不是朴素"分块 + 向量检索"。
打个比方 "三问"就像买工具前先问自己：这活儿没它真干不了吗？别人是这么用的吗？这型号是不是已经淘汰了？ 三个都过再掏钱——比"五金店看到什么顺眼买什么"靠谱得多。项目里每多一个中间件，面试官就多一个可以捅你的洞。
配套的口径纪律（最容易被追问的一条）："数据量是触发条件的标尺，不是选型的理由"。 错误说法："商品才 100 个，所以 LIKE 够用"——被问"那 50 万商品呢"就崩，且等于自认是玩具。 正确说法："商品搜索目前是最简实现，成熟方案还没做；它会在数据量上升、前缀通配导致全表扫时塌，触发条件是十万级或 P99>200ms，目标方案是 ES"。 注意："量级"只允许出现在触发条件里，不允许出现在理由位里。
机制与代码：三问落到实物上的样子

"砍掉它会怎样"不是空谈，它直接反映在代码注释里。比如购物车为什么不搬 Redis，Flyway V1 的建表注释就写死了理由：

db/migration/V1__init.sql:89-91
-- ★ 购物车采用「京东模式」：MySQL 持久化 + 实时库存校验 + 失效分组 + 原子 UPSERT。
--   之所以不用 Redis Hash：京东式购物车要"多端同步 + 持久化 + 失效商品分组"，这是 MySQL 的强项。
--   V3 引入 Redis 后也【不迁移】购物车，而是用它缓存"购物车读"，各司其职。

同样地，t_product_sku.version 字段也被注释钉死了口径——它是一个被"三问"判过死刑的伪需求（有 version 但没用它）：

db/migration/V1__init.sql:71
version INT NOT NULL DEFAULT 0 COMMENT '★预留字段，当前【未用作乐观锁】。
    防超卖靠 UPDATE ... WHERE stock>=? 的行锁 CAS（见 OrderServiceImpl）'
面试怎么讲
30 秒版本 "我给项目定了一条设计原则：每加一个技术之前先过三关——砍掉它会不会出真实业务问题、企业里是不是这么用、2026 年了这方案还主流吗。 比如我没上 Elasticsearch，不是因为数据少，而是商品的成熟搜索方案我还没做，我知道它会在什么条件下塌、换它的触发条件和目标方案是什么。 我更在意每个决策能不能说清'为什么做'和'为什么不做'。"
别说错 讲"三问"时千万不要顺手举个例子说"因为数据量小"——这是最容易翻车的地方，一句话就把自己降格成玩具项目。 两个安全例子：砍掉 MQ 审核就卡体验、砍掉 RAG 长文本塞不进 prompt。

1.4代码目录结构

四块工程 + 按业务域分包 熟悉

核实命令：find backend ai-service gateway -name "*.java" | wc -l → 192

一句话：仓库由 backend（主单体 177 类）、ai-service（唯一独立服务 13 类）、gateway（网关 2 类）、frontend（Vue3） 四块组成；主单体内部按业务域分包，而不是按 controller/service/mapper 横切分层。

为什么按业务域分包，而不是按技术分层分包？（这是面试官很爱问的架构题）

按业务域分包（本项目）
user / goods / content / order / pay / ai —— 每个域自带 controller / service / mapper / bean / dto。 好处：① 改一个业务只动一个目录，边界清晰；② 为 V4 拆服务埋好了刀口——真要拆，把整个 goods/ 目录搬走即可，不用在几十个横切包里挑文件；③ 新人看目录就知道系统有哪几块业务。
按技术分层分包
controller/ service/ mapper/ 三个大平层，所有业务的类都堆在里面。 问题：① 一个需求的改动散落在三个目录，改完容易漏；② 想拆服务时无从下手——"订单相关的类"要从三个大包里翻出来；③ 目录看不出业务全貌。
机制与代码

分包原则写在启动类注释里，是被"三问"审过的设计决策，不是随手建的包：

backend/…/AimallApplication.java:6-17
/**
 * AI 种草商城 —— V1 MVP 单体应用
 *
 * <p>启动类。按业务域分包（user/content/goods/order/ai），为 V4 拆微服务预留边界。
 * Mapper 采用逐接口 @Mapper 方式注册（风格与早期项目一致，无 @MapperScan）。</p>
 */
@SpringBootApplication
public class AimallApplication {
    public static void main(String[] args) {
        SpringApplication.run(AimallApplication.class, args);
    }
}

注意最后一句：Mapper 是逐接口 @Mapper 注册的，没有用 @MapperScan。这是有意为之——启动类不扫描才能保持每个 Mapper 的归属域显式可见（真被问到就答"显式优于隐式，且便于按域迁移"）。

面试怎么讲
30 秒版本 "项目虽然是单体，但我从 V1 起就按业务域分包，user/goods/content/order/pay/ai 每个域自带 controller、service、mapper。 这么做的直接好处是——V4 我只花了很小的代价就把 AI 拆成了独立服务，因为边界早就划好了。我是先想清楚"将来可能拆哪块"，再决定今天怎么组织目录的。"
别说错 别把"按域分包"吹成"微服务架构"。正确口径是"只拆了 ai-service，主体保持单体"。 分包是为拆分预留边界，不等于已经拆了——说成微服务会被追问 Nacos 服务列表、Feign 接口、分布式事务，一问就穿帮。

1.6一次请求的完整旅程

以「下单」为例：从浏览器到 MySQL 再回来 掌握

链路来源：gateway/TraceIdGlobalFilter.java · config/SaTokenConfig.java · order/service/impl/OrderServiceImpl.java

一句话：选"下单"（POST /api/v1/orders）是因为它穿过了全部七层，且每层都干了非它不可的事。看懂这条链，其他接口都是它的简化版。

浏览器axios 带 Token
Vite 代理/api → 9000
网关 9000注入 traceId + 路由
FilterTraceIdFilter 塞 MDC
拦截器Sa-Token 校验登录
Controller接参 + 校验
Service事务 + 业务
Mapper → MySQL行锁 CAS

关键不是"经过了哪几层"，而是每一层真正做了什么：

层它真正干的事（这才是要背的）
浏览器 / Viteaxios 拦截器统一挂 sa-token 头；Vite 把 /api 代理到网关 9000。前端只认一个入口，不感知后端拆了几个服务。
网关 9000TraceIdGlobalFilter（@Order(-1)，最先执行）生成或沿用 X-Trace-Id，加进下游请求头并回写响应头；按 mall_api 路由把 /api/** 转发到 lb://mall-app。顺带把 /internal/** 一律返回 404（内部接口不对公网暴露）。
Servlet FilterTraceIdFilter（HIGHEST_PRECEDENCE）把 traceId 放进 MDC，让本进程所有日志都带上它；finally 里必须 clear()——线程池复用不清会串号。
Sa-Token 拦截器SaInterceptor 拦 /api/**，默认全部需要登录，例外有三类：完全公开（登录/注册、支付回调、/internal/**、/error）、匿名只读（商品与笔记的 GET：列表/榜单精确匹配，详情要求前缀 + 纯数字 id）、其余一律校验登录。未登录抛 NotLoginException → 全局异常 → R.fail(401)。放行 ≠ 裸奔：回调靠验签、内部接口靠 HMAC 签名。
Controller薄薄一层：接 DTO（@Valid 校验）、取当前用户、调 Service、包 R.ok(...)。不写业务逻辑。
Service业务的真正所在：@Transactional 事务边界 + 幂等 token 消费 + 逐项校验 + 行锁 CAS 扣库存 + 落单 + 发延迟消息（afterCommit）。
Mapper → MySQLXML 里手写 SQL；UPDATE … WHERE id=? AND stock>=? 由 InnoDB 行排他锁 + 条件更新保证原子，返回 0 即库存不足。
返回统一 R{code,msg,data} 原路返回；任何一层抛的 BusinessException 都被 @RestControllerAdvice 兜成同结构，不把堆栈泄漏给前端。
打个比方 把请求想成一份要去公司大楼办的公文：Vite 是"指路牌"（把你送到正确的大楼）；网关是门卫（盖一个"访问编号" traceId，并告诉你哪些楼层不对外）；Filter 是走廊里的监控（编号跟着你走遍全程）；拦截器是刷卡闸机（没工牌进不去）； Service 才是真正办事的柜台；出事时接线员（全局异常）统一给你一句人话，而不是把内部流程图摔你脸上。
机制与代码（两段就够）

网关为什么是链路第一跳——它是唯一能"生成 traceId 并透传给所有下游"的地方：

gateway/…/filter/TraceIdGlobalFilter.java:46-54
String incoming = request.getHeaders().getFirst(TRACE_HEADER);
String traceId = (incoming != null && !incoming.isBlank())
        ? incoming
        : "gw-" + UUID.randomUUID().toString().substring(0, 8);
ServerHttpRequest mutated = request.mutate().header(TRACE_HEADER, traceId).build();
exchange.getResponse().getHeaders().set(TRACE_HEADER, traceId);

于是 grep <traceId> 能跨 gateway / mall-app / ai-service 三个进程捞出同一次请求的全部日志。这是 V1.5 埋的伏笔在 V4 兑现。

面试怎么讲
30 秒版本 "以一次下单请求为例：前端只认 /api 一个入口，Vite 代理到网关。网关做两件事——注入 traceId 让链路日志可 grep，以及把内部接口 404 掉。 进到应用后，Filter 先把 traceId 塞进 MDC；Sa-Token 拦截器校验登录态；Controller 只接参不写逻辑；Service 里开事务，先做幂等、再靠 WHERE stock>=? 的行锁 CAS 扣库存，最后在事务提交后投递延迟消息。 返回统一是 R{code,msg,data}，异常都被全局兜底成同样结构、不泄漏堆栈。"
别说错 两条最容易翻车的：① 扣库存说成"乐观锁"—— t_product_sku.version 是纯预留字段，正确说法是"行锁 + WHERE stock>=? 条件更新，CAS 思想"。 ② 说"网关做了鉴权"——项目里鉴权在应用的 Sa-Token 拦截器，网关只做 traceId 注入、路由、遮内部接口。把职责说错，面试官会顺着问网关的鉴权过滤器，你就接不住了。

机制与代码：为什么"只增不改"

Flyway 校验已执行脚本的 checksum，改了旧脚本会直接启动失败。所以表结构的演进方式只能是"新加版本文件"：

db/migration/V1__init.sql:8-11
-- 迁移约定：
--   1. 只做增量，不修改已执行的迁移文件（已执行文件的 checksum 会被校验）。
--      要改表结构请新增 V2__xxx.sql、V3__xxx.sql……
--   3. 不使用 DROP TABLE —— 迁移脚本必须是"向前"的，删表另写迁移。

V4 与 V5 正是这条约定的样板：两者都不建表，只做一次"清理或调整"——V4 把并发双击产生的重复支付单收拾干净后建立 uk_order_id；V5 给 t_note 加审核版本号、并把 t_audit_record 的唯一键从 3 列扩成 4 列（列变多只会更宽松，不会让存量数据违例）。

面试怎么讲
30 秒版本 "数据库一共 24 张表，由 Flyway 的 5 个迁移脚本管理：V1 十张打底（用户/商品/订单/会话），V2 十张做内容社区和 RAG 语料，V3 四张做支付和限量发售，V4 不加表、只加了一个唯一索引兜支付幂等，V5 也不加表——它给笔记加了审核版本号、并把审核流水的唯一键扩成四列，修掉一个幂等键退化导致的确定性缺陷。 我在设计上坚持表结构只增不改，因为 Flyway 会校验 checksum，改历史脚本等于让所有人启动失败——这也是为什么我特意保留了 version 这种'当前没用到'的字段：它是我明确标注过的预留，不是我忘了删。"
别说错 被问"你这张关注表怎么用的"——直说"这是预留表，关注流规划在 V5、还没实现"。 硬编一个关注流的实现，面试官让你讲拉模式推模式、大 V 写放大，你立刻露馅。诚实边界是加分项，编造才致命。

1.9面试怎么讲"介绍一下你的项目"

这是每个面试的第一问，也是你唯一能主动定义整场节奏的机会。下面两段直接可背——但顺序比措辞重要：先传统后端，AI 最后一句带过。

30 秒版本（面试官还在翻简历时用） "我做的是一个'AI 种草商城'，本质是一个内容电商平台：内容社区是流量入口，电商交易是变现主干，AI 是智能引擎，三者是一条闭环—— 用户发笔记被种草、看商品下单支付、完成后回社区晒单。 技术上我用 Spring Boot 3 单体起步，按业务域分包，然后按版本演进：V1 跑通下单闭环并解决防超卖，V1.5 补工程基建，V2 加内容社区和消息异步，V3 做支付与限量发售的削峰治理，V4 只把 AI 拆成独立服务。 每一步我都能说清'为什么这么做、为什么不那么做'。"
90 秒版本（面试官开始记笔记时用） "这个项目的核心是三条闭环：内容社区产出笔记、笔记关联商品形成种草、下单支付后口碑沉淀回社区。

技术上我重点做的几块：①下单防超卖——用 WHERE stock>=? 的行锁 CAS 条件更新，不是乐观锁；②限量发售削峰——"Redis 预减挡量、MQ 摊峰、DB CAS 保正确"三层，投递失败还做了对称回补；③幂等设计——四种手段（唯一索引 / 状态机条件更新 / 一次性 token / 消费端回查）各有真实落点；④缓存三兄弟——穿透空值标记、击穿互斥锁重建、雪崩 TTL 加随机，而且 Redis 挂了自动降级走 DB；⑤Feed 流游标分页——热度排序用 (hot_score, id) 二元组游标兜住页边界。

边界我也清楚：AI 和微服务是我的了解层，只拆了 AI 服务，主体还是单体；商品搜索目前是最简实现，成熟方案我还没做。"
开场别先讲 AI（最重要的一条） 面试官听到"AI 商城"的第一反应是"这是不是蹭热点"。你一开口就讲 Function Calling、RAG、向量检索，只会强化这个怀疑，而且把战场拉到你的弱项上。
正确顺序：先讲传统后端硬骨头（防超卖 / 幂等 / 缓存 / 消息 / 事务），让面试官先认可"这人有真东西"；AI 放在最后，并且用"业务场景之一"来定性——"AI 会在 AI 客服这个场景用到，我定位为了解层，重心在传统后端体系"。
这条纪律贯穿整本手册：06 页 AI 模块只需要 15 分钟，05 页高并发才是要背到滚瓜烂熟的王牌。
开口前再默念一遍口径红线 不说"乐观锁"（说"行锁 + WHERE stock>=? 条件更新，CAS 思想"）； 不说"幂等四式"（说"幂等设计的四种手段"）； 不说"微服务架构"（说"只拆了 ai-service，主体是单体"）； 不说"RAG 什么都能答"（说"RAG 只答非结构化内容，价格库存走 SQL"）； 不说"用 MySQL 全文索引搜商品"（全文索引用在笔记上，商品是 LIKE）。 完整红线见 08 页——这五条说错一条，前面讲得再好都会被扣分。
