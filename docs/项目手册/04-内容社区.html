04 · 内容社区

这页讲项目的「流量入口」——内容社区。它把一个普通 CRUD 商城变成了真实场景，代价是引入两个绕不开的技术问题：高并发互动（点赞/收藏/浏览，热点行被反复写）与非结构化数据检索（用户写的笔记怎么搜得到）。看完你能讲清：Feed 流为什么不能用 OFFSET 深分页、二元组游标凭什么必须存在、20 篇笔记怎么做到不发出 41 次查询、中文全文检索为什么必须 ngram。

阅读约 30 分钟 面试权重 ★★★ 涉及 10 张表 / 32 个类
本页的分工边界（先看这条，免得看串） 本页只讲内容域自己的设计取舍。凡是「跨页面横切主题」一律一句话带过并注明去向： MQ 可靠性闭环（confirm/returns、死信、补偿任务、幂等三防线细节）、缓存三兄弟、限流、降级体系 全部在 05 高并发与可靠性 讲透。

4.1内容域全景：10 张表各管一件事

内容社区听起来很玄，拆开就是一件事：把「用户写的东西」存下来、排好序、能被搜到、能被互动。V2 迁移文件 V2__content_and_rag.sql 用 10 张表把这四件事拆开，每张表只管一件。

打个比方 这 10 张表就是一间小出版社的部门分工：t_note 是编辑部（正文和状态），t_note_image 是美编（配图），t_note_tag 是目录员（贴分类标签），t_note_product 是商务（把文章和商品挂钩），t_note_like/collect 是读者留言簿，t_audit_record 是审稿档案室，最后两张 t_knowledge_* 是给 AI 用的资料卡片柜。 关键点：没有一张表是「顺便建的」——每加一张表都对应一个「不做就会出问题」的场景。
机制与代码：三个「为什么单独建表」的决策

① 标签为什么独立成表，不在 t_note 加 JSON 列？JSON 列三样都弱：不能高效索引（按标签筛选要全表扫）、不能聚合（将来做热门话题榜要 GROUP BY）、不能加约束。独立表一行一个标签，idx_tag 直接支持「按标签筛笔记」。

② 审核为什么有独立流水表？AI 判定是概率性的——会判错。判错就要能翻案（ai_result_json 存原始返回）、要能人工复核（reviewer 字段）、要能幂等（版本唯一键）。只在主表打一个状态，出问题就是黑箱。

③ 关注表建了却不用，算过度设计吗？不算。表是数据结构（Flyway 迁移只增不改，早建晚建成本一样），接口是行为（等 V5 关注流真要做时再加）。这是"按需演进"的边界感，不是过度设计。

4.2笔记模型：一篇笔记怎么关联多个商品和多个标签

一对多用关联表，不用字段拼接 掌握

对应代码：NoteCreateRequest.java / NoteExtraMapper.xml / NoteServiceImpl.saveExtras

一句话：一篇种草笔记要挂「最多 9 张图 + 最多 10 个标签 + 若干个关联商品」，这是一对多；项目用三张关联表存，而不是在 t_note 里塞 tags = "平价好物,通勤穿搭" 这种拼接字符串。

打个比方 拼接字符串就像把一本书的所有标签写在一张便利贴上贴在书脊——看着省事，但你想找「所有贴着『通勤穿搭』的书」时，只能一本一本翻过来读那张便利贴，没有任何目录能帮你。 关联表则是图书馆的索引卡片柜：一行一条关系，随时能按标签反查、能统计「这个标签下有几本书」、能保证不重复。

4.3Feed 流：为什么 LIMIT 100000, 20 不行

OFFSET 深分页的成本，与游标分页的代价 掌握

对应代码：NoteQuery.java（类注释就是这题的答案） · NoteMapper.xml#pageWhere + selectPage

一句话：Feed 流是「一直往下滑」的场景，用 LIMIT offset, size 翻到深处时，MySQL 必须先扫描并丢弃前 offset 行才能返回 size 行——用户滑得越深，你付的扫描成本越高，这个曲线在产品上就是「惩罚深度用户」。游标分页把这笔账变成常数。

打个比方 OFFSET 分页像老师点名叫第 5000 号同学上台：他必须从第 1 号开始逐个念过去，「5000 号之前的 4999 个人我都不需要，但我必须一个个数到那里」。 游标分页像直接说「从刚才那位同学后面接着来」：上一页最后一条的 id 就是那个「刚才那位」，WHERE id < cursorId 靠主键索引直接定位到起点，翻到第几页开销都一样。
机制与代码：复杂度对比 + 真实 SQL

先把「慢在哪」说透：关键不在「返回了 20 行」，而在为了这 20 行必须先读过 10 万行——被 LIMIT 丢弃的行照样要走一遍索引、照样可能回表。t_note 的 content 是 TEXT 字段，朴素写法连大字段都得读出来。

朴素 OFFSET 写法（反例）t_note · content 为 TEXT
SELECT * FROM t_note ORDER BY id DESC LIMIT 100000, 20;
-- MySQL 的执行方式：扫描并丢弃前 100000 行，然后返回 20 行
OFFSET 深分页

复杂度 O(offset + size)，随页深线性增长。

定位方式：扫过并丢弃前面所有行。

并发新增数据会错位/重复：你翻第 2 页时有人新发一条，第 1 页的末条被推到第 2 页，LIMIT 20,20 会把它再显示一次。

唯一优势：能跳页。

游标分页（本项目）

复杂度 O(logN + size)，与翻到第几页无关。

定位方式：WHERE id < cursor 用主键索引直接跳到起点。

并发新增不受影响：游标锚定在具体 id 上，新数据只会出现在最前面。

代价：不能跳页、不能显示总页数。

真实的 SQL 长这样，注意最后那行注释——游标分页最直观的标志就是 SQL 里根本没有 offset 这个数：

resources/mapper/NoteMapper.xml:96-111（selectPage）
<select id="selectPage" resultType="com.aimall.content.bean.Note">
    SELECT <include refid="Base_Column_List"/> FROM t_note
    <include refid="pageWhere"/>
    <choose>
        <when test="orderBy != null and orderBy == 'newest'">ORDER BY id DESC</when>
        <otherwise>ORDER BY hot_score DESC, id DESC</otherwise>
    </choose>
    <!-- 游标分页没有 offset：直接 LIMIT pageSize -->
    LIMIT #{pageSize}
</select>

服务层判断「还有没有下一页」也很朴素——本次拿满一页就认为还有：boolean hasMore = notes.size() >= query.getPageSize();（NoteServiceImpl.java:118）。

面试怎么讲（含「代价」这一段，必须主动说）
30 秒版本 "LIMIT 100000, 20 慢的原因不是返回 20 行，而是为了这 20 行必须先扫描并丢弃前 10 万行，这些被丢弃的行照样走索引。所以 OFFSET 的复杂度是 O(offset + size)，页数越深越慢。我改用游标分页：第一页照常 LIMIT 20，第二页带上上一页最后一条的 id，写成 WHERE id < cursorId ORDER BY id DESC LIMIT 20——靠主键索引直接定位起点，复杂度 O(logN + size)。代价我也能说：它不能跳到第 N 页，只能连续翻，所以后台管理那种要跳页的列表我还是用 offset——两种方案按场景选，不是谁替代谁。"
别说错 三处容易踩：
① 不要说「游标分页全面优于 OFFSET」——它不能跳页、不能显示总数，是有代价的交换。承认边界比绝对化说法加分。
② 别把慢的原因说成「返回数据多」——返回的都是 20 条，差别在扫描量。
③ 如果对方追问「非要用 offset 怎么办」，答延迟关联：子查询只走覆盖索引拿 id（不回表、不读 TEXT），外层再按主键取 20 行——它省掉了 10 万次回表，但扫描量随页深增长这件事没解决，要根治还是游标。

4.4二元组游标 (hot_score, id) 本页最易讲错

为什么最新排序一个 id 就够，热度排序就必须两个 掌握

对应代码：NoteMapper.xml#pageWhere:73-94 · NoteQuery.java:34-42

一句话：游标必须和排序键配套。按 id 排序时，id 单调且唯一，「下一页」定义得出来，单列游标就够；按 hot_score DESC, id DESC 排序时，热度会并列，单列游标在页边界上会漏数据——所以游标必须是 (hot_score, id) 这个二元组。

打个比方 排序键就是排队规则，游标就是「队伍从哪儿继续」的那句话。
如果队伍按「号码」排（id 递增、人人不重号），你说「从 105 号之后继续」毫无歧义。
但如果队伍按「考试分数」排，而满队都是 100 分的人，你只说「从 100 分之后继续」——后面那些同样考 100 分的人就被你一句话跳过了。必须补一句「100 分里，从 105 号之后继续」，才说得清。
机制与代码：用 5 条热度都是 100 的笔记走一遍

设 5 篇笔记的热度全是 100，id 分别是 1081 / 1077 / 1065 / 1042 / 1013，页大小 = 2。查询是 ORDER BY hot_score DESC, id DESC。

第 1 页：没有游标条件，返回 1081, 1077。前端把「上一页最后一条」的排序值带回来：{hotScore: 100, id: 1077}。

第 2 页 · 错误写法（只用 hot_score 单列游标）：

单列游标（反例）漏掉同热度后续笔记
WHERE hot_score < 100 ORDER BY hot_score DESC, id DESC LIMIT 2;
-- 结果：空集！
-- 因为剩下 1065 / 1042 / 1013 三篇的热度都等于 100，
-- 严格小于 100 一条都不满足 → 用户往下滑，Feed 直接断了（漏 3 条）

第 2 页 · 正确写法（二元组游标）：

二元组游标（本项目）先比热度，平了再比 id
WHERE hot_score < 100
   OR (hot_score = 100 AND id < 1077)
ORDER BY hot_score DESC, id DESC LIMIT 2;
-- 结果：1065, 1042  （正确）
-- 第 3 页游标变成 (100, 1042) → 1013 → 正常收尾

那「只用 id」行不行？在这个「热度全相同」的例子里侥幸正确（因为热度全平，id 逆序恰好等于排序序）。但现实中热度是分层的，一旦分层就错位——排序序是 (200,id30) → (150,id45) → (100,id50) → (100,id40) 时，第 1 页返回 200/30 与 150/45，单列 id 游标写 id < 45，就会把本该出现在第 2 页的 100/50 直接跳过。所以不能用「热度相同时碰巧对」赌正确性。

真实 SQL 原文（注意上面那段警告注释就写在代码里）：

resources/mapper/NoteMapper.xml:73-94（pageWhere 的游标段）
<!--
  ★ 游标必须与排序键配套，否则会漏数据：
    - 按最新排(id DESC)：游标 = id < cursorId
    - 按热度排(hot_score DESC, id DESC)：游标是二元组
      (hot_score < cursorHot) OR (hot_score = cursorHot AND id < cursorId)
      只用 id 做游标会漏掉"热度更高但 id 更小"的笔记。
-->
<choose>
    <when test="orderBy != null and orderBy == 'newest'">
        <if test="cursorId != null">
            AND id < #{cursorId}
        </if>
    </when>
    <otherwise>
        <if test="cursorHot != null and cursorId != null">
            AND (hot_score < #{cursorHot}
            OR (hot_score = #{cursorHot} AND id < #{cursorId}))
        </if>
    </otherwise>
</choose>

载体是 NoteQuery 的两个字段：cursorId（主游标）和 cursorHot（「热度排序时的游标第二分量」）——前端只要把上一页最后一条的 id + hotScore 一起带回来就行（NoteQuery.java:39-42）。

面试怎么讲
30 秒版本 "游标必须和排序键配套。按最新排序时 id 单调唯一，单列游标就够，写 WHERE id < cursorId；按热度排序时热度会并列，两篇笔记可能都是 100 分，如果游标只带热度，WHERE hot_score < 100 会把剩下所有 100 分的笔记全漏掉；只用 id 又不行，因为热度排序下 id 无序，页边界会错位。所以游标是 (hot_score, id) 二元组：WHERE hot_score < ? OR (hot_score = ? AND id < ?)。通用规律是：排序键有 N 列，游标就是 N 元组，最后一列必须是唯一键——比如按创建时间排，游标就该是 (created_at, id)。"
别说错 ① 不要说「游标就是一个 id」——这是本页最容易翻车的一句话。默认排序是热度，两个字段都得带。
② 不要只说结论不说后果——「漏数据」三个字太轻。要能说出「同一热度的笔记在页边界整批消失，用户看到的 Feed 会断」，这才叫懂。
③ 主动补一句边界：热度分是运行期会变的排序值（点赞让 hot_score 变大），所以热度排序天然存在轻微「漂移」；id 自增永不变，最稳。Feed 类场景常用发布时间/id 排序，就是为这个。

4.5N+1 攻防：20 篇笔记怎么不发出 41 次查询

列表接口优化的第一答：批量 IN + 内存分组 掌握

对应代码：NoteServiceImpl.assembleList:236-305 · NoteExtraMapper.xml / NoteLikeMapper.xml

一句话：Feed 返回 20 篇笔记，每篇都要显示作者昵称、封面、标签、关联商品、「我点过赞吗」——如果在循环里逐篇去查，就是 1 次列表 + 20×N 次关联查询（101 条 SQL）。解法是先把 20 个 id 收起来，一次 IN 查回来，再在内存里分组拼装。

4.6中文全文检索：FULLTEXT + ngram

为什么中文必须加 WITH PARSER ngram 掌握

对应代码：V2__content_and_rag.sql:38 / :151 · NoteMapper.xml:66-69 · KnowledgeMapper.xml:69-74

一句话：用户搜「降噪耳机」，如果用 LIKE '%降噪%' 就是全表扫描（前缀通配让 B+ 树索引全废）；如果建默认的 FULLTEXT 索引，中文一句话会被当成一个词，检索照样全失效。所以中文全文索引必须显式声明 WITH PARSER ngram，让 MySQL 按 2 个字符一组 切词建索引。

打个比方 MySQL 的默认全文解析器是为英文设计的：英文有空格，「noise cancelling headphones」天然就是三个词，按空格切开就行。 中文写「主动降噪耳机」中间一个空格都没有，默认解析器看它就是一整个词——你搜「降噪」，库里没有任何一个「词」等于「降噪」，自然一条都搜不到。 ngram 解析器的做法是改用「两字一截」的切法：主动 / 动降 / 降噪 / 噪耳 / 耳机。这样「降噪」这个词在索引里真实存在，才搜得到。

4.7点赞收藏：唯一索引幂等 + 计数不丢

狂点红心也只会有一条记录 掌握

对应代码：NoteServiceImpl.like:157-174 · NoteLikeMapper.xml:6-13 · V2__content_and_rag.sql:77

一句话：用户狂点红心（前端防抖失灵）时，两个「点赞」请求会同时到达。如果代码先 SELECT 再 INSERT，两个线程都会查到「没点过」然后各插一条——正确性交给 t_note_like 上的联合唯一索引兜底，撞键就当作「已点过」静默成功。

打个比方 「先查后插」就像两个人同时走进一间空会议室，都探头看了一眼说『没人，我进去』——他们看的那一眼是同一瞬间，所以两个人都进去了。 唯一索引则像会议室门口那把只有一把钥匙的锁：两个人同时伸手，物理上只有一个能拧开，另一个撞在锁上。把并发正确性交给数据库的唯一约束（物理层面拒绝），比在应用代码里判断可靠得多。

可以主动交代的真实缺陷（说出来比不说值钱） ① 口径不一致：全量重建只灌热度最高的 1000 篇，但增量刷新（refreshHotScore）不受这个限制——任何被点赞的笔记都会 zAdd 进榜。结果是一篇靠点赞爬进榜、但排名在 1000 名之外的笔记，下一次全量重建会把它静默擦掉，榜单随重建周期出现锯齿抖动。这不是性能问题，是正确性问题（增量与全量的口径必须一致）；解法有：增量侧加同样的边界判断、全量侧不做 delete 而是「灌全部 + 定期裁剪」、或用影子 key 原子切换。
② 先删后灌有毫秒级空窗，这期间读榜单会拿到空列表。标准解法是影子 key + RENAME 原子替换（Redis 的 RENAME 是原子的）。本项目接受这个空窗，因为榜单是派生数据——但要主动说「我知道标准解法是影子 key」，否则就是没意识到。
边界一句话（这条也是分水岭） 榜单是派生数据，可以容忍短暂不准——这正是敢用「增量 + 最终一致」的前提。反过来说：库存、金额是账目数据，绝不能这么干，必须强一致 + 条件更新兜底。能主动画出这条线，才算真懂自己为什么敢用 zset。

限流（一句话带过）：AI 对话接口用 Redis INCR + EXPIRE 的 Lua 原子固定窗口（aimall:rate:chat:{userId}，10 次 / 60 秒；RedisOps.allow，RedisOps.java:226-245）。为什么不拆成两条命令、固定窗口的 2 倍边界缺陷、Redis 挂了为什么是放行而不是拒绝——全部在 05 高并发与可靠性 讲透。

面试怎么讲
30 秒版本 "热门榜我用 Redis zset，因为排行榜需要三件事：去重、按分数排序、取 Top-N——只有 zset 一条结构同时满足，而且都是 O(log N) 级别。热度公式是点赞×3 + 收藏×5 + 浏览×1，收藏权重最高，因为它是最强的兴趣信号。维护用双轨：增量刷新保实时（每次互动重算这一篇的热度写回 zset，Redis 挂了静默降级不影响主业务）；定时全量重建保自愈——每 30 分钟以 DB 为真值重灌一遍，解决 Redis 重启后榜单空掉、以及长期增量累积的漂移。榜单读取时 zset 只出 id 顺序，明细用一次 IN 批量回查，避免 N+1，而且最后要按 zset 顺序组装，因为 IN 不保证顺序。"
别说错 ① 不要把重建说成「为了性能」——它的价值是正确性自愈：只有增量的话，Redis 一重启榜单就空了，而且没人互动就永远补不回来。
② 「增量保实时，全量保自愈」这句话要能背，并且能答出「只有增量会怎样」「只有全量会怎样」。
③ 主动交代缺陷：本项目全量只灌 Top1000、增量不设限，口径不一致会导致榜单抖动；先删后灌还有毫秒级空窗。敢主动讲这条，比「我用 zset 做了排行榜」值钱得多——它证明你在 review 自己的代码。
④ 别把 zset 说成「Redis 里放了个有序 List」——底层是 skiplist + dict：dict 负责按成员 O(1) 找分数，skiplist 负责按分数有序与范围查询。被问「为什么跳表不用红黑树」就答：跳表实现更简单、范围查询天然友好（原地顺序遍历）、平衡维护成本低。

4.9笔记发布与 AI 审核：为什么必须异步

发布秒回 + 异步审核 + 三重降级链 掌握

对应代码：AuditServiceImpl.java · AuditMqConfig.java · AuditConsumer.java · AuditMessage.java

一句话：AI 审核一次要 3~10 秒。同步做法是用户点「发布」后请求挂 10 秒才返回——用户第三次点发布时就卸载了。所以发布接口只做「落库为审核中」就立刻返回，审核交给 MQ 异步做，发布接口的 RT 与审核耗时彻底无关。

打个比方 这就像投稿给杂志社：你交稿的瞬间（发布）就拿到回执说「已收到，编辑部审核中」，而不是站在前台等编辑读完 10 秒再让你走。 审核结果稍后更新到你的稿件状态上（审核通过 = 已发布 / 驳回 = 附原因）——「受理」和「结果」分离，这就是异步解耦在业务上的样子。
机制与代码：延迟账 + MQ 拓扑 + 三重降级

先算这笔延迟账：审核 3~10 秒。若同步，每次发布接口 RT = 3~10 秒，占着的还是 Tomcat 工作线程；若异步，发布接口 RT = 一次落库（毫秒级），审核在后台跑，用户看到的状态是「审核中」。体验由架构保证，不靠祈祷 AI 快。

幂等三防线（注意顺序：先抢「结论权」，再落流水）（MQ 的语义是 at-least-once，重复投递是常态不是异常）——这里只列标题 + 一句话，细节与「消费端为什么吞异常 ACK」在 05 高并发与可靠性 讲透：

防线机制（真实代码）挡什么
①笔记状态机条件更新（CAS）先抢「结论权」：UPDATE t_note SET status=... WHERE id=? AND status='AUDITING'，返回 0 行 → 不落流水、直接返回MQ 重复投递（最常见）+ 并发审核
②流水表唯一键兜底：uk(biz_type, biz_id, biz_version, status) + INSERT IGNORE；只有抢到结论权的那一次才落流水状态被重置回 AUDITING 但版本号未递增的新路径（0 行时记 WARN）
③AI 失败只记 ERROR 流水、不动笔记状态，停 AUDITING 等补偿任务重试（键里含 status，所以 ERROR 不占终态幂等位）不误杀——宁可不作为，不可乱作为
已修复（2026-09-20 复核发现的问题：V5 迁移 + 审核链路改造 + 防线顺序对调） 复核发现第 ② 与第 ③ 条组合起来曾有一个洞：uk_biz 当时是 (biz_type, biz_id, biz_version)，而 biz_version 恒为 1 （AuditMessage 声明了该字段却没往下传，auditOnce 内部写死 1）。 于是一次 ERROR 流水或一次 REJECT 判定，就永久占用了这篇笔记的幂等额度； 之后任何重审（定时补偿 / /resubmit）走到 INSERT IGNORE 都返回 0 → return → 状态永不流转，被驳回或报错过的笔记会卡在 AUDITING。
三处修复（即上面这段代码现在的样子）： ① t_note 新增 audit_version（发布=1，每次重新送审 +1）并随消息传递， auditOnce(Note note, int version) 参数化——幂等键不再退化成常量； ② 唯一键纳入 status，即 uk_biz(biz_type, biz_id, biz_version, status)—— ERROR 不算审核结论，不再占用终态幂等位（V5__note_audit_version.sql）； ③ submit() 改由 AfterCommitExecutor 在事务提交后投递， 消费端回查不会再读到"还没提交的笔记"。
同轮第二处修复（两道防线的顺序对调）：上面三条修的是幂等键本身；还有一处是 执行顺序——修复前是「先落流水（撞键就 return）→ 再流转状态」， 两个并发执行会各写一条 PASS 与 REJECT：status 不同 → 唯一键不同 → 两条都能插入成功，而状态流转只有一个赢家 → 审计轨迹里出现两条互相矛盾的终态结论。现在改成 先 CAS 抢「结论权」、抢不到就直接返回不落流水，同一版本最多只有一条终态流水。
代价（诚实说明）：状态与流水不在同一事务。若 CAS 成功而流水写入失败， 笔记状态仍然正确（状态才是唯一真相，驳回原因随 updateStatus 写进了 t_note.audit_result），只是审核轨迹少一条，会记 WARN 便于发现。 之所以不把两者放进同一事务：AI 调用耗时长，与写库同事务会长时间占用数据库连接。
面试可以这样讲："我的审核幂等键是 (biz_type, biz_id, biz_version, status)。 版本号来自 t_note.audit_version：发布=1，每次重新送审 +1。 所以它区分的是『同一次审核的 MQ 重投』和『用户改完内容后的新一次审核』——前者应该被幂等挡掉，后者必须真正执行。 把 status 也放进键里，是因为 ERROR 只表示『这次没审成』， 它不该消耗掉这篇内容的审核额度。"

「深分页怎么优化？」高频必考

30 秒版本（逐字可用） "LIMIT 100000, 20 慢的原因不是返回 20 行，而是MySQL 必须先扫描并丢弃前 10 万行，被丢弃的行照样走索引，所以 OFFSET 的复杂度是 O(offset + size)，页数越深越慢。
我改用游标分页：把「第几页」换成「从哪继续」，第一页照常 LIMIT 20，下一页带上上一页最后一条的排序值。最新排序时游标就是一个 id，WHERE id < cursorId ORDER BY id DESC LIMIT 20，靠主键索引直接定位，复杂度 O(logN + size)，翻到第几页开销都一样。
但热度排序时游标必须是 (hot_score, id) 二元组——因为热度会并列，只带热度会漏掉同分的后续笔记，只带 id 又会因为 id 无序而错位，所以写成 WHERE hot_score < ? OR (hot_score = ? AND id < ?)。通用规律是排序键 N 列、游标就是 N 元组，最后一列必须唯一。
代价我也说清楚：游标分页不能跳页，所以后台管理那种需要跳页的列表我还是用 offset——两种方案按场景选，不是谁替代谁。"

「你们怎么做内容检索的？」口径高危

这题真正的考点不是「你用了什么」，而是「你有没有在用规模当借口」

30 秒版本（逐字可用） "内容检索我走的是 MySQL 全文索引：t_note 上建了 FULLTEXT(title, content) WITH PARSER ngram，查询用 MATCH ... AGAINST。
为什么必须 ngram：MySQL 默认的全文解析器按空格分词，是为英文设计的；中文一句话没有空格，会被整体当成一个词，导致检索全部失效。ngram 按两字一组切词——「主动降噪耳机」切成 主动/动降/降噪/噪耳/耳机，索引建在这些二元组上，搜「降噪」才命中。它的代价是纯字面切词、没有语义，而且单字搜不到（token 是 2 字），这是设计使然不是 bug——语义那部分交给向量检索，这也是 RAG 用关键词 + 向量双通道的原因。
关于 ES：当前还没有做成熟的搜索方案，ES 是明确规划中的升级方向。触发条件很具体：当检索需求超出 MySQL 全文索引的能力时——需要做相关度排序调权、复杂查询、多字段权重这些事。检索层我已经做了抽象，届时替换实现即可，业务代码不用动。"
这题的「别说错」清单 ① 绝不说「因为数据量才几百条，上 ES 是过度设计 / 装航空母舰」。这是规模借口，两条硬伤：面试官接着问「那 50 万条呢」你没有答案；而且等于主动承认项目没见过规模。正确姿势是「触发条件 + 已铺好的退路」——前者显得没想过，后者显得想清楚了选择不做。
② 不要照念迁移文件里的注释。V2__content_and_rag.sql 里写着「V2 不上 ES，数据量 500 篇足够」，这句话不能作为对外口径。
③ 不要把 ngram 吹成「智能分词」——它没有词典、没有语义，就是定长字符切分。主动说出边界反而加分。
④ 不要把商品搜索也套这套话术。商品搜索现在就是 LIKE 模糊匹配，「还没做成熟搜索方案」，不要包装成选型；也不要说「商品用 MySQL 全文索引搜」——全文索引用在笔记上。
本页速查：四个数字 / 四句话 四个数字：热度 = 点赞×3 + 收藏×5 + 浏览×1 · 计数落库 60 秒一次 · 热门榜全量重建 30 分钟一次 · 重建候选上限 1000 篇。
四句话：① 游标必须与排序键配套，热度排序的游标是 (hot_score, id) 二元组；② N+1 慢在往返次数，解药是一次 IN + 内存分组；③ 中文全文索引必须 WITH PARSER ngram，单字搜不到是设计使然；④ 点赞幂等靠唯一索引物理拒绝，不靠应用代码先查后插。
