02 · 用户与商品

这页讲项目里最"基础"的两个域：怎么证明"你是谁"，以及商品怎么建模。它们不花哨、没有高并发，但面试官恰恰用它判断你的基本功——鉴权能不能讲清无状态、SKU 能不能讲清为什么拆表、购物车能不能讲清为什么不放 Redis。

阅读约 20 分钟 面试权重 ★★ 涉及 6 张表 / 38 个类

2.1用户域全景：两张表，一条链路

用户域在 com.aimall.user 下，一共 16 个类，但真正承载数据的只有两张表。它们的分工非常干净：t_user 管"你是谁"，t_user_address 管"货寄到哪"。

表 / 类存什么 / 干什么关键约束
t_user账号本体：登录名、密码哈希、昵称、头像、角色、状态uk_username（用户名唯一）
t_user_address收货地址簿：收货人、电话、省市区、详细地址、是否默认idx_user（按用户查）
AuthRestController注册 / 登录 / 登出 / 当前用户，映射 /api/v1/auth登录、注册在白名单
AddressRestController地址增删改查 + 设默认，映射 /api/v1/addresses全部需登录
UserServiceImpl / AddressServiceImpl业务逻辑层：密码加密、Token 签发、默认位维护、归属校验越权校验在此层

整个用户域的业务链路就一条，记住这条线，后面所有章节都是它的展开：

注册POST /auth/register
BCrypt 加密后入库
登录POST /auth/login
比对哈希 → StpUtil.login(id)
拿 TokenLoginVO.token
前端存入 localStorage
带 Token 请求Authorization 头
SaInterceptor 校验 → 放行
业务取身份StpUtil.getLoginIdAsLong()
业务层不解析 Token
这条链路的一个设计意图 业务代码从不碰 Token。业务层要"当前用户 id"时统一调 StpUtil.getLoginIdAsLong()——"我是谁"由认证层给出，业务层拿到的是干净的 Long。这叫关注点分离：Token 长什么样、存在哪、什么时候过期，都跟商品、订单、购物车代码无关。

2.2注册与登录：Sa-Token + BCrypt

无状态 Token 登录 掌握

对应代码：UserServiceImpl.java / PasswordConfig.java / application.yml

一句话：登录成功后服务端签发一个 Token 给前端，之后每次请求都带它自证身份，服务端不保存 HttpSession。

打个比方 传统 Session 像酒店前台寄存行李——房卡只是个编号，行李必须存在前台（服务器内存），换一家分店就取不到；无状态 Token 像带防伪章的通行证——凭证本身写着你是谁、盖了章，任何一家分店都能独立验章放行，不需要共享行李间。
机制与代码：为什么是 Token 而不是 Session
Session（服务器内存）

会话数据存在单机内存里。多实例部署时，A 机登录、请求被负载均衡打到 B 机就读不到会话——必须做会话粘滞（sticky session）或会话共享（Session 复制 / 存 Redis）。水平扩展天然别扭。

无状态 Token（本项目）

身份信息随请求头走，服务端不存会话，集群多实例天然无需粘滞。校验是一次签名 / 映射比对，代价是每次请求多一次校验开销。

配置就在 application.yml 里，四个键能背出来就是真配过：

backend/src/main/resources/application.yml:215-222
sa-token:
  token-name: Authorization   # 前端请求头名；Sa-Token 自动兼容 "Bearer " 前缀
  timeout: 604800             # token 有效期 7 天（秒）
  is-concurrent: true         # 允许多端登录
  token-style: uuid

登录逻辑把"查用户 → 比密码 → 查状态 → 签发 Token"四步压在一个方法里，注意密码校验方向：不是拿明文去比明文，而是 matches(明文, 哈希)。

backend/src/main/java/com/aimall/user/service/impl/UserServiceImpl.java:47-56

// 统一提示，避免暴露"用户名是否存在"
if (user == null || !passwordEncoder.matches(req.getPassword(), user.getPasswordHash())) {
    throw new BusinessException(ResultCode.PASSWORD_ERROR);
}
if (user.getStatus() != null && user.getStatus() == 0) {
    throw new BusinessException(ResultCode.USER_DISABLED);
}
StpUtil.login(user.getId());
return new LoginVO(StpUtil.getTokenValue(), toVO(user));
面试怎么讲
30 秒版本 "登录用 Sa-Token 做无状态认证：校验通过后 StpUtil.login(userId) 签发 Token，前端放 Authorization 头，拦截器统一校验。也正因为无状态、服务端不存 HttpSession，集群部署不用做会话粘滞。"
追问 JWT 时："Sa-Token 的 Token 在服务端有映射，所以支持主动踢人、续期、看在线列表；纯 JWT 是自包含的，签发后作废不了，只能等过期或另建黑名单。我要'能踢人'这个能力，所以选 Sa-Token。"
别说错 不能说"我们完全无状态、服务端什么都不存"。Sa-Token 的 Token 在服务端是有映射的（默认内存，生产可切 Redis）——这正是它能"主动踢人"的原因。正确表述是：无状态指的是不依赖 HttpSession、集群免粘滞，不是"服务端什么都不记"。

密码存储：BCrypt 而不是 MD5 掌握

对应代码：PasswordConfig.java / t_user.password_hash

一句话：数据库里存的从来不是明文密码，而是 BCrypt 哈希串；登录时用 matches() 反查。

先在真实建表语句里核实一次——字段注释写得明明白白：

backend/src/main/resources/db/migration/V1__init.sql:19-30
CREATE TABLE IF NOT EXISTS t_user (
    id            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    username      VARCHAR(50)  NOT NULL COMMENT '登录名',
    password_hash VARCHAR(100) NOT NULL COMMENT 'BCrypt 密码哈希',
    ...
    UNIQUE KEY uk_username (username)
) ENGINE = InnoDB COMMENT ='用户表';
打个比方 MD5 像把青菜榨成汁——同一种菜榨出来永远是同一杯，只要有本"菜汁对照表"（彩虹表）就能反查；BCrypt 像每杯都随机加一撮盐再榨，同样的密码每次结果都不同，彩虹表彻底失效，且想暴力破解还得为每一次尝试付出昂贵算力。
机制与代码：BCrypt 强在哪
MD5 / SHA-1（不可用于存密码）

① 无盐：相同密码哈希相同，彩虹表一击即中；② 太快：GPU 每秒可算数十亿次，暴力破解成本极低。它是"摘要算法"，设计目标是快，而快恰恰是存密码的缺点。

BCrypt（本项目）

① 自带随机盐：盐和哈希拼在同一个串里存，无需另建盐字段，同一密码每次结果都不同；② cost 可调：默认强度下每次哈希约百毫秒，故意"算得慢"，让暴力破解在时间上不可行。密码学上属于自适应单向函数。

配置只有几行——项目刻意只引入 spring-security-crypto 这一个模块，不引入整套 Spring Security：

backend/src/main/java/com/aimall/config/PasswordConfig.java:12-18
@Configuration
public class PasswordConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

注册时加密、登录时比对，两处成对出现：

面试怎么讲
30 秒版本 "密码不存明文，存的是 BCrypt 哈希。BCrypt 两个好处：一是自带随机盐，每个用户盐不同，彩虹表失效；二是 cost 可调，故意算得慢，暴力破解成本极高。登录时用 matches(明文, 哈希) 比对，比对失败和用户不存在返回同一个提示，避免暴露用户名是否存在。"
追问为什么不用 Spring Security："我的鉴权需求只有'登录 / 未登录'一级，Spring Security 是过滤器链加授权模型的全家桶，杀鸡用牛刀。我只引了 spring-security-crypto 这一个模块拿 BCrypt，认证交给 Sa-Token。如果以后要做多角色 RBAC，我会重新评估。"
别说错 ① 别说"密码用 MD5 加密"——存密码叫哈希 / 摘要，且 MD5 已明确不可用于此；② 别说"加了固定盐"——BCrypt 的盐是每个密码随机生成并写进同一个哈希串的，不需要自己维护盐字段；③ 别说"用了 JWT"，本项目是 Sa-Token，两者在"能否主动作废"上不同。

2.3鉴权链路：拦截器 + 白名单

SaInterceptor：默认全拦，显式放行 掌握

对应代码：SaTokenConfig.java

一句话：/api/** 默认全部需要登录，只有白名单里的路径例外。这道闸门装在 Spring MVC 的拦截器层，登录校验、放行都在这里一次性决定。

为什么需要它：如果每个接口自己写"判断有没有登录"，漏掉一个就是裸奔。正确的姿态是 fail-closed（默认拒绝 + 显式放行），而不是 fail-open（默认放行 + 逐个加保护）。代码全文很短，但每一条放行都有理由：

backend/src/main/java/com/aimall/config/SaTokenConfig.java:16-33
registry.addInterceptor(new SaInterceptor())
        .addPathPatterns("/api/**")
        .excludePathPatterns(
                "/api/v1/auth/login",
                "/api/v1/auth/register",
                // V3：支付回调——第三方（支付宝服务器）不可能持有我们用户的 token。
                // 回调接口的"身份"由【验签】保证，而不是 token：
                //   业务接口靠"你是谁"（认证），回调接口靠"消息是谁发的、有没有被改"（完整性）。
                // 若这里不放行，回调会被 401 拦掉，订单永远无法变为已支付。
                "/api/v1/payments/callback/**",
                "/internal/**",
                "/error"
        );
支付回调必须免登录——这是本节最该记的一条 支付回调是第三方服务器（支付宝）主动打进来的请求，它不可能持有我们用户的 Token。如果这里不放行，回调会被 401 拦掉，订单永远无法变成已支付。
那放行安全吗？安全。因为回调的"身份"由验签保证——Token 管的是"你是谁"（认证），验签管的是"消息是不是对方发的、有没有被改"（完整性），这是两件事。同一逻辑也适用于 /internal/**：调用方是 ai-service，身份由内部 HMAC 签名 + 时间窗保证。放行 ≠ 裸奔，这些端点内部仍在校验签名。详见 03 订单与交易 的支付验签。
机制与代码：拦截器在请求链路的哪一环

请求进入 Spring Boot 后的顺序是固定的，理解这个顺序才知道为什么"登录校验用拦截器"、为什么"traceId 用 Filter"：

请求 → Filter（Servlet 容器级，早于 DispatcherServlet）→ DispatcherServlet → Interceptor（Spring MVC 级）→ AOP 切面（方法调用级）→ Controller

组件规范能拿到什么本项目用它做
FilterServlet 容器request/response，不知道是哪个 ControllertraceId 注入
InterceptorSpring MVC知道 HandlerMethod登录校验 + 白名单
AOPSpring AOP知道方法、参数、返回值事务、日志

两个关键取舍：① 登录校验为什么不用 AOP？因为 AOP 在方法调用期，请求已经进到 Controller 了；拦截器能在 MVC 入口统一拒绝，失败更早、语义更准。② 为什么不放 Filter？Filter 拿不到 HandlerMethod，无法做"按注解 / 按路径"的细粒度控制，而 MVC 拦截器天然知道路由。

面试怎么讲
30 秒版本 "鉴权用 Sa-Token 拦截器做，/api/** 默认全部要登录，只放行三类：登录注册、支付回调、/internal/** 内部接口。姿态是 fail-closed——默认拒绝、显式放行，避免漏掉某个接口裸奔。"
被问"支付回调放行安全吗"："安全。回调是支付宝服务器发的，它没有我们的用户 Token，身份由验签保证。Token 保证认证、验签保证完整性，是两码事。"
被问三者区别："Filter → Interceptor → AOP 依次在容器级、MVC 级、方法级；登录校验必须在 MVC 入口做，所以用 Interceptor。"
别说错 ① 别说"放行的接口就没有任何保护"——/internal/** 仍校验 HMAC 签名，支付回调仍验签；② 别把 /internal/** 说成"内部所以安全"，它安全是因为签名校验，而不是因为路径叫 internal；③ 别说拦截器能拿到原始字节流或做全局编码，那是 Filter 的活。

2.4收货地址簿：默认位与越权校验

t_user_address：一个用户多地址，一个有且仅有一个默认 熟悉

对应代码：AddressServiceImpl.java / AddressMapper.xml

一句话：一张从表存用户的多个收货地址，靠 is_default 标记默认地址；所有读写都强制带上当前用户 id，从 SQL 层就查不到别人的数据。

打个比方 地址簿像手机里的联系人分组——你只能看到自己分组下的联系人，分组 id 是系统按登录身份自动带上的，你手改 URL 也翻不到别人的。默认地址则是分组里贴的那颗星：同一时刻只能有一颗。
机制与代码：字段设计 + 默认位维护
字段类型说明
user_idBIGINT NOT NULL归属用户，idx_user 索引
receiver / phoneVARCHAR(50) / (20)收货人、联系电话，必填
province / cityVARCHAR(50) DEFAULT NULL省、市，可空（详情里直接写全也行）
detailVARCHAR(200) NOT NULL详细地址，必填
is_defaultTINYINT DEFAULT 0是否默认：1 是 0 否

建表语句见 V1__init.sql:32-45。注意：表上没有"每用户唯一一个默认"的数据库约束，默认位靠应用层成对维护。

默认位的规则有三条，全部在 AddressServiceImpl 里：

  1. 首条自动成为默认新增时 wantDefault = req.isDefault() || countByUserId(userId) == 0——用户没勾"默认"，但这是他的第一条地址，也自动设为默认。
  2. 设默认前先清零想让 B 成为默认，先 unsetDefault(userId) 把该用户所有地址的默认位清 0，再 updateDefault(B)——保证"有且仅有一个默认"。
  3. 删除默认后自动补位删掉的若是默认地址，就把剩余地址里排最前的一条自动设为默认，避免用户下次下单时没有默认地址。
backend/src/main/java/com/aimall/user/service/impl/AddressServiceImpl.java:92-99
@Override
@Transactional(rollbackFor = Exception.class)
public void setDefault(Long id) {
    Long userId = currentUserId();
    if (addressMapper.selectByIdAndUserId(id, userId) == null) {
        throw new BusinessException(ResultCode.NOT_FOUND, "地址不存在");
    }
    addressMapper.unsetDefault(userId);
    addressMapper.updateDefault(id, userId);
}

越权校验（本节的面试重点）：项目的做法是从 SQL 层就带 AND user_id = ?，别人的地址根本查不出来，而不是"先查出来再比对"。更新语句就是证据：

backend/src/main/resources/mapper/AddressMapper.xml:36-44
<update id="update">
    UPDATE t_user_address
    SET receiver = #{receiver},
        phone    = #{phone},
        province = #{province},
        city     = #{city},
        detail   = #{detail}
    WHERE id = #{id} AND user_id = #{userId}
</update>

删除、设默认、更新前都先调 ensureOwned(id)（AddressServiceImpl.java:101-105），查不到就抛 NOT_FOUND。注意错误码是 404 而不是 403——403 等于告诉攻击者"这地址存在，只是不属于你"，他就能顺藤摸瓜枚举 id；404 是"没这东西"，不暴露资源存在性（最小信息披露原则）。

面试怎么讲
30 秒版本 "地址是标准的水平越权高发区。我的做法是所有查询和更新 SQL 都带 AND user_id = ?，用户 id 从 StpUtil.getLoginIdAsLong() 统一取，绝不接受前端传的 userId。别人的地址在 SQL 层就查不到，返回 404 而不是 403，避免暴露资源是否存在。默认地址靠应用层成对维护：设默认前先清零全量，删默认后自动补位。"
追问"为什么不用数据库约束保证只有一个默认"："MySQL 上做'部分唯一索引'比较别扭，我在应用层用 unsetDefault + updateDefault 在一个事务里成对维护，逻辑更直观也更好讲。"
别说错 ① 别说"返回 403 没权限"——本项目口径是 404，防的是 id 枚举与探测；② 别说"越权校验写在 Controller 里"——它必须在 Service 层，这样定时任务、MQ、内部接口等任何入口复用同一份校验，放 Controller 会被绕过；③ 别说"用户 id 从前端请求参数里取"——那是把越权漏洞主动送出去。

2.5商品建模：SPU / SKU / 图片三层

为什么商品不塞进一张表 掌握

对应代码：t_product / t_product_sku / t_product_image（V1__init.sql:50-87）

一句话：商品被拆成三层——SPU 描述"这是个什么商品"、SKU 描述"具体哪个规格、多少钱、剩几件"、图片表描述"有哪些图"。

打个比方 SPU 像餐厅菜单上的一道菜（"宫保鸡丁"），SKU 像这道菜的规格选项（小份 28 元 / 大份 38 元，各自还有独立备料量）。菜单不会为"小份宫保鸡丁""大份宫保鸡丁"各写一页——它们共享同一段介绍、同一张图，只在价格和存量上分叉。

三层关系一眼看清：

t_product（SPU）商品名 / 副标题 / 分类 / 主图 / detail 详情 / status 上下架
t_product_sku（SKU）sku_name 规格名 / price 价格 / stock 库存 / sales 销量 / image 规格图
一个商品 N 条，各自独立价格与库存
t_product_image（图集）sku_id IS NULL → 商品级图集；sku_id 非空 → 该规格专属图；sort 排序
机制与代码：为什么必须拆表

核心论证一：规格会组合爆炸。一个商品若有 3 种颜色 × 3 种容量，就是 9 个"可独立售卖的单位"。若塞进一张表，要么把 9 个组合摊成 9 行（商品信息重复 9 遍，改一次标题要改 9 行），要么用 JSON 把规格塞进一个字段（价格、库存变成了应用层解析的字符串，SQL 无法聚合、无法用索引、无法 WHERE stock>=? 判断）。

核心论证二：价格和库存必须挂在 SKU 上。下单扣的是"曜石黑 32G 的库存"，不是"AirSound Pro 的库存"——买黑色并不会减少白色的存量。任何需要按规格单独读写、且要参与事务与并发控制的字段，必须是独立的列，而不是可解析的文本。所以 price / stock / sales 天然属于 SKU 表。

图集为什么要单独一张表：一个商品可能有 6 张详情图，一个规格又可能有自己的一组图。塞进商品表的 main_img 只有一个格子，装不下；用逗号拼接则丢失排序、无法按规格分组。于是 t_product_image 用 sku_id IS NULL 区分"这是商品级默认图集"，非空则属于某个规格。

SKU 表里哪些字段真的在用，哪些是预留——这一条务必记牢：

字段状态说明

stock真参与业务扣库存的靶子：WHERE stock >= ?
sales真参与业务与扣库存同一条 SQL 里 sales = sales + ? 累加
image在用选中规格时切换主图，为空则回退商品图集

2.6商品列表与详情

列表的"起售价聚合" 熟悉

对应代码：ProductMapper.xml / ProductServiceImpl.java

一句话：列表页展示的是 SPU，但价格要显示"这个商品最低多少起"——所以列表 SQL 用 LEFT JOIN 到 SKU 表，取 MIN(price) 作为起售价。

机制与代码：LEFT JOIN + MIN + GROUP BY

两个细节值得记住：一是必须 LEFT JOIN，否则一个还没配 SKU 的商品会从列表里消失；二是 count 不 Join，统计总数只需数 SPU，多一次 join 是白费。

backend/src/main/resources/mapper/ProductMapper.xml:21-30
<select id="selectOnSalePage" resultType="com.aimall.goods.bean.Product">
    SELECT p.id, p.spu_name, p.sub_title, p.category_id, p.main_img, p.status, p.created_at,
           MIN(s.price) AS min_price
    FROM t_product p
    LEFT JOIN t_product_sku s ON s.product_id = p.id
    <include refid="onsaleWhere"/>
    GROUP BY p.id, p.spu_name, p.sub_title, p.category_id, p.main_img, p.status, p.created_at
    ORDER BY p.id DESC
    LIMIT #{offset}, #{size}
</select>

聚合出来的 min_price 在实体里是非表列字段（Product.java:38-39 明确标注"SQL 聚合得出"）。详情页则是另一条路：先查 SPU，再查 SKU 列表和两套图集，最后组装 VO（ProductServiceImpl.java:42-61）。

面试怎么讲
30 秒版本 "列表查的是 SPU，但价格要显示起售价，所以列表 SQL 用 LEFT JOIN 到 SKU 表取 MIN(price)，加 GROUP BY 聚合。用 LEFT JOIN 是为了让还没配 SKU 的商品不出现在列表里丢行。分页是手写的 LIMIT offset, size，没有用分页插件。"
别说错 别把 min_price 说成数据库里的真实列——它是 SQL 聚合出来的虚拟字段，这也是为什么 Product 实体里要单独声明一个 minPrice 并注释"非表列"。

商品搜索：诚实地说"还没做成熟方案" 了解

对应代码：ProductMapper.xml:7-18（onsaleWhere）

一句话：当前商品搜索就是 LIKE CONCAT('%', #{keyword}, '%') 对商品名和副标题做模糊匹配，没有 ES、没有全文索引。

backend/src/main/resources/mapper/ProductMapper.xml:13-16
<if test="keyword != null and keyword != ''">
    AND (p.spu_name LIKE CONCAT('%', #{keyword}, '%')
         OR p.sub_title LIKE CONCAT('%', #{keyword}, '%'))
</if>
口径红线：商品搜索当前是 LIKE 模糊匹配，还没做成熟搜索方案。绝不可以说"用 MySQL 全文索引搜商品"——本项目的全文检索（ngram）用在笔记上，不在商品上。详见 04 内容社区。
为什么"没做"不等于"过度设计"或"规模借口" 这不是"在给自己找借口"。正确的话术是：数据量是"触发条件的标尺"，不是"选型的技术理由"。
意思是：ES 该不该上，取决于"当商品量、并发搜索量、对相关性排序的要求达到某个量级时，LIKE 会因为无法走索引（前置通配符）而全表扫描、拖慢整个库"——是数据量触发了它，而不是"因为现在数据少所以我懒得做"。
同时也要说清代价：上 ES 意味着引入一套独立中间件、数据同步链路、一致性维护，对当前项目是净负担。将来真到量级，迁移路径很清晰：MySQL → 先加密索引 → 再上 ES + Canal 同步。
面试怎么讲
30 秒版本 "商品搜索目前是比较朴素的 LIKE 模糊匹配，还没做成熟的搜索方案，这点我诚实说。它会随数据量增长而失效，因为前置通配符用不上索引、会全表扫描。将来要上，路径是先加密索引，量级再大就 ES + Canal 同步——但我不会现在为了简历好看就堆一套 ES，那样引入的同步和一致性成本远大于收益。"
别说错 ① 别说"我用 MySQL 全文索引搜商品"，那是笔者的（也是笔记的）能力，不是商品的；② 别说"因为数据少所以不用 ES"——这是规模借口，正确的说法是数据量决定何时触发迁移，而不是拿来当技术选型的理由；③ 别把 LIKE 说成"支持模糊搜索所以够用"，前置 % 的 LIKE 是走不了 B+ 树索引的。

2.7购物车：京东式设计

MySQL 持久化 + 原子 UPSERT 合并 掌握

对应代码：CartServiceImpl.java / CartMapper.xml / t_cart（V1__init.sql:89-101）

一句话：购物车是一张普通的 MySQL 表，用 (user_id, sku_id) 唯一键保证"同一用户同一规格只有一行"，重复加购靠 ON DUPLICATE KEY UPDATE 在数据库内原子累加数量。

打个比方 购物车像超市的购物篮：你不能把同一瓶牛奶放进篮子两次还占两格——要买两瓶就在那一格里写"2"。唯一键就是"一格一商品"的规则，UPSERT 就是把第二瓶牛奶并进已有那一格的动作，且这个"并进去"的动作是在货架管理员（数据库）手里原子完成的，两个人同时伸手也不会漏加。
机制与代码：唯一键、累加、封顶

唯一键是什么：核实后的答案是 UNIQUE KEY uk_user_sku (user_id, sku_id)——不是主键，也不是 (user_id, product_id)。粒度是 SKU：同一商品的不同颜色是两行，同一规格重复加购才合并。

backend/src/main/resources/db/migration/V1__init.sql:92-101
CREATE TABLE IF NOT EXISTS t_cart (
    id         BIGINT   NOT NULL AUTO_INCREMENT COMMENT '主键',
    user_id    BIGINT   NOT NULL COMMENT '用户 id',
    sku_id     BIGINT   NOT NULL COMMENT 'SKU id',
    quantity   INT      NOT NULL DEFAULT 1 COMMENT '数量',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_sku (user_id, sku_id)
) ENGINE = InnoDB COMMENT ='购物车表(京东模式，MySQL 持久化)';

重复加购是"累加数量"还是"新增一行"：是累加数量，而且是一句 SQL 里原子完成的，没有"先查再改"的竞态窗口：

backend/src/main/resources/mapper/CartMapper.xml:52-56
<insert id="upsert" useGeneratedKeys="true" keyProperty="cart.id">
    INSERT INTO t_cart (user_id, sku_id, quantity)
    VALUES (#{cart.userId}, #{cart.skuId}, #{cart.quantity})
    ON DUPLICATE KEY UPDATE quantity = LEAST(quantity + #{cart.quantity}, #{stockCap})
</insert>

为什么用 UPSERT 而不是"先 select 再 insert/update"：后者在并发下会丢更新（两个线程都读到 quantity=1，都写回 2，实际加了 2 次却成了 2 而不是 3）。UPSERT 把判断与累加收进数据库的一条原子语句，从根上消除竞态。LEAST(..., #{stockCap}) 是"库存封顶"——加购数不会超过可售库存（京东式：购物车里点"+"到上限就点不动，但不拒绝这次加购）。

业务层的边界处理（CartServiceImpl.java）：

  • 加购前先卡两道：商品已下架、SKU 已售罄（stock <= 0）直接拒绝——不可购买的东西不进购物车。
  • 改数量封顶：update 时先查出该条 join 出的实时库存 maxBuyable，目标数量超过它就压到上限；请求本身还有 @Min(1) @Max(99) 的 Bean Validation 兜底。
  • 删除 / 清空：DELETE ... WHERE id=? AND user_id=?，影响行数为 0 就抛"条目不存在"——归属校验同样做在 SQL 里。
  • 列表带实时状态：selectItemsByUserId 用 JOIN 把 SKU 价格、库存、商品上下架状态一次查出，CartItemVO 提供 isOffShelf() / isOutOfStock()，前端据此把失效商品置灰分组、只可删除不可结算。

诚实边界：购物车始终留在 MySQL，没有迁 Redis。这是刻意的取舍——京东式购物车要"多端同步 + 持久化 + 失效商品分组"，这正是 MySQL 的强项；Redis Hash 虽快，但持久化与分组查询反而是短板。项目里 Cart.java 的类注释还留着"V3 拟迁 Redis Hash"的旧规划，那没有落地，别照着它讲。

面试怎么讲
30 秒版本 "购物车用 MySQL 持久化，唯一键是 (user_id, sku_id)，所以同一用户同一规格永远只有一行。重复加购不是插新行，而是 ON DUPLICATE KEY UPDATE quantity = LEAST(quantity + ?, stock)——一条原子语句完成累加，没有先查后改的丢更新问题，同时按实时库存封顶。为什么不放 Redis？因为京东式购物车要持久化、多端同步、失效商品分组，那是 MySQL 的强项；Redis 快但不是为这个场景设计的。"
追问失效商品："购物车列表是 JOIN 商品和 SKU 查的，会带出实时上下架状态和库存，前端把下架或超库存的条目置灰分组，只允许删除不允许结算。"
别说错 ① 唯一键是 (user_id, sku_id)，不是 product_id，别把"同一商品的多个颜色"说成一行；② 别说"购物车放 Redis 会更快所以应该迁"，本项目明确不迁，且理由充分；③ 别说加购超库存会被"拒绝"——是封顶（加购成功但数量压到可售上限），拒绝只发生在售罄和已下架时；④ 别照搬 Cart.java 里"V3 拟迁 Redis"的旧注释。
