3.1订单域全景：两张表加一个状态机

订单域全景：两张表 + 一个状态机 掌握

对应代码：order/bean/Order.java · OrderItem.java · mapper/OrderMapper.xml · OrderItemMapper.xml

一句话：一次下单 = t_order 里一行主记录 + t_order_item 里 N 行明细。主表回答"这笔交易是谁的、多少钱、到哪一步了"，明细表回答"买了哪些 SKU、各几件、什么价"。

打个比方 订单主表像餐厅的账单抬头（桌号、总额、当前状态），订单明细像账单下面一行行的菜品。抬头会变（待支付 → 已支付 → 已取消），但下面那几行菜名和单价一旦写上去就不该再变——这正是 3.5 节要讲的"快照"。
表定位关键字段 / 约束
t_order 订单主表，一单一行 order_no（uk_order_no 唯一）、status、total_amount、收货人三字段、pay_time、cancel_time、version；索引 idx_user_created(user_id, created_at) 供"我的订单"分页
t_order_item 订单明细，一单 N 行，商品信息冗余快照 order_id、sku_id、product_name / sku_name / price（三个快照字段）、quantity；索引 idx_order(order_id)

订单号由代码生成（17 位时间戳 + 4 位随机 + 用户尾号），唯一性由 uk_order_no 兜底，而不是靠代码保证不重复——这条"能用数据库约束兜底的就不靠应用层判断"的思路，后面 3.4、3.9 会反复出现。

状态机：五个状态，两条出口

一句话：订单状态不是一堆 if-else，而是五个常量 + 一个由 SQL 条件更新实现的流转规则。所有状态变更都走同一条 SQL：UPDATE t_order SET status=? WHERE id=? AND status=?。

待支付还有一条出口：PENDING_PAY → CANCELLED（已取消）。触发它的只有两条路径——用户手动取消，或 30 分钟超时消息到达。取消成功后必须回补库存。

诚实边界（面试主动讲，是加分项） STATUS_SHIPPED 与 STATUS_COMPLETED 只是在 Order.java 里定义了常量，全项目没有任何一处代码会把订单推进到这两个状态（没有发货接口、没有确认收货接口）。同理 Payment.STATUS_FAILED 也从未被写入。所以准确的说法是："状态机定义了五个状态，目前落地了待支付 / 已支付 / 已取消三条边，发货和收货留到 V5"——不要说成"完整的订单生命周期都实现了"。
机制与代码：状态机是靠 WHERE 条件更新实现的

关键不在 Java 侧，而在 MyBatis 的 WHERE 子句——旧状态就是闸门。返回值 rows 才是真正有用的信息：1 = 我抢到了这次流转，可以继续做后续动作（回补库存、关支付单）；0 = 别人抢先了，我什么都不做。

mapper/OrderMapper.xml:54-61
<!-- 状态机 CAS：防并发重复流转。取消时回填 cancel_time -->
<update id="updateStatus">
    UPDATE t_order
    SET status = #{toStatus},
        <if test="toStatus == 'CANCELLED'">cancel_time = #{cancelTime},</if>
        version = version + 1
    WHERE id = #{id} AND status = #{fromStatus}

两个细节：一是version = version + 1 只是每次流转自增做个标记，WHERE 里没有拿它做比对（3.3 节详说这里为什么不能说成乐观锁）；二是cancel_time 用 <if> 动态拼接，只有取消才回填，支付时不写。

面试怎么讲
30 秒版本 "订单表有五个状态：待支付、已支付、已发货、已完成、已取消。所有状态流转都走同一条 SQL——UPDATE ... WHERE id=? AND status=旧状态，把并发裁决交给数据库的行锁。返回影响行数 0 就说明这次流转没抢到，直接放弃、不做后续动作。这套写法天然幂等：状态一旦改过去，再执行同样的流转就找不到旧状态的行了。"
别说错 1. 不要说"我们用了状态机引擎"。项目里没有 Spring StateMachine、没有 DSL，就是把 WHERE status = 旧值 硬编码在 Mapper XML 里。准确说法是"用条件更新实现状态机语义"。
2. 不要给 SHIPPED / COMPLETED 编流程。它们只是常量，代码里没有任何流转。
3. version 字段不是乐观锁——见 3.3，这条红线说错就露馅。

3.2下单主流程：八步走完一次 create

create 的八步 掌握

对应代码：order/service/impl/OrderServiceImpl.java:56-135

一句话：下单是一个包在 @Transactional 里的大方法，从幂等校验一路做到发延迟消息。任何一步抛业务异常，整个事务回滚，库存不会被扣掉。

打个比方 这八步像"一手交钱一手交货"的柜台流程：先查你是不是拿着号（token），再一件件点货出库（校验 + 扣库存），然后开单（主表 + 明细），最后把购物篮收走并设一个 30 分钟闹钟。任何一步卡住，整笔交易作废、货退回原位——这就是事务。
  1. ① 校验幂等 token（防双击）OrderServiceImpl.java:62-67。带 token 就调 redisOps.consumeToken(...) 消费，返回 false 立即抛"请勿重复提交订单"；token 为空则跳过（兼容未接入的调用方）。
  2. ② 校验明细非空OrderServiceImpl.java:68-71。条目为空抛 CART_EMPTY。最廉价的一道防御，放在扣库存之前。
  3. ③ 逐项查 SKU + 查商品，校验上架OrderServiceImpl.java:79-90。先 selectById 拿 SKU，再回查商品确认 status == 1。这里读到的 stock 只用来快速失败（提前给出友好提示），不是扣减依据。
  4. ④ 扣库存：CAS 条件更新OrderServiceImpl.java:91-95。调 skuMapper.deductStock(...)，返回 0 说明并发下库存不足，抛 STOCK_NOT_ENOUGH。这是整条链路的技术核心，3.3 节单独讲透。
  5. ⑤ 组装明细 + 累加总额OrderServiceImpl.java:96-103。把商品名、规格名、单价复制进 OrderItem（快照，见 3.5），同时算 total。金额来自库里查出的 sku.getPrice()，不是前端传的。
  6. ⑥ 插入订单主表OrderServiceImpl.java:107-115。生成订单号，状态固定为 STATUS_PENDING_PAY，insert 回填自增主键。
  7. ⑦ 批量插入明细 + 清购物车OrderServiceImpl.java:118-125。batchInsert 一次 SQL 写入所有明细；只有 fromCart == true 时才按 skuId 清购物车，直接购买不清——避免误删购物车里同款。
  8. ⑧ 注册"提交后发延迟消息"OrderServiceImpl.java:132。调 delayMessageSender.sendAfterCommit(order.getId())。注意是 afterCommit，不是当场发——3.6 节展开。
机制与代码：扣库存与建单在同一把行锁里

代码里有一段注释值得逐字读，因为它同时说清了"为什么快"和"代价是什么"：

order/service/impl/OrderServiceImpl.java:73-76

//    说明：扣库存放在最前，可尽早暴露库存不足（快速失败）；但热点行锁仍持有至本方法事务提交，

为什么扣库存放在最前：尽早失败，避免白跑后面几步。代价是什么：InnoDB 的排他锁一直持有到事务提交，意味着"写订单 + 写明细 + 清购物车"这三步也在这把锁的保护（和束缚）之下。作者在注释里主动写了改进方向——能主动说出自己方案的代价，比假装它没有代价更让人信服。

面试怎么讲
30 秒版本 "下单是一个事务方法，八步：幂等 token 校验、明细非空校验、逐项查 SKU 并校验上架、CAS 条件更新扣库存、组装明细并累加金额、插订单主表、批量插明细并按需清购物车、最后注册提交后发延迟消息。任何一步业务异常都抛出去让事务整体回滚，所以不会出现'库存扣了但订单没建'。金额统一用数据库里的 SKU 价格算，不信前端传的。"
别说错 / 预判追问 追问一："为什么扣库存放在最前面？"会的人答"快速失败 + 让热点行锁覆盖后续写操作"；不会的人答"随便放的"。
追问二："扣库存和建单在同一个事务里，锁不是很长吗？"答"是，这是已知代价，注释里写了改进方向——拆独立短事务或走 Redis 预扣"。
别说错：第 ③ 步查出的 stock 只是提示用，不能拿它当扣减依据——否则就退化成"先查再改"（3.3 节的反面教材）。

3.3防超卖：行锁 + WHERE stock>=? 条件更新

超卖是怎么发生的（先看事故，再看方案） 本页最重要

对应代码：mapper/ProductSkuMapper.xml:31-47 · goods/mapper/ProductSkuMapper.java

一句话：库存 1 件，两个请求同时到达，如果先 SELECT 查库存再 UPDATE 扣减，两个请求都会认为"还有货"，最后卖出 2 件。

时刻线程 A线程 B
t1SELECT stock → 读到 1—
t2—SELECT stock → 读到 1，也认为有货
t3UPDATE stock = 0，下单成功—
t4—UPDATE stock = -1，下单成功 → 超卖，库存变负

根因只有一句话："读"和"写"是两条 SQL，两步之间别人可以插队。这是 TOCTOU（检查时与使用时不一致）的经典形态。

打个比方 两人同时抢最后一张票。先查再改像是"先问售票员还有没有票（查到有），然后转身去取钱，回来再买"——你取钱的时候别人已经把票买走了。条件更新像是"一张嘴就说'给我出票，且必须还有余票'，售票员在同一个动作里既检查又出票"——不存在中间窗口。

本项目方案：一条 SQL 把"检查"和"扣减"焊死

mapper/ProductSkuMapper.xml:35-40
<update id="deductStock">
    UPDATE t_product_sku
    SET stock = stock - #{quantity},
        sales = sales + #{quantity}
    WHERE id = #{id} AND stock >= #{quantity}
</update>
order/service/impl/OrderServiceImpl.java:91-95
// 数据库层 CAS 扣减（WHERE stock >= ?）：InnoDB 对命中行加排他锁，返回 0 = 并发下库存不足
if (skuMapper.deductStock(sku.getId(), it.getQuantity()) == 0) {
    throw new BusinessException(ResultCode.STOCK_NOT_ENOUGH,
            "商品[" + product.getSpuName() + "]库存不足");
}

为什么"这一条 SQL 就是原子的"

三个事实，讲清楚就够了：

  • InnoDB 对 UPDATE 命中的行加排他锁（X 锁）。线程 A 执行这条 SQL 时，id=? 那一行被锁住；线程 B 对同一行的 UPDATE 必须阻塞等待，直到 A 的事务提交或回滚。
  • 条件判断发生在锁内。stock >= ? 是在 B 拿到锁之后、按最新的库存值重新判断的。A 把库存扣到 0 之后，B 拿到锁再判断 0 >= 1 为假，更新 0 行 → 扣不到货。
  • 返回值就是裁决结果。rows == 1 说明我抢到了，可以继续建订单；rows == 0 说明没抢到，直接抛"库存不足"。不需要应用层重试，也不需要额外加锁。

合成一句话：行排他锁保证了串行，谓词写在 UPDATE 里保证了"判断依据是最新值"。所以库存永远不会被扣成负数。

三条路的对比

先查再改（SELECT 再 UPDATE）

两条 SQL，SELECT 与 UPDATE 之间有窗口。并发下两个请求都能读到"还有货"，各自扣一次 → 超卖。有人想"加个 if (stock > qty) 判断"——那只是把窗口收窄，没消除，因为判断用的还是刚才读到的旧值。

SELECT ... FOR UPDATE 再改

正确，理论上和条件更新等效：先加锁、再读、再改，读到的就是锁内最新值。代价是比条件更新多一次数据库往返，而且锁的持有时间更长。

条件更新（本项目方案）

一次往返，判断与扣减在同一条 SQL 内由数据库原子完成，代码只需看返回值。本质是 CAS 思想（Compare-And-Swap）：把"期望条件"写进 WHERE，让数据库告诉我们有没有 swap 成功。

机制与代码：回补库存是逆操作，同样只认条件更新的结果

扣出去的库存必须有地方加回来（取消订单、超时未支付），对应 ProductSkuMapper.xml:43-47 的 addStock：UPDATE t_product_sku SET stock = stock + ? WHERE id = ?。它是无条件加，因为它只在"状态机确认取消成功之后"才被执行——OrderServiceImpl.cancel 先 updateStatus(id, PENDING_PAY, CANCELLED, now)，rows == 0 抛"仅待支付订单可取消"，rows == 1 才逐项 addStock。

顺序至关重要：CAS 成功之后才回补。如果反过来先回补再 CAS，"竞争失败"的线程也会执行回补 → 状态没变、库存却加了 = 库存虚增，真实资损。这和 3.6 的三方竞争是同一个道理。

另外，deductStock 的 XML 注释里主动写了"本 SQL 未使用 version 字段"，同时说明"锁持有范围从本语句到事务 COMMIT，含后续写订单/明细/清购物车"。作者自己把口径和代价都钉死了——很值得学的工程习惯。

面试怎么讲
绝不说"乐观锁"。扣库存只有一种正确说法："行锁 + WHERE stock>=? 条件更新，本质是 CAS 思想"。
t_product_sku.version 是纯预留字段，从未参与任何比对——翻 ProductSkuMapper.xml 就知道了：deductStock 的 SQL 里根本没有它，XML 注释也明写了"本 SQL 未使用 version 字段"。这一个词说错，面试官立刻就知道你没真读自己的代码。
30 秒版本 "防超卖的核心是一行 SQL：UPDATE t_product_sku SET stock = stock - ? WHERE id = ? AND stock >= ?。
InnoDB 会对命中的行加排他锁，stock >= ? 这个条件判断在锁内、按最新库存值执行，判断和扣减在同一条 SQL 里原子完成。返回影响行数 0 就说明并发下库存不足，抛业务异常回滚整个下单事务。
它是 CAS 思想——把期望条件写进 WHERE，让数据库裁决。不需要应用层重试、不需要额外分布式锁，也不需要 version 字段。"
别说错 / 预判追问 追问一："那 version 字段留着干嘛？"——诚实答："它是建表时的预留字段，目前只由 updateStatus 每次流转自增做标记，不参与任何并发控制。可以理解为技术债，留着是为了将来真要用版本号做并发控制时不用改表结构。"能主动承认"这是预留、没起作用"，比硬编一个用途可信得多。
追问二："这是乐观锁吗？"——"不是。乐观锁是'读版本号 → 带版本号更新 → 比对影响行数'，需要应用层重试循环；这里是数据库行锁 + 条件谓词，一次 SQL 完成。"
追问三："高并发下行锁会不会成瓶颈？"——"会。同一热点的 UPDATE 会串行排队，连接池可能先被打爆。" → 顺势引到 3.10 的限量发售（Redis 预减 + MQ 削峰就是为解决这个）。
红线延伸：本项目没有用分布式锁做扣库存，不要把"加个 Redis 锁"说成自己的方案——预减 + CAS 才是。

3.4下单幂等：一次性 token 的签发与原子消费

用户双击"提交订单"会发生什么 熟悉

对应代码：order/controller/OrderRestController.java:32-35 · OrderServiceImpl.java:141-147、62-67 · common/redis/RedisOps.java:313-325

一句话：结算页打开时后端签发一个一次性 token（写 Redis，TTL 10 分钟），提交订单时带回；服务端用 DEL 把它删掉——删到了就放行，删不到就说明这个 token 已经被用过，拒绝重复提交。

打个比方 像游乐场的一次性手环：进闸口时工作人员把腕带剪断收走（DEL），你第二次拿同一根断腕带过来，闸口自然不认。关键在于"剪断"这个动作本身就是"检查 + 作废"合体——不存在"先检查真假、再剪"的两步窗口。
order/service/impl/OrderServiceImpl.java:141-147
@Override
public String createIdempotentToken() {
    Long userId = StpUtil.getLoginIdAsLong();
    String token = java.util.UUID.randomUUID().toString().replace("-", "");
    redisOps.set(TOKEN_KEY_PREFIX + userId + ":" + token, "1", 600);
    return token;
}

key 的拼法是 aimall:order:token:{userId}:{token}——按用户隔离，防止 A 用户的 token 被 B 用户猜中或复用。TTL 600 秒要覆盖"进结算页 → 填地址 → 提交"的正常操作时长，同时不留下太长的泄漏窗口。

机制与代码：为什么这里用 DEL，而不是 Lua 脚本

本项目在需要"读—判断—写"复合语义时一律用 Lua。但这个 token 的消费不需要 Lua，因为 DEL 本身已经是单条原子命令：

common/redis/RedisOps.java:323-325
// 注释原文：DEL 是原子的——删除成功即"只此一次"
public Boolean consumeToken(String key) {
    return safe(() -> stringRedisTemplate.delete(key), null, "consumeToken", key);
}
order/service/impl/OrderServiceImpl.java:60-67
// 0. 幂等 token 校验（防双击重复下单）：DEL 原子消费，一次有效。
//    token 为空 = 调用方未接入（兼容）；Redis 不可用 = fail-open 放行。
if (org.springframework.util.StringUtils.hasText(req.getIdempotentToken())) {
    Boolean consumed = redisOps.consumeToken(TOKEN_KEY_PREFIX + userId + ":" + req.getIdempotentToken());
    if (Boolean.FALSE.equals(consumed)) {
        throw new BusinessException(ResultCode.BAD_REQUEST, "请勿重复提交订单");
    }
}

三种返回值必须分清（最容易被追问的细节）：true = 首次消费（DEL 真删掉了 1 个 key），放行；false = token 已被用过 / 不存在（DEL 返回 0），拒绝；null = Redis 不可用（safe() 包装降级），fail-open 放行。代码里的判断是 Boolean.FALSE.equals(consumed)——只把明确的 false 当重复，null 走放行，这个写法本身就是 fail-open 的实现。

关键取舍：Redis 不可用时 fail-open（放行），为什么？ 因为"防重"是优化，不是正确性。两条理由：
1. 后面还有兜底。就算 token 校验完全失效、用户真的提交了两次，订单表的 uk_order_no、状态机 CAS、以及支付侧的 uk_order_id 都还在——多出来的那一单不会造成资损级错误。
2. 反过来（fail-close）是灾难。如果 Redis 一挂就拒绝所有下单，等于把一个旁路缓存组件变成了全站单点故障——RedisOps 这个可降级门面的整个设计哲学就是"Redis 挂了业务变慢，而不是不可用"。
一句话背下来："防重是优化不是正确性，别让缓存故障挡住正常下单。"
面试怎么讲
30 秒版本 "下单防双击用的是一次性 token：结算页加载时后端签发 UUID 写 Redis、TTL 10 分钟，key 里带 userId 防串用；提交订单时带回，服务端用 DEL 消费——DEL 是单命令原子操作，返回 1 就是首次消费放行，返回 0 说明已被用过，直接拒。Redis 不可用时我们选择 fail-open 放行，因为防重是优化不是正确性，后面还有唯一索引和状态机兜底；fail-close 反而会让缓存故障变成全站下不了单。"
别说错 1. token 和分布式锁不是一回事。锁挡的是"并发"（会误杀两笔真实的并发订单），token 挡的是"重复"（同一个 token 用第二次）。两个用户拿不同 token 同时下单是允许的。
2. 不要把它说成"幂等四式"。口径是"幂等设计，我用了四种手段：唯一索引 / 状态机条件更新 / 一次性 token / 消费端回查"——"四式"是自造名词，已废弃。
3. token 可以为空。hasText(...) 为假时直接跳过校验（兼容未接入的调用方、Postman 调试）。这是兼容性取舍，安全上弱一点，但避免了"必须同步升级前后端"的部署僵局——主动说出来比被追问出来好。

3.5订单快照：为什么明细表要冗余商品信息

商品改名/改价，历史订单不能跟着变 熟悉

对应代码：order/bean/OrderItem.java:23-36 · db/migration/V1__init.sql:122-132

一句话：下单的那一刻，把商品的名字、规格名、成交单价复制一份存进订单明细。之后商家怎么改名改价，历史订单显示的仍是当时的样子。

打个比方 超市小票。你三年前买的牛奶小票上印着当时的价格，就算这款牛奶今天涨价了、改名了、下架了，那张小票上的数字一个字也不会变。小票不是"商品的引用"，而是"那一次交易的记录"。订单明细就该是小票。

如果不做快照会怎样？明细只存 sku_id，展示时 join 商品表——于是：商品改价后，用户翻历史订单发现"我明明花 199 买的，怎么显示 299"；商品改名后，历史订单里的名字也跟着变；商品下架后，订单里的商品名直接查不到、页面显示空白。这在电商里是投诉级 bug，也是对账纠纷的源头。

不要说"订单项只存 id 就够了"——那是没想过商品会变的答案。
连带追问："下单金额以谁为准？"——以数据库里 SKU 的价格为准（算 total 用的是 sku.getPrice()），不接受前端传的金额。

3.6订单超时取消：TTL + DLX 延迟消息

30 分钟不付款，库存要自动还回去 掌握

对应代码：order/mq/OrderDelayMqConfig.java · OrderDelayMessageSender.java · OrderCancelConsumer.java

一句话：下单成功后往一个没有消费者的队列里丢一条消息，这个队列设了 30 分钟 TTL 和死信路由；消息躺满 30 分钟"死亡"后被自动转运到真正的工作队列，消费端检查"订单是否仍待支付"，是则取消并回补库存。

打个比方 像洗衣店的寄存柜：你把衣服存进去（入队），柜子有 30 天保管期（TTL）。到期没人来取，管理员不会把衣服扔掉，而是按规则转送到"待处理区"（死信路由），那里的工作人员再判断"这件衣服的主人还要不要"（回查订单状态）。

为什么不用"定时任务扫表"

定时任务轮询扫超时单

比如每分钟扫一次 WHERE status='PENDING_PAY' AND created_at < now-30min。

问题：实时性差（平均晚 30 秒到 1 分钟）；DB 压力恒定——不管有没有超时单都在扫；订单量上来后单次扫描越来越慢。

MQ 延迟消息（本项目主方案）

下单时投一条消息，到期即触发，不用扫描。DB 只在真正需要取消时才被访问，负载与超时单数量成正比，而不是与总订单量成正比。

扫表的思路没被丢掉，它变成补偿任务的兜底（见下）。

兜底入口就是 OrderMapper.selectTimeoutPending（OrderMapper.xml:36-45）：扫描"超时仍未取消的待支付订单"，专门兜住"消息丢了 / 没发出去"的漏网之鱼。注释里也写了"小数据量直接全表过滤状态；量级上来后可加 (status, created_at) 索引"。

队列级 TTL vs 消息级 TTL：队头阻塞

RabbitMQ 为性能考虑，只检查队首消息是否过期，不扫描整个队列。于是消息级 TTL（每条消息自带不同过期时间）有一个致命坑：

队列位置TTL 设置实际结果
队首消息 A60 分钟没到期，堵在那里
第二条消息 B1 分钟不会 1 分钟后投递——必须等 A 先死、跟着一起走；实际延迟变成 60 分钟

这叫队头阻塞。本项目的规避办法是统一过期时间 = 用队列级 TTL（参数设在队列上，全队列共享一个时钟）：

order/mq/OrderDelayMqConfig.java:73-80
@Bean
public Queue orderDelayQueue() {
    Map<String, Object> args = new HashMap<>();
    args.put("x-message-ttl", ORDER_TTL_MILLIS);              // 队列里所有消息 30 分钟过期
    args.put("x-dead-letter-exchange", ORDER_EXCHANGE);       // 过期后投给业务交换机
    args.put("x-dead-letter-routing-key", DLX_ROUTING_KEY);   // 用这个 key 重新路由
    return QueueBuilder.durable(DELAY_QUEUE).withArguments(args).build();
}

TTL 常量是 ORDER_TTL_MILLIS = 30 * 60 * 1000L。为什么不用官方延迟插件（rabbitmq-delayed-message-exchange）：它要求 Broker 安装插件，生产环境不一定装得了，本地起的原生 RabbitMQ 也没有——而 TTL + DLX 是零插件的标准方案。代价是"所有订单只能同一个超时时长"，要做"VIP 15 分钟 / 普通 30 分钟"就得换延迟插件或多条不同 TTL 的队列。

三方竞争同一订单

消费者收到消息时，订单不一定还是待支付——消息在队列里躺了 30 分钟，这期间什么都可能发生：

线程 A：用户手动取消POST /api/v1/orders/{id}/cancel
线程 B：超时延迟消息到达OrderCancelConsumer.onCancelMessage
线程 C：支付回调到达PaymentService.handleCallback 第 ⑥ 步（反方向：PENDING_PAY → PAID）

A 和 B 都要做 PENDING_PAY → CANCELLED；C 要做 PENDING_PAY → PAID。三个入口共用同一个闸门——WHERE status = 'PENDING_PAY'，所以只有一个能过：

order/mq/OrderCancelConsumer.java:67-97（日志与 null 防御从略）
public boolean cancelIfStillPending(Long orderId) {
    Order order = orderMapper.selectById(orderId);
    // 已支付/已取消：最常见的正常分支，直接跳过
    if (!Order.STATUS_PENDING_PAY.equals(order.getStatus())) { return false; }
    int rows = orderMapper.updateStatus(orderId,   // 状态机 CAS：并发下只有一个线程能改成功
            Order.STATUS_PENDING_PAY, Order.STATUS_CANCELLED, LocalDateTime.now());
    if (rows == 0) { return false; }               // 输家：被别的线程抢先
    // 回补库存——必须在 CAS 成功之后，否则输家也会回补（库存虚增）
    orderItemMapper.selectByOrderId(orderId)
            .forEach(oi -> skuMapper.addStock(oi.getSkuId(), oi.getQuantity()));
    paymentService.closeIfPaying(orderId);
    return true;
}

如果 A、B 两次都成功取消，库存会被回补两次 → 库存虚增，这是真实资损。CAS 让输家拿到 0 行、在回补之前就返回，所以库存只会被加回一次——顺序仍然是关键：CAS 成功之后才回补。

A、B 竞争的处理是"静默输家"（log + return false）；而 B、C 撞车（取消 vs 支付）后果更严重：如果取消赢了、支付回调随后到达，就会出现钱收了、货没发——代码在这里只能 log.error 提示"需退款/人工兜底"。这不是 CAS 能解决的，资金状态与业务状态必须分开记账、差异显式化。

机制与代码：发送侧为什么必须 afterCommit

事务里直接发 MQ 是反模式。MQ 不参与数据库事务，是两个独立系统。如果在下单事务还没提交时就 convertAndSend，一旦后续步骤异常、事务回滚，消息却已经飞出去了——30 分钟后消费者查到一个根本不存在的"幽灵订单"。

order/mq/OrderDelayMessageSender.java:42-55
public void sendAfterCommit(Long orderId) {
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        log.warn("sendAfterCommit 在无事务上下文调用，退化为立即发送 orderId={}", orderId);
        sendNow(orderId);
        return;
    }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() { sendNow(orderId); }
    });
}

这个类被抽出来当"唯一出口"，本身就是踩坑的产物。早期只有普通下单发这条消息；后来限量发售（3.10）也建订单，却忘了发——导致抢购单永不超时取消，限量库存被死单永久占用。根因是"建单必发延迟消息"这个约束散落在各处、靠人记。抽成唯一组件之后，任何建单路径都调 sendAfterCommit，漏发 = 漏调方法，一眼可见。

sendNow 的降级也值得一提：MQ 不可用时只记日志、不炸主流程，漏掉的单由补偿任务兜底。超时取消属于"尽力而为"功能，不该因为它挂了就让下单失败。

消费端还有一条强相关的修复：早期版本在 @Transactional 方法内部 try-catch 吞掉异常——异常不冒出代理，Spring 无从感知，半截事务照样提交（状态已改、库存已回补，最后 closeIfPaying 抛异常 → 回滚不生效，支付单永远 PAYING）。现在的写法是让异常冒出 → 事务回滚 → 容器 reject（default-requeue-rejected=false，不重入队防毒消息循环）→ 死信路由进 DLQ 等人工。"事务里吞异常"和"事务里发消息"是同一族反模式：都骗过了事务管理器。详见 05 页。

为什么用队列级 TTL 而不是消息级：RabbitMQ 只看队首过期，消息级 TTL 会队头阻塞；我们所有订单超时时间一致，队列级天然免疫。

3.7支付闭环：t_payment 状态机 + PayChannel 抽象

为什么不在订单表加个"已支付"标记 掌握

对应代码：pay/bean/Payment.java · pay/channel/PayChannel.java · MockPayChannel.java · pay/service/PayChannelRouter.java

一句话：资金的事单独一张表、单独一个状态机。订单管交易，支付单管资金；一次"发起支付"的唯一标识是支付单号，它才是回调幂等的锚点。

打个比方 订单是合同，支付单是每一次打款的回执。合同可以多次尝试打款（第一次超时了再付一次），但每一笔打款都有且只有一张回执。把"已支付"标记直接打在合同上，你就说不清"是哪一次打款成功了"。
问题在订单表加 paid 字段会怎样
幂等粒度错一次订单可能多次发起支付（第一次超时后重付）。"哪一次成功了"这个事实只能锚在支付单号上，标记在订单上说不清。
对账无锚点第三方交易号 third_trade_no、回调原始报文 callback_body 放哪？塞进订单表会让它膨胀成大杂烩。
状态耦合订单有订单的状态机，支付有自己的状态机（PAYING → PAID / CLOSED），两者生命周期不同步——订单已取消，支付单可能还停在 PAYING 等关闭。

支付单的四个状态（Payment.java:24-30）：

PAYING待支付
已建单等付款
PAID已支付
终态，绝不回退
CLOSED已关闭
超时 / 取消
FAILED支付失败
常量已定义

合法流转只有三条边：PAYING→PAID（回调验签通过 / 主动查单查到已付）、PAYING→CLOSED（30 分钟超时 / 用户取消 / 订单取消）、PAYING→FAILED。说状态名时用代码里的真名，不要说成 WAITING_PAY / SUCCESS——那是通用叫法，本项目没这么写。

PayChannel：为什么恰好是这三个方法

一句话：任何第三方支付网关（支付宝 / 微信 / 银联 / Stripe）接入都逃不出三件事——下单换收银台、验签、主动查单。抽象出这三件事，接口就不会"为某家定制"。

pay/channel/PayChannel.java:28-54
public interface PayChannel {
    /** 渠道标识，与 t_payment.channel 对应：MOCK / ALIPAY / WECHAT */
    String code();
    /** ① 发起支付：返回给前端的"收银台"信息 */
    CashierInfo create(String paymentNo, java.math.BigDecimal amount, String subject);
    /** ② 校验回调报文签名 */
    boolean verifyCallback(java.util.Map<String, String> params);
    /** ③ 主动查单：用于"回调丢失"时的对账兜底 */
    QueryResult query(String paymentNo);
}

三个方法的设计意图正好对上后面几节：create 对应"发起支付"（3.7），verifyCallback 对应"防伪造回调"（3.8），query 对应"回调会丢 → 主动查单"（3.9）。接口的形状本身就是业务问题的形状。

路由类 PayChannelRouter.resolve(channel) 按渠道码挑实现，找不到时降级为 MOCK 并打 WARN，而不是抛错。理由很实在：支付是交易主链路，配置里写错一个字母就让整个下单不可用，代价太大。

诚实标注：这里的渠道是模拟的 MockPayChannel 是模拟渠道；AlipaySandboxChannel 这个类不存在——它只在 PayChannel 和 MockPayChannel 的注释里作为"将来配了沙箱凭证可以接入的实现"被提到过。
正确说法："我做了一层支付渠道抽象，默认实现是本地模拟渠道；换真实渠道只改实现类、业务代码零改动"。绝不能吹成"我接了支付宝/微信支付"，也不能说"支付功能是假的"——假的只有"第三方服务器不存在"这一件事，HMAC 签名、验签、幂等、金额核对、状态机、订单联动全是真实链路。
机制与代码：mock-pay 不直接改状态，而是走真实回调链路

模拟渠道没有"第三方页面"，怎么触发回调？PaymentController.mockPay 的做法很讲究：它自己不碰状态，而是以"第三方"的身份构造一条带真实签名的回调报文——填 payment_no / order_no / trade_no / amount / status=PAID，再用 mockPayChannel.sign(params) 算签名塞进 sign 字段——然后调 paymentService.handleCallback(MockPayChannel.CODE, params)。

所以验签、幂等、金额核对、状态机流转全部真实走过。这也意味着你可以真实验证安全链路：手动 curl 一条假签名的回调，它会返回 sign-error；把 amount 改小再签，它会返回 amount-mismatch。"模拟"的只有第三方不存在，工程链路 100% 是真的。

3.8HMAC 签名与验签：防伪造回调

不验签的回调接口 = 向全世界开放的"改单入口" 熟悉

一句话：支付回调是公网可访问、没有登录态的接口，如果不验签，任何人执行一条 curl 就能把任意订单标成"已支付"。

打个比方 验签像信封上的火漆印章。拆信（解析报文）之前先看印章（验签）对不对——印章不对，信里写得再动听（"这笔钱我付了"）也不能信。

不验签的世界会怎样

假设回调只做"取参数、改状态"，那么任何人都可以：白嫖订单（发一条 payment_no=P123，这单就被"支付"了）；篡改金额（把自己的 1 分钱订单标成已付，买走 399 的商品）；伪造退款。所以回调的第一件事永远是验签，它回答："这条报文真的来自第三方吗？中途有没有被改过哪怕一个字符？"验签失败必须拒绝，不存在"为了成功率放行"。

从哈希到 HMAC：三步演进

第一步：普通哈希。SHA256("amount=399&payment_no=P123") 得到一串固定长度的指纹，改一个字指纹全变，所以能发现"被改过"。但攻击者也知道你的拼接规则：他改完 amount 重新拼一遍、重新算个哈希附上，照样骗过你。缺的是"只有双方知道的秘密"。

第二步：加盐哈希。双方约定密钥 secret，算 SHA256(明文 + secret)。攻击者不知道密钥，改了报文就伪造不出正确哈希。但密码学上这种手搓拼接有已知弱点（长度扩展攻击），不能自己发明。

第三步：HMAC。标准化的"带密钥哈希"构造，内部用两轮哈希嵌套密钥，数学上免疫长度扩展攻击。一句话：HMAC = 篡改检测（哈希）+ 身份证明（密钥）的工程化合体。真实支付宝回调报文里的 sign 字段就是干这个的。

签名时参数排序的坑

pay/channel/MockPayChannel.java:95-106
public String sign(Map<String, String> params) {
    Map<String, String> sorted = new TreeMap<>(params);   // ① 按 key 字典序排序
    List<String> parts = new ArrayList<>();
    sorted.forEach((k, v) -> {
        // ② 签名字段本身不参与签名；空值不参与
        if (!SIGN_PARAM.equals(k) && v != null && !v.isBlank()) {
            parts.add(k + "=" + v);
        }
    });
    String plain = String.join("&", parts);                // ③ 拼成 k=v&k=v
    return hmacSha256(plain, secret);                       // ④ HMAC-SHA256
}

为什么必须 TreeMap 排序：HashMap 的遍历顺序由 hash 桶决定、语义上不保证稳定。同样的参数两次遍历可能拼出 a=1&b=2 和 b=2&a=1——签名时对时错，是那种"本地好好的、一上线随机失败"的诡异 bug。各家支付网关文档都强调"按 ASCII 码升序拼接"，原因就在这。

为什么 sign 自己不参与签名：签名不能签自己（循环依赖）。验签方拿到报文后把 sign 摘出来、用剩余参数重算，再比对。

为什么用 MessageDigest.isEqual 而不是 equals

pay/channel/MockPayChannel.java:66-79
public boolean verifyCallback(Map<String, String> params) {
    if (params == null || params.isEmpty()) { return false; }
    String sign = params.get(SIGN_PARAM);
    if (sign == null || sign.isBlank()) { log.warn("回调缺少签名字段"); return false; }
    String expected = sign(params);
    // 注意：用 constant-time 比较，防时序攻击（安全编码习惯）
    return MessageDigest.isEqual(expected.getBytes(StandardCharsets.UTF_8),
            sign.getBytes(StandardCharsets.UTF_8));
}

equals 碰到第一个不同的字符就立即返回 false——比对耗时与"正确前缀有多长"成正比。攻击者据此可以逐字节爆破：先试 256 种首字符，哪个响应慢一点点哪个就对；再试第二位……这就是时序攻击。MessageDigest.isEqual 是 constant-time 比较，无论差异在第几位耗时都恒定。

机制与代码：HMAC 与 RSA2 的选型，以及回调端点的身份模型

真实支付宝用的是 RSA2（非对称）：我方用应用私钥签名，支付宝用应用公钥验签；我方收到回调时用支付宝公钥验签。本项目用 HMAC-SHA256（对称），因为模拟渠道收发双方都是我们自己，对称密钥更合适。换 RSA2 只需替换签名/验签两个私有方法——接口形状不变，这就是抽象的价值。

HMAC-SHA256（本项目 Mock）RSA2（真实支付宝）
密钥收发双方共享同一个我方私钥签 / 对方公钥验（不共享）
适合自建渠道（收发都是自己）多方互信（我方 ↔ 支付宝）
泄露面密钥给谁谁就能伪造私钥只在自己手里

回调端点为什么不加登录校验（PaymentController 类注释）：第三方支付平台不可能持有我们用户的 token。回调接口的"身份"由验签保证，不是 token——业务接口靠"你是谁"（认证），回调接口靠"消息是谁发的、有没有被改"（完整性），这是设计上的根本差异。

返回值为什么是特定字符串而永不抛异常：支付宝要求收到字面量 success 才停止重发，返回其他内容或抛异常（包括 500 状态码）它都会持续重试（8 次以上）。所以 callback 方法连兜底 catch 返回的都是 "system-error" 字符串，而不是抛出去。

面试怎么讲

3.9支付幂等三层 + 主动查单对账

重复回调必然发生，回调也必然会丢 掌握

对应代码：pay/service/PaymentService.java:148-245 · mapper/PaymentMapper.xml · db/migration/V4__payment_order_unique.sql

一句话：回调重复靠三层防线吸收掉（唯一索引 / 已支付快路径 / 状态机 CAS）；回调丢失靠主动查单捞回来。两者是一对，缺一不可。

打个比方 快递电话（回调）可能被打两次（重复），也可能你一次没接到（丢失）。重复按两次门铃不会让快递多送一份——那是幂等；没接到就得自己上 App 查物流——那是主动查单。只做前者，漏接一次包裹就永远卡在"待收"；只做后者，你每次都得主动去查。

三层防线

第 1 层 · 物理层：uk_payment_no / uk_order_id 唯一索引重复"创建"直接被数据库拒绝——t_payment.payment_no 唯一；V4 又加了 uk_order_id 保证一订单一活单
第 2 层 · 快路径：已 PAID → 直接回 success挡"串行重复"（对方重发，最常见）。它挡不住并发——两个回调同时到达时，两个都查到 PAYING
第 3 层 · 慢路径：WHERE status='PAYING' 状态机 CAS挡"并发重复"。两个回调都往下走时，只有 CAS 让其中一个拿到 0 行。SQL 的 WHERE 才是幂等的真身

回调的完整六步（PaymentService.handleCallback）：① 验签 → ② 定位支付单 → ③ 幂等快路径 → ④ 金额核对 → ⑤ 支付单 CAS → ⑥ 订单 CAS → 回 success。每一步去掉会出什么事，值得背下来：

去掉哪一步后果
① 验签回调端点公网可访问无登录 → 任何人都能把订单改成已支付，curl 一条命令即可
③ 幂等快路径功能仍正确（CAS 兜着），但每次重复都要跑一遍 UPDATE——快路径是性能优化，CAS 才是正确性保证
④ 金额核对1 分钱买走 399：改小 amount 重新签名打回来
⑤ 支付单 CAS并发两个回调同时穿过第 ③ 步 → 用旧报文覆盖交易号
⑥ 订单 CAS与"超时取消"竞态：支付成功的瞬间订单被取消任务改成 CANCELLED → 钱收了货没发

第 ④ 步金额核对有三个分支：amount-missing（回调缺金额字段）、amount-invalid（不是合法数字）、amount-mismatch（与支付单金额不等）。代码注释里写着这一处的评审修正：「早期写法 amountStr != null 才核对——"回调不带金额字段"就能绕过核对，等于给"1 分钱买 399"留了门。金额是回调和支付单的必配字段，缺失本身就是异常。」

这三个分支有三个必须能说清的点：一是"缺失即拒绝"——如果允许缺失，攻击者只要不带 amount 字段就能绕过整条核对逻辑，"可选的安全检查等于没有安全检查"；二是用 compareTo 不用 equals——BigDecimal.equals 连精度一起比（399 与 399.00 不相等），compareTo 只比数值；三是金额以我方支付单为准（它取自 order.getTotalAmount()），回调只用来比对，不作为数据源。

回调会丢：主动查单对账

回调除了重复还会丢——第三方认为通知成功了，但我方实际没处理成功，这条通知就永久消失了。这时用户付了钱、系统不知道，是资损方向最严重的故障。

核心原则一句话："以第三方为准修正本地，但 UNKNOWN 绝不动状态"。查不到 ≠ 没支付——渠道超时、网络抖动都可能返回查不到，此时宁可不改，否则就是拿不确定的信息去覆盖确定的资金状态。QueryResult 的三个值 PAID / NOT_PAY / UNKNOWN 就是为这个语义设计的。

诚实边界 MOCK 渠道的 query 恒返回 UNKNOWN（没有真第三方可查），所以 sync 在 MOCK 下是一条死路径——它为真实渠道而生，接口契约先立好。这个边界主动讲出来，比被追问出来好得多。

三层防护：预减挡量 / MQ 摊峰 / DB CAS 保正确

"挡量"与"削峰"是两件不同的事，缺一不可——这是这题最值钱的一句话：

  • Redis 预减是准入闸门：放行的消息数 ≤ 库存量。库存抢完后，洪峰在 Redis 里被纯内存操作拒绝，DB 完全无感。
  • MQ 是节奏器：通过闸门的瞬时洪峰被摊平成消费速率，DB 的行锁不再被万级请求争抢、连接池不会被打爆。
  • DB 行锁 CAS 是正确性底线：Redis 只是准入层，不是真值；真值永远在 t_product_sku.stock。消费端仍然走 3.3 那条 WHERE stock >= ?，所以即使 Redis 计数失真也绝不会超卖。

消费端扣库存走的还是 3.3 那一条——skuMapper.deductStock(sku.getId(), msg.quantity()) 返回 0 就抛 STOCK_NOT_ENOUGH("已被抢完")（DropOrderExecutor.java:100-107）。削峰改变的是"流量到达 DB 的节奏"，防超卖的兜底层次一寸不少。

第三层是 t_drop_record 上的 uk_activity_user(activity_id, user_id)——一人一单的唯一索引物理拒绝。撞键会抛 DuplicateKeyException，在事务内成为回滚信号，被上层捕获做幂等跳过。语义上要说清：唯一索引硬保证"一人一次成功"，per_limit 约束的是"单次购买上限"，组合起来 = "每人可成功一次、单次最多 per_limit 件"（这是 V3 评审澄清过的一处，早期两者语义看起来是矛盾的）。

为什么"判重 + 扣减"必须在同一脚本：拆成两步（先 EXISTS 再 DECRBY）的话，同一用户的两个并发请求可能都通过判重、各自扣一次库存——名额被同一个人占两份。Lua 在 Redis 单线程里原子执行，天然串行。这也是把"防重复提交"从应用层下沉到 Redis 的原因：HTTP 线程无状态，挡不住同一用户的双击。

为什么不用分布式锁："判断 + 扣减"本质上是一次原子计数，Lua 一发入魂；加锁方案每次"加锁 → 读 → 改 → 解锁"要两次网络往返，而且全局串行化。锁适合保护复杂临界区（一长段业务逻辑），简单原子计数用 Lua 更快更简单。

为什么返回 QUEUED 而不是订单号

这是异步化的必然结果：接口返回时订单还不存在。buy 是"过闸门"（毫秒级返回受理），订单由 MQ 消费者异步创建，所以接口不可能返回 orderId。前端拿到 QUEUED 后每 1~2 秒轮询 result，SUCCESS 时带上 orderId 再跳订单页——"受理与结果分离"是秒杀/抢购类系统的标准接口形态。

判定优先级是：DB 记录（真值）> 失败标记 > 受理标记（处理中）> 未参与（DropService.result 就是按这个顺序 return 的：查到 t_drop_record 直接 success(orderId)，否则依次查失败标记、受理标记）。三个 Redis key 的分工也要分清：aimall:drop:stock:{id} 是库存计数（准入层），aimall:drop:user:{id}:{uid} 是受理标记（防重复提交，与扣减同脚本写入），aimall:drop:fail:{id}:{uid} 是失败标记（前端据此区分"处理中"和"失败"）。后两个标记 TTL 都是 600 秒，覆盖"排队 → 建单"的正常窗口。

机制与代码：失败三分流 + 降级链 + 三个不能说错的口径

消费端把三类异常分成三套路数（DropOrderExecutor.execute）：

异常含义处置
DuplicateKeyExceptionuk(activity_id,user_id) 冲突 = 该用户此前已建单成功（重复投递 / 并发提交）回补本条消息的预减，幂等跳过
BusinessException业务性失败（库存不足 / 不在发售时间）回补预减 + 写失败标记，ACK 不重试（重试也不会成功）
其他 Exception未知故障（DB 抖动等）原样重抛 → 容器 reject（default-requeue-rejected=false）→ 进 DLQ 等人工

这里有一个诚实加分点：分支① 如果是纯重投（首条消息已被消费过），这次回补会让 Redis 多记一点库存——多放几个请求进来，但 DB CAS 仍然兜底，方向是安全的；反过来"少记"才会让用户"有货抢不到"，那才是资损。所以取舍是：宁可多放，不可少记。能讲出"降级方向的正确性"，比背方案高一个段位。

降级链（与内容审核同款"可插拔"原则）：Redis 可用 + MQ 可用 → 标准链路；MQ 不可用 → 预减 + 本地线程池异步建单（无削峰但体验一致）；投递失败 → 立即回补预减 + 提示重试；Redis 不可用 → 本地线程池异步建单（DB CAS + 唯一索引硬扛）。

这里还有一个高频追问：为什么建单逻辑要单独拆成 DropOrderExecutor 一个 bean，而不是放在 DropService 里？因为本地降级路径需要事务方法经 Spring 代理调用——如果 createDropOrder 是 DropService 的私有方法，内部 this.createDropOrder() 自调用不走代理，@Transactional 就失效变裸奔（与 @Async 自调用失效同源）。拆成独立 bean 之后，消费端和降级端都通过代理调用它，事务语义才稳定。

三个口径必须说准。其一，消息里不带金额——只带 activityId / userId / quantity，金额在消费端回查 DB（act.getDropPrice().multiply(...)），不信任消息体，理由同 3.6："消息在队列里待着的时候，世界已经变了"。其二，预热必须用 SET NX：早期是 check-then-set（GET 判空 → SET 覆盖），并发首访时两个请求都会判"未预热"，后一个 SET 会把已经扣减过的库存重置回全量——直接超卖；setIfAbsent 把"判断 + 写入"原子化。其三，抢购参数必须过 Bean Validation：早期用裸 Map 接参，传负数会让 Lua 的 DECRBY 变成反向加库存、订单金额算出负数，现在由 DropBuyRequest 上的 @Min(1) @Max(99) 拦在最外层。最后是一致性边界（诚实说）：Redis 预减与 DB 实扣是两个存储、没有事务，回补也可能失败、TTL 到期重灌也可能覆盖，所以这是最终一致——活动结束后对账（Redis 剩余 vs DB 应余）校正，"已受理但订单还没建好"的窗口期由前端轮询掩盖。

把这两段背熟，订单链路这块就稳了 冲刺

口径依据：项目手册口径红线 · 08 面试速查与自查

「下单怎么防超卖？」30 秒版 "核心是一行 SQL：UPDATE t_product_sku SET stock = stock - ?, sales = sales + ? WHERE id = ? AND stock >= ?。
InnoDB 会对命中的行加排他锁，stock >= ? 这个条件判断是在锁内、按最新的库存值执行的——判断和扣减在同一条 SQL 里原子完成。返回影响行数 0，就说明并发下库存不足，抛业务异常让整个下单事务回滚。
这本质是 CAS 思想：把期望条件写进 WHERE，让数据库来裁决。不需要应用层重试、不需要额外加分布式锁，也不需要 version 字段。
要说代价也有：高并发下同一热点的行锁会串行排队，所以限量发售那种瞬时洪峰的场景，我在它前面加了 Redis 预减 + MQ 削峰。"
