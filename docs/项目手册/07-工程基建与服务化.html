上半工程基建（V1.5）：从"能跑"到"能上线"

先记住这一层的定位V1.5 不产出任何新功能，产出的是可信度。它的每一块都在回答："这个项目交给别人、或者出线上事故时，会发生什么？"面试官问这一层，不是想看你会用什么组件，而是想看你是不是只会写 CRUD。

7.1Flyway：数据库版本管理

Flyway 表结构版本管理 熟悉

对应代码：backend/src/main/resources/db/migration/（4 个文件）

一句话：把"建表"从"一个手工执行的脚本"变成"一串有版本号、必须按顺序执行、执行记录可查的迁移文件"。没有它，"这个字段到底加没加"只能靠口头约定——多人协作必炸。

手工 init.sql 的三宗罪：漂移（各自手工执行，脚本和真实库越差越远）、不可回溯（字段为什么从 VARCHAR(50) 改成 (100)？谁改的？无人知道）、新环境搭不起来（脚本是"最终态快照"，而线上库是三个版本前建的，中间的 ALTER 没有记录）。

打个比方像游戏的存档系统：每过一关自动存一次档（执行迁移并记录版本号）。下次进入游戏时逐个比对"哪几关还没打"，只补打缺的那几关，而不是把整局从头再打一遍。
机制与代码：版本表 + 校验和 + 顺序执行

启动时 Flyway 做四件事：① 查 flyway_schema_history 表（没有就建）；② 扫描 migration 目录，算出哪些版本还没执行；③ 按版本号顺序执行，成功后插一行记录（版本号、描述、执行时间、checksum）；④ 全部执行完才放行应用启动——启动即校验，结构永远与代码同步。

迁移文件内容
V1__init.sqlV1 的 10 张表初始结构（文件头写着"本文件是数据库结构的唯一权威来源"）
V2__content_and_rag.sql内容社区 + 审核流水 + RAG 知识库（含 ngram 全文索引）
V3__pay_and_drop.sql支付 + 限量发售
V4__payment_order_unique.sql给 t_payment.order_id 加唯一索引（"一订单一活单"）——只 ALTER 不建表
V5__note_audit_version.sql审核链路一致性修复：给 t_note 加 audit_version，并把 t_audit_record 的唯一键改成 (biz_type, biz_id, biz_version, status)——同样只 ALTER 不建表（所以表数仍 24）
db/migration/V1__init.sql:7-13
-- 迁移约定：
--   1. 只做增量，不修改已执行的迁移文件（已执行文件的 checksum 会被校验）。
--      要改表结构请新增 V2__xxx.sql、V3__xxx.sql……
--   3. 不使用 DROP TABLE —— 迁移脚本必须是"向前"的，删表另写迁移。
--   4. 存量库接入：application.yml 已配置 baseline-on-migrate=true，
--      非空库会被自动"基线化"到版本 1（把 V1 视为已执行），不会重复建表。

纪律四条：只增不改（改了已执行的文件，启动时 checksum 校验失败直接拒绝启动）；改表 = 新迁移；命名 V<版本>__<描述>.sql；失败处理（迁移执行到一半会留 success=0 记录，修复 SQL 后删掉那行再启动，因为 DDL 多数不支持回滚）。

关键决策：baseline-on-migrate——存量库怎么"追认"

接入 Flyway 时项目库里已经有表了。这时直接跑会报错：非空库且没有 baseline 记录，Flyway 不知道这个库处在什么版本，不敢乱动。这是本项目最值得讲的一个接入决策——用一个开关，让新库自动建表、老库自动基线化，两条路都能走通。

一句话讲透baseline-on-migrate=true 的意思是：遇到非空的存量库时不报错，先给它打一个基线（把某个版本"追认"为已执行），再从下一个版本接着走。本项目按 V1__init.sql 文件头的口径基线化到版本 1——把 V1 视为已执行，存量库不会重复建表；全新库则从零正常建表。
补充一种等价写法（V1.5 详解正文写的是这一种）：baseline-version=0 + 依赖 V1 迁移本身幂等——因为所有建表都写了 CREATE TABLE IF NOT EXISTS，重放也无害。两条路的共同点都是打开 baseline-on-migrate，这才是关键决策。
历史教训：单一权威源项目里曾经有一个 sql/init.sql 便利脚本，三个问题很典型：只建 8/24 张表（严重残缺）、用 DROP TABLE（跑一次就把数据清空）、注释口径和迁移文件相反。这份脚本已于 2026-09-19 删除，现在全项目只有 db/migration/ 一处建表来源。这个故事的价值不在脚本本身，而在"单一权威源"：同一件事有两个来源，就一定会有一次用错那个旧的。
读代码时的小发现 V1__init.sql 文件头还留着"sql/init.sql 保留仅作便利脚本"的旧措辞——文件已删，这句注释还没同步。真实项目里这种残留很常见。
面试怎么讲
30 秒版本"我用 Flyway 把表结构纳入版本管理，核心三条：迁移文件只增不改，改了已执行的文件 checksum 校验会拒绝启动；要改结构就新增一个迁移；启动时按版本号顺序补齐没执行过的，全部成功才放行应用。最关键的接入决策是 baseline-on-migrate——我的库接入时已经有表了，非空库没有基线 Flyway 会拒绝执行，打开这个开关后新库自动建表、老库自动基线化。"
别说错1. 别说"Flyway 能回滚数据库"，DDL 多数不支持回滚。2. 那个 sql/init.sql 已经删了，别再说"我们还有一份便利脚本"。

7.2traceId 全链路：日志从"一团乱麻"到"一根线"

traceId 三件套：Filter + MDC + TaskDecorator 掌握

对应代码：common/trace/TraceIdFilter.java · TraceIdContext.java · MdcTaskDecorator.java · logback-spring.xml

一句话：给每个请求生成一个 id，让这次请求打出的所有日志都带上它——出事故时 grep 这个 id 就能把一次请求的完整现场（入参、SQL、AI 调用、异常堆栈）一根线捞出来。没有它，几百并发下日志互相交织，你连"哪几条属于同一个请求"都分不清。

打个比方像在快递包裹上贴一个唯一运单号。中转站、分拨中心、派件网点每经一手都盖个章，但运单号不变——出问题顺着号就能把全程轨迹串起来。MDC 就是那个"贴号"的动作，而且贴在线程身上，不需要在每个方法签名里传参。
机制与代码：三件套各自干什么
① TraceIdFilter入口：生成/沿用 traceId
存 MDC + 回写响应头 + finally 清理
② TraceIdContext基于 SLF4J MDC 的工具类
底层是 ThreadLocal
③ logback pattern%X{traceId} 把值打进每条日志
不写这一步前面全白干
common/trace/TraceIdFilter.java:40-51
String incoming = request.getHeader(HEADER_TRACE_ID);
// 上游（网关/其他服务）传了就沿用，否则自己生成 —— 为 V4 微服务链路追踪预留
String traceId = StringUtils.hasText(incoming) ? incoming : TraceIdContext.generate();

TraceIdContext.set(traceId);
response.setHeader(HEADER_TRACE_ID, traceId);
try {
    filterChain.doFilter(request, response);
} finally {
    // 必须清理：Tomcat 线程池复用，不清会串号
    TraceIdContext.clear();
}

三个设计点：用 Filter 不用 Interceptor（Filter 在 Servlet 容器层，早于 DispatcherServlet，连被拦截器拦掉的 401 请求也有 traceId）；响应头回传（用户报障时贴出 X-Trace-Id 就能定位）；finally 必须 clear（Tomcat 线程池复用线程，不清理会把上一个请求的 traceId 带到下一个请求——串号比没有更糟，会误导排查方向）。

traceId 生成得很短：16 位十六进制（TraceIdContext.java:34），够唯一且不占日志篇幅。logback 用 %X{traceId:-N/A} 取出来（logback-spring.xml:23,27），"没有值时打 N/A"是为了不让日志列错位。

本章最重：异步线程里 traceId 丢了

事故现场：笔记发布走线程池做 AI 审核，日志里 Web 线程那半边有 traceId，池线程那半边什么都没有——一次请求的日志被切成两半，等于白做。注意它是静默的：不报错，只是那一截日志没有标识。

根因：MDC 底层是 ThreadLocal，天然线程隔离。请求线程 A 往自己的储物柜里放了 traceId，线程池的线程 B 打开的是自己的柜子——空的。这不是 bug，隔离正是 ThreadLocal 存在的意义。

解法：线程池的"任务包装器" TaskDecorator——提交时拍照、执行时还原、执行完清理。

common/trace/MdcTaskDecorator.java:41-59
public Runnable decorate(Runnable runnable) {
    // 在【提交方线程】拍下当前 MDC 快照
    Map<String, String> snapshot = MDC.getCopyOfContextMap();

    return () -> {
        try {
            // 在【执行方线程】还原快照
            if (snapshot != null) {
                MDC.setContextMap(snapshot);
            } else {
                MDC.clear();
            }
            runnable.run();
        } finally {
            // 归还线程池前必须清理，避免串号
            MDC.clear();
        }
    };
}
为什么不用 InheritableThreadLocalLogback 支持把 MDC 配成 InheritableThreadLocal，子线程创建时会继承父线程的值。但线程池的线程是提前创建好、长期复用的——创建它们时父线程里还没有 traceId，"继承了个寂寞"。所以线程池场景必须用装饰器手动传递。
Actuator：给运维一双眼睛/actuator/health 聚合各组件（db、redis、diskSpace…）的探活结果给 UP/DOWN，配 probes.enabled 后额外提供 liveness（存活）与 readiness（就绪）探针。liveness 失败 → 重启容器（进程卡死，重启能救）；readiness 失败 → 摘流量但别重启（启动中或依赖暂时不可用，重启没用）。两者搞反的后果：用 liveness 去探依赖，数据库抖一下就会全站容器连环重启（雪崩）。
面试怎么讲
30 秒版本"traceId 是一套三件套：入口用 TraceIdFilter 生成或沿用 traceId 存进 MDC 并回写响应头；logback 的 pattern 用 %X{traceId} 把它打进每条日志。最容易被问的是异步丢 traceId——MDC 底层是 ThreadLocal，切线程就丢，我用 TaskDecorator 在提交时快照、执行时还原、finally 清理。清理很关键，线程池会复用线程，不清理会串号。"
别说错当前是单机 + HTTP 头透传，不是真正的分布式追踪（那要有 span、父子关系、采样，需要 OpenTelemetry + Jaeger/SkyWalking）。另外 @Scheduled 走的是另一套 TaskScheduler，本项目没给它挂 decorator——别把"全链路"讲成一点不漏。

7.3对象存储抽象：本地 / MinIO 双实现

StorageService 抽象 + 上传安全三件套 熟悉

对应代码：common/storage/（7 个文件）

一句话：业务代码只依赖 StorageService 接口，不关心文件落在本地磁盘还是 MinIO。换存储只改一行配置，业务零改动。

为什么不能一直本地存？本地磁盘存图片有三宗罪：多实例部署必炸（上传打到实例 A，读请求打到实例 B，直接 404）；容器化即丢失（容器重启，没挂卷则文件全没）；无法做 CDN 与权限控制。

打个比方像给家里装标准插座，而不是把电器焊在电线上。插座规格（接口）不变，后面接市电还是接发电机（本地还是 MinIO），电器都不用改。
机制与代码：一个工厂方法选实现 + MinIO 懒初始化

StorageConfig 用一个工厂方法显式二选一：配置 aimall.storage.type=minio 就装配 MinioStorageService，其他任何取值（包括没配）都走本地实现——"未配置 = 本地"的兜底语义非常明确，保证零依赖能启动。

MinIO 的懒初始化：构造函数里不连 MinIO，等第一次真正上传时才建客户端（MinioStorageService.java:86-103，volatile + synchronized 双重检查锁）。意义是——配了 minio 但没起 MinIO 容器，应用照样能启动，只有"上传"这一个操作会失败。这是"可降级"哲学在存储层的落地。

预签名 URL（MinioStorageService.java:131-146）：配了 urlPrefix（如 CDN 域名）就直接拼 URL；没配则生成预签名 URL（有效期 7 天）。桶可以完全私有，靠签名临时授权访问——比"把桶设成公开可读、任人拖库"安全得多。另外 /files/** 的静态映射只映射 uploads 一个目录，不暴露整块磁盘（StorageConfig.java:40-56）。

上传安全三件套（红线）

上传接口是公网写入点，攻击面最大。三件套缺一不可，全部在服务端做——前端校验是体验，后端校验才是安全。

1. MIME 白名单（不是黑名单）：只放过 image/jpeg / png / webp / gif。黑名单永远列不全（漏一个 .html 就可能造成存储型 XSS——用户上传恶意页面，通过你的域名打开就能窃取同域 Cookie）；白名单"不在名单里 = 拒绝"，天然完备。
2. UUID 重命名（防路径穿越 + 防覆盖）：完全忽略用户上传的原始文件名，用 UUID + 日期目录 生成对象键。用户传 ../../etc/cron.d/evil 也没用，因为那个名字根本没参与拼路径。
3. 大小限制（防 DoS）：默认 10MB。不限制的话，一个几十 GB 的文件就能把磁盘写满。

7.4线程池：从 Boot 默认的 OOM 陷阱到有界 + 反压

有界队列 + CallerRuns 背压 + MDC 传递 熟悉

对应代码：config/AsyncConfig.java:39-53

一句话：用 @Async 但不配线程池，用的就是 Spring Boot 默认的 applicationTaskExecutor——它的队列容量是 Integer.MAX_VALUE。后果是一条静默的死亡链：

提交速度 > 执行速度任务开始排队
队列无限增长永远触发不到拒绝策略
堆内存耗尽 → OOM全站挂

最阴险的是它不报错、不打日志——直到 OOM 前一刻，系统看起来"一切正常"。所以生产代码必须显式配置有界池。

打个比方无界队列像一家不设候位上限的餐厅：来多少客人都往里放，走廊站满、大堂站满，最后整栋楼塌了。有界队列是"门口最多排 200 人，满了就让新来的客人自己去后厨帮忙"——压力立刻传回去，门口自然就不挤了。
机制与代码：逐参数精读
config/AsyncConfig.java:39-53
@Bean(name = {"taskExecutor", "appExecutor"})
public ThreadPoolTaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(200);
    executor.setThreadNamePrefix("aimall-async-");
    // 关键：把 MDC（含 traceId）从提交线程传递到执行线程
    executor.setTaskDecorator(new MdcTaskDecorator());
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(10);
    executor.initialize();
    return executor;
}

4/16 的依据：本应用是 IO 密集型（查库、调 AI、写文件），线程大部分时间在等 IO，所以线程数可以大于 CPU 核数——用线程切换的成本换吞吐。经验起点是核数 × 2 ~ × 4，压测再调。

队列 200：给突发留缓冲但不无限，超出即触发拒绝策略。宁可快速降速，也不要无限堆积。

CallerRunsPolicy：队列满时让提交任务的线程自己跑这个任务。Web 线程被迫去跑任务，处理后续请求的速度自然变慢，提交速率于是自动下降——这叫反压（backpressure）：把压力传回上游让上游自然减速，而不是丢任务（对比 AbortPolicy 抛异常快速失败、DiscardPolicy 静默丢弃）。

bean 名为什么叫 taskExecutor：@Async 默认就按这个名字找执行器，所以业务代码写 @Async 不用带参数就能用上这个带 MDC 传递的池。优雅停机两个参数让应用关闭时先跑完手里的活（等 10 秒），避免"发版瞬间丢一批审核任务"。

面试怎么讲
30 秒版本"@Async 不配线程池时用的是 Boot 默认执行器，队列是无界的——永远触发不到拒绝策略，任务堆积直到 OOM，而且整个过程不报错。我显式配了有界池：核心 4、最大 16、队列 200，拒绝策略用 CallerRuns。它的含义是队列满了让提交任务的线程自己跑——这是一种背压，把压力传回上游让它自然减速，而不是把任务丢掉。池上还挂了 TaskDecorator 传 traceId，并配了优雅停机。"
别说错1. 别把 CallerRuns 说成"降级"或"失败"——它是主动减速，任务照样被执行。2. 别把线程数说成"核数 + 1"——那是 CPU 密集型的公式，IO 密集型可以更大。

关键技巧：mockStatic 钉住 StpUtil

业务代码里到处是 StpUtil.getLoginIdAsLong()（Sa-Token 的静态调用），而单测里没有登录态。普通的 @Mock 注入进不去静态调用——这是最容易卡住的地方。解法是 Mockito.mockStatic：

order/service/impl/OrderServiceImplTest.java:87-88

    stp.when(StpUtil::getLoginIdAsLong).thenReturn(USER_ID);

为什么叫"钉"：mockStatic 只在 try-with-resources 作用域内生效，出域自动卸载。静态 mock 是全局副作用，必须严格限定作用域，否则会污染其它测试。有了它，Service 层测试不需要启动 Spring 容器、不需要走登录流程。

面试怎么讲

别说错（这条是加分项）当前是纯单元测试，Mapper 被 mock 了，所以 MyBatis XML 里 SQL 的正确性是盲区——列名拼错、WHERE 漏条件，单测全绿但线上必炸。主动说"我的测试覆盖不到 SQL，下一步是 Testcontainers 真起一个 MySQL 容器跑集成测试"，比只说"我写了 26 个测试"高级得多。

7.7为什么只拆 AI 服务

拆 AI 的五条理由 + 为什么不拆其余 掌握

对应文档：docs/版本详解/V4服务化详解.md 第 2 章

一句话：V1~V3 时用户 / 商品 / 订单 / 内容 / AI 全在一个 Spring Boot 进程里——这本身没有任何问题（单体被妖魔化了）。但有一个结构性隐患：AI 调用要 5~30 秒，占着 Tomcat 线程不放，AI 一慢，全站排队。

打个比方一家餐厅，前厅点餐、后厨做菜、收银结账都在一个铺子里。做一道要 30 分钟的菜（AI），后厨占住了人手，前厅点餐也得排队。注意：不是把餐厅拆成三家公司（那是过度拆分），而是只把"最慢的那件事"外包给中央厨房——中央厨房着火了，前厅照常营业，只是暂时没有那道菜。

五条理由（逐条背）

  1. 耗时差异：AI 调用是秒级到几十秒，普通接口是毫秒级。放在一起，AI 请求会占满 Tomcat 线程池，下单接口跟着排队。
  2. 故障隔离：模型超时、限流、供应商挂了，只有"AI 助手"不可用，下单 / 浏览 / 支付照常。
  3. 独立扩容：AI 是成本密集型（按 token 计费），需要独立扩缩容与独立限流。
  4. 密钥隔离：API Key 只存在于 ai-service，泄露半径最小——业务服务永远接触不到密钥。
  5. 模型可替换：换模型、换供应商只改这一个服务，业务侧零感知。

反向论证：为什么不把订单、商品也拆了（面试加分杀器）

每个候选服务都要过一遍"砍掉它会怎样"，有一条站不住就不拆：

候选不拆的话会怎样（拆的代价）结论
AI 服务AI 慢会占满线程池导致全站排队；模型挂会导致全站挂；密钥与业务同进程泄露面大拆
用户服务用户表被所有业务 join，拆开后每次查用户都要多一次网络往返不拆
商品 + 订单下单要在同一个事务里锁库存、建订单、清购物车——拆开就要引入分布式事务不拆

拆开订单会多出三样复杂度：分布式事务（本地 @Transactional 直接失效，要么 Seata、要么本地消息表）、网络开销与故障面（每次内部调用都是一次网络往返，多一倍可挂的点）、排障复杂（一个请求穿三个进程，没有链路追踪就是灾难）。

一句话结论（背下来）拆分是一种成本，只有当收益明确超过成本时才拆。
机制与代码：拆分的实质是"数据归谁"

建一个新 Spring Boot 工程只是"动作"；划清数据归属才是"设计"。

面试怎么讲
30 秒版本"我按五条理由只拆了 AI 服务：耗时差异、故障隔离、独立扩容、密钥隔离、模型可替换。AI 调用是秒级、普通接口是毫秒级，放一起会占满线程池把下单拖垮；拆出去以后模型挂了也只有 AI 助手不可用。用户 / 商品 / 订单我没有拆——它们事务耦合紧密，下单要在同一个事务里锁库存、建订单、清购物车，拆开就要上分布式事务，当前业务量不划算。我的判断标准是：拆分是一种成本，只有收益明确超过成本时才拆。"
别说错1. 不要说"微服务架构"——只说"只拆了一个 AI 服务，主体保持单体"。2. 不要把拆分理由讲成"为了简历好看/为了学微服务"——理由必须是业务和技术属性，第一条永远是耗时差异。

7.8服务间调用：声明式客户端 @HttpExchange

像调本地方法一样调远程 熟悉

对应代码：ai/client/AiServiceClient.java · AiServiceClientConfig.java

一句话：服务间调用本质就是你写过的 HTTP 客户端——mall-app 作为客户端 POST 一个请求给 ai-service，和前端 fetch 后端、和支付回调被第三方 POST，是同一件事。区别只在体验：以前你要拼 URL、设头、发请求、解响应（命令式），现在只写一个接口（声明式）。

打个比方命令式像每次寄快递都手写一遍面单；声明式像把地址簿存好，寄的时候只说"寄给张三"——写面单的事有代理自动做。
机制与代码：接口即客户端
ai/client/AiServiceClient.java:17-27
@HttpExchange(url = "${aimall.ai-service.url}")
public interface AiServiceClient {

    /** 非流式问答 */
    @PostExchange("/internal/v1/ai/chat")
    Map<String, Object> chat(@RequestBody Map<String, Object> body);

    /** 入索引请求（笔记审核通过 / 商品上架时调用） */
    @PostExchange("/internal/v1/rag/index")
    Map<String, Object> index(@RequestBody Map<String, Object> body);
}

它怎么做到的——动态代理：Spring 启动时扫描 @HttpExchange 接口，在内存里生成一个实现类（字节码级别），把"方法调用"翻译成"HTTP 请求"（查注解拿到方法和路径 → 序列化 body → 带签名头 → 发请求 → 反序列化响应）。装配在 AiServiceClientConfig：用 RestClient + HttpServiceProxyFactory 生成代理，并在 defaultRequest 里给每个请求自动带上签名三件套（见 7.9）。类上是 @ConditionalOnProperty(... havingValue = "remote")——默认 local 模式下这些 bean 根本不存在，不配置就零影响。

7.9服务间鉴权：HMAC 签名 + 防重放

三个头 + 一个时间窗 熟悉

对应代码：backend/ai/security/InternalSignature.java · ai-service/ai/security/InternalAuthFilter.java · config/InternalAuthFilter.java

一句话：服务之间也要"证明你是谁、报文没被改过"。先立一个事实——"内网就安全"是错觉：docker 端口误映射（-p 8081:8081 写进 compose 又部署到公网机器）、办公网或容器网被横向渗透后，裸奔的内部接口就是免费的后门（能直接烧光你的 AI 额度）。"内网"是一个会变的假设，鉴权不该建立在假设上。

打个比方像公司内部的访客登记。你不会因为"这是自家办公楼"就允许任何人进机房——门禁卡（身份）和签名（确认真是本人、且没被代签）是两件事。
机制与代码：协议与双侧对称

协议：三个头 + 一个时间窗（5 分钟）。客户端每次请求自动带上：

ai/security/InternalSignature.java:20-22, 28-29
public static final String HEADER_CLIENT = "X-Internal-Client";   // 我是谁
public static final String HEADER_TS     = "X-Internal-Ts";       // 当前毫秒时间戳
public static final String HEADER_SIGN   = "X-Internal-Sign";     // 签名

public static String sign(String client, String ts, String secret) {
    String plain = "client=" + client + "&ts=" + ts;
    // HmacSHA256(plain, secret) → 转十六进制字符串
}

服务端 InternalAuthFilter 校验三步（顺序不能反）：① 三个头齐全；② 时间戳新鲜度：|now - ts| > 5 分钟 就拒绝（防重放——攻击者截获一次合法请求原样重发，签名虽然"对"，但时间戳过期就拒）；③ 用同一算法 + 同一密钥重算签名，constant-time 比较（MessageDigest.isEqual，防时序攻击）。

双侧实现的对称性（最容易错的地方）：客户端侧 InternalSignature.sign() 与服务端侧 InternalAuthFilter.sign() 拼接串必须一字不差，secret 也必须同值。改一侧不改另一侧 = 全部 401——这就是"协议"的含义：约定先于实现，双侧同步演进。ai-service 侧为了只保护 /internal/*，用 FilterRegistrationBean 显式注册（WebConfig.java:26-33），而不是 @Component 自动扫描（后者会注册到 /*，还会与同名 bean 冲突导致启动失败）。

与 V3 支付验签对照着记（同一个 HMAC 思想，两处不同用途）这是 HMAC 在本项目的第三次复用：
场景密钥防什么额外机制
V3 支付回调与第三方约定的 secret伪造回调 / 篡改金额金额核对 + 状态机 CAS
V4 内部调用服务间共享 secret伪造内部请求时间戳防重放

为什么内部调用必须加防重放、而支付回调不用：支付回调有幂等保护，天然免疫重放（重复回调 = 已处理）；而内部 AI 接口没有幂等语义——截获一次合法请求重发一万次 = 烧光额度。同一个威胁，不同的免疫机制。支付验签的完整链路详见 03 页 · 支付闭环。

面试怎么讲
30 秒版本"服务间调用我做了 HMAC 签名鉴权，因为'内网就安全'是错觉——端口误映射或被横向渗透后，内部接口就是免费后门。协议是三个头：X-Internal-Client 身份、X-Internal-Ts 时间戳、X-Internal-Sign 签名；服务端校验时间戳在 5 分钟窗口内防重放，然后用同一个密钥重算签名做 constant-time 比较。这里最容易错的是双侧对称——客户端和服务端的拼接串、密钥必须完全一致，改一边不改另一边就全部 401。"
别说错1. 别说"内部调用不需要鉴权，反正外部进不来"——网关拒绝的是外部访问 /internal/**，服务之间仍靠签名校验，两层各管一段。2. 别说时间窗是"5 秒"——太快会因两侧时钟漂移误杀正常请求，5 分钟是"容忍漂移"与"限制重放窗口"之间的折中。

7.10网关：4 条路由 + TraceIdGlobalFilter

一个门牌、一个保安、一个前台 熟悉

对应代码：gateway/src/main/resources/application.yml:24-52 · filter/TraceIdGlobalFilter.java

一句话：网关（9000）是外部唯一入口。没有它，前端要记每个服务的地址，用户理论上也能直接打内部端点；有了它——一个门牌（前端只认识 9000）、一个保安（/internal/** 在门口就拒绝）、一个前台（跨域 / traceId / 访问日志统一处理）。

打个比方像小区大门。快递、访客、外卖都从这一个门进（统一入口），门口保安会拦下贴着"内部通道"牌子的人（安全边界），门厅还有块牌子记录每个访客进出时间（访问日志）。
机制与代码：全部 4 条路由
路由 id断言（Path）目标 / 动作
mall_api/api/**lb://mall-app（业务接口）
mall_files/files/**lb://mall-app（上传的图片等静态资源）
mall_actuator/actuator/**lb://mall-app（运维探针）
deny_internal/internal/**no://op + SetStatus=404（安全边界，不转发）

deny_internal 的作用：把 /internal/** 全部拒掉并返回 404。没有这条，外部只要知道 8081 端口就能直接打 ai-service 的内部端点。为什么是 404 不是 403：403 等于告诉探测者"端点存在但你没权限"（引导继续挖），404 是"没这东西"——这叫最小信息披露，和越权一律返回 404 是同一个思路。

注意是 4 条不是 3 条（mall_actuator 容易漏），也注意这张表里没有 ai-service 的路由——内部调用走 HMAC 直连，不经网关，这正是"外部只能从 9000 进来"的边界设计。

三个概念各司其职：断言（Predicate）判断请求归哪条路由；过滤器（Filter）在转发前后做加工（改头 / 改状态 / 记日志）；路由（Route）= 断言 + 目标 + 过滤器的组合。

TraceIdGlobalFilter：V1.5 伏笔的兑现

V1.5 的 TraceIdFilter 里写着"上游传了就沿用，否则自己生成——为 V4 微服务链路追踪预留"。现在上游真的存在了：网关是链路第一跳，负责生成 traceId 并透传给下游。@Order(-1) 让它最先执行，后续过滤器和路由都能拿到。

gateway/filter/TraceIdGlobalFilter.java:46-54
String incoming = request.getHeaders().getFirst(TRACE_HEADER);
String traceId = (incoming != null && !incoming.isBlank())
        ? incoming
        : "gw-" + UUID.randomUUID().toString().substring(0, 8);

ServerHttpRequest mutated = request.mutate()
        .header(TRACE_HEADER, traceId)
        .build();
exchange.getResponse().getHeaders().set(TRACE_HEADER, traceId);

于是 浏览器 → gateway(生成 gw-ab12cd34) → mall-app(沿用) → ai-service(透传)，grep gw-ab12cd34 能跨三个进程捞出同一次请求的全部日志——这是排障的救命稻草，也是"设计时想清楚、演进时零成本"的实例。

网关没做什么（诚实边界，一定要主动说）没做鉴权：用户 token 校验仍在 mall-app（Sa-Token）。生产可以把鉴权上移到网关（Spring Security + JWT），当前属于"知道位置即可"。没做限流：限流在业务侧（Redis），网关层限流（RequestRateLimiter + Redis）是规模化选项。
面试怎么讲
30 秒版本"网关是外部唯一入口，一共 4 条路由：mall_api、mall_files、mall_actuator，还有一条最关键的 deny_internal——把 /internal/** 全部拒绝并返回 404，用 404 不用 403 是为了不向探测者确认端点存在。网关里没有 ai-service 的路由，服务间调用走 HMAC 直连。另外网关实现了 TraceIdGlobalFilter，是 V1.5 埋的伏笔——网关生成链路 ID 透传给下游，三个进程的日志能用同一个 ID 串起来。"
别说错1. 别说"网关做了统一鉴权和限流"——这两件都没做，在应用层。2. 别把 404 说成"接口不存在"的技术错误——它是主动设计的安全响应。

7.11Nacos 注册发现

从"写死 IP"到"按名字找" 了解

对应配置：三个服务的 nacos.discovery（如 gateway/application.yml:56-70）

一句话：网关想转发到 mall-app，地址哪来？写死 http://localhost:8080 单机没问题，但当 mall-app 部署 3 个实例时，谁记得住、谁感知实例上下线？注册中心就是一本会自动更新的服务电话簿：服务启动时登记自己的地址，定期发心跳；调用方按服务名查实例列表。

打个比方像手机通讯录。你只记"张三"这个名字，不记他的手机号；他换号了通讯录自动更新。写死 IP 等于把号码写在便签上——换一台机器就得改所有便签。
机制与代码：lb:// 拆开讲 + 三层实现

lb://mall-app 不是 URL，是一条指令：① 向 DiscoveryClient 要 mall-app 的实例列表；② 负载均衡器（轮询）挑一个；③ 用真实地址（http://192.168.6.1:8080）发请求。服务名是逻辑地址，实例是物理地址——注册发现就是把"逻辑到物理"的翻译自动化。

层配置 / 说明
Nacos 主enabled: true + fail-fast: false——Nacos 不在时打 WARN 照常启动，客户端自动重连补注册
静态实例兜底spring.cloud.discovery.client.simple.instances 里写死 mall-app / ai-service 地址——Nacos 挂了 lb:// 仍有解析目标
单体模式aimall.ai.mode=local（默认）不需要 ai-service，也不依赖注册中心

两个实现（Nacos 与 Simple）实现的是同一个接口 DiscoveryClient.getInstances(serviceName)——切换只改 starter 和 server-addr，lb:// 与全部业务代码零变动。这与项目里 storage / embedding / pay 的可插拔是同一套设计哲学的又一次出现。

真实踩坑：多网卡机器的注册 IP（本机实测）启动后 Nacos 控制台看到 mall-app 注册的地址是 192.168.49.1——VMware 虚拟网卡！其他机器照这个地址访问必然失败。根因：Nacos 客户端"自动选 IP"的策略是取第一块非回环网卡，而装了 VMware / VirtualBox 的 Windows 上虚拟网卡往往排在最前。修复：三个服务的 yml 全部显式指定注册 IP（gateway/application.yml:60 的 nacos.discovery.ip）。

教训（比知识点值钱）："自动检测"在复杂环境下是隐形炸弹——注册 IP、时区、编码，凡是环境相关的东西，生产都值得显式声明。
面试怎么讲
30 秒版本"注册发现我用的是 Spring Cloud 标准的 DiscoveryClient 抽象：Nacos 作主，服务启动即注册；同时配了静态实例兜底——Nacos 挂了 lb:// 还能解析，转发不断。路由里的 lb://mall-app 是一条指令：查实例列表、负载均衡挑一个、用真实地址转发，逻辑地址和物理地址解耦。我踩过一个真实的坑：多网卡机器上 Nacos 自动选了 VMware 虚拟网卡 192.168.49.1，跨机器不可达，后来三个服务都显式指定了注册 IP。"
别说错lb:// 不是协议也不是 URL，别解释成"负载均衡协议"。另外 Nacos 在这里主要用注册发现，配置中心能力只是顺带提到、并未深入使用——别拔高。

7.12熔断：Resilience4j

给故障装一根保险丝 熟悉

对应代码：ai/service/impl/RemoteAiService.java:47-70

一句话：没有熔断器，ai-service 挂了（读超时 120 秒才失败）会让 mall-app 的每个请求都在"等死"，Tomcat 线程被占满，商品、订单接口也没有线程可用——全站瘫痪，这叫级联故障 / 服务雪崩。熔断器跳闸后，请求不再发往 ai-service，毫秒级直接走降级，线程立刻释放。

打个比方家里的保险丝。电器短路时它熔断——牺牲一个保险丝，保住整栋房子。没有它，短路电流持续通过，电线发热，全屋烧毁。

三态机（面试必背，能画出来）

CLOSED 闭合正常放行
滑动窗口统计失败率
OPEN 跳闸失败率 ≥50%
快速失败，请求根本不发
HALF_OPEN 半开等 30s
放 3 个请求试探

试探全成功 → 回到 CLOSED（恢复）；任一失败 → 回到 OPEN（继续歇）。关键理解：熔断是自动的——跳闸与恢复都不需要人干预。"快速失败"与"重试"是反义词：重试是"再试试"（加重对端压力），熔断是"先不试"（保护双方）。

机制与代码：一个注解 + 一个降级方法
ai/service/impl/RemoteAiService.java:47-70
@Override
@io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker(name = "aiService", fallbackMethod = "chatFallback")
public String chat(String message, String imageBase64) {
    // ... 正常调 ai-service ...
}

// 降级方法：签名必须与原方法一致 + 末尾多一个 Throwable
@SuppressWarnings("unused")
private String chatFallback(String message, String imageBase64, Throwable t) {
    log.warn("AI 调用熔断/失败，走降级文案: {}", t.toString());
    return "AI 助手正在休息中（服务暂时不可用），请稍后再试～";
}

三个细节：① fallback 返回友好文案而不是抛异常——用户看到"AI 在休息"，商城其它功能照常，这是故障隔离的最终呈现；② name = "aiService" 必须对应配置里的 resilience4j.circuitbreaker.instances.aiService，名字对不上就又是"配置不生效"；③ @CircuitBreaker 靠 AOP 代理拦截，同类内自调用（this.chat()）不走代理、注解会失效（与 @Transactional 自调用同源）。

配置的真实坑：必须挂在顶层 resilience4j:resilience4j 是顶层配置。如果把它挂到 spring: 下面——不报错、应用照常启动、熔断器照常工作，但全部用默认参数（滑动窗口 100 而不是 10）。这就是静默失效：你演示"6 次失败就跳闸"时发现跳不动（默认要 100 次才统计），排查半天才发现是层级错了。

验证方法：启动日志里 Resilience4j 会打印实例参数，或看 /actuator/circuitbreakers 端点。本项目配置的口径是：滑动窗口 10 / 失败率阈值 50 / 跳闸 30 秒后半开 / 至少 5 次才开始统计（防冷启动时"第一次失败 = 失败率 100%"的误判）。

这条元教训很值钱：Spring 生态里非 spring 前缀的配置（resilience4j / sa-token / management）挂错层级都是静默失效——改完 yml 一定要解析校验 + 看启动日志确认参数。
面试怎么讲
30 秒版本"熔断三态：CLOSED 正常统计失败率，超阈值跳闸到 OPEN 快速失败——请求根本不发出去，等 30 秒进 HALF_OPEN 放 3 个试探请求，成功就恢复闭合。熔断是快速失败，不是重试。我给 AI 调用加熔断的业务理由是：AI 本来就慢，超时后每个请求还要等满 120 秒，线程被占住，这正是拆 ai-service 想解决的问题。降级方法返回一句友好文案，用户看到'AI 在休息'，下单浏览完全不受影响。"
别说错1. 配置必须顶层 resilience4j:，挂 spring: 下会静默失效——这个坑我真实踩过，讲出来很加分。2. 熔断不等于限流：限流是"别进来"（防自己被打爆），熔断是"别出去"（防下游拖垮自己），降级是"出不去就算了"（给兜底结果）。

7.13双模式与降级矩阵

local / remote 一配置切换 熟悉

对应代码：ai/service/impl/ChatServiceImpl.java:93-114, 169-173

一句话：aimall.ai.mode 有两个值——local（默认，单体直连 AI，行为等于 V3）、remote（走独立 ai-service）。切换只改配置，代码零变动；而"会话管理 / 鉴权 / 落库"这些业务职责永远留在 mall-app，换的只是执行方式，不变的是业务。

打个比方像家里的电源开关：接市电还是接发电机，插座（业务接口）没变，电器（上层调用）也不用改。
机制与代码：显式构造器按配置选实现

为什么不用 @RequiredArgsConstructor：Lombok 按类型注入，而 local / remote 是同一个 AiService 接口的两个实现，会冲突。必须用显式构造器 + @Qualifier("remoteAiService") 才能表达"按名二选一"。

ai/service/impl/ChatServiceImpl.java:99-113
public ChatServiceImpl(ConversationMapper conversationMapper,
                       MessageMapper messageMapper,
                       ChatClient chatClient,
                       ChatClient visionChatClient,
                       @Qualifier("remoteAiService")
                       ObjectProvider<AiService> remoteAiProvider,

三个要点：① 构造时定格（aiModeFlag 是 final，不每次请求读配置，模式启动时就定死，可预测）；② 惰性注入 ObjectProvider——不能直接注入本地实现，因为 local 模式的实现又委托回 ChatService，会构成 ChatServiceImpl ⇄ LocalAiService 循环依赖（Boot 3 默认禁止，启动直接失败），Provider 到 remote 分支 getObject() 时才解析 bean；③ 评审背景——这个抽象一开始写了没有任何调用方，配 remote 完全不生效，属于"写了不等于生效"，改成显式构造器接线后才算真正落地。

7.14面试话术

两句话术 + 一条"别说错" 面试用

本节是准备材料，不涉及代码

面试怎么讲
「你的项目是单体还是微服务？」30 秒版"我的项目主体是单体，只把 AI 能力拆成了一个独立服务。理由是 AI 调用和其他接口的属性完全不同——它是秒级的、会占满线程池、要用密钥、换模型时希望业务零感知。把这四件事隔开，模型挂了也只有'AI 助手'不可用，下单、浏览、支付照常。但用户、商品、订单我没有拆——它们在一个事务里工作，拆开就要上分布式事务，我判断当前业务量下收益不超过成本。所以准确说，这是一个'按需拆分'的架构，不是微服务架构。"
「为什么不用 Feign？」30 秒版"我用的是 Spring 6 原生的声明式客户端 @HttpExchange。它和 OpenFeign 的编程模型几乎一样——都是接口 + 注解 + 动态代理，但 @HttpExchange 零额外依赖，spring-web 自带；引 OpenFeign 就要引 spring-cloud-openfeign 和整套 BOM，版本对齐反而成了负担。我只拆了一个服务，用不上 Feign 与注册中心/负载均衡的深度整合。而且两者写法接近，将来真要迁 Feign，成本很低。"
别说错1. 不要说"微服务架构"。这句话一出口，面试官接着就会问"几个服务？怎么保证一致性？调用链怎么追踪？"——而你只有一个 AI 服务。正确说法是"只拆了一个 AI 服务，主体保持单体"。2. 也不要为了显得"技术全面"而主动吹 Nacos / Gateway 的深度使用——本页把它们定位为"了解层"，答得出原理与取舍即可，被深挖就诚实引开。
