06 · AI 模块

这页只回答三件事：AI 模块由哪几块组成、边界在哪（什么走 RAG、什么走 SQL）、被追问时怎么守。不教你做大模型，也不要求你懂原理。

阅读约 15 分钟 面试权重 ★ 跨 backend + ai-service 两个服务

6.0先读这一条：这页为什么要做短

本页定位：AI 是「了解层」，不是你的主战场

在你简历里，AI 只占 1 条 bullet：「基于 Spring AI 接入大模型，通过 Function Calling 让模型按需调用商品查询工具（避免编造价格库存）；Hybrid RAG 检索商品说明书与用户种草笔记，向量 + BM25 双通道 RRF 融合，回答附来源引用」。

所以这页不是把你教成 AI 工程师，而是办三件事：① 知道 AI 模块由哪几块组成、每块干什么；② 守住两句话——Function Calling 工具调用（Agent 查商品）+ RAG 检索增强；③ 被深挖时能体面地把话题引回主战场。

时间分配：AI 15 分钟封顶。剩下的时间投给 03 订单与交易 与 05 高并发与可靠性——那里才是面试官打分的地方。问 AI 的深度通常只到「这东西是不是你自己做的、边界清不清楚」；细节答不上来不致命，把 AI 说成项目主打才致命。

口径红线（背下来）：AI 是了解层，重心在传统后端（事务 / 并发 / 缓存 / 消息）。完整口径表见 08 页。

这张图怎么用来开场答
30 秒版本 "AI 这块我在项目里定位是了解层。入口在 mall-app——会话、鉴权、限流、落库都是普通业务逻辑；模型调用在 ai-service，因为它慢、按 token 计费、还要隔离 API Key。两边用 HTTP + HMAC 签名调，中间有熔断，AI 挂了只影响 AI 助手，下单支付不受影响。AI 服务里就两件事：Spring AI 的工具调用，和 Hybrid RAG 检索。"
别说错 不要说"我们做了微服务架构"。正确口径是：只拆了 ai-service，主体保持单体（07 页）。

6.2Spring AI 装配：两条 ChatClient 链路

chatClient（文本）与 visionChatClient（视觉） 了解

对应代码：backend/src/main/java/com/aimall/config/AiConfig.java

一句话：Spring AI 把"调大模型"包装成 Spring 风格的 Bean——ChatClient。项目装配了两个：一个服务纯文字问答，一个服务带图识图，调用时按 req.hasImage() 分流。

打个比方 像同一个收银台开了两个窗口：一个只收现金（文字），一个能刷脸（图片）。后面坐的是同一位柜员——两个窗口用的是同一个模型，只是窗口前贴的流程说明（system prompt、温度、消息构造方式）不同。
诚实标注：两条链路用的是同一个模型 deepseek-v4-flash-vision-exp。视觉链路的 .options().model(VISION_MODEL) 是无效覆盖（常量值与 yml 默认值相同），真实的差异只有温度——视觉 0.5、文本 0.7。
机制与代码
backend/.../config/AiConfig.java:42-63
@Bean
public ChatClient chatClient(ChatClient.Builder builder,
                             ProductSearchTool searchTool,
                             KnowledgeSearchTool knowledgeTool) {
    return builder
            .defaultTools(searchTool)     // 结构化：价格/库存/分类 → SQL
            .defaultTools(knowledgeTool)  // 非结构化：说明书/笔记 → Hybrid RAG
            .build();
}

@Bean
public ChatClient visionChatClient(ChatClient.Builder builder,
                                   ProductSearchTool searchTool,
                                   KnowledgeSearchTool knowledgeTool) {
    return builder.defaultTools(searchTool).defaultTools(knowledgeTool).build();
}

模型名与密钥都不是硬编码：模型写在 application.yml:91（model: deepseek-v4-flash-vision-exp，温度 0.7），API Key 一律走环境变量 ${DEEPSEEK_API_KEY:}（application.yml:87，冒号后为空 = 没有默认值）。本地开发把密钥写进被 gitignore 的 application-local.yml，生产用环境变量或命令行覆盖；换厂商只改 base-url + model 两行。

为什么文本和视觉要分成两个 ChatClient？因为两条链路的 system prompt、温度、消息构造方式（视觉要构造多模态 Media）都不同。早期版本只有一个客户端，工具对视觉调用同样生效，导致识图偶发答非所问；拆成两个 Bean 后"一模型一配置"，互不污染。源码里那句注释写得很直白：VISION_MODEL 这个按次覆盖当前是无效的，两条链路实际同模型。

注：当前代码里两个客户端都挂了双工具（注释说明视觉模型同样支持 function calling）。这与早期"视觉链路不挂工具"的版本不同——演进过程记在 08 页的技术债清单。

面试怎么讲
30 秒版本 "我用 Spring AI 的 ChatClient 装配了两个 Bean：文本链路和视觉链路。视觉模型本身支持工具调用，所以两条都挂了同样的工具。而且我很清楚它们其实是同一个模型——视觉那条的 .options().model() 目前是无效覆盖，真正生效的差异只有温度 0.5，识图要稳。"
别说错 不要说"我做了视觉专用模型"，也不要说"两个模型"——两个 ChatClient 不等于两个模型。主动说出"这个覆盖当前无效"比假装用了两个模型值钱得多，这证明你真读懂了自己的代码。

6.3Function Calling：AI 会自己查商品 必守的一句话

把 Java 方法注册成"AI 能调用的工具" 了解

对应代码：backend/.../ai/tool/ProductSearchTool.java · ai-service/.../tool/ProductSearchTool.java

一句话：大模型不知道你店里卖什么，所以不给它数据、而是给它一只可以查库的手——把一个普通 Java 方法注册成工具，模型判断需要时自己决定调用它、自己填参数，拿到真实查询结果后再组织回答。

打个比方 像给新员工一张可以拨的内线电话清单（工具清单 + 每个电话的用途说明），而不是让他背下全公司通讯录。他遇到"这个多少钱"就自己拨仓库的电话（searchProduct），遇到"这耳机戴着疼吗"就拨知识库的电话（searchDocs）。怎么拨由他决定，你只负责把电话接到真实数据上。
机制与代码

工具定义的全部秘密就是这段注解——description 会被 Spring AI 转成 JSON Schema 随请求发给模型，模型看不到你的 Java 代码，只靠这段文字决定调不调、怎么传参：

backend/src/main/java/com/aimall/ai/tool/ProductSearchTool.java:68-76

        + "当用户问商品、价格、或要找某类商品时调用，别自己编造商品。")

幕后是两轮 HTTP，这是必考流程：第 1 轮请求带上 tools=[本方法的 JSON Schema] → 模型不直接回答，而是回一句"我要调 searchProduct({"keyword":"降噪"})"（这叫 tool_call）→ 框架在你的 JVM 里执行这个方法、真实查库 → 第 2 轮把结果作为 role=tool 的消息发回 → 模型才生成最终回答。"模型执行了工具"是错觉：模型只点菜，执行的是框架调用的你的方法。

关键论点（这句最值钱）：工具方法复用业务 Service——方法体里调的是 productService.pageOnSale(query)（同文件 :89），不是另写一条 SQL。所以 AI 检索到的数据和用户在搜索页看到的数据永远是同一份（同样的在售过滤、同样的排序）："AI 能力复用业务 Service，而不是绕过它"。查不到时工具返回空列表，system prompt 又要求"商品库里没有就坦诚说明"，所以 AI 不编造，查不到就说查不到。

两个真实踩坑：① description 只写"搜索商品"四个字时，模型该调不调、开始自己编商品——描述必须写清"返回什么 + 什么时候该调 + 别自己编造"；② 参数默认必填时模型硬填 categoryId=0 交差——所以全部设为可空，方法体内再逐个兜底。结论：工具入参要按不可信的外部输入校验（模型可能传 null / 0 / 负数）。

面试怎么讲
30 秒版本 "电商里最怕 AI 编价格——用户按它说的价格下单就是资损。我的做法是不给模型数据、给它一个查商品的工具：@Tool 注解一个方法，模型自己判断要不要调、自己填参数，框架在 JVM 里执行真实查库，再把结果回灌给它。所以价格库存永远来自 MySQL，AI 不编造，查不到就如实说查不到。而且这个工具复用的是商品模块的 ProductService.pageOnSale，AI 看到的数据和前端搜索页是同一份。"
别说错 不要说"模型自己去数据库查了"——模型只输出一个"想调哪个方法、传什么参数"的 JSON，执行的是框架调用的你的方法。主谓关系说反，等于承认自己没搞懂。
也别说"我在 prompt 里写了不要编造所以不会幻觉"——提示词不是保证，真数据才是。工程解法是"给工具"，不是"求它别编"。

6.4多模态识图链路

发一张图，AI 认出是什么商品 了解

对应代码：frontend/src/views/Chat.vue · ChatServiceImpl.java:398-415

一句话：用户发图 → 前端先压缩 → 转 base64 → 后端组装成"文字 + 图片"的多模态消息 → 走视觉链路。整条链路只比文本链路多一个"图片附件"。

打个比方 像寄快递前先抽真空打包：原图是"几 MB 的整箱货"，运费（token）高还容易超限；压成 1280 长边的 JPEG 之后，模型认商品够用，成本与体积都降下来。
机制与代码
  1. 前端 canvas 压缩Chat.vue 把图片画进 canvas，最长边压到 1280、按 JPEG 质量 0.8 导出 dataURL（白底填充是防透明背景变黑）。真实截图动辄几 MB，不压会让请求体过大，也会撞上存储字段上限。
  2. 后端拆 base64 并嗅探真实格式兼容 data:image/png;base64,xxx 与裸 base64 两种输入；MIME 按文件头字节判断，不采信前端声明——项目踩过"前端压成 JPEG 却声明 png"的坑。
  3. 组装多模态消息并调视觉链路
backend/.../service/impl/ChatServiceImpl.java:408-415
Media media = new Media(MimeTypeUtils.parseMimeType(mimeType),

要压缩的根本原因就两条：token 成本（图片按尺寸计 token，原图贵得多）与传输体积（请求体与数据库存储）。所以历史消息不重复带图——toAiHistory() 只还原文字，图片仅供前端回显；代价是用户追问"图里这件还有别的颜色吗"时，模型已经看不到那张图了。

面试怎么讲
30 秒版本 "识图比文本就多一个图片附件：前端 canvas 压缩、转 base64，后端解码后用 UserMessage.builder().text().media() 组装多模态消息，走视觉那条 ChatClient。压缩是必须的——图片按尺寸计 token，原图既贵又容易撞请求体和存储上限；格式按文件头字节嗅探，因为前端声明的 MIME 和真实格式不一定一致。"
别说错 不要说历史消息里也带着图片。图片只存 base64 供前端回显（V1 的简化方案，多图会撑爆库），不重复喂给模型——这是有意的成本控制，也是一个明确的技术债。

6.5Hybrid RAG：双通道 + RRF 融合 必守的一句话

先立边界（本节最重要） 说反即原理性错误

对应代码：ai-service/.../rag/HybridRagService.java · docs/版本详解/V2内容社区与RAG详解.md 第 5 章

一句话：RAG = 先查资料、再回答（检索 → 增强 → 生成），治的是大模型的"知识截止"和"幻觉"。但它只管文档，不管数据。

正确边界
价格、库存走 SQL（searchProduct）：实时结构化数据，必须精确。
说明书与 UGC 笔记走 RAG（searchDocs）：非结构化文本，问的是体验和参数说明。
说反了就是原理性错误
用 RAG 答价格：语料是快照会过期，检索又是模糊命中——拿概率检索去答必须精确的实时数据，是设计错误。
用 SQL 答"戴久了耳朵疼吗"：答案根本不在结构化字段里。
打个比方 价格库存像收银台的实时报价屏（必须查系统，一秒前的数字都不能算）；说明书与用户评价像货架上的宣传册和意见簿（非结构化，翻一翻、找最相关的几页就够）。
机制与代码

① 语料是什么。两份来源：官方说明书（答参数：防水等级、续航、材质）与真实用户种草笔记（答体验：戴久了疼不疼、值不值）。这不是凑数——体验类问题只有 UGC 语料能答：说明书只会写"IPX5 防水"这类参数，不会写"戴久了耳朵疼"，而内容社区恰好产出了这个数据。社区给 AI 提供语料，AI 给社区带来曝光。笔记下架时会同步移除索引，不能让检索召回已下架的内容。

② 双通道：为什么要两路。关键词通道（MySQL FULLTEXT + ngram 分词，建在 RAG 语料切片上——注意全文索引用在笔记/语料，商品搜索仍是 LIKE 模糊匹配）擅长精确词——"蓝牙5.3""IPX7"这类型号规格；向量通道擅长语义模糊——"戴久了舒服吗"能匹配到"长时间佩戴体验"。但两者各有死穴：换个说法关键词就搜不到（搜"续航"搜不到"电池耐用"），而向量对专有名词不敏感（"蓝牙5.3"和"5.0"在语义空间里极其接近）。电商两类问题都高频，所以两路都要。这就是"语义鸿沟"。

③ RRF 融合。一行公式：score(d) = Σ 1 / (k + rank_i(d))，本项目 k = 60（原论文推荐值）。为什么用 RRF 而不是加权求和：两路的分数量纲完全不同——BM25 的分可以上百，余弦在 [0,1]，直接加权等于拿厘米和斤相加。RRF 只看名次、不看分数，天然免疫量纲问题，也不需要调权重；而且一个片段两路都命中时得分自动叠加（双确认），用更少的假设拿到更稳的效果。

ai-service/.../rag/HybridRagService.java:127-134
/** RRF：按排名累加 1/(k+rank)，双路命中自动叠加（双确认） */
private void accumulate(Map<Long, Float> scores, Map<Long, ChunkRow> uniq, List<ChunkRow> ranked) {
    for (int rank = 1; rank <= ranked.size(); rank++) {
        ChunkRow c = ranked.get(rank - 1);
        uniq.putIfAbsent(c.id(), c);
        scores.merge(c.id(), 1f / (rrfK + rank), Float::sum);
    }
}

④ embedding 可插拔。接口是 EmbeddingClient，两种实现：默认 local 哈希（2-gram 切分 + 哈希分桶，256 维，零外部依赖），可切成 spring-ai 接真实 embedding 模型——改一行配置 aimall.rag.embedding，业务代码零改动。为什么默认用本地哈希：项目硬约束是"任何环境都能启动"，而 DeepSeek 官方不提供 embedding 接口——硬依赖某个 embedding 服务的话，没配它的机器 RAG 整条链路就跑不起来。所以默认实现可降级、零外部依赖，诚实定位是"字面非语义"：它能匹配"降噪耳机"和"耳机降噪"这种字面重叠，但匹配不了"续航久"和"电池耐用"。语义召回的质量由关键词通道托底，接真实 embedding 后整体效果才有显著提升。

面试怎么讲
必考题预答：几百份文档为什么不直接塞进长上下文？ 四条理由，缺一条都是"没想清楚"：
① 语料动态更新——笔记每天在发、说明书随时改，"每次全量塞"今天的 128K 明天就不够；RAG 是按需取用，语料增长不影响单次请求大小。
② C 端首字延迟——长上下文的 Prefill 耗时随长度线性涨，塞 500 篇（约 25 万字）时打字机的第一字要等好几秒，体验直接崩。
③ 权限隔离——RAG 在检索层就能按来源过滤、下架内容直接剔除；全塞进 prompt 就没有权限边界了，模型"看见"了所有内容。
④ 成本——token 按量计费，全量灌入 × 每次对话，费用随调用量线性失控。
收口一句："长上下文只适合一次性长文档分析——文档固定、单次交互、无权限分层。"
30 秒版本（RAG 本体） "我做的 RAG 边界很清楚：价格库存走 SQL，说明书和用户笔记走 RAG。检索是双通道——MySQL 全文索引管精确型号词，向量管语义模糊的问法，因为电商这两类问题都高频。两路结果用 RRF 融合，只看排名不看分数，因为 BM25 分可以上百、余弦在 0 到 1，量纲不可比。embedding 默认用本地哈希的降级实现、零依赖；我如实说它只匹配字面、不匹配语义，接真实模型改一行配置就行。"
别说错 绝对不要说"用 RAG 查价格"——这是本项目第一条 AI 口径红线。
也不要吹"我做了向量数据库"——项目没有向量库，向量以 JSON 存在 MySQL 列里、检索时全量加载到内存算余弦。当前切片规模下这是正确取舍，十万级才需要上 ANN 索引，主动讲出来是加分。
不要提 Rerank——项目没做（当前是双路召回 → RRF → Top-5）。

6.6双工具 Agent 分流：为什么不写 if-else 必守的一句话

把两个工具都注册给模型，由模型自己选 了解

对应代码：ai-service/.../tool/ProductSearchTool.java · KnowledgeSearchTool.java · rag/HybridRagService.java

一句话：模型手上同时有两份"工具说明书"，用户问价格它选 searchProduct，问体验它选 searchDocs——代码里零意图判断，分流发生在模型侧。

打个比方 像给助理一页纸写明"报销找财务、合同找法务"，然后让他自己判断你要办的是哪件事。而不是你站在门口拦人：嘴上说"钱"字的往左、说"合同"的往右——后者听起来可控，实际上"这个多少钱""预算够不够""值不值"全被堵在门外。
机制与代码

分流全靠 description 的正向 + 负向引导——既说清什么时候该调，也说清什么时候不该调：

ai-service/.../tool/ProductSearchTool.java:41-43
@Tool(description = "搜索本店在售商品：可按关键词、分类过滤，返回商品列表(名称/副标题/起售价)与总数。"
        + "当用户问商品、价格、或要找某类商品时调用；"
        + "使用体验、佩戴感受、功能细节等说明性问题不要用本工具（用 searchDocs）。")
ai-service/.../tool/KnowledgeSearchTool.java:33-37
@Tool(description = "检索商品知识库（官方说明书+真实用户种草笔记）：返回与问题相关的知识片段及其来源。"
        + "当用户询问商品的使用体验、佩戴感受、功能细节、防水续航等说明性/体验性问题时调用；"
        + "价格、库存、是否有货等实时信息不要用本工具（用 searchProduct）。")
public String searchDocs(@ToolParam(description = "用户的自然语言问题") String question) {

为什么不写 if-else：规则路由是 if (问题里有"多少钱") 走 SQL else 走 RAG。问题是自然语言意图无法枚举——"这玩意儿贵吗""预算内有没有替代款""值不值"都是价格意图，"戴着闷不闷""跑步会不会掉"都是体验意图，规则永远写不全，必然漏。而判断意图恰好是模型最擅长的事，把它硬编码成人肉规则，等于用你最弱的部分替换它最强的部分。

还有一层"总-分"双保险：system prompt 定总纲（"涉及价格库存先调 searchProduct，涉及体验先调 searchDocs"，见 ChatServiceImpl.textSystemPrompt()），两个工具的 description 定分工。边界之外也要诚实：用户问"3 号订单到哪了"，两个工具都不该调——当前没有订单工具，模型应如实说查不了。工具边界也是 RAG 边界的一部分。

面试怎么讲
30 秒版本 "我的 AI 有'两只手'：查商品的 searchProduct 走 SQL，查知识库的 searchDocs 走 RAG。两个工具都注册给模型，由模型自己选——我不在代码里判断意图。原因很直接：用户问价格有几十种说法，规则枚举不完，而理解意图正好是模型的长处。为了让它不选错，我用两层引导：system prompt 定总纲，工具描述里写清'什么时候该调、什么时候不要用我'。问订单这类没有工具的场景，它会如实说查不了，而不是硬编。"
别说错 不要说"我用规则判断问题类型然后路由"——那恰好是项目刻意没做的，说成这样反而显得没理解。正确说法是：由模型基于工具描述自主决策（Agentic 路由），代码零 if-else。

6.7AI 审核与文案生成

审核走 MQ 异步 · 文案只出草稿 了解

对应代码：backend/.../content/service/impl/AuditServiceImpl.java · NoteGenerateService.java

为什么这么设计：用户发布笔记时，AI 审核要秒级才出结果——同步等的话用户点"发布"要转圈好几秒。业务上不能忍，所以走 MQ 异步：接口立刻返回"审核中"，审核在消费端跑，完成后回写笔记状态。这是"用户体验倒逼架构"的典型例子。

跨页说明 审核异步的可靠性细节（幂等防线 / 消息只带 id / 死信队列 / MQ 挂了走线程池降级）在 05 高并发与可靠性；笔记与审核的业务流程在 04 内容社区。本节只讲业务上为什么这么设计。
机制与代码

① AI 审核。UGC 内容必须过审才能公开，审核作为独立 AI 任务走 MQ 异步，结果落审核流水表。同一套提示词工程在不同任务上用不同温度：审核要"稳"（判得一致），文案创作要"活"（有灵气）。

② AI 文案：只出草稿，绝不自动发布。这是产品红线，不是技术限制。生成时会把 RAG 检索到的真实用户反馈作为素材拼进 prompt，所以草稿里带的是真实体验细节，而不是凭空编的"绝绝子"：

面试怎么讲
30 秒版本 "AI 在这块有两个用途。审核走 MQ 异步——发布接口不能等 AI，秒回'审核中'，结果回写；可靠性那套（幂等、死信、降级）在高并发那部分。文案生成只出草稿，接口明确返回 editable，用户编辑后再走正常发布审核。我不让它自动发布：AI 可能编造体验，未经审核直接公开就是虚假宣传，这个责任主体不能是 AI。"
别说错 不要说"AI 生成的笔记会自动发出去"。"只出草稿"体现的是分寸感，是这条 bullet 的加分点，别自己抹掉。

6.9防守话术：AI 被深挖怎么办 本页的落点

面试官问 AI，通常不是想考你模型原理——他是在验证"这东西你到底做到哪一步、边界清不清楚"。所以策略不是"答得深"，而是答得准、守得住、能收束。

标准答法：只守两句话，细节一律引开 第一句 · Function Calling 工具调用："AI 要查商品，靠的是工具调用——我把商品查询方法注册成工具，模型自己决定调不调、自己填参数，框架执行真实查库再回灌结果。所以价格库存永远来自数据库，它不编造，查不到就说查不到。"
第二句 · RAG 检索增强："非结构化的内容走 RAG——商品说明书和用户种草笔记作为语料，关键词 + 向量双通道检索再用 RRF 融合，回答会注明来源。边界很清楚：价格库存走 SQL，说明书和笔记走 RAG。"
然后主动收束："这块我定位是了解层，能讲清组成和边界；项目里我投入最多的是交易链路和可靠性那部分，比如下单防超卖和 MQ 的幂等设计——要不要我从那儿讲？"
不要说的四件事 ① 不要说"我很懂大模型"。这是初级 Java 岗，你越强调懂 AI，面试官越会往原理深处挖——而你的时间投在别处，深挖必翻车。
② 不要主动提项目里没有的东西：MCP、Rerank、向量数据库（Milvus / pgvector）、Agent 自主规划。这些都没实现。主动提 = 给自己挖坑；被问到时答"当前没做，下一步可以考虑"才是加分。
③ 不要把 AI 说成项目主打。正确顺序永远是先讲交易、并发、缓存、消息，AI 是"业务场景之一"。把它说成核心，等于把最薄的部分当成最厚的卖。
④ 不要说"RAG 什么都能答""模型不会出错"。正确说法是"RAG 只答非结构化内容，价格库存走 SQL"；模型异常是常态，所有调用都要兜底。
诚实边界：主动交代，化被动为主动 1. 流式是"伪流式"。RemoteAiService.stream() 内部直接 return Flux.just(chat(message, null));（RemoteAiService.java:72-77）——先把完整回答拿到，再一次性包成 Flux；跨服务真实流式透传（WebClient 直连 ai-service 的 SSE 端点）是明确的下一步。用户侧打字机效果不受影响（本地链路是真的 .stream()），但被问到跨服务流式时要如实说。
2. 向量检索是"全量加载 + 内存算余弦"，没上 ANN 索引；embedding 默认是字面匹配的降级实现，不是真语义。
3. 引用只落在回答正文里，前端没做可点击的结构化引用卡片。
提前把这三条说出来，比被追问时支支吾吾强得多——面试官要的是"你知道自己的系统边界在哪"。
