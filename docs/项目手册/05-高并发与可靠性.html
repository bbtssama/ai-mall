5.1一张图先看「可靠性体系」

先建立整体图景。一个请求从进来到落库，中间会经过若干「保护层」；不同链路的层数不一样，但每层都在回答同一个问题——「上游出问题时，我怎么不退化成故障」。

① 请求进来（读路径 / 写路径）
读：商品详情、笔记 Feed、热门榜 · 写：点赞、下单、支付回调、抢购、AI 问答
↓ 先过缓冲层：能不碰 DB 就不碰 DB
② 缓存层 · ProductCacheService
穿透（空值标记）/ 击穿（`SET NX` 互斥锁）/ 雪崩（TTL 抖动）。命中即返回，Redis 挂了降级查库，变慢不挂掉。详见 5.3
③ 限流层 · RedisOps.allow
`INCR + EXPIRE` 的 Lua 原子固定窗口，按成本部署（AI 接口 10 次/60 秒）。Redis 挂了 fail-open 放行。详见 5.6
↓ 写路径再过一层：挡住「重复」与「洪峰」
④ 幂等层
参数校验 → 一次性 token（DEL 原子消费）→ 唯一索引。四种手段按语义选，详见 5.7
⑤ 削峰层 · Redis 预减 + MQ
Lua 判重+扣减（准入闸门，挡量）→ MQ 异步建单（节奏器，摊峰）。业务链路见 03 页，机制见 5.8
↓ 真正的正确性只有一处：DB 的行锁 CAS（`WHERE stock>=?` / `WHERE status=旧值`）
⑥ 同步主链路
下单 = 行锁 CAS 扣库存 + 事务写订单 + afterCommit 挂延迟取消。详见 03 页 / 5.9
⑦ 异步消费（幂等收敛）
MQ 是 at-least-once：不重靠消费端回查 + 状态机 CAS + 唯一索引，详见 5.8
↓ 最后一层：所有「没走完」的异步链路都靠它收敛
⑧ 补偿层 · CompensationTask（订单超时兜底 / 审核堆积重送 / 支付查单对账）
主链路追求「快」（异步），补偿任务保证「最终对」（定时扫描）。重复靠幂等、丢失靠补偿——两个机制都要有。详见 5.11
打个比方 这套结构像一栋楼的安保体系：门禁（限流）决定谁进得来，前台登记（幂等）保证同一个人不会领两把钥匙，电梯分流（削峰）把早高峰的人摊开，保险柜（DB 行锁）才是真正锁钱的地方，而监控回放（补偿任务）负责事后把每一次「好像没走完的流程」查清楚。 关键不是某一层特别强，而是每层都想清楚了「它自己挂了该怎么办」。
看这张图要抓的 3 个认知 1. 保护层不是「每层都要过」。读路径走 ①②；写路径走 ④⑤⑥；异步链路还要加 ⑦⑧。挑层是按链路选的，不是堆得越多越好。
2. 只有 DB 层承担正确性。Redis 预减、缓存、限流全部是「准入/加速」层——「Redis 层永远不承诺正确性，正确性永远在 DB 层」，这是全项目所有 Redis 使用的统一哲学。
3. 每一层都有一条降级路径。这是项目「零依赖能启动」的硬约束（docker-compose 不起也能跑），也是本页反复出现的主题。

5.2RedisOps 门面：把「降级」收敛到一处 设计亮点

全项目最重要的一个类 掌握

对应代码：common/redis/RedisOps.java（341 行，所有 Redis 调用的唯一入口）

一句话：Redis 是旁路缓存——它挂了，业务应该「变慢」（直接查库）而不是「不可用」。但如果业务代码里到处裸调 redisTemplate.opsForValue().get(key)，那么 Redis 一断连，所有走过这行代码的接口全部 500——缓存反而成了故障放大器。所以项目把所有 Redis 操作收敛到一个门面类，每个方法都被 safe() 包住：任何异常 → 打 WARN → 返回兜底值 → 业务自然走 DB。

打个比方 门面就像小区门口那位万能管家：你找他办任何事（取快递、报修、缴物业费），他从不为难你——办不成时只会说「今天先这样，您走另一条路试试」，而不会把整栋楼的门全部锁死。
如果没有他，每个住户都得自己跑各种窗口；一旦某个窗口下班（Redis 挂），住户们就集体卡在门口。把「办不成怎么退」这件事统一收在一处，是这一层存在的全部理由。
机制与代码：safe() 包装 + 逐方法选降级值

① 异常 → 降级，收敛在一处：所有 Redis 操作都经过这个方法，降级日志刻意用 WARN 而不是 ERROR。

common/redis/RedisOps.java:331-340（safe 包装）
private <T> T safe(Supplier<T> supplier, T fallback, String op, String key) {
    try {
        T v = supplier.get();
        return v == null ? fallback : v;
    } catch (Exception e) {
        // 注意：这是 WARN 不是 ERROR——降级是设计内的路径，不是故障
        log.warn("Redis 不可用，降级为空操作 op={} key={} : {}", op, key, e.getMessage());
        return fallback;
    }
}

② 降级默认值必须逐方法按业务语义选——这是本类最容易被问的设计点，fallback 不是随便填的。注意两个三态方法：consumeToken 返回 Boolean，用 null 和 false 表达两种完全不同的意思。

方法降级兜底值调用方拿到的信号业务后果
get / getObjectOptional.empty()「缓存未命中」查库，变慢但正确
set / setObject / delete空操作「写没成功」缓存下次重建，无害
setIfAbsent / tryLockfalse / null「没抢到锁」走兜底路径（直接查库）
incr / hIncrBynull「计数不可用」回退 DB 直写
takeAllAndClear / hmGetLongsMap.of()「没有增量」本轮不落库，下轮再来

consumeToken（幂等 token）null（放行）「Redis 不可用」fail-open：防重是优化不是正确性，别让缓存故障挡住正常下单

③ 为什么 null 和 false 必须分开（读代码核实的「三态设计」）：以一次性 token 为例，方法签名是 public Boolean consumeToken(String key)（RedisOps.java:323-325），返回三个值：

common/redis/RedisOps.java:313-325（注释就是三态定义）
/**
 * 一次性消费 token：DEL 是原子的——删除成功即"只此一次"。
 *
 * <p>幂等 token 的经典语义：签发时 SET（TTL 兜底防泄漏），提交时 DEL；
 * 返回 true=首次消费放行，false=已被用过拒绝。第二次提交同一个 token
 * 删不到任何东西（返回 0），天然防重。</p>
 *
 * @return true=消费成功放行；false=token 已被使用/不存在；null=Redis 不可用
 *         （降级放行——fail-open，别让 Redis 故障挡住正常下单）
 */
public Boolean consumeToken(String key) {
    return safe(() -> stringRedisTemplate.delete(key), null, "consumeToken", key);
}

调用侧的分支把三种语义分开处理（OrderServiceImpl.java:62-67）：Boolean.FALSE.equals(consumed) 才抛「请勿重复提交订单」——注意是 FALSE.equals 而不是 !consumed。如果写成 !consumed，那么 null（Redis 挂了）会被自动拆箱成 NPE 或当成「已用过」，所有用户在 Redis 故障期间都下不了单。这个细节就是「null 与 false 语义必须分开」的代价所在。

④ 可观测性：每次降级打 WARN 日志（带 traceId）。类注释原话——「Redis 挂了你却不知道比 Redis 挂了更可怕」。降级日志刻意不用 ERROR，否则 Redis 一挂全站 ERROR 刷屏，真正的故障会被淹没。

面试怎么讲
30 秒版本 "我把所有 Redis 调用收口在一个 RedisOps 门面里，每个方法都过一层 safe() 包装：异常 → 打 WARN → 返回一个兜底值 → 业务自然走 DB。这样 Redis 挂了只会「变慢」，不会「变不可用」——否则缓存就成了故障放大器。
关键是兜底值不是统一填的，而是逐方法按业务语义选：缓存读返回空（→ 查库）、计数返回 null（→ 走 DB 计数）、限流返回 true 放行、幂等 token 返回 null 放行。限流和 token 用 fail-open 的理由是——它们一个省钱、一个防重，都不是正确性本身；拒绝所有用户反而是更大的事故。而且 token 那里必须用三态：true 放行、false 拒绝、null 放行，null 和 false 语义不同，合并了就会在 Redis 故障时误拒全部下单。"
别说错 ① 不要说「Redis 挂了就拒绝请求更安全」。旁路组件挂了却让全站不可用，是把缓存变成了单点故障。
② 不要笼统说「降级就是返回 false」。逐方法语义完全不同，这张表能背下来才算真懂。
③ 被追问「怎么知道 Redis 挂了」，答降级 WARN 日志（带 traceId）+ 可统计降级次数；并主动说这条边界：项目没有降级告警，只有日志，这是已知缺口。

5.3缓存三兄弟：穿透 / 击穿 / 雪崩 必考

这三个词是所有后端面试的第一道缓存题。但它们不是同一件事，防的也是三种完全不同的死法。下面每个都先「撞南墙」——不处理会发生什么。

穿透：查一个数据库里也不存在的 id 掌握

对应代码：ProductCacheService.java:43-49 · :109-124

一句话：攻击者（或写错的爬虫）狂刷 GET /products/-1。这个 id 数据库里也不存在，所以缓存永远不命中——每个请求都穿透缓存直插 DB。100 QPS 的恶意流量 = MySQL 平白多扛 100 QPS 全无效查询。而朴素缓存只在「查到东西」时才回写，所以它对此完全失能。

打个比方 这像总有陌生人打前台电话找一个不存在的员工：前台查一次通讯录说「没有这个人」，挂了电话；一分钟后同一个人又打来问同一个名字——前台又查一次通讯录。真正要做的不是查得更快，而是把「查无此人」也记在便签上贴桌上：下次再问，看一眼便签直接回「没有」，通讯录碰都不用碰。
机制与代码：空值标记 + 对比布隆过滤器

对策（本项目采用）：空值缓存。查不到也往缓存里写一个标记，TTL 设短。四个细节都要点名：

goods/service/impl/ProductCacheService.java:42-52（常量定义）
/** 缓存空值的标记（防穿透）。用特殊串而不是 null，因为很多客户端不存 null。 */
private static final String NULL_MARK = "__NULL__";
/** 基础 TTL（秒） */
private static final long BASE_TTL = 30 * 60;
/** TTL 随机抖动上限（秒），防雪崩 */
private static final int TTL_JITTER = 10 * 60;
/** 空值 TTL（秒）：比正常短，避免"刚上架就查不到" */
private static final long NULL_TTL = 2 * 60;
goods/service/impl/ProductCacheService.java:109-124（loadAndCache + marker key）
private ProductVO loadAndCache(Long productId, String key) {
    ProductVO vo = productService.detail(productId);
    if (vo == null) {
        // 防穿透：不存在也写标记，短期挡住重复查询
        redisOps.set(NULL_MARK_KEY(productId), "1", NULL_TTL);
        return null;
    }
    // 防雪崩：TTL 加随机抖动，避免同批商品同时失效
    long ttl = BASE_TTL + ThreadLocalRandom.current().nextInt(TTL_JITTER);
    redisOps.setObject(key, vo, ttl);
    return vo;
}

private String NULL_MARK_KEY(Long productId) {
    return KEY_PREFIX + "null:" + productId;      // aimall:product:null:{id}
}

读路径命中 marker 时直接 return null，DB 一次都不碰（ProductCacheService.java:73-76）：if (redisOps.get(NULL_MARK_KEY(productId)).isPresent()) { return null; }

空值标记（本项目）

实现成本：几行代码，零新增组件。

精度：精确——命中即确定「不存在」。

代价：攻击者灌海量垃圾 id 会占内存，靠短 TTL（2 分钟）限制。

副作用：2 分钟内真上架的商品查不到（脏读窗口）。

布隆过滤器（知道但没用）

实现成本：要预热全量 id、要能重建（重启后必须重灌）。

精度：有假阳性——说「没有」才绝对可靠，说「有」可能是误判。

代价：不支持删除（清零会连带误清其他位），要计数布隆或定期重建。

新增要同步写、删除要额外处理，一致性成本高。

诚实说明为什么不选布隆：商品 id 空间小、有 t_product 主键、误判的代价只是多查一次 DB；而布隆的预热/重建/删除一致性成本更重。这是「知道方案但不盲目上」，不是「不知道布隆过滤器」。真到百万级 key 时，布隆才是对的选择。

两个必答细节：① 为什么 TTL 只有 2 分钟——空值缓存 30 分钟 = 商品上架后半小时用户都查不到，2 分钟是「挡刷子」与「不脏读」的平衡；② 为什么用独立 key + 哨兵值 "1" 而不是往商品 key 里写 null——很多 Redis 客户端不存 null，而且「key 存在但值是标记」和「key 不存在」是两种可区分的状态，独立 key 还从结构上避免了「空值覆盖真值」这种大事故。

一个很容易漏的联动 evict() 必须两个 key 一起删（ProductCacheService.java:102-105）：delete(KEY_PREFIX + productId) 加 delete(NULL_MARK_KEY(productId))。只删商品缓存不删 marker 的话，之前发生过穿透的商品新上架后仍会被 marker 挡在门外。能主动说出这一手，是很好的加分点。
面试怎么讲
30 秒版本 "穿透是「数据不存在」——查一个 DB 里也没有的 id，缓存永远不命中，请求全打到库。我用空值缓存：查不到也写一个标记，但用独立 key aimall:product:null:{id} 存哨兵值 "1"，TTL 只给 2 分钟——挡刷子够用，又不会出现「刚上架查不到」。
为什么不缓存 null：很多客户端不存 null，而且「key 存在但是标记」和「key 不存在」是两种状态，必须区分。删缓存时两个 key 要一起删，否则新上架商品会被旧 marker 挡住。
更彻底的方案是布隆过滤器：用极小内存回答「这个 id 一定不存在吗」。但它的代价我用不上——有假阳性、不支持删除、新增要同步、重启要重建。商品 id 空间小、误判只是多查一次库，所以我选了空值缓存。"
别说错 ① 穿透和击穿的区别是本条最容易混的：穿透打「不存在的 key」，击穿打「存在但恰好过期的热点 key」。一句话——穿透 = 数据不存在；击穿 = 数据存在但缓存没了。
② 不要说「布隆过滤器一定有假阳性所以不能用」——它解决的是穿透，而且在高规模下是对的选择；本项目不用的理由是成本收益，不是方案不好。
③ 不要说「空值缓存 TTL 随便设个几十分钟」。长短都要能讲出理由。

击穿：热点 key 过期的瞬间 掌握

对应代码：ProductCacheService.java:65-99 · RedisOps.tryLock / unlock:135-152

一句话：某个爆款商品的缓存到期。同一个毫秒内几千个请求涌进来，全部发现缓存未命中（旧的已删、新的还没写），于是几千个请求同时查 MySQL 并回写。单次查询没什么，但几千个并发同时落库——MySQL 被打出一个尖刺。击穿是「一个点」被击穿。

打个比方 像公司食堂唯一的电饭煲坏了，全公司一千个人同时冲进厨房自己煮——每个人都想「我自己煮一锅就好了」，结果一千个人挤在一个厨房里谁也煮不成。
互斥锁的做法是：只放一个人进厨房煮，其余人在门口等 50 毫秒再看一眼锅里有没有饭。等到了就直接盛，还在煮就直接去外面买（兜底查库）——绝不在门口死等。
机制与代码：互斥锁重建 + 对比逻辑过期

对策（本项目）：互斥锁重建——同一 key 的重建只让一个线程做，其余等待后重读，重读不到直接查库兜底。

goods/service/impl/ProductCacheService.java:65-99（detailWithCache）
public ProductVO detailWithCache(Long productId) {
    String key = KEY_PREFIX + productId;

    // ---- 1. 读缓存 ----
    var cached = redisOps.getObject(key, ProductVO.class);
    if (cached.isPresent()) {
        return cached.get();                     // 命中：99% 的请求走到这就结束了
    }
    // 命中"空值标记"：说明这个商品确实不存在，直接返回 null（防穿透）
    if (redisOps.get(NULL_MARK_KEY(productId)).isPresent()) {
        return null;
    }

    // ---- 2. 未命中：互斥锁重建（防击穿）----
    String lockKey = LOCK_PREFIX + productId;                 // aimall:lock:product:{id}
    String lockValue = redisOps.tryLock(lockKey, 3000);       // SET NX PX 3000
    try {
        if (lockValue != null) {
            // 拿到锁：查库 → 回写缓存
            return loadAndCache(productId, key);
        }
        // 没拿到锁：别人在重建，等一下再读
        sleepQuietly(50);
        var retry = redisOps.getObject(key, ProductVO.class);
        if (retry.isPresent()) {
            return retry.get();
        }
        // 兜底：仍读不到就直接查库（缓存只是旁路，不能让它决定可用性）
        return productService.detail(productId);
    } finally {
        if (lockValue != null) {
            redisOps.unlock(lockKey, lockValue);
        }
    }
}

四个必须点名的细节：

  1. 锁 TTL 为什么是 3 秒：防止赢家查库途中崩溃导致死锁。代价是「赢家超 3 秒没干完，锁没了别人也能进」——最坏退化成无锁并发重建，不会出错，只是多查一次库。正因为代价这么轻，本项目才不引入看门狗续期。按代价选复杂度。
  2. 为什么要存 UUID：标识「这把锁是我的」。释放时校验，防锁误删——A 的锁超时自动释放后，A 执行到 finally 把 B 刚拿到的锁删了。
  3. 输家为什么 sleep 50ms 而不是一直等：赢家查库加回写通常小于 50ms；等太久请求堆积。等待要有上限——与 V3 的 Redis 连接池 max-wait（2 秒）是同一个思想。
  4. 输家兜底为什么敢直接查库：击穿的本质是「瞬时尖刺」。输家直接查库只是把尖刺从几千降到几十，可控。缓存是旁路，不能让它决定可用性——等锁不能等成故障。
互斥锁重建（本项目）

一致性：强——锁内写完，大家读到的都是新值。

延迟：未抢到锁的线程 sleep 50ms 重读。

复杂度：简单（一个 SET NX + 等待逻辑）。

隐藏坑：锁 TTL 到期重建未完会「双重建」——多查一次库，不伤正确性。

逻辑过期（知道但没用）

一致性：最终一致——过期后一段时间仍读旧值。

延迟：几乎无延迟（立即返回旧值 + 异步重建）。

复杂度：value 要包 data + expireAt，还要异步线程池。

隐藏坑：异步刷新线程挂了，缓存里永远是一份旧数据（没有物理过期兜底）。

本项目选互斥锁的理由：商品详情不是微博热搜那种量级，50ms 等待可接受；而「读到旧价格」是电商硬伤，比慢严重——所以选一致性优先。逻辑过期适合极致热点（追求零延迟、能容忍短暂脏读）。

一致性：为什么是「先更库再删缓存」 掌握

对应代码：ProductCacheService.evict:102-105 · ProductRestController 的接线位置

一句话：写路径只有两步——UPDATE DB → DELETE cache。不是「更新缓存」。理由两条：① 删除是幂等的，谁删都一样，而更新要自己算新值且并发下顺序可能倒置；② 先更库再删缓存即使有并发读把旧值灌回缓存，也只是「短暂且必然被随后的删除清掉」——失败方向更安全。

打个比方 「更新缓存」像黑板上的通知改了，你得挨个通知每个路过的人「新内容是这个」——人多的时候你喊的话可能被后来的人盖掉；「删除缓存」像直接把黑板擦了——谁来看都是空的，下次有人要看自然去办公室里拿最新的贴上来。
擦黑板不用记内容、不怕顺序错、谁擦都一样——这就是「删除比更新安全」的全部理由。

5.4计数增量桶：写放大治理

一次互动三次 DB 写，热点行会被打爆 熟悉

对应代码：NoteCounterStore.java · NoteCounterFlushTask.java:24 · NoteServiceImpl.incrCount:507-528 / flushCounters:544-565

一句话：热门笔记每次被浏览，原实现要做「查 → 更新计数 → 重算热度」共 3 次 DB 写（代码注释原话是「1 SELECT + 3 UPDATE」），而且全打在同一行上——InnoDB 的行锁把这行串行化，热点笔记的这行被高频写打爆。改法是：互动只往 Redis Hash 里 HINCRBY 攒增量（内存、微秒级），每 60 秒由定时任务原子取走并加法回写 DB。

打个比方 这像超市收银台不再「每卖一件就跑去仓库改一次库存牌」，而是先把每一笔记账在小本子上，每隔一小时把小本子上的总数一次抄进账本。
关键是小本子上记的是「这一小时卖了多少」这个增量，不是「现在还剩多少」这个全量——因为抄全量时两边会互相覆盖，而加法永远不会算错。

取走+清空必须原子（Lua）：拆成 HGETALL → DEL 两步的话，两步之间到达的 HINCRBY 会被随后的 DEL 一起删掉——增量凭空丢失（落库丢计数）。脚本内先取后删原子执行，取走之后新到的增量进入「新一轮」，下轮再落（RedisOps.java:283-311，TAKE_ALL_LUA）。

代价是什么（面试要能主动说） 可能丢最后 60 秒的计数。Redis 在这一刻宕机，未落库的增量就没了。为什么能接受？计数是「展示数据」不是「资金数据」——丢了最多是点赞数少几个，不丢单不资损。代码注释原话：计数与订单/支付的一致性等级刻意区分。反过来说，这个取舍不能用在下单/支付上，那里必须强一致 + CAS 兜底。能主动画出这条线，才叫真懂一致性等级。

我改成 Redis 攒增量 + 60 秒定时落库：互动只做一次 HINCRBY（内存、微秒级），定时任务把增量原子取走后批量加法回写 DB，热度的重算也收敛到落库路径上——所以热度的更新频率等于落库频率，与流量解耦，这就是写放大治理的完整闭环。
关键设计是存 delta 不是全量：存全量时「Redis 全量值」和「DB 值」会互相覆盖，丢更新的窗口永远在；存增量两侧都是加法，天然可交换、可重试，没有覆盖语义。取走+清空用 Lua 保证原子，否则两步之间新到的增量会被 DEL 误删。
代价我主动说：Redis 宕机会丢最后 60 秒的增量。但计数是展示数据不是资金数据，一致性等级和订单/支付刻意区分开——Redis 不可用时还会自动降级回 DB 直写，功能不坏只是慢。"
别说错 ① 别说「放 Redis 就是为了快」就完事——真实动机是写放大治理（热点行的行锁被高频写打爆），说清动机才叫懂。
② 别说「定时落库保证计数不丢」——它会丢最后一个周期的增量，代价必须主动交代。
③ 别说「存 Redis 全量值然后定时刷回 DB」——那正是被否掉的写法，会丢更新。

zset 是唯一同时满足「去重 + 有序 + TopN」的结构 熟悉

一句话：排行榜需要三件事——成员唯一（一篇笔记只上一次榜）、按分数自动有序、能取 Top-N 和查排名。Redis 五种基本结构里只有 zset 一条同时满足，而且全是 O(logN) 级别。同时榜单用两条轨道维护：互动时增量刷新保实时，定时全量重建保「Redis 挂了也能自己爬起来」。

代价：多一次重算 + 一次 Redis 写。

全量重建（30 分钟）

解决的问题：冷启动 / 漂移自愈——以 DB 为真值重灌一遍，纠正 score 算错与长期不一致。

代价：一次批量写 + 毫秒级空窗。

只有它会怎样：榜单最坏滞后 30 分钟——刚爆火的笔记上不去，体验差。

一句话口径：增量保实时，全量保自愈。更底层的理由是——缓存永远可以由源数据重建，DB 才是真值，Redis 只是加速。这也是 HotRankRebuildTask 类注释的原话。

读榜：zset 只出 id 顺序，明细一次 IN 批量回查。这条是「反 N+1」在榜单上的复用（代码注释明确记了一次 P2 修复：早期实现是循环逐条 selectById，Top50 = 50 次 SQL，与列表接口辛苦做的批量查询自相矛盾）。另外排序的真相在 zset 里——IN 返回顺序不保证与传入一致，所以最后一步是按 zset 顺序组装，DB 只负责补明细（NoteServiceImpl.java:406-456）。

可以主动交代的真实缺陷（说出来比不说值钱） ① 口径不一致：全量重建只灌热度最高的 1000 篇，但增量刷新（refreshHotScore）不受这个限制——任何被点赞的笔记都会 zAdd 进榜。结果是一篇靠点赞爬进榜、但排名在 1000 名之外的笔记，下一次全量重建会把它静默擦掉，榜单随重建周期出现锯齿抖动。这不是性能问题，是正确性问题（增量与全量的口径必须一致）。解法有：增量侧加同样的边界判断、全量侧不做 delete 而是「灌全部 + 定期裁剪」、或用影子 key 原子切换。
② 先删后灌有毫秒级空窗：这期间读榜单会拿到空列表。标准解法是影子 key + RENAME 原子替换（Redis 的 RENAME 是原子的）。本项目接受这个空窗，因为榜单是派生数据——但要主动说「我知道标准解法是影子 key」，否则就是没意识到。
边界一句话（这条也是分水岭） 榜单是派生数据，可以容忍短暂不准——这正是敢用「增量 + 最终一致」的前提。反过来说：库存、金额是账目数据，绝不能这么干，必须强一致 + 条件更新兜底。能主动画出这条线，才算真懂自己为什么敢用 zset。

5.6接口限流：Redis INCR + EXPIRE 的 Lua 原子固定窗口

分开执行 INCR 和 EXPIRE 会导致用户被永久限流 掌握

对应代码：RedisOps.java:214-240（RATE_LIMIT_LUA + allow） · 调用点 ChatRestController.java:118-124

一句话：只有 AI 对话接口带限流（每用户 10 次 / 60 秒），因为 AI 是按 token 计费的真实成本，被脚本刷一晚就是真金白银，而且一次问答耗时 3~10 秒会占住 Tomcat 线程池，把正常用户连坐。实现是 Redis 固定窗口计数——但计数与设置过期必须在同一个 Lua 脚本里。

打个比方 把 INCR 和 EXPIRE 分开写，像进景区先刷一次卡（计数 +1）、再走到另一个窗口去盖章（设置有效期）：万一你刷完卡、走到盖章窗口时窗口临时关了——你的卡永远不过期，此后每次刷卡都显示「已超次数」。
Lua 的做法是刷卡和盖章在同一张桌子上一次办完：要么都成功，要么都没发生，不存在「刷了卡没盖成章」的中间态。
机制与代码：真实 Lua 脚本 + 固定窗口的边界缺陷

真实 Lua 脚本与调用代码：

为什么必须用 Lua（这是本节的核心）：早期两步写法是 INCR 之后再 EXPIRE。如果 INCR 成功但 EXPIRE 恰好失败（Redis 瞬断），key 存在但永不过期 → 计数器只增不减 → 该用户被永久限流到 10 次，而且没人能发现原因。Lua 把两步合成原子操作，从根上消除这个窗口。代码注释原话：「这也是多命令复合语义必须 Lua 的又一实例（与限量发售预减同理）」——本项目第三次应用这个原则。

为什么 if n == 1 才设置过期：只有窗口内第一次请求需要设 TTL。若每次都 EXPIRE，窗口会被无限延长，变成「60 秒内没请求才算过窗口」的滑动语义，与固定窗口不一致。

限流键为什么要带 userId：按用户隔离。所有用户共用一个 key 就是「全局限流」——一个人刷爆，所有人都用不了。带上 userId 才是「每人每分钟 10 次」。

fail-open 的取舍：Redis 不可用时 allow 返回 true 放行。代码注释原话——「限流组件不应成为可用性瓶颈」。理由要能讲透：限流是为了控成本，「因限流组件挂了导致正常用户全用不了」是更严重的事故。拒绝服务比多花点钱更糟。这与「缓存挂了走 DB」是同一种思想：兜底优先保可用。

固定窗口的边界缺陷（必须主动说） 窗口切换瞬间最多放行 2 倍。比如第 1 分钟最后 1 秒打满 10 次 + 第 2 分钟第 1 秒再打 10 次——1 秒内实际 20 次穿过。这是固定窗口的固有缺陷，不是实现 bug。
更严格的方案（说得出名字就够）：
滑动窗口——用 zset 存每次请求的时间戳，ZREMRANGEBYSCORE 清掉窗口外的、ZCARD 计数，统计精确；代价是每个请求要写一次 zset，内存与开销更大。
令牌桶 / 漏桶——恒定速率放行、允许受控突发，网关常用。
本项目为何用固定窗口：代码注释已写明——「限流的目的是防刷与成本控制，固定窗口实现简单、性能好；边界处最多放行 2 倍对本场景可接受。真要严格限流用 Redisson 的 RRateLimiter 或网关层限流。」能说出自己方案的缺陷，比堆砌高级方案更显功底。
面试怎么讲
30 秒版本 "我在 AI 对话接口做了限流，每用户 10 次 / 60 秒。为什么只限 AI 而不限商品列表？因为 AI 按 token 计费，一次问答真实花钱，被脚本刷一晚就是真金白银；而且 AI 调用秒级耗时，会把 Tomcat 线程池占满、连坐正常用户。限流是成本治理，不是炫技。
实现是 Redis INCR + EXPIRE 的固定窗口，但必须放在同一个 Lua 脚本里原子执行——早期分成两行写有个隐蔽 bug：INCR 成功但 EXPIRE 恰好失败，key 就永不过期，该用户会被永久限流到 10 次。Lua 在 Redis 单线程里原子执行整段，从根上消除这个中间态。

别说错 ① 别说「限流用 Redis INCR 加 EXPIRE 两行就够」——那正是被评审修掉的 bug，两行之间永远有「恰好失败」的窗口。
② 别说「Redis 挂了就拒绝请求」——那是 fail-close，等于把限流组件变成单点故障。
③ 被问「哪里用了限流」只答 AI 接口，并说清成本理由。项目没有网关层限流、没有 Sentinel、没有滑动窗口/令牌桶——主动说清这个边界，别说成「全站都有接口级限流」。

5.7幂等设计：四种手段与真实落点 必考 · 口径高危

幂等的定义：同一个请求执行 N 次，效果等于执行 1 次。它不是「防重复请求」，而是「让重复请求无害」——因为重复一定会发生，来源有三个：

① 用户重复提交双击「提交订单」、网络慢时反复点、浏览器重放。这是最直观的来源。
② 第三方重复回调支付回调必然重复——支付宝文档明确：未收到 success 会重试 8 次以上，间隔逐渐拉长。
③ MQ 重复消费MQ 的语义是 at-least-once：先做业务后 ACK，进程在 ACK 前崩溃 → 消息重投 → 重复执行。重复是常态不是异常。

在资损场景（下单、支付、限购、库存回补），幂等不是加分项，是入场券——重复一次就是重复扣钱/重复回补库存/超卖。项目用四种手段覆盖不同层面，下面是完整对照。

手段真实落点防的是什么
唯一索引t_note_like / t_note_collect 的 uk_note_user、t_payment 的 uk_order_id、t_drop_record 的 uk_activity_user、t_audit_record 的 uk_biz防「新增重复」：并发下物理拒绝多出一条记录
状态机条件更新OrderMapper.updateStatus / PaymentMapper.updateToPaid / NoteMapper.updateStatus 的 WHERE status = 旧值防「流转重复」：同一个状态不允许被改两次
一次性 token下单幂等：签发侧 OrderServiceImpl.createIdempotentToken:142-147、消费侧 :60-67、原子 DEL RedisOps.consumeToken:323-325防「进入流程重复」：不碰 DB 的第一道闸
消费端回查AuditConsumer 消息只带 noteId 回查、OrderCancelConsumer 消息只带 orderId 回查、抢购消息不带金额防「过期状态」：消息在队列里躺着时，世界已经变了

手段一：唯一索引——直接 INSERT，不先查 掌握

对应代码：NoteServiceImpl.like:157-174 · V2__content_and_rag.sql:70-79 · PaymentService.create:106-115

一句话：狂点红心（前端防抖失灵）时两个请求同时到达。如果代码先 SELECT 再 INSERT，两个线程都会查到「没点过」然后各插一条——把并发正确性交给数据库的唯一约束（物理层面拒绝），成本最低也最可靠。

打个比方 「先查后插」像两个人同时走进一间空会议室，都探头看了一眼说「没人，我进去」——他们看的那一眼是同一瞬间，所以两个人都进去了。
唯一索引像门口那把只有一把钥匙的锁：两个人同时伸手，物理上只有一个能拧开。把并发正确性交给物理约束，比在应用代码里判断可靠得多。

为什么「先查再插」不行（最容易被追问的一点）：查与插之间有窗口，两个线程的 SELECT 都在对方 INSERT 之前完成，都以为「没点过」→ 插两条。这是经典的 TOCTOU（Time-Of-Check-To-Time-Of-Use）竞态——看起来更严谨的写法反而是错的。

深挖一层（撞键后事务其实已标回滚）：撞键发生在事务内，Spring 会把 DuplicateKeyException（DataIntegrityViolationException 的子类）视为运行时异常 → 标记事务回滚。所以 NoteServiceImpl.like 里 catch 住它之后，这次请求整体回滚（含 incrCount），只是不返回错误给用户。结果正好是「红心已经是亮的、计数没有被重复 +1」——正是幂等想要的结果（第一次点赞早已成功提交）。这条因果关系能讲清，是很硬的加分项。

唯一索引 vs 状态机 CAS 的分工（必答）：唯一索引防「新增重复」（防止多出一条记录）；状态机 CAS 防「流转重复」（防止同一个状态被改两次）。一个管「有没有」，一个管「变没变」。

手段二：状态机条件更新（CAS） 掌握

对应代码：OrderCancelConsumer.cancelIfStillPending:67-97 · PaymentService.handleCallback:194-213 · OrderMapper.updateStatus

一句话：所有状态流转都写成 UPDATE ... WHERE status = 旧值，返回影响行数：rows == 0 = 这个状态已经被别人改过了（我输了竞争，什么都不做）；rows == 1 = 我赢了，可以放心做后续动作（回补库存、关支付单）。把判断塞进 SQL 的 WHERE，让数据库的行锁保证「判断与更新原子完成」。

打个比方 状态机 CAS 像换乘闸机：只有「手持进站票」的人才能刷开换乘通道；已经换乘过的人手里票已经变了，再刷只会被拒。它不是靠保安肉眼判断你有没有换乘过，而是闸机本身只认那一种票——判断和放行是同一个机械动作。

顺序至关重要：CAS 成功之后才回补库存。顺序反了（先回补再 CAS）→ 输家也会回补 → 状态没变但库存加了 = 虚增，这是真实资损。代码注释原话：「只有取消成功者才回补库存——顺序错了 = 状态没变库存却加了（虚增）」。

支付侧自己也有状态机（幂等第二道防线）：updateToPaid(..., STATUS_PAYING, ...) 返回 0 时仍返回 success——因为「别人已处理」对第三方来说就是成功；返回失败会让它继续重发（PaymentService.java:194-203）。

审核侧同一招（防线二）：noteMapper.updateStatus(noteId, AUDITING, newStatus, reason)，返回 0 行说明笔记已被别人改过，忽略（AuditServiceImpl.java:134-136）。

为什么状态机 CAS 天然幂等（深层理由）：状态机是单向的、有终态的。PENDING_PAY → CANCELLED 一旦发生，再执行一次「把 PENDING_PAY 改成 CANCELLED」就找不到 PENDING_PAY 的行了 → 自然幂等。「幂等」不是额外加的功能，而是「用旧状态做闸门」的副产品。

诚实边界（两条） ① 没有状态机引擎。项目没有 Spring StateMachine、没有 DSL，就是把 WHERE status = 旧值 硬编码在 Mapper XML 里。讲的时候说「用条件更新实现状态机语义」最准确。
② CAS 的局限：它只保证「同一条记录的同一次流转」不重复，不能保证跨表/跨服务的原子性。PaymentService.handleCallback 里支付单已改 PAID 但订单流转失败（orderRows==0）就是这种跨表不一致——只能靠 log.error + 退款/人工兜底。要做强一致就得引入 TCC/Saga，本项目按业务量判断不划算。

一句话：支付、取消、库存回补都幂等了，唯独建单之前没有防线——用户双击「提交订单」就是两张单。方案是结算页加载时后端签发一次性 token（Redis 记 10 分钟），提交时带回，服务端 DEL 原子消费：删到了=首次放行，删不到=已用过拒绝。

不用「记住每个人的脸」来判断，而是用「手上还有没有这个一次性凭证」——核销与判断是同一个动作，没有窗口。

为什么 DEL 本身就是原子的：Redis 单线程执行命令，DEL 一条命令完成「检查存在 + 删除」，没有「先 GET 判断存在再 DEL」的两步窗口。SET NX 是「不存在才写」的原子版本，DEL 返回 1/0 就是「存在才删」的原子版本。

返回含义处理
true首次消费（DEL 真的删掉了 1 个 key）放行
falsetoken 已用过/不存在（DEL 返回 0）抛「请勿重复提交订单」
nullRedis 不可用fail-open 放行

fail-open 的论证（这条是王牌，务必讲透）：① 防重是「优化」不是「正确性」——即使 token 校验失效、用户真的重复提交，后面还有订单状态机 CAS + 唯一索引兜底，多出来那一单不会造成资损级错误；② 反过来（fail-close，Redis 挂了就拒绝下单）是灾难——Redis 是旁路组件，它挂了却让所有人都下不了单，就是把缓存组件变成了单点故障；③ 一句话背下来：「防重是优化不是正确性，别让缓存故障挡住正常下单。」

与唯一索引的分工：token 挡在「进入下单流程之前」（根本没开始建单，成本最低，连 DB 都不碰）；唯一索引挡在「插入的那一刻」（最后一道物理防线）。token 是第一道闸，唯一索引是最后一道闸——两者不冲突，是纵深防御。

诚实边界：代码里 hasText(...) 判断意味着 token 为空就跳过校验（兼容老前端、Postman 调试）。这是兼容性取舍：安全上弱一点，但避免了「必须同步升级前后端」的部署僵局。诚实说出来比假装没有这个缺口好。

与分布式锁的区别（可能被问）：分布式锁是「同一时刻只让一个执行」（互斥），token 是「同一个请求只执行一次」（幂等）。两个客户端拿不同 token 同时下单是允许的（那是两笔真实订单）；锁会把第二笔挡住——锁在这里是错的工具。

手段四：消费端回查——消息只带 id 熟悉

对应代码：AuditConsumer.java:36-54 · OrderDelayMessageSender.sendNow:58-68 · DropOrderExecutor.createDropOrder:109-114

一句话：消息里只放 id，不放状态，消费时回查 DB 最新态再决策。「消息在队列里躺着的时候，世界已经变了。」——一条审核消息从入队到消费可能隔几秒，一条订单超时消息要在队列里躺 30 分钟。这期间笔记可能已被编辑、订单可能已被支付或手动取消、商品可能已改价。

打个比方 这像快递面单上只写单号、不写「客户现在在家」：如果面单上写着「客户在家」就派件，等快递员到门口时客户早出门了。正确做法是拿单号去查当前状态——消息传递的是「发生了什么」（一个事实），而不是「现在是什么」（一个状态）。

            return;

        // ★ 版本号必须从消息带下去，不能硬编码

消息只带 id 的四个好处：① 天然避免过期状态——永远读最新值，不会拿半小时前的快照做决策；② 消息体小——convertAndSend(queue, orderId) 连消息类都不用定义；③ 敏感数据不进 Broker——笔记正文、用户地址、金额都不落到 MQ；④ 幂等责任归属清晰——消息只是「一个提醒」，真正的幂等由消费端的唯一索引 + 状态机 CAS 保证。

削峰链路同理：DropOrderExecutor.createDropOrder 的金额回查 DB 的 act.getDropPrice()，不信任消息体（DropOrderExecutor.java:109-114）——消息里只带 activityId / userId / quantity。

回查 + CAS 的闭环（四种手段之间的关系）：回查解决「读到最新态」，CAS 解决「改不重复」，二者缺一不可。只回查不 CAS——两个消费者同时回查到 PENDING_PAY，都会去取消，库存回补两次（虚增）；只 CAS 不回查——消息里带的状态是旧的，可能拿旧值去当闸门。所以最终幂等靠「回查最新态 → 用最新态做条件更新」这一对动作共同保证。

代价（诚实说）：① 多一次 DB 查询——但比「审错版本 / 重复取消」便宜得多；② 实体可能已不存在——所以必须有 note == null → log.warn + 正常 ACK 丢弃（重试一万次也不存在，别浪费消费能力）；③ 消费逻辑依赖 DB 可用。

细节加分：消息里的 bizVersion 是审核业务版本（不是并发版本号），来自 t_note.audit_version（发布=1，每次重新送审 +1），进 uk_biz(biz_type, biz_id, biz_version, status) 用于流水去重——它是「区分『同一次审核的 MQ 重投』与『改完内容后的新一次审核』」的钥匙。消费端还会先比对消息版本与笔记当前版本，过期消息直接丢弃，避免用旧版本号去审新内容。

面试怎么讲
30 秒版本 "我的 MQ 消息只带 id，不带内容——因为消息在队列里躺着的时候，世界已经变了。审核消息可能等几秒，超时取消消息要在队列里躺 30 分钟，这期间笔记可能被编辑、订单可能已被支付或手动取消。所以消费端统一用 id 回查 DB 最新态再决策。
四个好处：永远读最新值、消息体小、敏感数据不进 Broker、幂等责任归属清晰（消息只是提醒，幂等由消费端唯一索引 + 状态机负责）。
回查和 CAS 必须配对：回查解决「读到最新态」，CAS 解决「改不重复」。只回查不 CAS，两个消费者都读到待支付就会回补两次库存；只 CAS 不回查，可能会拿消息里的旧状态当闸门。"

5.8MQ 可靠性闭环：不丢不重 高频

「重复靠幂等、丢失靠补偿」 掌握

对应代码：MqProducerConfig:36-58 · OrderDelayMqConfig · AuditMqConfig:60-66 · OrderCancelConsumer · AuditConsumer · CompensationTask

一句话：消息「不丢」不是某一个开关能保证的，而是发送端 + Broker + 消费端三段的合力；消息「不重」也不靠 MQ，靠消费端幂等。项目是三段式：生产者 confirm/returns 回调 → 交换机队列持久化 → 消费端决定 ACK → 失败进死信 → 定时补偿兜底。

打个比方 这像寄一份重要文件：confirm 是快递员签收时给你的回执（证明「到了中转站」）；returns 是「地址写错了、退回给你」（证明「到了中转站但分不到网点」）；持久化是把文件放进保险柜而不是堆在门口；ACK 是收件人签收后你才销单；死信是「投递失败件」专门格口；补偿任务是每隔一段时间盘点一次「有没有该发没发的」。
机制与代码：三段式闭环 + 回调落地（含一个真实事故）

可靠性闭环全景：

① 发送端 · publisher-confirm消息有没有到 Broker？ack=false（nack）= Broker 没收到（内部错误/队列满）→ 记 ERROR
② 发送端 · mandatory + returns消息有没有路由到队列？到了 Broker 但找不到队列（routing key 写错/队列没声明）→ 退回给生产者 → 记 ERROR
③ Broker · 持久化交换机 new DirectExchange(name, true, false)、队列 QueueBuilder.durable(...)，Broker 重启消息不丢
④ 消费端 · 决定 ACKAUTO 模式 + default-requeue-rejected=false：审核链路吞异常 ACK（AI 挂了重试无用），订单取消链路异常冒出 → 回滚 → reject
⑤ 失败 · 死信队列reject 且 requeue=false → 按队列的 x-dead-letter-* 进 DLQ。「失败可被发现」优于「失败被无限重试」
⑥ 兜底 · 定时补偿CompensationTask 周期性扫描「没走完」的链路，详见 5.11

回调落地：这是本项目一个「配置写了没生效」的真实事故。application.yml 早就开了 publisher-confirm-type: correlated 和 publisher-returns: true，但从不注册回调——Broker 的确认/退回事件到达后被静默丢弃，等于两个开关都是摆设。修复是后补的 MqProducerConfig：

config/MqProducerConfig.java:36-58（两个回调落地）
@Bean
public RabbitTemplateCustomizer reliableRabbitTemplate() {
    return template -> {
        // mandatory：路由不到队列时退回（配合 publisher-returns: true），而非静默丢
        template.setMandatory(true);

        // Broker 确认：ack=false 即消息未到达 Broker
        template.setConfirmCallback((correlationData, ack, cause) -> {
            if (!ack) {
                log.error("MQ 消息未到达 Broker（nack）cause={} correlationData={}",
                        cause, correlationData);
            }
        });

        // 路由失败退回：到得了 Broker 但找不到队列
        template.setReturnsCallback(returned ->
                log.error("MQ 消息路由失败被退回 exchange={} routingKey={} replyText={} message={}",
                        returned.getExchange(), returned.getRoutingKey(),
                        returned.getReplyText(),
                        returned.getMessage() != null
                                ? new String(returned.getMessage().getBody())
                                : null));
    };
}

两个回调分别管什么（面试最易混）：一句话记牢——confirm 管「到没到 Broker」，returns 管「进没进队列」。两者是两个阶段，不是二选一。特别注意：ack=true 只代表「Broker 收到了」，不代表「进了队列」——队列不存在时 confirm 仍然 ack=true（Broker 确实收到了），要靠 returns 才能发现。这个区分是面试官最爱追问的一刀。另外 mandatory=true 是 returns 生效的前提：不设它，Broker 对路由不到的消息直接丢，ReturnsCallback 根本不会被调用。

为什么回调里只记 ERROR、不自动重发（主动说的取舍）：本项目消息均为「尽力而为 + 补偿任务兜底」语义，自动重发要配幂等与退避，复杂度不划算。若某条链路升级为「必达」（如资金类），再在 ConfirmCallback 里做「nack → 重投/告警」。可靠性等级按业务定，不吹「百分百不丢」。

必须出现在回答里的一句话 「重复靠幂等、丢失靠补偿」——两个机制都要有。MQ 的语义是 at-least-once，「重复」是常态（先做业务后 ACK，进程在 ACK 前崩溃就会重投），所以消费端必须幂等（见 5.7）；而「丢失」永远堵不完（配置对了还有崩溃窗口），所以必须有补偿任务做最终收敛（见 5.11）。只答「我们用了 confirm」是不完整的。

消费端两种相反策略（同项目里并存，最能体现「按语义选」）：

5.9事务与 MQ：为什么不能在 @Transactional 里发消息

事务回滚了，消息已经飞出去 掌握

对应代码：common/tx/AfterCommitExecutor.java · order/mq/OrderDelayMessageSender.java:42-55 · OrderServiceImpl.create:127-132 · DropOrderExecutor.createDropOrder:128 · AuditServiceImpl.submit:93-121

一句话：MQ 不参与 DB 事务。如果在 @Transactional 方法体里直接 convertAndSend，事务后面回滚了，消息却已经飞出去了——30 分钟后消费者查到的是一个「幽灵订单」（订单不存在或状态不对）。项目的解法是 afterCommit 注册：把发送动作注册到事务提交之后。这条链路现在收敛成全项目唯一的出口 AfterCommitExecutor.run(what, action)（common/tx/），订单延迟消息与内容审核消息都走它。

打个比方 事务内发消息像合同还没盖完章就先把「合同已生效」的公告发出去了——万一最后一步盖章失败、合同作废，公告却已经满城皆知，所有人都来找你履约。
afterCommit 是等合同真正归档了，再发公告：盖章失败就没有公告，不会产生「宣布了却没发生」的状态。
机制与代码：反模式推演 + afterCommit 实现
反模式：事务内直发

1. 事务开始，插入订单

2. convertAndSend(延迟队列, orderId) —— 消息已出

3. 后续某步抛异常 → 事务回滚，订单不存在了

4. 30 分钟后消费者收到消息，回查到 null 或状态不符 → 幽灵消息

本项目消费端有 null/状态防御所以后果较轻，但这仍是反模式——正确的做法不是「消费端兜住」，而是「根本不发」。

本项目：afterCommit 注册（统一出口 AfterCommitExecutor）

1. 事务内只注册同步回调，不发消息

2. 事务提交成功 → Spring 回调 afterCommit()

3. 此时才真正投递（审核链路是 doSubmit()，订单链路是 sendNow()）

4. 若事务回滚 → afterCommit 不执行 → 消息从未发出

代价：提交成功、发送前进程崩溃仍会丢消息 → 由补偿任务分钟级收敛兜底。

order/mq/OrderDelayMessageSender.java:42-68（sendAfterCommit + sendNow）
public void sendAfterCommit(Long orderId) {
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        // 没有事务直接发：极端场景（手动触发），比静默丢消息好
        log.warn("sendAfterCommit 在无事务上下文调用，退化为立即发送 orderId={}", orderId);
        sendNow(orderId);
        return;
    }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            sendNow(orderId);
        }
    });
}

/** 直接投递（MQ 不可用时静默降级：不投递，由补偿任务兜底） */
public void sendNow(Long orderId) {
    RabbitTemplate rabbit = rabbitTemplateProvider.getIfAvailable();
    if (rabbit == null) {
        return;
    }
    try {
        rabbit.convertAndSend(OrderDelayMqConfig.DELAY_QUEUE, orderId);
    } catch (AmqpException e) {
        log.warn("延迟消息投递失败（不影响业务，补偿任务兜底）orderId={}: {}", orderId, e.getMessage());
    }
}

为什么抽成唯一出口（P0-3 修复的产物）：早期只有普通下单发这条消息，后来限量发售也建订单却忘了发——抢购单永不超时取消，限量库存被死单永久占用。根因是「建单必发延迟消息」这个约束散落在各处靠人记。抽成唯一出口后，任何建单路径（普通下单 / 秒杀下单 / 将来的拼团）都调 sendAfterCommit——忘了发消息 = 忘了调这个方法，一眼可见。类注释原话：「延迟消息唯一出口（Drop 下单也用它——『建单必发超时取消』不再靠人记）」。

对比其他方案，为什么本项目用 afterCommit 就够：

方案机制强度 / 代价
afterCommit（本项目）注册 TransactionSynchronization，提交后发送轻量、零新增组件、代码可读；残余窗口：提交成功但发送前进程崩溃 → 消息丢（补偿任务收敛）
本地消息表「要发的消息」与业务数据同一事务落库，定时任务扫描投递强一致，消息一定不丢；代价是双写 + 扫描 + 需要消息状态机（本项目未做）
事务消息（RocketMQ）半消息 + 事务回查由 MQ 原生支持；本项目用 RabbitMQ，没有这个能力

判断依据是业务语义：订单超时取消是「尽力而为 + 对账收敛」——订单多挂 5 分钟完全可接受，不值得为它引入本地消息表；资金类（如扣款通知）才需要必达，那时才升级。诚实交代残余窗口：「我清楚 afterCommit 有崩溃窗口，所以这是最终一致而不是强一致。」

另一个同源坑（V2 审核链路，已升级为同一出口）：发布笔记在 @Transactional 里调 AuditService.submit 发 MQ——早期注释写着"事务提交后发"，但 Controller 层根本没有事务，实际仍在事务内直发，消费者回查不到未提交的笔记就丢弃消息。现在 submit() 已改为调 AfterCommitExecutor.run(...)：订单延迟消息与审核消息共用同一个 afterCommit 出口，不再各自写一遍。这也是"同一个问题在两处犯了、最后收敛成一个组件"的典型。

这个类的三个约定（面试可以主动讲）：① 异常必须在这里吞掉——commit 之后再抛异常无法回滚，只会让调用方看到"下单失败"而数据其实成功了；② 无事务上下文时退化为立即执行并记 WARN，而不是静默跳过（"宁可早发，不可不发"，早发的后果由消费端 null 防御兜住）；③ 传入的动作自身不要再往外抛，因为这里已经是最外层防线。

面试怎么讲
30 秒版本 "不能在事务里直接发 MQ，因为 MQ 不参与 DB 事务。事务后面回滚了，消息却已经飞出去——消费者过一会儿查到一个「幽灵订单」，或者查不到对应记录。
标准解法有两档：afterCommit 注册（轻量，我用这个）和本地消息表（消息与业务数据同一事务落库，定时扫描投递，强一致场景用）。我用 TransactionSynchronizationManager.registerSynchronization 注册一个同步回调，只在事务提交成功后才真正 convertAndSend；事务回滚的话回调根本不执行，消息从未发出。
为什么 afterCommit 就够：订单超时取消是「尽力而为 + 对账收敛」语义——多挂 5 分钟可接受，再配上补偿任务兜底就闭环了；资金类才需要升级到本地消息表或事务消息。我也知道 afterCommit 不是 100% 安全：提交成功、发送前进程崩溃仍会丢消息——这就是为什么必须有补偿任务。
另外这类"事务提交后再发消息"的代码我抽成了全项目唯一出口 AfterCommitExecutor，订单延迟消息和内容审核消息都走它——早期抢购下单漏发过这条消息（抢购单永不超时、库存被死单占死），根因就是"建单必发"这个约束散落各处靠人记；抽成唯一出口后，漏发 = 漏调方法，一眼可见。这个类还有两个约定值得说：提交后抛的异常必须在里面吞掉（事务已提交、回滚不了，往外抛只会制造假故障），没有事务上下文时退化为立即执行并记 WARN（宁可早发、不可不发）。"
别说错 ① 不要说「事务里发消息也没事，消费端兜住就行」——消费端防御是最后一道，不是设计依据。
② 别说「我们用了 RocketMQ 事务消息 / 本地消息表」——项目没有这两个，用的就是 afterCommit，且 framework 是 RabbitMQ。
③ 别说「补偿任务保证消息一定不丢」——它保证的是「最终收敛」，代价是分钟级延迟，不是零丢失。

5.11补偿任务三合一：异步链路的最终一致性收敛

主链路追求「快」，补偿任务保证「最终对」 掌握

对应代码：common/job/CompensationTask.java（三个 @Scheduled 方法）

一句话：三条异步链路各有自己的「最优路径」，但最优路径每一环都可能掉链子——延迟消息可能丢、审核消息可能被 ACK 掉、第三方回调可能网络丢失。补偿任务做三件事，把这三种「没走完」定时收敛成「确定完成」：订单超时兜底 / 审核堆积重送 / 支付查单对账。

打个比方 补偿任务像仓库每天下班前的盘点：白天靠流程（出库单、扫码、系统自动扣减）正常走；但总会有几笔「单据说发了、系统里没扣」或者「系统说扣了、单据没归档」的账。盘点不去追究哪一单出了问题，而是把「所有对不上的账」捞出来，重新走一遍正确的流程。
所以它有个前提：重新走一遍必须是无害的（幂等）——否则盘点就变成了「每天定时把账再搞乱一次」。

/**
 * 订单超时兜底：扫描"本该被延迟消息取消却仍是待支付"的订单。
 * 宽限 5 分钟（30 分钟 TTL + 5），避免与正常延迟消息重复劳动（重复也无害，幂等）。
 */
@Scheduled(fixedDelay = 5 * 60 * 1000, initialDelay = 60 * 1000)
public void cancelTimeoutOrders() {
    LocalDateTime before = LocalDateTime.now().minusMinutes(35);
    List<Order> stale = orderMapper.selectTimeoutPending(before, 100);
    if (stale.isEmpty()) {
        return;
    }
    log.info("[补偿] 发现 {} 笔超时未取消订单，逐笔执行取消", stale.size());
    for (Order o : stale) {
        // 直接调消费端方法：它自带事务 + CAS + 全部取消副作用，与消息路径完全同语义
        try {
            orderCancelConsumer.onCancelMessage(o.getId());
        } catch (Exception e) {
            log.error("[补偿] 订单取消失败 orderId={}: {}", o.getId(), e.getMessage());
        }
    }
}

三个方法共享同一骨架——定时扫描 → LIMIT 取一批 → 逐条 try-catch 调用「主链路本来就有的那个方法」→ 失败只记日志，下一轮再来。日志统一带 [补偿] 前缀，便于线上 grep 验证。

为什么必须有它（异步系统的不等式）：类注释画得很清楚——订单超时取消的延迟消息可能因 MQ 宕机/消息丢失/投递失败而到不了；内容审核的 MQ 消息可能丢失或被 ACK 掉；支付依赖第三方异步回调，回调可能网络丢失。不追求每条消息必达，而是接受丢失率，用周期性对账收敛。代价是分钟级延迟，对这三个场景完全可接受（订单多挂 5 分钟、审核晚 10 分钟）。

关键设计细节（讲出来就显真读过代码）：

  1. 为什么宽限 35 分钟而不是 30：延迟消息 TTL 是 30 分钟。补偿扫描如果也卡 30 分钟，会和正常抵达的延迟消息抢同一批单——重复劳动（虽然幂等无害）。宽限 5 分钟是让常规路径先走完，补偿只处理「常规路径没走到的」。
  2. 为什么复用消费端方法而不是另写一套取消逻辑：注释写得很直白——「它自带事务 + CAS + 全部取消副作用，与消息路径完全同语义」。如果补偿另写一份删除逻辑，两套逻辑会随时间漂移（回补库存少了一步、忘关支付单），那才是真正的灾难。「补偿路径与主路径同语义」是这套设计最重要的一句话。
  3. 为什么只扫 PAYING：PAID / CLOSED 都是终态，扫它们没有可补偿的动作；只对「悬而未决」的状态做对账。
  4. 分批限量（LIMIT 100）：让单轮工作量有上限，补偿任务不会「一次性把积压一年的数据全捞出来」拖垮自己（也拖垮 DB）。
  5. 审核这条补偿为什么现在真的能救回：重审用的是同一个版本号（t_note.audit_version 未变），属于「同一次审核的重复执行」；而 t_audit_record 的唯一键含 status，AI 失败留下的 ERROR 流水不占用终态幂等位，所以补审拿到 PASS/REJECT 时能正常落库并流转。修复前唯一键不含 status，一次 ERROR 会把后续所有补审挡在 INSERT IGNORE 之外——那才是「永久卡在 AUDITING」的真正成因（V5 迁移修掉）。

前提是幂等（这是能不能上生产的条件，不是加分项）：三个补偿动作全部复用各自的状态机 CAS——订单取消 WHERE status='PENDING_PAY'、审核回写 WHERE status='AUDITING'、支付单 WHERE status='PAYING'。三处 rows==0 的语义都一样：状态已被别人改过（正常现象），直接跳过。所以类注释能写下这句话——「扫 100 次和扫 1 次结果一致」。

为什么补偿必须幂等（两个真实原因）：① 多实例部署会重复执行——@Scheduled 在每个应用实例里都会跑，部署 2 个实例 → 同一个超时订单被扫到 2 次；② 补偿与主链路会撞车——延迟消息正常抵达的瞬间补偿恰好也扫到这一单，或用户手动取消与超时补偿同时发生。三方竞争能安全收敛，靠的就是 WHERE status='PENDING_PAY' 这一行。

诚实边界：@Scheduled 的局限与升级路径 ① 单线程调度：一个任务跑久了会拖延其他任务（类注释明确写「生产应配置独立调度线程池」，当前任务量小默认够用）；② 单机执行：多实例下同一任务会并发重复执行，当前靠动作幂等扛住（正确性没问题），但没有「只有一台执行」的保障。
升级路径：XXL-Job（分片广播、失败重试、可视化管理）或 ShedLock（给任务抢一把数据库锁，最简单）。为什么现在不上：任务量小、幂等已保证正确性，多引一个中间件（XXL-Job 要部署调度中心）不符合「零依赖能启动」的硬约束。「知道它的问题、知道升级路径、也知道现在为什么不上」——这个三段回答比背出 XXL-Job 的特性更值钱。

5.12真实事故库（面试「遇到最难的问题」素材）

这一节是本页最「不像八股」的部分。面试官问「你项目踩过什么坑」时，这里的素材比任何背诵都真——因为每条都是「现象 → 定位 → 修复 → 加了什么防线」的完整叙事。来源：README 的「可靠性大修缮（2026-09-09，P0/P1/P2 系统性修复）」+ V3 详解第 11 章评审复盘。

事故 1 · 事务内吞异常，导致半截事务照样提交

现象：超时取消订单偶尔出现「状态已改、库存已回补，但支付单永远停在 PAYING」——用户取消的订单还能付款。

定位：OrderCancelConsumer 早期在 @Transactional 方法内部 try-catch 把异常吞掉 → 异常不冒出 AOP 代理 → Spring 无从感知 → 半截事务照样提交。最后一步 closeIfPaying 抛的异常被吞，回滚不生效。

修复：让异常从监听方法冒出。链路变成——① 当前事务回滚（不留半截状态）→ ② 监听容器 reject（default-requeue-rejected=false，不重入队防毒消息循环）→ ③ 队列死信路由进 DLQ 等人工。

加的防线：取消队列补上 DLX（此前失败 = 消息消失）；补偿任务作为最终兜底。代码注释现在就写着「异常必须冒出方法，不许在事务内吞掉」。

元教训事务边界与异常传播是绑定的——「catch 住不抛」在事务里等于「假装没发生」，而 Spring 只认抛出来的异常。

事故 2 · 抢购参数裸 Map 接参，可传负数反向刷库存

现象：限量发售接口如果传 quantity=-5，库存不减反增、订单金额算出负数。

定位：早期 buy 接口用裸 Map 接参，quantity 没有任何校验。负数会让 Lua 的 DECRBY 变成 INCRBY（库存反向增加），DB 侧 stock = stock - (-5) 同样加库存。

修复：换成 DTO + Bean Validation 在最外层拦死（DropBuyRequest.java:16-23）：@NotNull + @Min(1) + @Max(99)。

pay/dto/DropBuyRequest.java:16-23
@Data
public class DropBuyRequest {
    @NotNull(message = "quantity 不能为空")
    @Min(value = 1, message = "购买数量至少为 1")
    @Max(value = 99, message = "单次最多 99 件")
    private Integer quantity;
}

加的防线：代码注释写下原则——「越是高并发的入口，参数校验越要在最外层拦死（Bean Validation 一行顶十行防御）」。

元教训高并发接口的第一道防线不是缓存也不是锁，是参数校验——它挡在一切业务逻辑之前，成本最低。

事故 3 · 预热竞态：check-then-set 并发首访把已扣库存重置回全量

现象：极端情况下限量发售会超卖——Redis 里的库存「自己涨回去了」。

定位：早期懒预热写的是 check-then-set（先 GET 判空，再 SET 覆盖）。并发首访时两个请求都会判「未预热」，后一个 SET 会把已经扣减过的库存重置回全量。

修复：改用 SET NX（setIfAbsent）把「判断 + 写入」原子化，只有一个请求能真正灌入（DropService.java:88-102 的 warmUpIfAbsent）。强制覆盖只保留在「活动开始」这个明确的开售事件上（warmUp），懒预热一律 NX。

加的防线：RedisOps 的类注释把这个案例写成了 setIfAbsent 的设计说明——「NX 语义把『判断+写入』原子化，天然幂等」。

元教训check-then-act 在任何存储上都是竞态——Redis 的手册里 Map 那些 GET/SET 看着像内存操作，但跨线程、跨进程时一样有窗口。

事故 4 · 支付「查完再插」，并发双击产生两张 PAYING 单

现象：用户双击「去支付」，数据库里出现两张同订单的支付单——回调时不知道认哪一张。

定位：早期 PaymentService.create 是「先查有没有 → 没有就插入」，非原子：两个并发请求都查到「无行」，都会插入。

修复：Flyway V4__payment_order_unique.sql 给 t_payment 加 uk_order_id(order_id)，从 DB 层兜底；并发第二个插入撞索引抛 DuplicateKeyException → 捕获后回查复用。支付模型随之变成「一个订单的支付尝试只占一行」：PAYING → PAID/CLOSED 之后再次发起支付，不再是插新行，而是复用该行重开（换 payment_no、重置金额/渠道/过期时间）；而 PAID 行永不可重开（由 updateForRecreate 的条件更新守卫）。

加的防线：迁移脚本第一步先清理历史重复行（DELETE p1 FROM t_payment p1 INNER JOIN t_payment p2 ON p1.order_id = p2.order_id AND p1.id < p2.id），否则唯一索引根本建不起来。「先在应用层做正确的事，再用唯一索引把兜底焊死」——这是项目一致的写法。

元教训凡是「先查后写」的地方都要问一句：查和写之间有没有窗口？有窗口就下沉成唯一索引或条件更新。

事故 5 · 热门榜 Top50 循环逐条查（N+1）

现象：榜单接口 Top50 要发 50 次 SQL——「与列表接口辛苦做的 5 条批量查询自相矛盾」。

定位：早期实现是拿到 zset 的 id 列表后循环 selectById，典型的 N+1。

修复：zset 只出 id + score 保持顺序，明细用一次 IN 批量回查（noteMapper.selectByIds），在内存里用 Map 建索引，最后按 zset 顺序组装（NoteServiceImpl.java:406-456）。代码注释里明确记了这次 P2 修复。

加的防线：计数增量也用同样的批量思路 readDeltas（HMGET 批量），榜单与列表页共用同一套「把 N 次往返压成 1 次」的策略。

元教训N+1 慢的从来不是 SQL 本身，是往返次数；而且同样的错很容易在「新写的接口」里再犯一次——所以代码注释要写清「为什么这么写」。

事故 6 · MQ 生产者确认「配了但没人消费」，两个开关都是摆设

现象：日志里从来没有过 MQ 投递失败的记录，看起来一切正常——但真出了路由错误也没人知道。消息可靠性「好像做了」。

定位：application.yml 早就开了 publisher-confirm-type: correlated 和 publisher-returns: true，但从不注册回调。Broker 的确认/退回事件到达后被静默丢弃——等于两个开关都是摆设。这是「配置写了没生效」的典型：开启收集 ≠ 使用结果。

修复：新增 MqProducerConfig，用 RabbitTemplateCustomizer 在 Boot 自动配置的模板上追加 setMandatory(true) + setConfirmCallback + setReturnsCallback（MqProducerConfig.java:36-58）。用 Customizer 而不是自己 new 一个 RabbitTemplate，是为了不丢掉 Boot 的自动配置（如 JSON 消息转换器）。

加的防线：除回调外，还补上了取消队列的死信（此前失败 = 消息消失）。回调内只记 ERROR 不自动重发——因为项目是「尽力而为 + 补偿兜底」语义，资金类才升级为必达。

元教训评审的第一个动作是 grep 调用点——「写了」不等于「生效了」。同类问题在本项目还出现过一次：缓存三兄弟的代码写得很漂亮，但 Controller 层压根没接线（V3 评审 P0 第 1 条）。

事故库怎么用（30 秒组织法） 面试官问「遇到最难的问题」，不要讲「我加了了个缓存」这种成功叙事，要讲「我发现什么不对 → 怎么定位 → 修了什么 → 加了什么防线」。上面的六条都能套这个四段式。
首选讲事故 6（MQ 确认）或事故 1（事务边界）——前者体现「配置与实现脱节也能发现」的工程嗅觉，后者把「事务」和「异常传播」绑在一起讲，技术密度高。
事故 2/3/4 一起讲更好——它们都是「并发下的竞态」：参数没拦、预热有窗口、插入非原子。串起来说「我在高并发入口上系统性地排查了所有 check-then-act」，比单独讲一条更有分量。

5.13面试话术汇总

本页的内容在面试里会收敛成四个问题。下面四段建议逐字背下来，再按自己的语速改顺。每段后面附「最容易说错的点」。

Q1 · 「缓存三兄弟怎么处理？」 必考

30 秒版本（逐字可用） "三个问题的成因完全不同，所以对策也不同。
穿透是查一个 DB 里也不存在的 id，缓存永远不命中、请求全打到库。我用空值缓存：查不到也写标记，用独立 key 存哨兵值，TTL 只给 2 分钟——挡刷子够用，又不会出现「刚上架查不到」。更彻底的方案是布隆过滤器，但有假阳性、不支持删除、要预热重建，商品这个规模我选了成本更低的空值缓存。
击穿是热点 key 恰好过期那一瞬间，几千个请求同时涌向 DB。我用 SET NX 互斥锁重建：只让一个线程查库回写，其余 sleep 50ms 重读，重读不到就直接查库兜底——缓存是旁路，不能让它决定可用性。锁的 TTL 3 秒防死锁、value 用 UUID 防误删。
雪崩是大量 key 同时过期。我的成因具体——商品批量导入时给了同一个 TTL——对策是 TTL 加随机抖动：30 分钟基础值 + 0~10 分钟随机。
写路径是 Cache-Aside：先更库再删缓存，删除是幂等的，比更新缓存安全。最后：所有 Redis 调用都收在一个可降级门面上，Redis 挂了只会变慢不会挂掉。"
最容易说错的点 ① 最致命：「击穿和雪崩差不多」。一个是单点、一个是一整面。这条说错，后面全崩。
② 别说「缓存 null 值」——是独立 key + 哨兵值，且 evict 要两个 key 一起删。
③ 别把「多级缓存 / 熔断保护缓存」说成项目做了——项目只有三兄弟 + 先更库再删缓存，其余是「知道方案没做」。
④ 别漏掉降级门面——「Redis 挂了怎么办」是这题的王牌追问，答「变慢不挂掉」并把 fail-open 的理由讲出来。

Q2 · 「幂等怎么做的？」 口径高危

30 秒版本（逐字可用） "先说一个前提：重复一定会发生，来源有三个——用户双击、第三方回调重传（支付宝会重试 8 次以上）、MQ 的 at-least-once 重投。所以在资损场景里幂等是入场券。
我做的是幂等设计，用了四种手段：
第一，唯一索引——点赞靠 uk_note_user、支付单靠 uk_order_id、限购靠 uk_activity_user。代码直接 INSERT 不先查，撞键就走对应处置。关键是同一招在不同业务里处置不一样：点赞是「状态确认」型，重复就等于已达成，所以静默；限购是「资格获取」型，必须报「请勿重复抢购」；支付单是「资源绑定」型，撞键回查复用，两次请求返回同一张单。
第二，状态机条件更新——所有状态流转都写 WHERE status = 旧值，rows==0 就是竞争失败、直接跳过。0 行是正常分支不是异常。典型场景是三方竞争同一订单：用户取消、超时消息、支付回调同时到达，闸门只有一个。
第三，一次性 token——下单防双击：结算页签发 UUID 到 Redis，提交时 DEL 原子消费，删到就放行。Redis 挂了 fail-open 放行——因为防重是优化不是正确性，别让缓存故障挡住正常下单。
第四，消费端回查——消息只带 id，消费时回查最新态再决策，因为消息在队列里躺着的时候世界已经变了。回查解决「读到最新态」，CAS 解决「改不重复」，两者缺一不可。"
最容易说错的点 ① 命名纪律（必守）：说「幂等设计（四种手段）」，绝不说「幂等四式」——那是自造名词，一说就被追问「哪四式、谁定义的」。
② 别说「先查再插更安全」——那是 TOCTOU 竞态，错的。
③ 别只说方案不说处置差异——「同一招为什么限购要报错、点赞不报错」是这题的深挖点，答出来才叫懂语义。
④ 别说「我们有一张专门的幂等表」——项目没有，幂等全落在业务表自身的唯一索引 + 状态机上。

Q3 · 「消息不丢不重怎么保证？」 高频

30 秒版本（逐字可用） "我按三段答。不丢：发送端开 publisher-confirm + mandatory + returns，而且真正注册了回调——这里有个真实教训：配置早就开了，但从来没注册回调，Broker 的事件到达后被静默丢弃，等于两个开关都是摆设；Broker 交换机和队列都 durable；消费端由业务决定 ACK 语义，失败进死信。
不重：靠消费端幂等——状态机 CAS + 唯一索引。MQ 的语义是 at-least-once，重复是常态：先做业务后 ACK，进程在 ACK 前崩溃就会重投。
最后收成一句：「重复靠幂等、丢失靠补偿」——光有 confirm 不够，还得有补偿任务兜底。
两个细节补上：confirm 管「消息到没到 Broker」，returns 管「进没进队列」，而且 ack=true 只说明 Broker 收到了，队列不存在时它照样是 ack，得靠 returns 才能发现。消费端我还有两种相反策略：审核链路AI 挂了重试无用，所以吞异常 ACK、记 ERROR 流水；订单取消链路必须回滚避免半截事务，所以让异常冒出、reject 进 DLQ。"
最容易说错的点 ① 别说「我们用的是手动 ACK」——项目是 AUTO + default-requeue-rejected=false，没有手写 basicAck。被追问配置层要如实说，并讲清「为什么这样比 manual 更适合」——manual 还要处理「事务未提交就 ack」的坑。
② 别把 confirm 和 returns 说成一回事——阶段不同，一个管到没到、一个管进没进队列。
③ 别吹「百分百不丢」——承认「尽力而为 + 补偿兜底」更可信；主动说 afterCommit 还有崩溃窗口。
④ 别漏掉那句总结——「重复靠幂等、丢失靠补偿」是这道题的标准收口。

Q4 · 「库存预减了但建单失败怎么办？」 王牌

30 秒版本（逐字可用） "失败必须对称回补，否则就是「白吃名额」——Redis 里库存少了、DB 里却没人真正买到，等于「看着抢完了实际有货」，是用户侧资损。
消费端有三类异常、三套路数：撞唯一索引（重复投递/并发提交，说明该用户此前已建单成功）→ 回补本次预减 + 幂等跳过；业务性失败（库存不足、不在发售时间内）→ 回补预减 + 写失败标记，前端轮询到 FAILED，消息正常 ACK 不重试，因为重试也不会成功；其他未知异常（DB 抖动）→ 原样重抛 → 容器 reject → 进死信队列等人工。
回补本身也是原子的：库存加回和删受理标记在同一个 Lua 脚本里——拆开执行的话，两步之间用户重试提交会被删了一半的标记挡住或放过。
投递失败也要回补：MQ 投递抛 AmqpException 时立即回补并提示用户重试，不允许「扣了名额但消息没出去」的白占坑。
最后补一句边界：预减是准入层不是真值，防超卖的底线永远是 DB 的 WHERE stock >= ? 条件更新；预减与实扣之间没有事务，所以这是最终一致——活动结束后还有对账兜底。"
最容易说错的点 ① 别说「失败就重试到成功」——业务性失败（如库存不足）重试一万次也不会成功，只会打爆日志；重试要分类型。
② 别说「Redis 预减就是防超卖」——预减是准入闸门，真值在 DB，正确说法是「Redis 预减挡量 + MQ 削峰摊峰 + DB CAS 保正确，三层缺一不可」。
③ 措辞红线：扣库存说「行锁 + WHERE stock>=? 条件更新（CAS 思想）」，绝不说「乐观锁」——t_product_sku.version 是纯预留字段、从未参与比对。
④ 别漏掉「投递失败也要回补」——这是最容易只答「消费端回补」而漏掉的一半。
本页速查：三句话 + 六个数字 三句话：① Redis 挂了只会变慢不会挂掉——因为所有调用收在一个可降级门面；② 重复靠幂等、丢失靠补偿——两个机制都要有；③ 降级路径与主路径同等重要，都是被测试过的。
六个数字：空值缓存 TTL 2 分钟 · 缓存 TTL 30 分钟 + 0~10 分钟抖动 · 计数落库 60 秒一次 · 热门榜全量重建 30 分钟一次 · AI 限流 10 次 / 60 秒 · 下单幂等 token TTL 10 分钟。
一句话世界观：Redis 层永远不承诺正确性，正确性永远在 DB 层。
