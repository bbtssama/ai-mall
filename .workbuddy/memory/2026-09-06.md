**识破的 5 处拼接痕迹**:
1. **RAG 定位混乱(最严重)** —— 设计把"规格/价格"塞进 RAG 语料 = 原理性错误。结构化数据走 RAG 是反模式(价格变次要重新向量化、库存不实时、无法做范围过滤)。
   - **正确定位**:RAG 语料 = 商品说明书(商家上传) + **种草笔记(UGC)** 双源。关键洞察:**种草笔记本身就是最优质 RAG 语料**(用户问"戴久耳朵疼吗"说明书答不了,UGC 笔记有真实体验),与"种草"定位天然契合,非硬塞。
   - **分工**:Agent 判断意图 → 价格/库存走 `searchProduct`(SQL);体验/说明书走 RAG。
   - **2026 升级**:朴素 RAG 已过时 → **Hybrid RAG(向量+BM25+RRF+Rerank)**;商品查询多型号规格词("蓝牙5.3""IPX7"),精确词是 BM25 主场。向量库用 pgvector/Redis Stack。必须建评测集。
   - **必背追问**:"文档才几十份为何不全塞长上下文?" → 语料动态增长/C端首字延迟/权限隔离/成本(2026 业界决策树)。
2. **秒杀 = 八股堆砌** —— 种草商城对标小红书+得物,没有秒杀场景。→ 改为**限量发售(Limited Drop)**(得物/潮玩真实场景),防超卖技术含量不变但业务说得通。
3. **NL2SQL = 高危伪需求** → 降级为可选 + 加 5 层护栏(仅商家端/白名单表+行级过滤/仅SELECT+AST校验/只读账号+超时限行/失败降级预设看板)。
4. **推荐系统 = 无数据支撑** → 改为**基于内容的相似推荐**(同品类同价格带+笔记关联商品)+ Redis zset 热门榜,可验证可讲解。
5. **微服务缺乏业务驱动** → **只拆 AI 服务 + Gateway**(Nacos+OpenFeign),正合用户"只做基础微服务"。**唯一站得住的理由:AI 调用秒级 vs 下单毫秒级会抢线程池 + 故障隔离 + 独立扩容 + API Key 隔离 + 模型可替换**。要能讲清"为什么不拆其余"(事务耦合紧,拆了要引分布式事务,当前业务量不划算)。

## 【已修复】V2 首次启动失败(16:48,exit code 1)——三个雷

用户 mvn spring-boot:run 失败。排查定位三个问题并修复:

1. **主因:6 个 content Mapper 全缺 @Mapper**——项目是逐接口 @Mapper 注册(无 @MapperScan,AimallApplication 注释明确),新 mapper 无注解=不生成 bean → NoteServiceImpl/AuditServiceImpl 注入失败。已批量补 @Mapper+import。
2. **循环依赖**:AuditServiceImpl 注入 NoteService(死字段,方法体从未用) ↔ NoteServiceImpl 注入 AuditService,Boot3 默认禁循环直接崩。已删 noteService 字段(审核只需 NoteMapper 回查)。
3. **@Async 自调用失效**:submit 内 this.auditAsync() 不走代理,注解失效变同步。已改为手动 taskExecutor.execute() 提交(AsyncConfig 的 ThreadPoolTaskExecutor,bean 名 taskExecutor 唯一按类型注入无歧义)。
4. **附带发现(MQ 永不生效的暗雷)**:AuditMessage 是 record 不实现 Serializable,默认 SimpleMessageConverter 发送必抛 MessageConversionException(extends AmqpException)被 catch 静默降级——MQ 路径永远走不通且无报错。已配 Jackson2JsonMessageConverter bean(Boot 自动应用到 template+监听工厂,收发两侧生效)+ DefaultJackson2JavaTypeMapper setTrustedPackages("*")(默认只信 java.util/java.lang,自定义包被拒)。

预检:6 个新 XML namespace 与接口全对齐;全项目无缺 @Mapper;AuditServiceImpl 花括号配对。

**教训(面试可讲)**:@Mapper 逐接口注册 vs @MapperScan;@Async/@Transactional 自调用失效同源;record 默认不 Serializable;SimpleMessageConverter 的限制;循环依赖靠"删多余依赖"解决优于 @Lazy。
**待确认**:若下次启动报 Flyway "Detected failed migration" → 需对 flyway_schema_history 清 failed 行(DELETE WHERE success=0)后重跑。
